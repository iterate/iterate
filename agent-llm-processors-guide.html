Overview

How apps/os turns a chat message into an LLM turn — three stream processors co-hosted on one agent stream.

Every agent lives on one event stream (e.g. /agents/web/main). A single AgentDurableObject per stream (agent-durable-object.ts) hosts several StreamProcessor subclasses that all watch that same stream. Processors never call each other directly — the stream is the only bus. Each processor:

  • reduces consumed events into its own durable state (a pure fold, checkpointed per batch), and
  • runs side effects that append new events back onto the stream — which the other processors then consume.

Provider selection is data: the agent's state carries llmProvider + llmConfig.model (set by llm-provider-selected, e.g. from project agent-defaults). Both providers consume the same agent/llm-request-requested event and each ignores it unless payload.provider equals its own slug. Requests travel by reference: the requested event carries no prompt body — the provider re-reads the stream and re-folds agent state up to the request's offset to rebuild system + history deterministically. The request's identity is the event's offset (llmRequestId = offset).

The two side-effect lanes (and the third, hidden one)

Hooks get two schedulers from the framework (stream-processor.ts); how a side effect is scheduled decides its crash behaviour:

LaneSemanticsOn failure / crash
BLOCKING blockProcessorWhile(work)The batch's checkpoint (and every later batch) waits for the work. Runs under the host keep-alive.Batch not checkpointed → host re-handshakes and the stream redelivers the batch; idempotency keys dedupe the retry. Exactly-once effect, at-least-once execution.
BACKGROUND runInBackground(work)Fire-and-forget (keep-alive backed). Checkpoint advances immediately.Failure is only logged. Because the checkpoint already moved past the triggering event, it is never redelivered — lost work needs its own recovery mechanism (or wedges).
BATCH-SETTLE awaited in processEventBatchDerived from the whole-batch reduced state, once per batch, after all per-event hooks. Awaited directly, so it blocks the checkpoint like blocking work.Same as blocking: batch retries. Used where a per-event decision would be wrong because earlier same-batch appends are invisible.

Rule of thumb in this codebase: appends that keep history consistent are blocking; anything that waits on wall-clock or a network call is background — and every background execution needs a story for "the DO died mid-way" (that story is where the two providers differ, see improvement notes).

Cancellation also exits from scheduled. Every exit increments requestGeneration, which keys the idempotency of the next llm-request-scheduled — so however many inputs arrive between two request lifecycles, exactly one scheduling event survives the append-dedup layer.

How the loop ends. A script that returns undefined (and doesn't throw) produces no rendered input → no pending trigger → no next request. A response with no code block adds history but triggers nothing. Hard stops: the circuit breaker (loop-stopped after 20 consecutive agent-loop turns) and the failure cap (after 3 consecutive LLM failures the error input stops auto-retrying).
