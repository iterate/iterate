# Local OS dev auth minting depends on auth-worker JWKS

## Problem

The documented local agent/debug path says a developer can start OS locally and
mint a browser session:

```bash
doppler run --project os --config dev -- pnpm auth:mint --browser-url
```

In practice, against a fresh local `apps/os` dev server, navigating to the
printed `/api/iterate-auth/session-from-token?...` URL can fail with:

```text
Token validation failed: JWKSNoMatchingKey: no applicable key found in the JSON Web Key Set
```

That means the local dev server is not reliably trusting the same forge public
key that `scripts/auth/mint-session.ts` uses to sign the session tokens.

## Why this matters

Headless agents need a deterministic way to authenticate into the project UI
without Google OAuth, email OTP, or a separate local/auth preview worker. This
is especially important for screenshot/debug flows where the agent needs to
open routes under `/_app/projects/...` from a clean browser profile.

The deploy path already handles this by baking a static auth JWKS with the
forge public key via `scripts/lib/bake-auth-jwks.ts`. Local dev should have an
equally documented and automated equivalent.

## Repro

From a clean browser profile:

```bash
doppler run --project os --config dev -- pnpm --dir apps/os dev restart --detach
URL="$(doppler run --project os --config dev -- pnpm --silent auth:mint --admin --browser-url --return-to /projects)"
open "$URL"
```

Observed response:

```text
Token validation failed: JWKSNoMatchingKey: no applicable key found in the JSON Web Key Set
```

Manual workaround that confirmed the likely cause:

1. Derive the public JWK from `AUTH_FORGE_PRIVATE_JWK`.
2. Inject it into `APP_CONFIG_ITERATE_AUTH__JWKS`.
3. Restart `pnpm dev` with `doppler run --preserve-env=APP_CONFIG_ITERATE_AUTH__JWKS`.

After that, `session-from-token` can validate the forge-signed tokens.

## Expected behavior

One of these should be true and documented:

- `pnpm dev` automatically bakes/injects a local static JWKS containing the
  forge public key when `AUTH_FORGE_PRIVATE_JWK` is present, or
- `pnpm auth:mint --browser-url` targets a local-only session path that does
  not require the auth worker's runtime JWKS at all, or
- there is a first-class command such as `pnpm dev login-url` that starts OS,
  prepares the local JWKS/session machinery, and prints a browser URL.

The happy path should work from a clean browser profile with no auth-worker
availability requirement.

## Suggested fix

Reuse the deploy-time logic from `scripts/lib/bake-auth-jwks.ts` in the local
dev startup path:

- `apps/os/scripts/dev.ts` already has `doppler.loadOsSecrets(...)`.
- When starting without `--skip-doppler`, load the configured OS secrets.
- If `APP_CONFIG_ITERATE_AUTH__JWKS` is absent but `AUTH_FORGE_PRIVATE_JWK` is
  present, synthesize a JWKS by stripping the private `d` field and appending
  the forge public key.
- Pass the resulting `APP_CONFIG_ITERATE_AUTH__JWKS` into the spawned Vite
  process.
- Add an integration-style test or scripted smoke that starts the dev server,
  runs `pnpm auth:mint --browser-url`, and asserts
  `/api/iterate-auth/session-from-token` redirects instead of returning a JWKS
  validation error.

## Acceptance criteria

- `doppler run --project os --config dev -- pnpm --dir apps/os dev restart --detach`
  followed by `pnpm auth:mint --browser-url` works without a separate auth
  worker deploy.
- The dev docs explicitly describe the auth-mint path for agents and clean
  browser profiles.
- The failure mode is covered by a smoke test or documented manual test.
