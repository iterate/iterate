# Bump sqlfu to 0.1.1

Status summary: done — pin bumped, codegen regenerated, one call site adapted; typecheck + tests green in both apps. PR: https://github.com/iterate/iterate/pull/1722

## Why

The hosted sqlfu studio (sqlfu.dev/ui) crashed with `TypeError: Cannot read properties of undefined (reading 'filter')` when browsing tables served by our pinned `sqlfu@0.0.3-14` backend — the hosted UI (built from newer sqlfu) expects `foreignKeys`/`referencedBy` fields that `schema.get` only returns from 0.1.1. Upstream fix (supported-version floor + CI canary) is https://github.com/iterate/sqlfu/pull/151; on our side the fix is just moving to 0.1.1.

## Checklist

- [x] bump `sqlfu` to `0.1.1` in `apps/auth` and `apps/semaphore` (the only two consumers) _both package.jsons + lockfile_
- [x] regenerate sqlfu codegen in both apps (`pnpm db:generate` / `pnpm sqlfu:generate`) — 0.1.1 adds `snake_case`→`camelCase` result mapping to generated query wrappers _semaphore in the first implementation commit; auth's two really-changed files (oauth-project-selection, project) were initially lost to an oxfmt/lint-staged round trip and re-landed via a follow-up regenerate commit_
- [x] adapt `apps/semaphore/src/lib/resource-store.ts` — its hand-rolled `ResourceRow` type duplicated the mapping the codegen now does; switch its field names to the camelCase shape _local ResourceRow type now camelCase; parseData/leaseState validation unchanged_
- [x] verify: `pnpm typecheck` + `pnpm test` in both apps _green in the worktree after each commit_

## Notes

- The camelCase result mapping is a runtime behavior change in generated wrappers, not just types. Auth's queries were already alias-friendly; semaphore's resource store is the most-affected call site.
- `sqlfu@0.1.1` requires Node 24+ at runtime despite declaring `engines: node >=22` (untranspiled `await using` in the published dist) — fine for us (deploy scripts and CI run newer), tracked upstream.
- Six of auth's eight generated files differ from 0.1.1 codegen output only by indentation (sqlfu emits tabs, repo oxfmt uses spaces) — `pnpm format` after regenerating is load-bearing.

## Preview e2e failure post-mortem

First preview deploy broke signup and create-project e2e (both stall navigating to the new project's onboarding agent). Diagnosis trail: deploy itself succeeded; `internal.project.createForOrganization` 500'd on the _insert_ path only (adopt path fine); `wrangler tail` showed `Error: Project ... is missing organization id`; root cause is an upstream sqlfu 0.1.1 typegen bug — it infers `RawResult` from table column names, **ignoring `RETURNING`-clause `AS` aliases**, so the generated `mapResult` read `row.organization_id` from rows that actually carried `organizationId` (our aliases) and every mapped field came back `undefined`. Old sqlfu had the same wrong _type_ but passed raw rows through, which is why `toProjectRecordFromReturnedRow` (`_shared.ts`) had a both-shapes dance — the type lie was harmless until 0.1.1 acted on it.

Fix: drop the `AS camelCase` aliases from the three RETURNING clauses (`insertProjectReturning`, `updateProjectReturning`, `upsertOAuthProjectSelectionReturning`) — the raw rows are then snake_case exactly as typegen assumes, and its mapping produces the same camelCase `Result` the aliases used to. Verified at runtime against local D1 before pushing (typecheck cannot catch this bug class). Upstream issue filed on sqlfu.
