Architecture proposal · Iterate Kit · ESPHome

Make an ESPHome device part of Iterate with one YAML block

Represent each physical device as one durable stream under /kit/<device-id>, add a live capability while it is online, and keep high-bandwidth media on a separate negotiated channel.

Brief

Research how sensors, buttons, actuators, displays, audio devices, and unusual ESP32 hardware can connect directly to an Iterate deployment over an outbound WebSocket. The preferred user experience is a YAML-only ESPHome configuration change, with secure enrollment, durable events, callable capabilities, and useful offline behavior.

01

Answer first

Yes: YAML-only enablement is a realistic primary product shape. An ESPHome external_components entry can fetch an Iterate component, and an iterate_kit: block can register that component with ESPHome’s entity registry. ESPHome then compiles and flashes the resulting firmware through its normal workflow; users do not write or patch C++.

The important qualification is that the YAML change still causes a firmware rebuild. A device whose already-flashed firmware does not contain Iterate code cannot suddenly initiate an Iterate WebSocket. The only broadly viable no-reflash path is a LAN gateway that connects to an existing ESPHome Native API or MQTT endpoint and represents it upstream.

02

Recommended architecture

The device should authenticate into a narrow Kit device session, not receive a full project capability. The session binds one credential to one project and one canonical device path, translates bounded device messages into stream operations, and exposes only the verbs a device needs.

Durable truth and live reachability share a semantic address but have different lifetimes.

Why not expose the raw Stream API?

  • Generic replay batches can be much larger than the device’s fixed control-message and JSON-token budgets.
  • The current project credential grants access to the whole project, not one device path.
  • Server-side translation lets the wire protocol stay stable while Iterate’s internal Stream API evolves.
  • The facade can enforce event size, types, command TTL, entity IDs, and per-device rate limits.

Why keep the live capability?

  • It advertises what this exact device can do right now.
  • It supports low-latency interactive calls while the socket is alive.
  • It is naturally revoked when the device session disconnects.
  • Meaningful requests and outcomes still go to the durable stream, avoiding ambiguous RPC-only side effects.
03

The YAML-only experience

ESPHome external components are normal components with YAML validation and code generation. The Iterate component can register as a controller, enumerate the application’s entities, subscribe to their updates, and dispatch incoming commands through the same public entity APIs used by ESPHome’s own API server.

living-room-dial.yaml 
external_components:
  - source: github://iterate/iterate@kit-v0.1
    components: [iterate_kit]

iterate_kit:
  deployment: https://os.iterate.com  # production can become the default
  entities:
    include: all
    exclude:
      - wifi_signal
      - uptime
  telemetry:
    sensor_min_interval: 5s
    send_on_change: true

# Existing ESPHome entities remain ordinary ESPHome YAML.
sensor:
  - platform: bme680
    temperature:
      name: Room temperature

What the component should infer

  • Entity IDs, kinds, units, classes, and supported traits.
  • State callbacks for sensors and stateful actuators.
  • Command adapters for switches, lights, covers, fans, climate, numbers, selects, locks, and buttons.
  • A chunked manifest so large devices stay within the bounded C peer’s message limits.

What enrollment should decide

  • The Iterate deployment and project.
  • The server-issued immutable device ID.
  • The user-facing name and canonical /kit/<device-id> path.
  • The exact per-device authority. Firmware must not choose an arbitrary project path after authentication.

A naming trap worth making explicit

In ESPHome, a button is normally a stateless command target—something a client presses. A physical GPIO push-button is usually represented as a binary_sensor or an event source. The bridge should preserve this distinction rather than flattening both into “button.”

04

Stream and activity model

Use one stream per device, not one stream per entity. One stream gives a total order across physical inputs, requested actions, observed state, connectivity, and firmware changes. High-volume media and exceptional telemetry can be split later without fragmenting the device’s ordinary history.

Suggested event vocabulary 
kit/device-announced          # firmware, model, manifest version
kit/entity-manifest-chunk      # bounded entity/trait descriptions
kit/entity-state-observed      # sensor or actuator state
kit/entity-event-observed      # press, gesture, RFID tag, motion event
kit/activity-requested         # durable intent + idempotency key + TTL
kit/activity-started           # device accepted work
kit/activity-progressed        # optional, bounded/coalesced
kit/activity-succeeded         # terminal result + observed state
kit/activity-failed            # classified durable explanation
kit/media-session-opened       # negotiation metadata, never PCM bytes
kit/device-diagnostics         # queue high-water, loss, reconnect reason

State-setting commands

Prefer desired state plus observed state: “light should be 40%” is safely reconcilable after reconnect.

Impulse commands

“Dispense,” “press,” and “unlock” require an idempotency key, TTL, bounded processed-ID memory, and an explicit terminal outcome. Exactly-once physical effects cannot be guaranteed across a crash at the actuation boundary.

Realtime activities

“Start listening” or “tap camera” is a durable request that negotiates a short-lived media session. The bytes travel elsewhere; lifecycle and failure remain auditable.

Backpressure must be semantic

Never grow an offline queue indefinitely. Coalesce replaceable sensor/state samples, preserve important transitions where capacity permits, and append an explicit loss diagnostic after reconnect. Server-side commands remain durable until consumed, expired, or cancelled.

05

Enrollment and authentication

OAuth’s Device Authorization Grant is the right human-interaction pattern: a device with limited input shows a code and a user completes authorization on a phone or laptop. However, a normal user access token is the wrong final device identity. Enrollment should mint a revocable credential bound to one device record, project, and stream path.

Use device flow for consent; issue device authority, not an enduring user session.

Recommended credential

Generate a per-device keypair and authenticate by proving possession of the private key. Store it using ESP-IDF secure storage where the board and product posture permit. A random per-device secret is an acceptable simpler first version if it is hashed server-side, independently revocable, and never a project-wide key.

Provisioning surfaces

A display can show the code. A headless device can expose it through serial logs, the browser flasher, or a local provisioning page. ESPHome’s Improv/provisioning components can continue handling Wi-Fi; Kit enrollment begins after internet access exists.

What can be reused today

The auth app already installs a device-authorization plugin with an eight-character user code, 15-minute expiry, and five-second poll interval. It currently admits only the iterate-cli client and does not choose a project or device path. Reuse the interaction and storage primitives, but create Kit-specific consent and device-credential issuance.

08

Implementation sequence

Foundation

Keep the bounded peer, transport-independent core, and dual control/media lanes

The branch already establishes these constraints. Close the known receive/backpressure defects rather than redesigning the upper layers around them.

Protocol

Define KitDeviceSession and the device-stream event contract

Path-bound authentication, bounded manifest chunks, append batches, command delivery with cursor/TTL, live capability mount, diagnostics, and media negotiation.

vertical slicesensorswitchphysical button
ESPHome

Ship the external component with a small first trait set

Enumerate entities, register controller callbacks, map incoming calls, and prove resource bounds on representative ESP32-S3 and classic ESP32 boards. Expand entity domains only after each mapping has honest semantics.

Enrollment

Make first boot safe and YAML-only

Device-code consent, project/name selection, per-device credentials, secure storage, rotation/revocation, factory reset, and installer/serial/headless code display.

Activities

Add durable action state machines and richer capabilities

Desired/observed reconciliation, impulse idempotency, cancellation, progress, offline expiry, and typed live discovery.

Reach

Add media, sleepy-device, gateway, and non-ESP32 modes deliberately

Each is a distinct runtime profile with separate acceptance criteria; none should be hidden behind “any ESPHome device.”

09

Best experimental devices

Best all-round protocol demo

M5Stack Dial v1.1

Rotary encoder, round touch display, RFID, buzzer, RTC, and a physical button. It exercises input events, observed state, remote rendering, commands, and a rich live capability without making audio the first dependency.

Best high-cardinality input demo

M5Stack Cardputer Adv

A 56-key keyboard, display, microphone, speaker, IMU, IR emitter, and expansion ports. It is excellent for keyboard event bursts, screen capabilities, activity sessions, and eventual audio—but has a larger board-specific integration surface.

Best media boundary demo

M5Stack Atom Echo / Voice

Tiny microphone, speaker, RGB, and button hardware. It proves that activity lifecycle belongs on the device stream while PCM uses a separate negotiated socket. Its tighter memory budget is a useful constraint test.

Best telemetry-policy demo

ESP32-S3 + LD2410 mmWave radar

Presence, distance/energy values, and adjustable gates create enough data to force honest sampling, coalescing, and trait-driven commands. ESPHome has an official LD2410 component, so the experiment tests the bridge rather than a custom sensor driver.

Best assumption-breaker

Deep-sleep e-paper or soil sensor

It intentionally violates the permanent-WebSocket assumption. Use it to design the publish/poll/sleep profile and prove that “offline” is not misclassified as a defect when sleep is explicit policy.

Existing branch continuity

M5StickS3 / StackChan

Continue the current capability, display, push-to-talk, and simulator work as the firmware transport proving ground, while the Dial becomes the clean ESPHome entity bridge demo.

11

Decisions to annotate

Should gateway/no-reflash support be part of the first product?

Recommendation: no. Design the device-stream contract so a future gateway can implement the same KitDeviceSession, but ship the YAML-enabled direct client first.

Decide with: product + platform

One stream per device, or substream per entity?

Recommendation: one device stream. Use entity IDs inside events; split only named high-volume channels whose retention and processing genuinely differ.

Decide with: streams owners

Public-key device identity or random device secret first?

Recommendation: design the server record for public keys, but allow a per-device random secret for the earliest internal vertical slice. Never reuse the project API key.

Decide with: auth + firmware

How should an explicitly sleeping device appear?

Recommendation: enrollment declares a runtime profile. “Sleeping until…” is modeled state with a deadline, not an unexplained disconnect and not a permanently online capability.

Decide with: Kit protocol owners
