# Cap'n Web runtime and capability model

## What can transport unify safely?

### Takeaway

Unify subscriptions, `provide()` and live capability delivery around one _ephemeral live-provider lease_: a stable logical key, one session-owned duplicated stub, one session-break watcher, and a pager/reattach protocol. Do not unify that lease with persisted context state, nor promise that a live reference survives a Durable Object restart. Cap'n Web and Workers RPC are interoperable enough to share an adapter contract, but their lifecycle semantics and current feature sets make a transport boundary necessary.

### Cited Findings

- Cap'n Web is an object-capability RPC system: references are authority, functions and `RpcTarget` instances travel by reference, and promise pipelining can combine dependent calls into one round trip. It supports HTTP batch, WebSocket and `postMessage` transports. [Cap'n Web README](https://github.com/cloudflare/capnweb#capn-web-a-javascript-native-rpc-system)
- A Cap'n Web `RpcTarget` is an alias of the Workers runtime `RpcTarget` on Workers; RPC stubs, Service Bindings and Durable Object stubs may cross the other RPC system and are proxied automatically. The upstream documentation nevertheless records mismatches: Workers RPC had types Cap'n Web did not, aliases/cycles, and did not support `RpcPromise` parameters or magic `map()`. [Workers RPC interoperability](https://github.com/cloudflare/capnweb#cloudflare-workers-rpc-interoperability)
- The current upstream issue list still reports missing `Map`, `Set`, `URL` and `RegExp` support, plus an open forwarded-`ReadableStream` bug. Hence “same capability API” must restrict itself to the intersection of wire values, or validate and route exceptional values in an explicit adapter. [Cap'n Web open issues](https://github.com/cloudflare/capnweb/issues)
- `RpcTarget` deliberately exposes prototype methods/getters and does not expose instance-owned properties; therefore runtime introspection of object fields is not an API-description mechanism. [Cap'n Web README: RpcTarget](https://github.com/cloudflare/capnweb#rpctarget)
- Cloudflare documents that a single `RpcTarget` class instance is more efficient than returning a plain object holding several functions, because the class produces one stub whereas each function becomes a stub. [Workers RPC reference](https://developers.cloudflare.com/workers/runtime-apis/rpc/)
- A WebSocket Cap'n Web session supports bidirectional callbacks and pipelining; calling `[Symbol.dispose]()` on its root stub closes the connection. The session is an appropriate transport for a live provider, while HTTP batch is deliberately short-lived. [WebSocket transport](https://github.com/cloudflare/capnweb/blob/main/packages/docs/src/content/docs/transports/websocket.md)
- A Cap'n Web `Response` carrying a Workers WebSocket can now cross Cap'n Web RPC by tunnelling its messages through the session, but only the `Response.webSocket` form is serializable, a socket can be sent once, and the tunnel does not forward ping/pong or provide inbound backpressure to the source socket. [Cap'n Web WebSocket tunnelling](https://github.com/cloudflare/capnweb#tunneling-websockets)
- Iterate currently pins `@iterate-com/capnweb@0.12.3`; its `fetch-upgrade.ts` explicitly says the bespoke upgrade-leg/splice exists because Workers RPC cannot serialize a WebSocket-bearing `Response`, and the fork added Cap'n Web socket-in-`Response` transport. [Iterate package catalog](https://github.com/iterate/iterate/blob/main/pnpm-workspace.yaml), [Iterate fetch-upgrade adapter](https://github.com/iterate/iterate/blob/main/apps/os/src/context/fetch-upgrade.ts)
- The current fork's 0.12.0 changes fixed failure-path argument/capture disposal and added an `RpcPromise(Promise)` constructor that queues pipelined calls until a provider becomes available. That supports a small “resolve lease, then pipeline” adapter, but does not make an old broken session reconnectable. [Cap'n Web 0.12.0 changelog](https://github.com/cloudflare/capnweb/blob/main/CHANGELOG.md)
- An open upstream defect says a `ReadableStream` returned through a stub forwarded via an intermediate session fails, while a direct session works; the stated workaround is a capability with `next()` and a client-built stream. This rules out treating streams as transparent through an arbitrary shared live-provider relay today. [Cap'n Web issue #228](https://github.com/cloudflare/capnweb/issues/228)

### Inferences

- The clean core boundary is `LiveProviderRegistry` rather than separate subscription, callback, tunnel and “live capability” registries. Its persisted/event-visible state should contain only `{ key, declared contract, availability }`; its session table should contain the stub and one revoker. A subscription is then a provider whose declared contract is `deliver(event)`; a user tool is a provider whose declared contract is its method surface. This follows the shared callback and stub ownership model documented by Cap'n Web. [Callback retention documentation](https://github.com/cloudflare/capnweb/blob/main/packages/docs/src/content/docs/transports/websocket.md)
- The registry should expose an intentionally narrow `invoke(key, expression)` / `deliver(key, value)` adapter and one “terminal fetch / WebSocket response” escape hatch. Do not model raw stubs as durable data or teach every subsystem Cap'n Web/Workers-RPC branches. This is a design inference from the known socket and forwarded-stream transport discontinuities. [Cap'n Web WebSocket tunnelling](https://github.com/cloudflare/capnweb#tunneling-websockets), [issue #228](https://github.com/cloudflare/capnweb/issues/228)
- `itx.builtins` should be a local projection of a declarative manifest plus context state and grants. It should not be obtained by enumerating remote stub properties: neither JavaScript types nor `RpcTarget` instance properties are an available wire schema. The manifest can describe capability names, invocation kind, argument/result schemas, durability and authority requirements, then produce both the expression resolver and a discoverable description.
- Keep native-Workers-RPC handling and Cap'n Web handling behind the same lease interface, but retain separate adapters for (a) native Stub/DO invocation, (b) Cap'n Web session invocation and (c) upgrade responses. “One provider mechanism” is safe; “one transport implementation” is not established by the sources.

### Gaps

- No primary source found that provides runtime reflection of a TypeScript interface, Cap'n Web API, or `RpcTarget` surface. TypeScript erases types and Cap'n Web explicitly has no schemas; providers must declare a manifest/validator or generate one at build time. Cap'n Web points to `capnweb-validate` for build-time validators, but that does not make a generic remote stub self-describing. [Cap'n Web README](https://github.com/cloudflare/capnweb#capn-web-a-javascript-native-rpc-system)
- The sources do not establish that Cap'n Web's socket tunnel alone replaces Iterate's resumable splice across a Durable Object reset. It solves a different hop: transferring a socket inside a Cap'n Web session.

## What lifetime guarantees differ across the edge, Workers RPC and Durable Objects?

### Takeaway

All live objects need explicit ownership. A stateless edge can own a session and its live provider stub; a DO may borrow one only temporarily. A DO cannot hibernate while it has ordinary WebSocket API usage or an outbound WebSocket, and a hibernated object reconstructs from persisted data. Native `RpcTarget` instances and Cap'n Web sessions have no documented persistence/rebinding across that reconstruction.

### Cited Findings

- Cap'n Web says garbage collection cannot reliably reclaim remote resources because it cannot trace remote graphs and runtimes may not collect without local pressure. Its supported strategies are explicit stub disposal or short-lived sessions; long-lived WebSocket sessions need disposal. [Cap'n Web disposal documentation](https://github.com/cloudflare/capnweb#resource-management-and-disposal)
- Cap'n Web ownership rules say a caller owns stubs passed as parameters and returned results; parameter duplicates are automatically disposed on call completion, while returned duplicates are released after pipelined calls finish. A callback retained past registration must use `.dup()`, and the retaining owner must dispose it on replacement/teardown. [Cap'n Web disposal documentation](https://github.com/cloudflare/capnweb#automatic-disposal)
- Native Workers RPC similarly disposes received parameter stubs on return and requires `.dup()` to retain them; object results receive a disposer, and `RpcTarget[Symbol.dispose]` runs after the last duplicate is disposed. The remote disposer is asynchronous from the client’s viewpoint and its exceptions do not propagate to the caller. [Workers RPC lifecycle](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/)
- Workers RPC ends an execution context when a handler returns unless stubs crossed the call; such stubs extend it until disposal. A client disconnection cancels the server execution context immediately, even when stubs exist. [Workers RPC lifecycle](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/)
- Cap'n Web calls `onRpcBroken` when an underlying connection is lost or an RPC promise rejects. A dropped WebSocket makes every associated stub permanently broken; the library does not reconnect, so recovery requires a new session and acquiring new capabilities. [Cap'n Web WebSocket transport](https://github.com/cloudflare/capnweb/blob/main/packages/docs/src/content/docs/transports/websocket.md)
- Cap'n Web issue #210 remains open and reports that `onRpcBroken` callbacks registered on an unresolved remote import survive local disposal, retain captured closures for the session lifetime and fire later at teardown; its report says session stats do not reveal the leak. [Cap'n Web issue #210](https://github.com/cloudflare/capnweb/issues/210)
- Durable Objects may hibernate after 10 seconds only if, among other conditions, no standard WebSocket API is in use, no awaited fetch remains, and no outbound TCP/WebSocket exists. Hibernation discards in-memory state; a subsequent event reruns the constructor. [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)
- `state.acceptWebSocket()` is the hibernatable WebSocket API. It preserves a client socket over hibernation and dispatches the next message after reconstructing the object, unlike `ws.accept()`. [Durable Object WebSocket hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- Open workerd issue #6087 states that runtime RPC targets do not survive a DO isolate eviction/reconstruction, and that Cap'n Web listeners on a normal socket prevent hibernation; it is open and describes the stateless proxy as a workaround, not a completed platform feature. [workerd issue #6087](https://github.com/cloudflare/workerd/issues/6087)
- Iterate’s present relay follows that boundary: it keeps the Cap'n Web client stub at the stateless `/api` relay, holds a DO pager socket as an offer to lend, and lets the DO borrow a fresh native RPC leg only while needed. [Iterate RPC-stub relay](https://github.com/iterate/iterate/blob/main/apps/os/src/context/rpc-stub-relay.ts), [Iterate RPC-stub directory](https://github.com/iterate/iterate/blob/main/apps/os/src/context/rpc-stubs.ts)

### Inferences

- The central live-provider state machine can be reduced to four observable states: `absent`, `offered` (pager/session exists but no DO borrow), `borrowed` (one live leg in the DO), and `broken`. Transitions must dispose the replaced lease exactly once. The context log should record semantic availability/connect/disconnect, not pager/redial internals.
- A provider key is durable identity, not durable authority. After hibernation, deploy reset or WebSocket failure, the key may remain described in the context but must be `unavailable` until an authenticated edge/session reattaches it. Reattachment must create a new stub; retaining the old one violates Cap'n Web’s terminal-broken rule.
- The existing pager is a reasonable runtime adapter forced by #6087, but the surrounding core can stop treating it as a different concept from subscription callbacks. A common lease controller can own the duplicate, one `onRpcBroken` registration, pager lifecycle, bounded re-dial and a one-shot disconnect emission.
- Do not attach a fresh `onRpcBroken` callback per borrowed DO leg or per event delivery. Current upstream behavior makes this an unbounded closure-retention risk on a long session; one registration at lease creation plus local fan-out is the safe pattern.
- The lease controller needs a bounded pending-call policy. A disconnected session can leave a call incomplete from the context's point of view, while a DO's in-memory borrower delays hibernation; timeout/probe/revoke outcomes should be explicit availability results rather than retries hidden in stream code.

### Gaps

- No source promises that an accepted hibernatable WebSocket can host Cap'n Web directly while retaining Cap'n Web's session objects and callback state. The open workerd issue says the opposite limitation remains.
- The exact time of a DO eviction outside its hibernateable path is platform-controlled. Cloudflare documents 70–140 seconds for idle non-hibernateable objects but this is not a correctness deadline. [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)

## Which Iterate workarounds reflect upstream defects, and what should remain isolated?

### Takeaway

Keep platform workarounds small and explicitly isolated at the transport boundary. The largest current candidates are the fetch-upgrade/resumable-splice path and the pager relay, both rooted in still-open capability/hibernation limitations. They should not shape the event model, builtin description mechanism, or userspace agent abstractions.

### Cited Findings

- Iterate’s `fetch-upgrade.ts` documents that a WebSocket-bearing `Response` cannot travel over Workers RPC and routes terminal `fetch` through a real fetch upgrade, passing only a marker over RPC. It also documents the forked Cap'n Web socket-in-`Response` transport and a deletion checklist for the upstream day. [Iterate fetch-upgrade adapter](https://github.com/iterate/iterate/blob/main/apps/os/src/context/fetch-upgrade.ts)
- Cap'n Web’s current socket tunnel implements WebSocket-in-`Response` transport, but its documented limitations include one-time socket transfer, no ping/pong forwarding and no source-side inbound backpressure. It cannot by itself prove the native Workers-RPC leg serializes socket Responses. [Cap'n Web WebSocket tunnelling](https://github.com/cloudflare/capnweb#tunneling-websockets)
- A current Iterate failing regression test pins a workerd defect where a DO forwards a Request received by Workers RPC and logs `ReadableStream received over RPC disconnected prematurely` after the upstream read the whole body. The test links the known family to workerd #7277 and makes the failure visible rather than silently healing it. [Iterate forwarded RPC body regression](https://github.com/iterate/iterate/blob/main/apps/os/src/context/forwarded-rpc-body.test.ts), [workerd issue #7277](https://github.com/cloudflare/workerd/issues/7277)
- Iterate’s production fault alarm lists the false stream-disconnection line as a pinned, scoped exception and ties it to the regression test, rather than treating all such runtime errors as acceptable. [Iterate production fault alarm](https://github.com/iterate/iterate/blob/main/scripts/ci/prd-fault-alarm.ts)
- Upstream Cap'n Web #228 reports an uncorrected forwarded-stream failure, so a refactor must not replace Iterate’s terminal-fetch/stream escape hatch with blind generic stub forwarding. [Cap'n Web issue #228](https://github.com/cloudflare/capnweb/issues/228)
- Cap'n Web's current README describes Workers RPC interop as broadly proxyable but separately lists missing/different features. This supports preserving one narrow compatibility adapter even after higher-level code is consolidated. [Cap'n Web Workers interop](https://github.com/cloudflare/capnweb#cloudflare-workers-rpc-interoperability)

### Inferences

- Put the pager, `fetch-upgrade`, socket splice, Worker-RPC error classification and any retry/probe logic under `context/runtime/` as a single “Cloudflare live transport” module. Export only: lease a provider, invoke a provider, issue a terminal fetch, release provider. This confines a genuine platform complexity without forcing event storage, rewriting, builtins or agents to know transport details.
- Treat Cap'n Web’s `RpcPromise(Promise)` as an implementation optimization, not an availability contract. It can make calls pipeline while an in-process provider resolution is pending, but it cannot bridge provider disconnection, a DO reset or a session replacement. [Cap'n Web 0.12.0 changelog](https://github.com/cloudflare/capnweb/blob/main/CHANGELOG.md)
- Preserve the regression tests that name open platform faults and compact repetitive tests around the shared lease state machine. Tests that merely restate the same lease transition once through subscriptions, once through live stubs and once through agent-specific wiring become candidates for replacement by one transport contract suite plus one feature-level acceptance test per public API.
- Descriptions/types must be declared at install/provide time. A provider manifest should use JSON-schema-like data (or build-generated validators) for values and a separate capability contract for remote methods; projected `itx.builtins` can then merge static builtins, grants, jails and live-provider manifests deterministically. This is an inference from schema-free Cap'n Web and erased TypeScript types, not an upstream-provided API.

### Gaps

- I found no primary source establishing which particular Iterate pager retries or socket-splice recovery branches remain necessary on the exact deployed Workers runtime. The code documents them as observed behaviour, but deciding deletion needs its existing production telemetry and a deployed regression run.
- The source review did not establish a Cloudflare release/issue resolution for socket-bearing native Workers RPC responses. Until a direct upstream resolution is verified, removing the upgrade adapter would be speculative.
