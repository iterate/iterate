# Cloudflare Workers, Durable Objects, facets, and dynamic Workers runtime review

Research status: reviewed 2026-09-29. Sources below are current official Cloudflare documentation, the public `cloudflare/workerd` source tree and issue tracker. A claim marked **documented contract** is safe to design around at the compatibility date stated in the deployed worker; a claim marked **source observation** describes current workerd and needs a regression test if Iterate relies on it; an **issue report** is not a guarantee.

## Which runtime workarounds are truly necessary today, and what compatibility date should govern them?

### Takeaway

Retain a small recovery boundary around durable state, message delivery, and stale handles. Do not retain broad recovery machinery for normal storage interleaving: Durable Object input/output gates already give strong consistency. Ordinary live RPC targets/stubs cannot survive a Durable Object isolate replacement, while a hibernatable server WebSocket can. Cloudflare OS separately implements restoration recipes using `ctx.restore()`; its irrevocable-stub-storage flag is explicitly insecure and unsuitable for Iterate's jail model. Restoration recipes do not preserve a held live session. Pin the platform worker and all dynamically-loaded code to an explicit compatibility date, and test the actual deployed runtime; `2026-09-29` is a sensible review baseline but is not a substitute for declaring the date in every `WorkerCode`.

### Cited Findings

- **Documented contract:** a Durable Object is hibernated only after no incoming events for the present 10-second window and only if it has no timers, awaited `fetch`, standard WebSocket API use, in-flight event, outbound TCP connection, or outbound WebSocket. Hibernation discards in-memory state; the next event runs the constructor again. [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)
- **Documented contract:** Objects may also shut down for a deployment, inactivity, runtime update, or placement decision. There are no shutdown hooks, and Cloudflare directs applications to persist progress incrementally. In-flight HTTP/RPC that reaches storage can be stopped on shutdown; WebSocket requests are terminated on shutdown. [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)
- **Documented contract:** current Worker RPC requires compatibility date `2024-04-03` or later (or the `rpc` flag). Ordinary data crosses as structured-cloneable values; `RpcTarget`, functions, streams, `Request`/`Response`, and RPC stubs are special reference/stream cases rather than cloneable application objects. [Workers RPC](https://developers.cloudflare.com/workers/runtime-apis/rpc/)
- **Source observation, narrowed:** current workerd explicitly throws
  `DOMDataCloneError` when asked to deserialize a generic `RpcStub`. This
  shows that ordinary live stubs are not structured-clone durable values. It
  does not rule out the separate, flagged `ctx.restore()` facility, whose
  irrevocable-stub-storage mode is inherently insecure and not appropriate for
  this core. [workerd `io-channels.c++`](https://github.com/cloudflare/workerd/blob/main/src/workerd/io/io-channels.c++)
- **Issue report, corroborated by source observation:** the open workerd issue for hibernatable RPC targets says the runtime has no mechanism to preserve or rebind `RpcTarget` references across isolate reconstruction. It remains open with no linked implementation as reviewed. [workerd #6087](https://github.com/cloudflare/workerd/issues/6087)
- **Documented contract:** a client-held `RpcTarget` stub pins memory in the callee until it is disposed. Stubs created in an event are automatically disposed at event completion; when a stub crosses an RPC, the execution context can be extended until it and calls through it are disposed. Explicit `using`/`Symbol.dispose`, and `dup()` when ownership must be retained, are the prescribed lifecycle controls. [RPC lifecycle](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/)
- **Documented contract:** normal DO storage read-modify-write is protected by input gates, and the output gate withholds observations until storage writes finish. Cloudflare specifically recommends against wrapping normal operations or external I/O in `blockConcurrencyWhile`; its example gives roughly 200 requests/second for a 5ms global block. [Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)
- **Documented contract:** failed DO calls can leave a stub broken; callers should create a fresh durable-object stub for a retry. Retry only errors marked `retryable` when the operation is idempotent, use backoff, and do not retry errors marked `overloaded`. [DO error handling](https://developers.cloudflare.com/durable-objects/best-practices/error-handling/)
- **Documented contract:** each object has one alarm; alarm execution is at-least-once, one alarm handler runs at a time, failures retry with exponential backoff from two seconds up to six times, and only the newest `setAlarm()` has that retry behavior. Constructors run before an alarm after wake-up, so setting an alarm in a constructor can interfere with the alarm due to fire. [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- **Documented contract:** `ctx.abort()` immediately resets the DO and cannot be caught by application code. It retries an interrupted alarm by default; `{ retryAlarm: false }` is required on every abort path intended to stop the interrupted alarm. This was added on 2026-08-25, so it requires the production runtime and local Wrangler version that support it. [DO state API](https://developers.cloudflare.com/durable-objects/api/state/) and [Cloudflare changelog](https://developers.cloudflare.com/changelog/post/2026-08-25-durable-object-alarm-abort-no-retry/)
- **Source observation:** `ctx.abort()` synchronously shuts down storage before terminating execution to prevent a promise/output-gate race that could allow writes to finish after cancellation. That means an application-level “record abort, then reset” protocol needs its own durable completion marker and must never assume code following `abort()` runs. [workerd `actor-state.c++`](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/actor-state.c++)
- **Documented contract:** a Dynamic Worker `WorkerCode` carries its own compatibility date and flags; `get(id)` may reuse an isolate but has no identity guarantee: even two requests on the same returned `WorkerStub` may execute in different isolates and its code callback may run again. Code for an ID must remain exactly the same, or receive a new ID. [Worker Loader API](https://developers.cloudflare.com/dynamic-workers/api-reference/)
- **Source observation:** workerd describes a Worker Loader as a cache that automatically unloads unused workers; a shared loader ID permits bindings to share that cache. This is a performance implementation detail, not an application session/lifetime contract. [workerd configuration schema](https://github.com/cloudflare/workerd/blob/main/src/workerd/server/workerd.capnp)
- **Documented contract:** a DO shares an I/O context across all of its concurrent requests, and currently has a collective limit of 10 distinct in-flight Dynamic Workers. The limit increased from four on 2026-08-28. [Dynamic Worker limits](https://developers.cloudflare.com/dynamic-workers/platform/limits/) and [changelog](https://developers.cloudflare.com/changelog/post/2026-08-28-durable-objects-dynamic-workers-limit/)

### Inferences

- Core may treat a DO call as an at-most-one _attempt_, not exactly-once execution. The smallest sound primitive is: assign a durable operation/event identity before externally visible effects; store enough result/progress to make replays idempotent; reacquire a fresh DO stub on an eligible retry. This replaces multiple ad hoc “revive” routes with one operation ledger or append offset.
- A subscription callback delivered as an `RpcTarget` is safe only as an ephemeral accelerator. It must be disposable, bounded, and recoverable from a durable cursor because it may disappear at event end, client disconnect, isolate termination, explicit disposal, or DO reset. It cannot be the durable subscription itself.
- Avoid treating `WorkerLoader.get()` as a singleton, cache, or place to hold capability/session identity. Use content-addressed `codeId` plus an explicit durable declaration (source/version/class/capability schema) as the identity. Re-run the loader callback and reconstruct the dynamic worker/facet whenever required.
- The core should own only the runtime facts: append-only event log and cursor reads; durable context metadata; declared capabilities/facets and their code identity; activation/reconstruction; bounded delivery; and a small failure taxonomy. Agent orchestration, voice, external integrations, and business-specific projections should become facets or ordinary loaded workers/userspace.
- Pin an explicit compatibility date in the platform configuration and in every loaded `WorkerCode`, recording it in the capability declaration. The report should call out that a date is a compatibility contract, not a current-runtime version pin; production behavior also requires a deploy/runtime test. The latest reviewed docs use `2026-09-29` in their facet configuration example, but this does not prove any Iterate deployment already uses it. [Facet configuration example](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/)

### Gaps

- Cloudflare documentation does not publish a formal promise for the exact hibernation timing beyond the present 10-second statement, nor a public implementation date for hibernatable RPC targets. Do not use a timer as a correctness boundary.
- I found no authoritative Cloudflare source establishing that a generic Cap’n Web connection can be adopted by the hibernatable WebSocket API. The current open runtime issue and workerd persistence source point the other way for long-lived RPC references.
- The project’s actual compatibility dates, Wrangler/workerd versions, and Cloudflare feature flags must be read from the final branch’s deployment configuration before deleting version-specific workarounds.

## Can event subscriptions share live-provider RPC mechanics, and what behavior belongs in a hibernatable transport?

### Takeaway

Yes, a subscriber callback and a live-provider callback can use one internal ephemeral-handle/pager abstraction, provided both are explicitly optional optimizations over a durable cursor. They must not share a promise that the handle survives hibernation. For an idle browser connection, the durable transport should be a hibernatable server WebSocket with a serializable session/cursor attachment; the revived DO reconstructs the provider/callback path from durable declaration and then catches up from the log.

### Cited Findings

- **Documented contract:** `ctx.acceptWebSocket()` is the hibernation API: inbound messages invoke DO `webSocketMessage` and closes invoke `webSocketClose`. It replaces `ws.accept()` and event listeners; using the standard API/event listeners is incompatible with this mode. [DO state API](https://developers.cloudflare.com/durable-objects/api/state/)
- **Documented contract:** hibernatable WebSockets remain connected while the DO leaves memory. A message wakes/recreates the DO and runs its constructor. `serializeAttachment`/`deserializeAttachment` preserves a structured-clone value per connection through hibernation, with a 16,384-byte limit; changes require a new serialization call and attachments vanish when either endpoint closes. [DO WebSocket best practices](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- **Documented contract:** the hibernation API supports at most 32,768 attached sockets per DO, subject to memory/CPU limits; `getWebSockets()` may temporarily include sockets in `CLOSING`, and a new close-auto-reply compatibility flag changes that behavior on dates from 2026-04-07. [DO state API](https://developers.cloudflare.com/durable-objects/api/state/)
- **Documented contract:** automatic request/response pairs can answer static heartbeats without waking a hibernated DO. This is the platform-supported way to avoid a liveness protocol becoming a residency pin. [DO state API](https://developers.cloudflare.com/durable-objects/api/state/)
- **Documented contract:** outgoing WebSockets do not hibernate; active outbound TCP/WebSocket connections make the DO non-hibernateable and billable while they keep it resident (presently up to 15 minutes per connection). [DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/) and [WebSocket best practices](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- **Documented contract:** plain values are copied under structured clone, while `RpcTarget` and functions are replaced by stubs that route calls back to their origin; RPC stubs can themselves cross a live RPC hop. [Workers RPC](https://developers.cloudflare.com/workers/runtime-apis/rpc/)
- **Documented contract:** a returned `RpcTarget` is a remote reference, not object cloning; properties and methods are asynchronously invoked at the origin. The system gives returned object graphs a disposer that releases contained stubs. [Workers RPC](https://developers.cloudflare.com/workers/runtime-apis/rpc/) and [RPC lifecycle](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/)
- **Issue report:** the currently open workerd hibernatable-RPC issue says a Cap’n Web-style active listener pins the isolate and that the hibernation mechanism does not preserve `RpcTarget` objects. It is useful corroboration, but not a public runtime contract. [workerd #6087](https://github.com/cloudflare/workerd/issues/6087)
- **Source observation:** workerd’s hibernation package contains socket metadata and serialized attachment, but not general JavaScript/RPC target state; workerd comments state that a non-serialized attachment does not survive hibernation. [workerd `web-socket.h`](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/web-socket.h)

### Inferences

- Define one core `LiveHandle` interface for both providers and subscribers: `offer(cursor, batch) -> accepted/backpressured/closed`, plus `dispose`. Its registry is in-memory only and is wiped/rebuilt on every construction. The durable subscription is `{subscriptionId, event filter, nextOffset, delivery policy, session/capability declaration}`; it is not a stored stub.
- The pager sends a bounded batch after an append or wake. On `closed`, timeout, overload, or callback failure, remove the live handle and retain only the durable cursor. The next poll, WebSocket message, or explicit resume re-registers a handle and reads from that cursor. This is the same mechanism for live capabilities and subscriptions, without claiming a shared RPC identity across generations.
- For very low latency, append can synchronously offer to live handles after the durable append is protected by the output gate. A handle’s acknowledgement may advance a durable cursor only when the delivery semantics require it; event payload acknowledgements need idempotency keys/offsets because a connection failure can occur after receipt and before acknowledgement.
- Put only tiny recoverable selectors in a socket attachment: protocol version, session/subscription ID, and last acknowledged offset (or a compact epoch). Keep filter definitions, credentials, loaded-code identity, and large cursors in supervisor storage. On constructor, call `getWebSockets()` and re-associate by attachment; then look up declaration and catch up. This makes hibernation ordinary reconstruction instead of a special revive tree.
- An `RpcTarget` live provider can still be used between a loaded worker/facet and the context only for the duration of an active invocation. Require `using` ownership, ban storage of the target/stub, and translate an invalid/broken handle into the same pager `closed` outcome. This removes separate “subscriber callback” versus “live provider” lifecycle machinery while preserving behavior.

### Gaps

- Documentation does not specify exact cross-event ordering between a WebSocket message, alarm, RPC call, and callback into a different dynamic worker. The core should give each subscriber one serialized pager/offset discipline instead of relying on runtime order.
- No primary source found describes Cap’n Web-specific reconnection/stream resumption guarantees in Cloudflare Workers. Any Cap’n Web wire-level resume design needs an integration test against the production compatibility date.
- Cloudflare’s documented WebSocket attachment limit is per connection, but the public docs do not specify a total attachment-memory budget per DO. Keep attachments deliberately tiny and measure the target workload.

## What do facets and Worker Loader actually guarantee, and how should ITX.Builtins / context description expose them?

### Takeaway

Facets already supply the clean runtime layering: supervisor context, named child with isolated database, dynamically loaded class, and a returned DO-like stub. Use that model directly. Replace a hand-produced, privileged `ITX.Builtins` object with a declarative, serializable context manifest that drives capability construction and emits both runtime descriptors and TypeScript types; keep actual live stubs out of the manifest. It should describe durable surfaces and explicitly label ephemeral live handles.

### Cited Findings

- **Documented contract:** a facet is a dynamically loaded `DurableObject` child of a supervisor. Each named facet has isolated SQLite storage, colocated with but unreadable from the supervisor database; the supervisor controls dynamic code, creation, and forwarding. [Durable Object Facets](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/)
- **Documented contract:** `ctx.facets.get(name, startup)` creates or resumes the named facet. The startup callback runs if it has not started or has hibernated, otherwise the existing facet is reused. It returns a DO-like stub usable with `fetch` or direct RPC. [Durable Object Facets](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/)
- **Documented contract:** `ctx.facets.abort(name, reason)` shuts down a running facet, invalidates all existing stubs, and preserves its database; a later `get` can restart it with a different class. `delete` also aborts but permanently removes its database. [Durable Object Facets](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/)
- **Documented contract:** a `FacetStartupOptions` declaration contains a loaded DO class and optional ID. If no ID is supplied the facet inherits its parent’s ID. [Durable Object Facets](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/)
- **Documented contract:** `WorkerLoader.load()` is a fresh one-off worker every call; `get(id, callback)` may reuse a warm isolate but explicitly offers no same-isolate guarantee, even for the same stub. A code change must use a new ID; the callback for a stable ID must return the same content. [Worker Loader API](https://developers.cloudflare.com/dynamic-workers/api-reference/)
- **Documented contract:** a loader’s `WorkerCode` explicitly includes a compatibility date, optional flags, modules, RPC-serializable environment, and optional outbound capability. This is the runtime declaration already closest to a capability manifest. [Worker Loader API](https://developers.cloudflare.com/dynamic-workers/api-reference/)
- **Documented contract:** Dynamic Workers have a collective in-flight-worker limit on a DO’s shared I/O context. Any layering that fan-outs into a unique loaded worker per individual event can hit that fixed limit even if each worker is otherwise correct. [Dynamic Worker limits](https://developers.cloudflare.com/dynamic-workers/platform/limits/)
- **Historical issue, corrected:** workerd #3184 reported a `DataCloneError`
  when wrapping an `RpcTarget` in a JavaScript `Proxy`, but workerd #3212
  fixed that failure in 2024. It is not evidence of a current general proxy
  prohibition. Proxying remains unsuitable as the core typing/description
  mechanism because it does not supply runtime schemas or authority policy.
  [workerd #3184](https://github.com/cloudflare/workerd/issues/3184)

### Inferences

- Make the durable context manifest the one input to `ITX.Builtins`, rather than letting each built-in manufacture an untyped path/authority. Suggested shape: `{manifestVersion, contextAddress, eventLog: {schema, retention}, capabilities: Record<name, {kind: "facet" | "worker" | "endpoint", codeId, compatibilityDate, classOrEntrypoint, publicMethods, placement, requiredBindings, state: "durable" | "ephemeral"}>, subscriptions: Record<name, {eventTypes, delivery, cursorPolicy}>}`. Store durable pieces alongside the context and validate it before activation.
- Generate the TypeScript surface from the same catalogue used to validate runtime paths: an explicit `CapabilitySpec<Input, Output, PublicMethods>` schema can produce (a) declaration/manifest JSON, (b) `ITX` typed methods, (c) public-method allowlist, and (d) human-readable context description. This eliminates separate authoritative lists for built-ins, access checks, loader recipes, and documentation.
- Do not put authority-bearing objects, `Fetcher`s, `RpcTarget`s, DO stubs, secrets, or functions in the manifest. They are live handles rather than durable context facts. Build them from the manifest in a short-lived resolver, dispose them at the execution boundary, and record only the stable selector/code/version required to recreate them.
- The supervisor should be the sole owner of event append, subscriptions/cursors, manifest validation, and facet activation. A facet should receive a narrow capability binding (append a permitted event; page from a bounded cursor; resolve one declared capability) instead of `ITX.Builtins` as an omnibus privileged object. This preserves capabilities but makes their public description, types, placement, and recovery uniform.
- Use `facets.abort` for an intentional code-generation or declaration generation change, retaining data when the migration is compatible; use `facets.delete` only for explicit lifecycle/data deletion. Any current hand-written reset/cleanup paths that merely reproduce that runtime contract are candidates for removal after end-to-end verification.

### Gaps

- The public facet API does not state transactional/ordering semantics between supervisor storage and facet storage, so cross-database changes must remain message/event based and idempotent. Do not infer an atomic two-database transaction from colocation.
- Cloudflare publishes no general reflection API that returns a loaded Worker’s complete exported RPC types. The manifest/type generator needs to be Iterate-owned build-time metadata, not a promise of runtime reflection.
- The exact existing `ITX.Builtins` call paths and all in-flight branch assumptions need a code-level inventory before selecting manifest field names. The proposed shape is an architectural direction, not a compatibility-preserving patch by itself.
