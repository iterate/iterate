## 1. Current incident-scarred invariants at risk

- **Zero-lag recovery covers the whole ingest attempt—not merely `runInBackground`.** The June 10/July 7 fix durably tracks blockers, background work, and the host’s entire sink attempt, because both stream and processor DOs can disappear after the stream believes there is no lag ([stream-processor-keepalive.ts:4](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-keepalive.ts:4), [stream-processor-keepalive.ts:164](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-keepalive.ts:164), [stream-processor-host.ts:503](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:503)). Recovery also depends on mark-before-work, bounded backoff, quiet-clean reset, deploy-version reset, hung-work detection, and alarm reassertion ([stream-processor-keepalive.ts:27](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-keepalive.ts:27), [stream-processor-keepalive.ts:237](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-keepalive.ts:237)). A typed revived event alone preserves none of this.

- **There is currently an at-head/final-fold barrier.** `reconcile` runs only after the complete batch and only when the raw durable head is observed, specifically to avoid reissuing vendor work whose terminal fact is in a later page ([stream-processor.ts:449](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:449)). The host additionally performs an unfiltered trailing pull so non-consumed tail events advance the checkpoint and create that at-head pulse ([stream-processor-host.ts:522](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:522)). Without an equivalent runner-level `onCaughtUp`, requested event N followed by unconsumed N+1 can wedge forever: N is “catching up,” N+1 invokes no `processEvent`, no work starts, and therefore no revival is ever armed.

- **The batch overrides contain real semantics that strict blockers do not replace.** GitHub’s `#batchConversation` propagates asynchronous collaborator verification to later webhooks in the same delivery and resets it at route boundaries ([github-agent-processor-implementation.ts:100](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/integrations/github/github-agent-processor-implementation.ts:100), [github-agent-processor-implementation.ts:196](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/integrations/github/github-agent-processor-implementation.ts:196)). The verification fact appended by event N is not folded before already-delivered event N+1; deleting this as “pure” can drop authorized follow-ups. Slack and Telegram similarly carry the latest lifecycle fact across catch-up pages and paint only at head ([slack-agent-processor-implementation.ts:319](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/integrations/slack-agent-processor-implementation.ts:319), [telegram-agent-processor-implementation.ts:263](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/integrations/telegram-agent-processor-implementation.ts:263)).

- **Obligations are intentionally derived from final folded state.** Repo creation explicitly avoids event-time creation because refold/catch-up could force-push seed commits over user work ([repo-processor-implementation.ts:275](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/repos/repo-processor-implementation.ts:275)). Agent scheduling and capability execution similarly use final state to avoid redoing settled work ([agent-processor-implementation.ts:461](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/agents/agent-processor-implementation.ts:461), [capability-host-processor-implementation.ts:269](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/capability-host/capability-host-processor-implementation.ts:269)). An ordinary relevant-event arm regresses this unless raw-head gating survives.

- **Failure ordering is deliberate.** All already-started blockers are settled before rejection; failure leaves the checkpoint unchanged; durable persistence happens before in-memory advancement and waiter resolution ([stream-processor.ts:534](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:534), [stream-processor.ts:565](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:565)). Malformed consumed events deliberately advance the checkpoint before diagnostic append, preventing an error-reporting failure from re-poisoning the rescued batch ([stream-processor.ts:592](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:592)). Per-event execution must retain those guarantees.

- **The inline core must remain a hard boundary.** Its append path is synchronous/await-free through validation, reduction, and commit; all fallible side effects occur post-commit ([stream-durable-object.ts:213](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-durable-object.ts:213), [stream-durable-object.ts:295](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-durable-object.ts:295)). Its rebuild is paged specifically to avoid constructor OOM ([stream-durable-object.ts:994](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-durable-object.ts:994)). Shared “runner” abstractions must not leak async checkpoint/recovery behavior into this path.

## 2. Concrete omitted migration work

- **The inventory is eleven semantic overrides, not eight total:** eight production `processEventBatch` overrides and three `reconcile` overrides. Scheduler’s override is domain logic—`nextWakeAtMs(state)` plus awaited alarm repoint—not generic checkpoint work ([scheduler-processor-implementation.ts:162](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/scheduler/scheduler-processor-implementation.ts:162)). GitHub, Slack/Telegram, repo/agent/capability, scheduler, and the two browser processors each need distinct replacements.

- **Legacy cursor conversion must preserve processing acknowledgement even when state is invalid.** Existing records are `{offset,state}` at `stream-processor:<slug>:snapshot` ([stream-processor-host.ts:202](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:202), [stream-processor-host.ts:438](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:438)). Convert valid state to both cursors at `offset`; if state/reducer schema is stale, retain `acknowledgedThroughOffset=offset` and reduce-only rebuild to it. Treating the record as absent replays effects. Overwriting the same key is also rollback-fatal: old code rejects the new shape and resumes from zero ([stream-processor.ts:801](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:801)). You need versioned dual-read/dual-write or an explicit no-rollback migration.

- **The proposed idempotency format is not compatible.** Current `<slug>/<key>@<path>:<offset>` intentionally includes slug and source path; path prevents same-slug fan-in collisions at equal offsets ([stream-processor.ts:635](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:635)). If an effect commits under the old key and eviction occurs before checkpoint, post-deploy replay with the new key duplicates it. Revision 0 should remain byte-identical to the legacy format.

- **Event-derived and obligation-derived keys must remain separate concepts.** A recovered repo obligation handled by each new `repo/revived` event cannot include that revival’s offset: every recovery pass would get a fresh key and could repeat seed work ([repo-processor-implementation.ts:275](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/repos/repo-processor-implementation.ts:275)). Agent/capability normal, reconciliation, and backstop lanes deliberately share stable completion keys so races collapse ([agent-processor-implementation.ts:614](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/agents/agent-processor-implementation.ts:614)). Agent also parses literal old key prefixes for its autonomous-loop breaker ([agent-processor-implementation.ts:1139](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/agents/agent-processor-implementation.ts:1139)); changing serialization alters behavior, not just deduplication.

- **Browser persistence needs a real SQL migration and new committer API.** The table only has `reduced_state,max_offset` ([processor-state-storage.ts:23](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/client-libraries/browser/processor-state-storage.ts:23)); `CREATE TABLE IF NOT EXISTS` will not add reducer version, reduction offset, acknowledgement, and revision. Projection statements and progress must enter the same `SqlClient.batch(transaction:true)`. Also retain `prepare()` ordering: raw schema/reset currently runs before checkpoint read to prevent silently skipping history ([implementation.ts:31](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/client-libraries/browser/raw-events/implementation.ts:31)).

- **Every current use of `snapshot().offset` needs classification.** Wake replay must return processing acknowledgement, not the reduction-pinned snapshot offset; the stream persists that handshake value as its delivery watermark ([stream-processor-host.ts:559](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:559), [stream-subscribers.ts:493](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-subscribers.ts:493)). RPC/generated API types, scheduler progress checks, browser replay cursors, `waitUntilEvent`, and live-state publication all need deliberate updates. Preserve the current gate that prevents default/partial refold state from escaping ([stream-processor.ts:724](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:724)).

- **Recovery storage and contracts require transition logic.** The current keepalive record has no processor identity and revival catches up every registered processor ([stream-processor-keepalive.ts:55](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-keepalive.ts:55), [stream-processor-host.ts:270](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:270)). Per-runner records must adopt existing debt or temporarily fan out. Each typed revived fact also needs a resolvable event schema plus `consumes`, not merely a string added to `consumes` ([stream-processor.ts:473](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor.ts:473)).

## 3. One-PR sequencing risks

- **A single flag-day deploy is not rollback-safe.** It simultaneously changes persisted record shape, idempotency wire format, recovery event vocabulary, wake cursor meaning, and all processor semantics. A failed rollback can restart processors at zero and replay external effects. One mergeable PR is defensible only if it ships additive old/new readers and both runtime paths, with activation independently gated per slug.

- **The blast radius is understated.** Six production DO classes create the host—not four—and they contain thirteen registrations: agent, capability-host, project, repo, scheduler, and secret ([agent-durable-object.ts:36](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/agents/agent-durable-object.ts:36), [project-durable-object.ts:76](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/projects/project-durable-object.ts:76), [scheduler-durable-object.ts:50](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/scheduler/scheduler-durable-object.ts:50)). One shared-runner defect can stall every processor in a hosting DO.

- **Stage activation, even if code review remains one PR:** legacy progress reader/writer and revision-0 keys first; one low-side-effect processor canary; simple processors next; obligation processors after at-head/revival evidence; scheduler and browser transactional processors last. `agent` is a poor first production proof target because it is the incident-bearing processor with background work, timers, stable cross-lane keys, and multiple at-head obligations.

- **Rolling incarnations are not atomic.** Stream and target DOs can run different code generations, existing sinks retain old cursor revisions, and browser clients are independently long-lived. Keep old generic revival, old handshake/storage reads, and old idempotency serialization through a rollback window. New audit/revived facts are permanent journal data, so old contracts must safely tolerate them.

## 4. Materially wrong, underspecified, or dangerous

- **“Retry blockers indefinitely” contradicts the current transport.** A rejected wake backs off and eventually parks ([stream-subscribers.ts:814](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-subscribers.ts:814)). Either the runner owns indefinite internal retries without rejecting the sink, or upstream parking and resume semantics must change; `skipThrough` alone will not revive an already parked subscription.

- **The recovery construction check tests the wrong implication.** “Recovery configured ⇒ consumes revived” does not prevent the dangerous cases: `runInBackground`, blockers, or ingest running without recovery. Recovery must be mandatory whenever consequential work is possible, and the registry must track full ingest attempts.

- **Cursor controls are not local KV operations.** Rewinding acknowledgement does not rewind the stream’s active pump, whose cursor was fixed at wake handshake. Controls must serialize with ingest, invalidate/close old sinks, fence stale commits and background appends by revision, and force replay or self-pull. `skipThrough` also needs `expectedCursorRevision`, durable-head bounds, and defined reduction semantics.

- **Audit append plus cursor mutation is cross-DO and non-atomic.** The plan does not define requested/completed/failed audit facts, ordering, crash recovery, actor/reason, or what occurs if audit succeeds and CAS fails—or vice versa. These destructive controls also need a privileged operator surface; the existing processor facade is intentionally read-only to avoid checkpoint corruption ([rpc-targets.ts:5847](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/rpc-targets.ts:5847)).

- **The two-cursor state machine is incomplete.** `reducedThroughOffset <= acknowledgedThroughOffset` is valid during reducer invalidation only if effects remain blocked until reduction catches up. Otherwise the normal per-event order suggests reduction may lead acknowledgement. Specify valid states, atomic commits, reducer-version ownership/bump policy, and how `skipThrough` reduces skipped events. Incremental re-reduction also needs a pending state slot or an explicit decision to publish partial/default state; the proposed progress record has nowhere to stage an atomic swap.

- **The “thin registry” omits required responsibilities:** unfiltered catch-up, cold-load/schema-refold gating, read-your-writes waiters, live-state assembly, sink serialization, observers, inherited alarm adoption, and scheduler alarm slices all currently live in the host ([stream-processor-host.ts:334](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:334), [stream-processor-host.ts:377](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:377), [stream-processor-host.ts:461](/Users/jonastemplestein/.herdr/worktrees/iterate/stream-runner/apps/os/src/domains/streams/stream-processor-host.ts:461)). Deleting the host before assigning each invariant a concrete owner is unsafe.
