# V4 project-worker portability to RivetKit Actors

**Scope.** Research only; this does not propose a port or a product refactor. It asks what should remain deliberately portable while V4 stays on Workers. Findings are pinned to Rivet Actors source [`caed5835fe3cc3cd37c9a6eb715abd5105024f2a`](https://github.com/rivet-dev/actors/tree/caed5835fe3cc3cd37c9a6eb715abd5105024f2a) (checked 2026-09-07; `main` commit dated 2026-09-04). The current published npm release is [`rivetkit@2.3.15`](https://www.npmjs.com/package/rivetkit/v/2.3.15); tag `v2.3.15` resolves to this same commit, so the source findings apply to the release rather than only an unshipped `main`. Claims below are either **source-supported** (documentation/source) or explicitly labelled **not runtime-tested**. No Rivet deployment was created.

## Verdict

RivetKit is a plausible host for the _durable per-context stream and processor engine_, but not a drop-in host for the current context's live-capability, Worker-loader, or native-RPC semantics. Treat these as three independently portable modules rather than putting a broad `ActorPlatform` interface under the whole product.

| Concern                                                                     | Assessment                      | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Context identity, event log, checkpoints, idempotency, core reduction       | **Easy / medium**               | One actor key can represent `{projectId, path}` and an actor owns isolated SQLite. The current stream already concentrates persistence behind [`DurableObjectStorageSlice`](../packages/v4/project-worker/src/stream/stream-storage.ts). SQL syntax/iteration and async transaction shape must translate.                                                                                                                                                                                      |
| Ordered post-commit delivery and wake-up recovery                           | **Medium**                      | Rivet durable schedules wake actors, but actions are the scheduled unit; a failed one-shot is complete and recurring overlaps are skipped. V4's alarm-driven obligation/retry loop therefore needs explicit persisted attempt state and a Rivet action that re-derives obligations.                                                                                                                                                                                                            |
| Plain HTTP / raw WebSocket fetch door                                       | **Medium**                      | Rivet has raw actor `fetch` and `onWebSocket` routes, but its gateway URL/auth/routing model replaces Workers' `fetch` 101 passthrough and host-based project ingress.                                                                                                                                                                                                                                                                                                                         |
| Owner-scoped dynamic workers/facets and their `globalOutbound` ITX          | **Hard**                        | Workers `WorkerLoader` plus `ctx.facets`, `ctx.props`, service bindings, and injected `env.ITX` are runtime-specific. Rivet actor-to-actor calls are typed action RPC, not object-capability injection.                                                                                                                                                                                                                                                                                        |
| Session-lent callback stubs, provenance, native stub props, deep pipelining | **Hard / substantive redesign** | Rivet documents connections and actor-to-actor actions, not transferable live object references, `RpcTarget`-style lending/recall, native `RpcPromise` pipelining, or arbitrary callback capabilities. Keep capability semantics in a distinct transport module; do not pretend an actor handle has those properties.                                                                                                                                                                          |
| User-supplied bundled TypeScript                                            | **Hard, separate executor**     | The checked-in public dynamic-actor surface is not evidence of a production dynamic-code executor: [`DynamicActorIsolateRuntime.start()`](https://github.com/rivet-dev/actors/blob/caed5835fe3cc3cd37c9a6eb715abd5105024f2a/rivetkit-typescript/packages/rivetkit/src/dynamic/isolate-runtime.ts#L37-L42) calls its loader and discards the returned source. Dynamic untrusted code needs a separately isolated executor with explicit resource and egress controls, not actor `state`/SQLite. |

The current program makes this division unusually visible: the reading guide distinguishes durable configuration from live authority and the “decide before commit / react after commit” rule ([reading guide](../packages/v4/project-worker/docs/reading-guide.md)). Preserve that distinction; it is the portability seam.

## What RivetKit actually supports

### Storage, serialisation and actor exclusion — source-supported

Rivet documents isolated actor state and a per-actor embedded SQLite database ([state](https://rivet.dev/actors/docs/state/)); its source also states the single-writer invariant for an actor's KV and SQLite ([source](https://github.com/rivet-dev/actors/blob/caed5835fe3cc3cd37c9a6eb715abd5105024f2a/CLAUDE.md#L212-L213)). Use SQLite as the source of truth for V4's event, chunk, cursor, checkpoint and resource-halt tables—not `c.state`, whose saves are throttled by default.

`c.db.transaction(async tx => …)` commits when its callback resolves, rolls back on throw, and queues other actor SQL FIFO; it has a 60-second default safety timeout ([SQLite transactions](https://rivet.dev/actors/docs/sqlite/)). The release's public/native database interface is Promise-returning for both statements and begin/commit ([source](https://github.com/rivet-dev/actors/blob/caed5835fe3cc3cd37c9a6eb715abd5105024f2a/rivetkit-typescript/packages/rivetkit/src/common/database/config.ts#L76-L108)); even if a particular embedded backend happens to execute locally, that is not a portable synchronous API. Thus the blocker is **not SQL syntax**—V4's tables and transaction scope translate—but converting the synchronous stream core/persistence calls to an async transaction boundary (or introducing a carefully bounded synchronous domain mutation that collects SQL commands). More importantly, V4's [`Stream.armAlarmNoLaterThan`](../packages/v4/project-worker/src/stream/stream.ts) intentionally does not await `setAlarm`, relying on the Workers invocation output gate. A Rivet implementation must expose a _uniform async commit operation_ whose completion includes durable schedule insertion/update, or write a pending-obligation row inside the transaction and separately invoke an idempotent armer. It must never silently turn that fire-and-forget native assumption into best effort.

### Wake/schedule — source-supported, different failure contract

Schedules survive sleep, restart, upgrades and crashes and invoke actions on the same actor ([schedule](https://rivet.dev/actors/docs/schedule/)). But Rivet says failed runs receive no immediate retry; a one-shot is complete after its attempted invocation; overlapping recurring runs are skipped. Consequently a translation should store `nextAttemptAt`, attempt number, and any cursor/retry reason in SQLite, and schedule a named `driveObligations` action. Each invocation scans durable obligations, delivers idempotently, persists its result, and schedules the next earliest due item. That mirrors V4's already explicit cursor/retry state without claiming identical alarm delivery.

### Connections, HTTP and tenant authentication — source-supported

Rivet supports low-level `onWebSocket`, standard WebSocket objects and `handle.webSocket()` ([WebSocket handler](https://rivet.dev/actors/docs/websocket-handler/)); its connection model offers `onBeforeConnect`, connection state, `onConnect` and `onDisconnect` ([connections](https://rivet.dev/actors/docs/connections/)). Hibernatable raw connections are documented via actor configuration/connection state, but no run was made here to verify V4's hibernation scale or close ordering.

Tenant identity should be an actor-key/route decision made by a trusted outer HTTP gateway, then verified again in `onBeforeConnect`/`createConnState` and action authorization. Rivet Cloud actors are private behind a publishable token; self-hosted actors are public by default; application authentication/authorization remains required for frontend or public traffic ([authentication](https://rivet.dev/actors/docs/authentication/)). A publishable token is not an unforgeable ITX authority nor a substitute for V4 provenance.

Rivet’s server-side `c.client()` calls other actors via typed clients/actions ([actor-to-actor communication](https://rivet.dev/actors/docs/communicating-between-actors/)). That is useful for a named context/processor topology but does **not** establish support for sending a browser-owned callable object to an actor or returning it as an attenuated capability. The current `rpc-stub-directory`, relay and pager behavior must remain a transport-specific module until a protocol is deliberately designed and tested.

### Dynamic execution and outbound network — not a portability proof

The checked source exports `dynamicActor({ load })`, whose loader has `{ key, client }` and returns source plus optional Node CPU/memory limits ([public type](https://github.com/rivet-dev/actors/blob/caed5835fe3cc3cd37c9a6eb715abd5105024f2a/rivetkit-typescript/packages/rivetkit/src/dynamic/internal.ts)). The current runtime implementation is a stub for execution/lifecycle, as noted above. It is therefore unsafe to infer code isolation, module policy, provenance, secret mediation, or egress controls from it.

Rivet's separate agentOS/sandbox materials demonstrate that sandboxing is a distinct concern, and even recommend restricting sandbox network egress ([agent example guidance](https://rivet.dev/actors/learn/ai-agent)). For V4 dynamically bundled TypeScript, specify a separate executor interface with: verified bundle identity, per-execution resource limits, a deny-by-default network broker, secret substitution only in that broker, structured audit/provenance, and an explicit RPC/HTTP protocol. Do not put `fetch` or deployment secrets directly in dynamically loaded code.

## Practical seams to preserve when change is otherwise justified

This is a small set of _real_ seams, not a universal vendor-emulation layer. There should be an adapter only where V4 has (or gains) two concrete hosts.

1. **`ContextStore` seam, at the stream commit point.** Preserve the domain-level operations V4 already uses—atomic append/reduce/checkpoint/cursor/resource-halt plus read/page—not raw `DurableObjectStorage`. The Workers adapter keeps `transactionSync`; a Rivet adapter owns the SQL dialect/lazy-row conversion and uses `c.db.transaction`. Make scheduling part of the commit outcome (`nextWakeAt`), not an ambient `setAlarm` call. The interface is deep because callers state an event transition and receive its committed result, while each host hides transactions and schedule mechanics.
2. **`ObligationDriver` seam.** Given a context and durable state, it derives delivery/retry/quiesce obligations and records results. A Workers adapter binds it to `alarm()`; a Rivet actor action binds it to `c.schedule`. This directly protects the current “react after commit” semantics and exposes host-specific at-least-once/retry behavior instead of faking alarms.
3. **`ContextTransport` seam only for public, serialisable requests.** It should name `invoke(expression,args)`, append/read, and fetch-shaped requests/results where serialisable and protocol-defined. Current `ReachableContext` is a useful direction ([`stream.ts`](../packages/v4/project-worker/src/stream/stream.ts)), but it must not claim borrowed callback stubs, property access, or pipeline batching are portable.
4. **Keep live authority outside those seams.** `RpcStubDirectory`, capnweb session relay, provenance/admission, WorkerLoader facets and the `globalOutbound` ITX injection remain Workers implementations. Extract a transport-neutral _policy/result vocabulary_ only after a second implementation exists; do not invent a hollow “capability adapter.”
5. **Separate `ConstrainedExecutor` seam, later.** It takes a content-addressed bundle plus a narrow, audited input/output and brokered egress interface. It is not an actor adapter and does not receive a raw actor context. This is the only credible route for dynamic worker/facet code on Rivet.

## Test structure: preserve behaviour without pretending hosts are identical

| Tier                         | Run where                                                                  | Examples and purpose                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shared behavioural contracts | Node/unit, using a real SQLite-backed test store where transactions matter | Event ordering, idempotency, chunk round-trip, atomic append + core reduction + checkpoint, pause/admission, cursor retry progression, restart/rebuild from tables, and deterministic obligation derivation. These should reuse/extend the existing stream and processor tests, not mocks that erase transactions.                                                                                                                                 |
| Adapter conformance          | Once per host                                                              | Workers: native `transactionSync` rollback and alarm output-gate tests. Rivet: `c.db.transaction` rollback/FIFO test, migration/restart test, and scheduled-action retry/overlap test against Rivet’s actual scheduler. Assert the declared differences (not identical timing). Rivet documents `setupTest`, but fake JS timers do not drive its scheduler ([testing](https://rivet.dev/actors/docs/testing/)); poll a bounded observable outcome. |
| Native runtime acceptance    | Each platform, deliberately non-shared                                     | Workers keeps `__workers-tests__` and deployed/e2e coverage for RPC pipelining, lent stubs, hibernation, `ctx.facets`, `WorkerLoader`, 101 forwarding and provenance. Rivet adds its own actor key/routing, auth rejection, raw WS reconnect/hibernation, SQLite migration, actor-to-actor action and schedule acceptance tests.                                                                                                                   |
| Executor/security acceptance | Separate executor deployment                                               | Malicious bundle cannot read host secrets, bypass egress broker, forge provenance, retain a revoked permission, or escape CPU/memory/time limits. This is mandatory before dynamic code is called portable.                                                                                                                                                                                                                                        |

Existing HTTP/capnweb e2e assertions may be valuable outcome specifications, but their current fixtures and native Worker tests are not automatically portable: source fixtures import `cloudflare:workers`, and Cap'n Web/native RPC behavior is exactly the unsupported part. Reuse test _intent and assertion bodies_ where protocol-compatible; preserve native controls in their platform lane.

## Alchemy v2 example

There is a useful historical runtime-portability example, pinned to Alchemy source commit [`1d0d7af2c88d962049f2ca69a61d7d99d55df6bf`](https://github.com/alchemy-run/alchemy/commit/1d0d7af2c88d962049f2ca69a61d7d99d55df6bf), 2026-08-07. It has `alchemy@2.0.0-beta.68` and `rivetkit@2.3.10` in its package manifest ([package](https://github.com/alchemy-run/alchemy/blob/1d0d7af2c88d962049f2ca69a61d7d99d55df6bf/packages/alchemy/package.json)); the SHA is the pin, not a claim that it is the beta.68 tag.

It is stronger than mere IaC: one unmodified shared Counter fixture ([counter](https://github.com/alchemy-run/alchemy/blob/1d0d7af2c88d962049f2ca69a61d7d99d55df6bf/packages/alchemy/test/Worker/conformance/counter.ts)) is bridged into a Rivet actor ([bridge](https://github.com/alchemy-run/alchemy/blob/1d0d7af2c88d962049f2ca69a61d7d99d55df6bf/packages/alchemy/src/Rivet/ActorBridge.ts)), deployed, and exercised by a remote shared conformance suite ([test](https://github.com/alchemy-run/alchemy/blob/1d0d7af2c88d962049f2ca69a61d7d99d55df6bf/packages/alchemy/test/Worker/conformance/rivet/Conformance.test.ts)). The commit message reports all 9/9 conformance tests locally against `rivetdev/engine:2.3.10`. Its source-level scope is KV persistence/isolation/list/delete, SQL, alarms, stream result and typed Effect failure—not V4's capability system.

By contrast, Alchemy's [`EcsRunnerHost`](https://github.com/alchemy-run/alchemy/blob/1d0d7af2c88d962049f2ca69a61d7d99d55df6bf/packages/alchemy/src/AWS/Rivet/EcsRunnerHost.ts) builds/pushes an image and runs a Fargate runner: that is deployment/IaC wiring only. Neither portion proves V4-specific transaction/schedule equivalence, transferable live capabilities, native pipelining, executor isolation, provenance or egress policy; those still need the layered acceptance tests above. The implementation has since been deleted from current `main` and is not documented in current Alchemy public docs, so characterize it strictly as a historical public-source experiment/conformance suite—not a current supported Alchemy feature.

## Decision guardrails

The combined [runtime portability plan](v4-runtime-portability-plan.md) maps these
findings to current source files, a concrete test layout, and a small first
implementation. It also records why the historical Alchemy bridge is a useful
conformance pattern but not a guarantee of V4 semantic parity.

Do not refactor now merely to make a hypothetical port compile. When a second host is being built, introduce each seam beside a concrete Workers implementation and a concrete Rivet implementation, move one behavior through it, and add the corresponding contract plus both native acceptance tests. Stop at a semantic mismatch and name it; do not emulate provider-only features behind misleading common methods.
