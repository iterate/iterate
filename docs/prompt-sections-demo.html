The life of a prompt

Click any event card: it expands to the full event (YAML), the right pane shows the actual provider request as of that offset (computed live by a miniature of the real fold), and the URL updates so you can link to any state. The standing lane renders as ONE system message: the tagged document in canonical order (hot sections last). Line highlights mark the diff vs the previous event; the ✂ line marks where the provider's cached token prefix ends (with permanent send stamps, that is everything except the newest suffix). Assistant turns are REAL raw outputs — they exhibit the rules that were in force when they were generated, which is what makes the replace-vs-append question visible.

The opinion — re-adding a key is the update; temporal position is the coherence mechanism. A standing instruction reads as timeless, and the standing document sits ABOVE every turn — so editing it both busts the cache for the whole conversation behind it and can manufacture "history contradicts my instructions". The design avoids both by construction:
  1. Birth window: keyed adds coalesce in place, free. Until a request has been sent, re-adding a key edits the pending standing section directly — nothing sent, nothing contradicted, nothing cached yet. Templates do all their shaping with the same everyday event as everyone else.
  2. Once sent: the same keyed add lands at the tail, at its moment in time. The new occurrence renders as a system message in the timeline with supersedes linkage — everything before it visibly predates it (no contradiction, no marker needed), and the entire prefix stays byte-stable (cache intact). The superseded copy rides until compaction collapses to latest. (Whether these render as system or developer is a provider-mapping detail.)
  3. context-rewritten (replace/delete) is deliberate history rewriting — redaction, un-saying, delete *. They bust the cache from the standing document down and, applied to behavioral rules with contradicting visible history, produce the scenario-3a anti-pattern. Not the everyday verb.
Reference — two events, and the ops inside context-rewritten
event what it is
agents/context-added The everyday event — the only one most authors ever use. Without key: a turn (user / assistant / developer message at its offset). With key (or segments: [{key, content}] for many at once): keyed standing content — and re-adding a key IS the update: an un-sent occurrence coalesces in place (free); a sent one appends at the tail, at its moment in time, with supersedes stamped by the fold. First occurrence joins the standing document when no conversation exists yet. Existing streams' keyed events already mean exactly this — no legacy mapping.
agents/context-rewritten Deliberate history rewriting — rare, audited, named to discourage. {op: "replace"|"delete", key, content?} (plain fields, no selector grammar; key: "*" = everything, both lanes). Changes what PAST render positions contain: busts the cache from the standing document down and, applied to behavioral rules with contradicting visible history, produces the scenario-3a anti-pattern. For redaction (author supplies replacement text) and un-saying.
agent/created · agent/configured · agent/llm-request-requested Machinery, unchanged: existence; scheduling/parsing config (debounce born high, lowered by the worker as its done-configuring signal — never model-visible); the request whose offset is its identity and whose send defines "sent" for every occurrence at or below it. Script machinery (capability-host/script-run-requested and -settled) is likewise never model-visible: its consequence is the RENDERED developer result, which includes the script\u2019s measured duration — slow operations become knowable — and the ONE machinery event with a rendered face: it projects into the timeline as the permanent "Current date and time" line (no separate timestamp event, no floating tail; every request\u2019s prompt is a strict superset of the last, stamp included).
