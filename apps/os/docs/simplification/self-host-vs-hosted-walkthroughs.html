Self-hosted vs iterate-hosted — the walkthroughs

Every differing step shows what happens hosted and what happens self-hosted, concretely. Grey rows = byte-identical.

One codebase. The kernel and OS worker are identical in both. The only differences are the values of ~5 config knobs (config.ts): leased OAuth clients, platform egress keys, hostname base, identity authority, billing counterparty. Kernel = streams · files · secrets · ingress+egress · capability resolver · identity · confined-runner. Same everywhere.

6 · The stateless OS app & how sign-in works

The big idea: the OS dashboard stops being a large special thing. It becomes a stateless front-end worker that you reach by proxy — exactly like the tasks app in your config template already does (config-repo-template/worker.ts:45–66).

browser → os--<proj>.iterate.app or os.<yourdomain>
↓ proxy (a project's fetch)
① gate: itx.auth.get({policy}) — is this visitor a member/operator?
↓ if allowed, proxy through with identity attached
stateless OS front-end worker (the dashboard UI — holds no state)
↕ renders / calls
the capability tree (kernel)

Same shape as tasks, the inbound MCP server, and any user app: a stateless protocol adapter over the capability tree, reached by proxy. You could swap in a different OS front-end and nothing else changes.

Signing in — the flow

self-hosted iterate-hosted
1 Visit os.<yourdomain> — request passes Cloudflare Access (your wall) first Visit os--<proj>.iterate.app — hits iterate's ingress
2 Identity comes from your IdP: the cf-access-jwt header (or your own OIDC) Identity from iterate's OIDC / operator-session (redirect to sign in, cookie) auth/operator-session.ts
3 Authorize: the proxy calls itx.auth.get({policy:"project-member"|"operator"}).fetch(req) to gate membership — identical (the same gate tasks/todo use today)
4 Serve: proxy forwards to the stateless OS front-end, which renders by calling the capability tree — identical. The front-end holds no session; auth lives entirely at the proxy.

Why this connects to auth: today the dashboard has bespoke operator-session auth on the os host, separate from how project apps authenticate. Making the OS a proxied stateless app collapses them into one gate — every front-end (dashboard, MCP, tasks, user apps) authenticates the same way: identity established at the wall (iterate OIDC, or your Cloudflare Access), authorization via itx.auth at the proxy.

Contested resources & multi-project

Resource Self-provisionable?
Leased OAuth clients (Google restricted-scope, verified Slack app) No — need vendor approval. The deepest moat.
*.iterate.app ingress hostnames No — iterate's domain; you use your own domain instead.
Single billing counterparty No — else you pay each provider directly.
Everything else (auth, egress keys, hostnames-on-your-domain, the whole kernel) Yes — same code, your instance / your keys.

Multiple projects when self-hosting? Yes. The kernel addresses everything by {projectId, path} and the directory maps many slugs → many projects. Only the convenience hostname is tied to *.iterate.app; with your own domain you run as many projects as you like. Multi-project is a kernel property, not a hosted feature.
