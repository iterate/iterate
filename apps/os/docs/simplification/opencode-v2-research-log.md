## Entry 002 — Iterate comparison baseline, before source spelunking

- Iterate's stated doctrine is unusually strong: a durable thing is born as event 1 in its own stream; durable state is a pure fold of the journal; checkpoints are disposable; all consequential writes are events; and side effects live outside reducers in an at-least-once reconciler model.
- The most important comparison will therefore not be “both systems have events.” It will be authority and recovery: what is the source of truth, what can be reconstructed, where side effects become obligations, and what happens after process/DO eviction at every possible cut point.
- Iterate intentionally splits processor code into a contract (event schemas, state, reducer, declared `emits`) and an implementation (side effects), then tests reachable crash states with a host-shaped Node harness. OpenCode may optimize for a single local process and SQLite/filesystem rather than distributed Durable Object eviction; any apparent simplicity has to be evaluated against that different failure model.
- Existing untracked simplification documents in this worktree belong to Jonas and are being treated as source context, not overwritten.

## Entry 004 — v2 is a dependency architecture, not a rewrite inside `packages/opencode`

- The branch's root `AGENTS.md` explicitly marks `packages/opencode` as v1/reference-only. V2 is split into `schema` → `core`/`protocol` → `server`, with `client` consuming schema/protocol but forbidden from depending on core/server; `sdk-next` is the composition layer. This is already a philosophical contrast with Iterate's single deployed OS worker and capability-surface organization: OpenCode v2 makes build-time dependency direction a primary architecture boundary.
- The v2 authoring guidance contains more semantic design than many formal architecture docs. Particularly notable rules: durable events contain only irreducible facts; projections may enrich them; prompt admission is transactionally durable and separate from execution; execution wakes are advisory; the runner is serialized per Session but concurrent across Sessions; runner/model/tools/permissions/filesystem are Location-scoped; and one Step is exactly one logical LLM call, potentially containing a second physical attempt only for overflow recovery.
- OpenCode v2 explicitly says local drains remain process-local and that post-crash continuation recovery “requires a separate explicit design.” This is a bright-line limitation relative to Iterate's processor doctrine. OpenCode durably admits not-yet-consumed user input, but intentionally does **not** yet promise recovery of provider work after the runner has consumed/adopted it.
- Its terminology is being designed as carefully as its tables: a future “assistant turn” will contain all Steps from input promotion until idle; “step” is the model-visible logical call; “physical attempt” is a provider invocation; a drain has neither durable identity nor transcript boundary. That vocabulary prevents accidental persistence of orchestration implementation details.
- `session_pending` is explicitly only unconsumed work. Promotion into a visible user message and deletion of the pending row occur in the same event transaction. Reusing a prompt message ID is an exact-retry protocol with conflict detection, including reconciliation after the pending row has already been projected away. This is a concrete, user-facing idempotency contract—not a generic “dedupe key everywhere.”
- Instruction persistence is hybrid and deliberately normalized: event history stores source keys plus content hashes, blob bodies are content-addressed once in `instruction_blob`, and `instruction_state` is a rebuildable fold cache. This looks immediately relevant to Iterate's simplification work: keep the audit/event vocabulary small while moving bulky immutable values out of repeated event payloads.

## Entry 005 — the v2 event kernel is two channels with one race-free bridge

- Every event definition is statically either `durable` or `ephemeral`. A durable definition names the aggregate field and schema version; the stored row uses `type.version` while public payloads keep the stable logical type and gain `{ aggregateID, seq, version }`. An ephemeral payload is forbidden from having a durable envelope.
- The split is used coherently for LLM output: text/reasoning/tool-input deltas are ephemeral, while started and ended boundaries are durable; the ended event contains the complete text/raw input. A disconnected client loses animation-quality fragments but can reconstruct the semantic result. Tool progress is durable only as a bounded semantic checkpoint, with a code comment explicitly warning tools not to persist every stdout/stderr chunk.
- `EventV2.publish` commits a durable event, its registered synchronous projectors, and an optional operation-specific `commit(seq)` callback inside one immediate SQLite transaction. Only after commit does it notify typed/live in-memory PubSubs. That makes the journal and read models atomically consistent on one database without introducing a separate asynchronous projector offset.
- This transactional projector hook is both elegant and constraining. Projectors are allowed to query and mutate arbitrary relational state and must finish on the writer's latency path. OpenCode gets read-your-writes and no projection lag; it does not get Iterate's clean “state is a pure reducer output and checkpoint is disposable” boundary for free.
- Durable tailing is particularly good. `log({ aggregateID, after, follow })` subscribes to a one-slot wake channel **before** capturing the current watermark, pages rows through that watermark, emits exactly one `log.synced` marker, and then drains any later watermarks from SQLite. Wakes are hints, rows are truth. This closes the classic replay/live gap without making PubSub reliable.
- The watermark marker may carry a sequence beyond the last public event because filtered/private event types share the aggregate sequence. Unknown durable types are skipped during reads while the raw row sequence still advances the cursor, so an older reader does not loop forever on a schema it cannot decode. This is mature streaming protocol design worth comparing directly with Iterate's stream subscription boundary behavior.
- Replay is strict and useful for replication: an already-present `(aggregate, seq)` is accepted only if id, versioned type, timestamp, and encoded data match byte-semantically; divergence dies. New replay rows must be contiguous. Optional aggregate owner claims fence competing replay sources. The code explicitly separates those replay-owner claims from future clustered Session execution ownership.
- The current durable manifest does not retain historical schema versions for the new Session event family; only each definition's current version is registered. Prelaunch v2 migrations repeatedly reset v2 state, so version numbers currently support wire/storage identity more than long-lived upcasting. This will need a firmer compatibility story before users accumulate irreplaceable v2 logs.

## Entry 006 — relational projections are the product model, not merely a cached fold

- Session events project into normalized `session`, `session_message`, `session_pending`, instruction, and legacy message/part tables. A logical assistant message is a mutable row: `step.started` inserts it at that event's sequence, then text/tool/retry/step-terminal events update the same JSON row. The journal exposes transitions; the read model exposes the current coherent message.
- `session_pending` is a genuine durable inbox projection. Admission writes `session.input.admitted`; its projector inserts the pending row in the same transaction. Promotion writes `session.input.promoted`; its projector deletes the pending row and creates the visible user/synthetic message atomically. There is no window in which an input is neither pending nor visible.
- Exact prompt retry goes beyond checking the pending table. Once promotion has deleted the row, retry lookup finds the projected message and scans durable admission events for the matching input id, then compares Session, type, delivery mode, and encoded payload. A fork-copied message without an admission event in this aggregate is correctly rejected as a retry target.
- Creation is still transitional: v2 publishes the legacy `SessionV1.Event.Created` containing a complete SessionInfo record, and its projector inserts the session row. Reusing a Session ID simply adopts the existing Session without validating the requested location/title/agent/model. The choice is documented, but callers need to understand that Session ID is an adoption key, not a compare-and-set creation request.
- Deletion is a sharp philosophical difference from Iterate: v2 first publishes `session.deleted`, whose projector deletes the Session row (cascading projections), and then calls `events.remove(sessionID)`, deleting the aggregate's event log and sequence row. The tombstone is deliberately not an audit record. “Events are the only writes” is therefore not the product's retention doctrine.
- Forking is also not a pure fold of the child log. The one child `session.forked` event causes its projector to query the parent's current relational projection, bulk-copy messages under fresh IDs, reserve the parent's sequence prefix, and rebuild instruction state. Inherited events are not copied; the child log contains a reserved gap and starts child-authored events after `parentSeq`. This is storage-efficient and gives chronological cursor compatibility, but rebuilding the child depends on cross-aggregate state, not solely its own journal.
- Revert commits preserve historical events while destructively deleting projected messages/pending inputs at and after the boundary, then reset instruction state. Thus the log is an edit history whose normal message projection is a selected timeline, not a literal fold that displays every recorded fact.

## Entry 007 — durable admission stops just before durable execution ownership

- `SessionRunCoordinator` is a clean process-local keyed coordinator: one fiber drains a Session, Sessions run concurrently, repeated wakes collapse into a one-slot doorbell, a late wake cannot be lost between drain completion and coordinator cleanup, and callers can either signal or join. It solves the local concurrency race precisely without pretending to be a distributed lease.
- A busy period receives durable `execution.started` and exactly one intended terminal event (`succeeded`, `failed`, or `interrupted`), but the busy period is not itself a recoverable job. On process death the coordinator map, in-flight provider request, retry delay, accumulated output fragments, and tool fibers all disappear. The root architecture notes acknowledge this rather than smuggling recovery claims into the word “durable.”
- The decisive crash boundary is input promotion. Admission is durable in `session_pending`; promotion atomically removes that row and materializes the user message; only after promotion does the provider call run. A crash after admission but before promotion is naturally recoverable by another wake. A crash after promotion but before a terminal Step can leave a visible input with no pending obligation, so ordinary pending-work discovery will not resume it. Explicit force-resume can continue, but v2 has not yet made that automatic or exactly-once.
- This means OpenCode's event log is more durable than its scheduler. Iterate's obligation/reconciler pattern asks a different question: can desired durable state reveal that an external consequence is still owed after eviction? OpenCode currently records rich execution facts, but a missing terminal fact is not yet an automatically claimed obligation.
- The runner resolves a Session's Location only when a drain begins, then constructs a Location-scoped environment for agent selection, model/provider resolution, tools, permission policy, plugins, instructions, and filesystem. Moving a Session first interrupts an active drain and then publishes `session.moved`; this avoids one run silently spanning two filesystem/security contexts.
- Per drain, pending `steer` inputs are all promoted while at most one `queue` input is promoted. That gives “interrupt/augment current intent” and “do this next” real durable semantics rather than representing both as an undifferentiated chat array. A no-work advisory wake is a no-op; an explicit resume can force one model call with no pending input.
- One Step is one logical model call. A provider invocation is one physical attempt; an overflow response before usable output may trigger compaction and one more physical attempt without changing the logical Step. Ordinary transient provider retry is allowed only before output/retry evidence, uses bounded exponential delay, emits a durable `retry.scheduled`, and keeps the assistant identity stable. The delay is still process-local, so the event documents intent more strongly than the runtime guarantees completion.
- Provider events are consumed through an in-memory publisher that serializes durable writes, accumulates ephemeral text/reasoning/tool-input deltas, and writes complete durable terminal values. Tool execution is concurrent in fibers but its event transitions are serialized. Step closeout explicitly fails any unsettled tools; on a later drain, projected tools left in streaming/running state are marked interrupted rather than silently treated as successful or re-executed.
- That last policy is conservative and user-legible, but it exposes the core trade-off: v2 chooses “never accidentally replay a local tool” over transparent continuation. Iterate's reconciler can safely retry only when the external effect has a stable idempotency/obligation protocol; neither system can manufacture exactly-once semantics for an arbitrary shell command.

## Entry 008 — tests exercise the event boundary much harder than the process boundary

- The selected v2 suites are substantial—roughly nine thousand lines across event storage, session projection, prompt admission, execution, run coordination, the main runner, recorded-provider streams, tool events, and server feeds. They run against real temporary SQLite and compose production Effect layers with narrow fakes, rather than mocking the database API into meaninglessness.
- Event-log tests target the right races: projection rollback in the same transaction, replay divergence, schema versions, aggregate ownership, listener failure isolation, subscription-before-watermark handoff, reads paused at injected cut points, wake coalescing, private/unknown sequence gaps, and the exact `log.synced` watermark. A `beforeAggregateRead` test hook makes otherwise probabilistic replay/live races deterministic.
- Recorded runner tests replay provider HTTP cassettes and assert the semantic durable sequence. A simple response produces admission, instruction snapshot, promotion, Step start, text start/end, and Step end; the ephemeral text deltas are intentionally absent from the recovered sequence. This is a crisp executable statement of the two-channel contract.
- The layer graph is powerful but visibly expensive. Runner tests assemble database, project, provider, model, permission, tool, instruction, plugin, event, session, and execution services. That makes dependencies overrideable, yet a reader must traverse a large Effect environment before seeing the scenario. Iterate's host-shaped processor harness has the opposite emphasis: fewer application services, more explicit journal/checkpoint/effect cut points.
- Coordinator tests prove fiber-local ordering, cancellation, joining, late-wake succession, and cross-Session parallelism. They do not simulate a fresh OS process discovering an abandoned promoted input, because v2 deliberately has no such recovery mechanism yet. Most “restart” coverage is service/fiber restart over the same SQLite database, not process death at every durable/external-effect boundary.
- The global server event feed and per-Session durable log are different products. The global feed encodes one SSE frame and fans it out through bounded per-subscriber queues; a slow subscriber can overflow and disconnect without backpressuring everyone, internal events are filtered before consuming capacity, and a later subscriber can recover after an encoding failure. It is intentionally live and lossy. The Session log is replayable SQLite truth with a sync watermark. Calling both of them “streaming logs” would conceal the most important reliability distinction.

## Entry 009 — qualification: graceful restart continuity now exists

- Entry 007's abrupt-process-death caveat still holds, but the current tip has a narrower managed restart protocol that deserves separate credit. Before an orderly managed-server teardown interrupts drains, it writes `time_suspended` onto every locally active Session row. On the next managed-server start it atomically clears each marker and force-resumes up to four Sessions concurrently.
- The consumption update has a non-null guard, so competing restart workers cannot both adopt the same suspension marker. A drain that completes normally after being marked clears the stale marker as part of its terminal event commit, while teardown interruption leaves it for the successor. Tests exercise both cases.
- This is continuity across **graceful replacement**, not crash recovery from journal facts. `time_suspended` is mutable projection state rather than a Session event; an ungraceful kill cannot set it. Embedded and stdio servers intentionally do not participate. After a clean handoff, force-resume can continue a promoted input even though it is no longer pending; after an abrupt kill at the same point, no durable scanner knows it should do so.
- The design is pragmatically incremental: it closes deploy/restart loss without first solving distributed runner leases. It also makes the remaining semantic gap more precise for an Iterate comparison: Iterate should distinguish orderly ownership handoff, alarm/eviction recovery, and arbitrary external-effect replay instead of placing all three under “restart safe.”

## Entry 010 — OpenCode's current fork is a projection copy with a sparse child log

- The public fork API creates a child Session from the parent's projected messages, optionally copying only messages **before** a selected message boundary. The child records one durable `session.forked.v2` event containing `{ sessionID, parentID, parentSeq, from? }`; that event is sequence 0 of the child's own aggregate.
- Its synchronous projector reads the parent's current Session row and message projection, generates fresh message IDs, bulk-copies the selected rows, copies any corresponding non-compaction pending rows, rebuilds instruction state, and then reserves the child's event sequence through `parentSeq`. Subsequent child events therefore start after the parent's fork-point sequence even though the inherited prefix is not present in the child event table. Tests deliberately observe child sequences such as `[0, 5, 6]`.
- This is neither “copy all durable events” nor “one conversation DAG in one stream.” It is copy-on-fork materialization of a **semantic read model**, plus lineage metadata and a sparse logical clock. The child is immediately independent; later parent changes do not flow into it; inherited message IDs are rewritten; usage/cost totals reset to zero; running compactions are excluded; and inherited messages are not valid exact-retry inputs because the child has no matching admission facts.
- The benefit is bounded read complexity: normal child context queries touch one Session's rows, no ancestry traversal. The costs are subtle. The fork event cannot reconstruct the child from its own aggregate alone; replay requires the parent projection and the projector code current at replay time. The recorded `parentSeq` reserves ordering space but is not enough to prove the exact inherited content. Parent deletion recursively deletes children, sidestepping what an orphaned lineage reference would mean.
- Copying projected messages rather than events is a strong opinion about what a conversation fork means: inherit model-visible semantic history, not operational history. Provider retries, execution lifecycle, token deltas, permission asks, and other transitions that helped produce a message are not inherited as child facts. This avoids claiming that child-side effects occurred, but it also means the child has no self-contained provenance chain for why its inherited messages exist.
- The fresh message IDs avoid global identity collisions, yet copying opaque message JSON creates a general hazard: every nested cross-reference must either be intentionally stable or rewritten. OpenCode explicitly remaps only the top-level message ID in this projector. Whether current nested content contains Session/message-local references is now a schema-by-schema question; this is exactly the kind of coupling a generic “copy all non-ephemeral events” implementation would amplify.

## Entry 011 — writing an agent is profile composition; executing one is Session orchestration

- A v2 Agent is intentionally small and declarative: stable id/name, optional preferred model, request overlays, optional replacement system prompt, description, mode (`primary`, `subagent`, or `all`), visibility/color/step limit, and an ordered permission ruleset. JSON/JSONC and Markdown are two authoring syntaxes for the same schema; a Markdown file's body is the system prompt and its relative path becomes the agent ID.
- Built-ins, configuration documents, and plugins all contribute scoped transforms to one Location-scoped agent state. Reload starts from an empty map and reapplies transforms in registration order; closing a plugin scope removes its transform and rematerializes the state. Later scalar settings replace earlier ones, request maps merge, permission rules append, and the last matching permission wins. A single ephemeral `agent.updated` notification announces a fully rematerialized catalog rather than persisting each configuration mutation.
- This separates an **agent definition** from a **running agent instance** more cleanly than language such as “the agent object” often does. The Session stores a selected agent/model, the runner snapshots the effective profile at a Step, and messages/events own execution history. Changing a Markdown agent affects later Steps but does not rewrite past ones.
- Tools are likewise canonical opaque typed values, not methods on an Agent. A Location-scoped registry takes scoped registrations, materializes the exact advertised definitions for a model request, captures those implementations for settlement, filters catalog visibility by the Agent rules, and leaves execution authorization inside each tool leaf. This makes agent authoring mostly prompt/policy/model composition instead of subclassing an orchestration engine.
- The `subagent` tool creates a fresh child Session with `parentID`, chooses the child's configured model or inherits the parent's, admits one prompt, and runs it foreground or as a process-local background Job. Foreground returns the latest completed assistant text. Background immediately returns a child ID and later injects a synthetic completion message into the parent. The child has fresh conversational context; it is **not** a fork of parent history.
- There is an acknowledged permission gap: the child currently receives its own configured rules, not a capability-restricted derivation from the parent. This can violate monotonic authority—an agent allowed to invoke a named subagent may indirectly obtain powers the parent itself lacks. The source has a TODO for deriving restricted child permissions, and this should be treated as a security/design item rather than mere configuration polish.
- The documented per-agent request headers/body are currently retained in the profile but not applied by the runner. The docs warn users explicitly. This is a useful signal about v2's status: the schema and authoring surface are ahead of execution in a few places, so comparisons should distinguish intended contract from wired behavior.

## Entry 013 — Iterate's stream runtime makes recovery a processor property, not a journal implication

- Iterate's durable unit is a Stream Durable Object identified by `(projectId, path)`. Event 1 creates the domain object; later events are an immutable local journal; the processor state is a pure fold over consumed events; and the stored state/checkpoint is explicitly disposable. OpenCode instead makes one SQLite transaction responsible for the durable event, synchronous relational projection, and optional operation-specific commit. Both systems get local atomicity, but they place authority differently: Iterate says the journal plus reducer defines state, while OpenCode's product-facing relational projection is itself an authoritative transactional artifact.
- A hosted `StreamProcessor` contract owns its event catalog and states the event types it consumes and emits. The runtime serializes ingestion, validates consumed payloads, calls the pure reducer, performs blocking per-event/batch effects, and only then advances state and offset. A parse failure is recorded and skipped after checkpoint advancement rather than wedging the stream. That protects availability, but it also means a malformed durable fact can become permanently invisible to a processor unless an operator refolds after correcting the schema/code.
- Iterate separates two consequence modes more honestly than most agent runtimes. `blockProcessorWhile` is at-least-once work under checkpoint retention: a failure or eviction leaves the offset behind. `runInBackground` is only a droppable attempt. Anything that must eventually happen after eviction needs durable evidence of the obligation plus an at-head reconciler that can re-derive the attempt. This is the conceptual machinery OpenCode lacks after a promoted input or `retry.scheduled` event loses its process-local coordinator.
- The processor host has a durable alarm/keepalive recovery loop, crash-loop backoff, and incarnation fencing. Its test harness boots the real host and real processors over an in-memory stream, fake checkpoint/KV/alarm stores, then `crash()` preserves durable journal/checkpoint/alarm state while making the old incarnation unable to write. This is stronger evidence for eviction recovery than a service-layer restart over the same database. OpenCode's current managed-server suspension handoff covers graceful replacement; Iterate's harness can place the cut at each journal/effect/checkpoint boundary.
- Iterate also distinguishes durable and ephemeral events, but less strongly at admission. Ephemeral rows receive real offsets and are committed, yet default reads and durable subscribers omit them and future eviction is allowed; durable terminal events must contain enough information to recover semantic state. Unlike OpenCode's statically inventoried event definitions, the raw Stream append API can accept arbitrary type strings. Type ownership and validation live in processor contracts at consumption time, so the platform has more open vocabulary and a weaker global guarantee that every durable row is understood and versioned.
- Subscriptions are themselves stream facts. A durable `subscription-configured` event declares a push, wake, or webhook delivery; a subscriber-owned checkpoint/cursor controls progress; ephemeral subscriptions are tied to a session; and named expressions are re-evaluated at delivery time under current authority. Every project-scoped stream is born with the project worker push feed. Delivery is at least once and per-source-stream ordered; handler failure retains the cursor. The standard idempotency key is source path plus source offset, exposing why offsets are not merely transport metadata in this architecture.
- Cross-stream delivery intentionally creates a real target-stream event carrying provenance rather than a reference to a remote row. Stream-control events received second-hand are inert, multi-hop forwarding is capped, and provenance prevents loops. This is a carefully constrained copy protocol; it does **not** imply that copying arbitrary durable Agent events is safe. Agent lifecycle events contain offsets and source coordinates that mean something only in their home stream.
- The Agent processor's model-visible state is a fold: system prompt, selected model, conversation history, scheduled/requested execution, retry counters, open LLM-request obligations, and usage. `llm-requested` records its own offset as the durable execution handle; started/chunk/completed lifecycle events refer back to it. Output chunks are ephemeral and completed output is durable. On a crash after `llm-started`, recovery cancels that attempt and schedules a fresh request rather than claiming that an arbitrary provider stream can resume exactly.
- Agent code mode is unusually user-space-oriented. A durable assistant output containing an executable fence is extracted into `script-execution-requested`; the eventual script result is rendered back as a new input. Compaction is a blocking summary operation followed by `history-reset`; earlier journal rows remain, while current model context crosses a semantic reset boundary. These derived obligations, location-bearing execution IDs, and reset boundaries are precisely the facts a fork must not blindly replay in a child.
- The same Agent Durable Object can host the Agent processor and Slack, Telegram, email, and pull-request processors. This composes domain projections around one stream without baking every integration into the Agent reducer. It is closer to event-driven vertical slices than OpenCode's in-process hooks, but each installed processor is privileged platform code with a declared contract, host lifecycle, checkpoint, and recovery policy—not a dynamically loaded end-user plug-in.
- Iterate's current weaknesses become clearer beside v2. There is no manifest-level historical upcaster registry equivalent to a deliberately versioned event protocol; a current Zod parser may reject an old durable row during refold. Event-type ownership is checked around a processor and direct dependencies rather than by one repository-wide durable definition registry. Agent offsets do too much work as identity. And the Agent's model history is retained directly in folded state, so long histories and branch materialization need an explicit context-storage strategy rather than falling out of the journal abstraction.

## Entry 014 — OpenCode plug-ins and Iterate config workers are extension systems at different layers

- OpenCode v2 plug-ins are beta, in-process, Location-scoped contributions. Internal pre-plug-ins register built-in agents, commands, skills, providers, integrations, and tools; user/package plug-ins run next; internal post-plug-ins apply final configuration transforms. Each activation has a scope, cleanup runs on disable/reload/shutdown, a failed replacement restores the previous generation, and one failed plug-in load is isolated from loading the rest. The ordering and reload story are more deliberate than a one-time configuration callback.
- A public plug-in can add or transform the agent/model/provider/integration/command/reference/skill/tool catalogs; register tools; intercept AI-SDK/language behavior and tool execution; subscribe to the current public event feed; and use a deliberately small Session client to create/get/prompt/command/interrupt Sessions. This can implement a large amount of product behavior: custom agent profiles, new model/provider discovery, MCP-like tools, policy around model requests, logging/export, commands, and orchestration through child Sessions.
- It cannot contribute a native durable event type. `EventManifest` is a static inventory imported by the core/schema packages; the public event capability exposes `subscribe`, not `publish` or `define`; plug-ins cannot register a projector, migration, table, log reader, runner transition, API endpoint, or durable background-job claimant. A plug-in can persist externally or encode state in files/tool results, but that state does not join OpenCode's transaction, replay, fork, or Session-log semantics. This is the most direct answer to “can plug-ins contribute their own event types?”: **not in the v2 source at this snapshot**.
- “OpenCode core is implemented as plug-ins” needs a qualifier. The built-ins use the same scoped composition/lifecycle machinery, but internal plug-ins receive privileged core services. The public `PluginHost` is capability-narrowed and intentionally does not expose those services. The temporary OpenAI Codex provider seam even notes that plug-ins do not yet have the LLM route-construction hook it needs. Public userspace could reproduce much of the catalog and tool layer, but not the persistence, event kernel, protocol/server surface, transaction/projector layer, Session runner/coordinator, permission kernel, or reliable recovery policy.
- There is beta-level contract drift at the exact branch tip. The plug-in documentation advertises a Session `request` hook, but the source `SessionDomain`/public host exposes only create/get/prompt/command/interrupt and the actual hook registry has AI-SDK and tool domains. The fair reading is an intended surface ahead of its implementation, not a working extension point. Recommendations should be based on source-backed capabilities, with docs-only hooks labeled as planned.
- OpenCode plug-ins are therefore not close analogues of Iterate `StreamProcessor`s. A plug-in is principally a scoped catalog transform plus synchronous runtime hooks in the host process. A stream processor owns a typed event vocabulary, deterministically folds durable facts, advances a checkpoint only after blocking work, and may reconcile owed effects after eviction. A hook observes or changes an operation; a processor maintains a recoverable projection and consequence protocol. They can solve overlapping product problems while making very different failure promises.
- Iterate's config repository worker is closer to an out-of-process application platform. Its `IterateWorkerEntrypoint.processEvent` receives every durable project event at least once and in order per source stream; it can call the project capability surface and append events. Ordinary exported getters/methods become flattened `itx.worker.*` capabilities. Imported npm code is bundled, and named stateless Workers or stateful Durable Objects can expose real HTTP/fetch, streaming, WebSocket, and storage-backed applications. That isolation and deployment freedom is much greater than an in-process OpenCode plug-in.
- Yet the config worker is not currently a dynamically installed hosted processor. `processEvent` is a catch-all untyped project feed rather than an explicit `consumes`/`emits` manifest; its source-stream cursor gives at-least-once delivery, but the worker lane does not inherit the processor host's alarm/keepalive/reconciler contract. It may append an arbitrary new event type, but doing so does not register a schema/version/owner or teach platform projections how to consume it. It can build durable behavior using its own Durable Object and idempotency protocol, but that is application architecture, not automatic participation in the stream runtime.
- The useful translation is a two-tier model, not choosing one mechanism. Keep config workers as isolated deployment/capability plug-ins. Add an explicit extension manifest for event interests, emitted event definitions, required capabilities, durability policy, and reducer/reconciler ownership; compile that manifest into push subscriptions and generated typed clients. Do **not** let arbitrary config code inject reducers into the core Agent host or run inside its transaction merely to imitate OpenCode's hooks. The process boundary is one of Iterate's strongest security and operational properties.
- Conversely, Iterate can steal OpenCode's scoped contribution algebra: contributions have stable IDs, deterministic precedence, a disposable activation scope, atomic generation replacement, and failure rollback. Applied to config repositories, this would make “which worker supplied this command/agent/tool/event reaction?” inspectable and allow a new configuration generation to become active as one unit rather than through partially observed reload effects.

## Entry 016 — a raw Iterate event copy is not merely inefficient; it changes what happened

- The phrase “copy all non-ephemeral events” confuses retention with context. Iterate durable rows include stream birth/control facts, durable subscription expressions, provenance chains, processor consequence coordinates, agent execution lifecycle, open obligations, script requests/results, capability references, resets, and accounting. Only a schema-aware subset of the Agent's **semantic model context** is appropriate inheritance.
- Paths and offsets appear in several incompatible roles. The committed envelope's `path` is assigned by the destination Stream; `source.processor.stream.path`, `whileProcessing.offset`, and `crossPostedFrom` describe historical provenance and must not be rewritten. `message-received.from.path` is a historical sender. Attachment paths address project storage. By contrast, subscription expressions, agent-default workspace capabilities, wake destinations, and idempotency keys are live configuration for one exact stream and must be regenerated. A generic recursive path rewriter cannot infer which meaning a string has.
- Appending a spread committed event to another Stream would not preserve identity anyway. The input `offset` is treated as an optimistic-concurrency assertion; the destination assigns a new offset, path, and `createdAt`. Stripping the old offset makes every offset-based semantic reference stale. Preserving it is not supported and would falsely claim that one physical fact occurred in two journals.
- A first-hand copied `stream/subscription-configured` is active. Only deliberately cross-posted stream-control facts are made inert by provenance. More seriously, the current processor host resolves a wake by processor slug but does not assert that the request's stream coordinate equals its configured home coordinate. A copied parent wake expression could address the parent Agent Durable Object while delivering child events, eventually advancing a parent processor checkpoint with child offsets. Forking must not copy controls, and the host deserves an independent coordinate-fencing fix/test.
- Agent offsets are domain identities. The offset of `llm-request-requested` becomes the handle carried by started/chunk/completed/usage/cancel facts and the key in the reducer's open-request map. Processor consequence IDs include the cause's `event.path:event.offset`. Re-offsetting copied facts does not deduplicate an old consequence; it creates a new cause and therefore a new consequence key.
- The observable failures are severe. At-head reconciliation can start copied requested work or settle/requeue copied started work. Replaying a copied assistant `output-added` extracts the fenced JavaScript again and appends a new `script-execution-requested` whose execution ID is derived from the new output offset. A copied completion can be rendered into history again. Excluding ephemeral LLM chunks changes none of this because the dangerous semantic and lifecycle boundaries are deliberately durable.
- The Stream already receives its own creation, project-worker subscription, and wake facts before user Agent data. There is no empty destination into which a parent Stream can be cloned. `history-reset` is not a fork primitive either: it replaces model history but intentionally leaves current request, request generation, and open LLM-request state intact, and it carries no lineage.
- Path nesting is also behavioral. Capability resolution walks lexical parents, so `/agents/a/fork-1` would receive live inherited mounts and future mutations rather than a pinned fork scope. That path form already means a delegated child agent and changes routed Slack/Telegram/email/PR behavior. Every child also gets a path-derived workspace capability, while today's workspace copy-on-write base tracks current main rather than another agent's uncommitted overlay. Conversation lineage must not be smuggled into path hierarchy.
- The coherent implementation is a fresh physical Stream whose first **Agent-domain** birth fact contains immutable lineage and a versioned semantic snapshot. It is not physical event 1 because the Stream kernel has already written control facts. Its reducer is seed-only: set system prompt/model/model-visible history, record lineage, and initialize `currentRequest`, pending triggers, failure counters, open requests, generation, autonomous-turn count, and token usage to empty/zero. It must never schedule a model, render a result, execute a script, deliver a webhook, or copy a subscription.
- The fork boundary must be pinned as `(projectId, parentPath, throughOffset, contextDigest)` before reading. The projection reads durable pages only through that exact offset and emits canonical system prompt, effective model, instruction/context state, and model-visible history. Creation is retried with a stable fork ID; because current Stream idempotency accepts an existing key without body comparison, the service must read the existing fork fact and verify its canonical digest/parent coordinate before treating a retry as success.
- Forking has at least five independent axes that the API should not collapse: transcript context; running work; tool/capability authority; workspace/filesystem state; and accounting/telemetry. Inherit the first by materialization. Reset running work. Declare capability scope. Make workspace policy explicit (`fresh`, `shared-live`, or eventually immutable snapshot/COW). Keep child counters local and expose ancestry cost separately.
- Offset is an audit coordinate, not necessarily a turn boundary. A response spans requested, ephemeral chunks, durable output, completion, usage, and possibly script execution. The public fork API should resolve a stable completed/interrupted conversation item boundary. If the source is active, either wait, fork the preceding causally closed boundary, or first record an interruption. Do not turn partial ephemeral output into inherited truth by accident.
- A one-physical-stream branch DAG is logically possible: tag every conversation event with `branchId`, record `branch-created { parentBranchId, parentThroughOffset }`, and project a branch from its ancestor cutoffs plus local tail. In the current system it would require every Agent state field, obligation, idempotency key, permission decision, subscriber, poison/pause state, and effect to become branch-aware, while all branches serialize through one Durable Object. It also cannot reconstruct an old parent state from today's fold without snapshots. This is a plausible future redefinition of “one Agent path owns many conversations,” not an incremental fork feature.

## Entry 017 — prior art converges on shared semantic prefixes and branch-local operational state

- Git makes immutable commit identity independent from mutable branch heads. A branch is an O(1) pointer and shared history is not copied; merges are explicit DAG nodes. The transferable lesson is lineage and structural sharing, not that agent execution histories are safely mergeable. A transcript contains non-repeatable effects and authority decisions that Git blobs do not execute when traversed. See the [Git data model](https://git-scm.com/docs/gitdatamodel.html) and [repository layout](https://git-scm.com/docs/gitrepository-layout.html).
- Temporal is the closest append-only-history precedent. A `HistoryBranch` contains ancestor branch ranges plus a fresh local branch ID; reads stitch immutable ancestor ranges with the local tail, and reclamation accounts for shared references. It does not append copies of every inherited history event. This is an excellent eventual storage model for Iterate, provided inherited ranges feed a conversation projection only and are never delivered again to consequence handlers. See Temporal's [history service architecture](https://github.com/temporalio/temporal/blob/8224a5375112079ad905c4ea829420306431462c/docs/architecture/history-service.md) and [history-tree protocol](https://github.com/temporalio/temporal/blob/8224a5375112079ad905c4ea829420306431462c/proto/internal/temporal/server/api/persistence/v1/history_tree.proto).
- Kurrent/EventStore link streams preserve the source event's identity while building another ordering or projection. That is safer than cloning, but one link per inherited row is O(prefix length), couples retention, and remains too broad for Agent control/lifecycle facts. A prefix-range reference or curated context segment is a better conversation primitive. See [system projections](https://docs.kurrent.io/server/v25.0/features/projections/system) and [`linkTo` stream semantics](https://docs.kurrent.io/server/v25.0/features/streams).
- Kafka consumer offsets do not create branches. Two consumers starting at the same partition offset continue to see the same future records; a consumer-group cursor describes processing progress, not a durable divergent lineage. Iterate subscription checkpoints likewise belong to branch-local operational state and must never be copied as conversation inheritance. See [Kafka's design](https://kafka.apache.org/20/design/design/).
- Persistent data structures call this full persistence: an old version may become the base of a new future, normally through structural sharing/path copying. [Driscoll et al.](https://www.cs.cmu.edu/~sleator/papers/making-data-structures-persistent.pdf) supplies the underlying model. A content-addressed persistent vector of context segments could make Iterate forks O(1), but bounded post-compaction context makes an O(context) semantic snapshot a sensible first implementation.
- Automerge and Yjs show why generic branch merge is the wrong analogy. Their changes are designed to be idempotent/commutative or are reconciled by CRDT semantics. Assistant answers, tool calls/results, shell effects, approvals, and capability grants are neither. CRDTs could merge branch labels, notes, or shared artifacts; they should not union execution transcripts. See [Automerge forks/history](https://automerge.org/automerge-swift/documentation/automerge/changesandhistory/) and [Yjs updates](https://docs.yjs.dev/api/document-updates).
- Neon branches at an LSN and resolves unchanged pages through an ancestor while the child writes its own WAL. lakeFS uses zero-copy branch pointers; Dolt demonstrates how even database-aware merges need conflict/constraint semantics. These reinforce the storage shape “parent through offset plus child tail,” while also reinforcing that workspace branching is its own domain operation, separate from conversation branching. See Neon's [page-at-LSN model](https://neon.com/blog/get-page-at-lsn), the [lakeFS model](https://docs.lakefs.io/v1.81/understand/model/), and [Dolt merge semantics](https://www.dolthub.com/docs/concepts/dolt/git/merge/).
- LangGraph forks checkpointed state by linking a new checkpoint to an earlier parent configuration, then can replay later graph nodes. That replay behavior is the warning: a workflow fork and a conversation-context fork are different operations. Iterate should inherit already-produced context without implicitly re-running every node after the point. See [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) and [time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel).
- Claude Code's `/branch` and `--fork-session` create a fresh Session ID with copied conversation, while session-scoped permissions do not carry. Codex creates a fresh thread from a curated canonical rollout representation, records `forked_from_id`, allows fresh cwd/config/sandbox/approval choices, and inserts an interruption marker if the selected stored prefix cuts through a turn. Both precedents separate conversation persistence from filesystem and authority state. Sources: [Claude Code sessions](https://code.claude.com/docs/en/sessions), Codex [fork parameters](https://github.com/openai/codex/blob/2e1607ee2fa8099a233df7437adee5f16a741905/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L486), and [fork implementation](https://github.com/openai/codex/blob/2e1607ee2fa8099a233df7437adee5f16a741905/codex-rs/core/src/thread_manager.rs#L970).
- OpenCode's own history contains the exact class of structural-sharing bug Iterate should expect. Kit's commit [`aa2c1472`](https://github.com/anomalyco/opencode/commit/aa2c1472faa1988745b35c7db5c2d5ee979f3200), “copy the context checkpoint when forking a session,” explains that copied messages retained parent sequence values while a fresh checkpoint baseline began near zero. The fold then admitted stale parent context updates and triggered a spurious rebaseline. Forking had to inherit the checkpoint horizon as well as visible messages. Dax's later [`96717c1a`](https://github.com/anomalyco/opencode/commit/96717c1a8c25ae69a9e276a4b897defbe51e8bba) separates conversation-fork metadata from `parentID`, which represents subagent/orchestration parenthood. Iterate should likewise model `spawnedByAgent` and `forkedFromConversation` as different relationships.
- The recommended first Iterate shape is therefore **snapshot plus lineage**: O(compacted context) creation, O(1) normal child reads, independent child export/replay, and no parent dependency for execution. A later prefix-range/content-addressed representation can optimize storage while preserving the same public semantics. The tree is a rebuildable projection over lineage facts; a small family metadata Stream may index it, while each active branch remains its own physical Agent Stream.
- Merge should initially mean an explicit context/artifact import, not history union: record the source coordinate, selected semantic item IDs/artifact refs, a summary, and optional workspace commit as a new target fact. A fast-forward is possible only when the target has not diverged and the source is its descendant. Git should own code merges; the Agent log should describe which context or artifact was imported.

## Entry 018 — OpenCode's own replay test proves the fork event is not a self-contained snapshot

- The most concrete evidence for the fork tradeoff is not an inference from the projector; it is an asserted test outcome. In `session-runner.test.ts`, the parent instruction source progresses from `Initial context` to `Changed context` and then `Latest context`. A child fork selected before the second message is initially projected with `Changed context`, as expected. The test then deletes the child rows, replays **only the child's recorded events**, and expects the rebuilt child instruction state to contain `Latest context`.
- That result follows because the child's lone `session.forked` fact stores a parent Session ID/sequence and boundary, not the selected instruction values or a digest of the inherited projection. Replaying later dereferences whatever the parent lineage projects under the current code and current database. In event-sourcing terms, the child journal is not sufficient input to a deterministic fold; it is a recipe containing an external read.
- This may be an acceptable local product tradeoff—parent and descendants are recursively deleted together, the shared database normally retains parent rows, and projection copying makes child reads cheap—but it weakens export, archival restore, independent child retention, parent redaction, and refold invariance. The test usefully makes that choice explicit rather than hiding it.
- Iterate should not inherit this particular property. The fork fact should embed or content-address the canonical selected context plus a digest and lineage coordinate. Parent ancestry can remain navigable metadata, but child execution and child refold should produce the same context after parent deletion, parent continuation, projector upgrades, and movement to another store.

## Entry 019 — final synthesis: the systems optimize different atomic boundaries

- The comparison is clearest as two different atomicity choices. OpenCode atomically commits a command's event plus local relational projections, optimizing “after this API returns, every local query agrees.” Iterate retains a processor checkpoint until its blocking consequences settle, optimizing “after eviction, a successor can determine which durable reaction is still owed.” These mechanisms are complementary; neither is implied by “event sourcing.”
- OpenCode's most transferable artifact is its domain protocol work, not Effect or SQLite: explicit durable/ephemeral definitions, admission versus promotion, separate Step/attempt/settlement identities, fixed-target `log.synced`, scoped contribution generations, and tests that name races. Iterate's most defensible advantages are per-Stream isolation, explicit at-least-once consequence semantics, alarms/incarnation fencing, and out-of-process Worker/DO userspace.
- “Plugin” should remain three concepts in Iterate: catalog contributions/hooks, an isolated config application runtime, and a durable stream processor. Combining them would either force trivial configuration through a recovery engine or let untrusted callbacks enter core transactions. A manifest can unify discovery, provenance, version ownership, and activation without unifying execution physics.
- The fork result follows from the same distinction. A child inherits **semantic read state** but not **processor work state**. The recommended embedded canonical snapshot is intentionally less clever than a prefix DAG. Once the snapshot format and independent-refold invariant are proven, storage can move to content-addressed segments or immutable ancestor ranges while preserving the contract.
- The immediate non-fork finding with the highest severity is the processor-host coordinate gap: a wake request is trusted after processor-slug resolution without checking its stream coordinate against the host. Fork code must never copy controls, but the host should fail closed regardless. The immediate design-debt finding with the widest impact is durable event version governance: current contract parsers do not by themselves guarantee that every historical journal remains foldable.
