## 0. Grounding — the config worker as it now stands (merged code, not speculation)

- `apps/os/config-repo-template/worker.ts`:
  `class ProjectWorker extends IterateWorkerEntrypoint { async fetch(req); processEvent(event) }`.
  The user's whole config surface is these two entry points.
- **`fetch`** = the HTTP door. Stateless, per-request routing. Inbound requests
  reach it via `apps/os/src/ingress.ts` (`decideIngressRoute` → `lane:"project"`)
  → `worker.ts` dispatch → `DynamicWorkerRunner.fetch` with platform-set headers
  `x-itx-project-id`, `x-iterate-app`. (This is the #2156 config-worker proxy path.)
- **`processEvent`** = the fold reaction. Post-fold side effects with
  `append` / `appendTo`, `delivery.caughtUp`, `blockProcessorWhile` /
  `runInBackground`. Signature `ProcessEventArgs` at
  `packages/iterate/src/processors/stream-processor.ts:154`.
- **`reduce` (pure fold) + `processEvent` (effects) = two hooks on ONE engine**,
  dual cursors (`reduction` keyed by reducerVersion, `processing` keyed by
  cursorRevision — `stream-processor-runner.ts:101`). The "collapse 2 fold
  engines → 1" convergence landed. `#2248` tidied every template to this shape.
- **Secrets** are not handed to `processEvent`. They live in `this.env.SECRETS` /
  `itx.secret(name)` and surface at the egress gate as `request.secretPaths`.
- **Egress is one door**: `ProjectEgressEntrypoint` (`domains/projects/egress.ts:39`)
  → `ProjectDurableObject.fetch` → one rule list, first-match-wins, may require a
  signed human approval. _No per-worker egress lanes._

> So a project touches the outside world at exactly three points: **events
> (streams in/out), secrets, and the one egress door.** Hold that — everything
> below is a policy on one of those three.

## 1. Hosted vs self-hosted is not a fork of the core — it's who manages & meters the same three points

The pile already leans here (`DESIGN.md` R10 "deployment is a placement choice,
not an architectural one"; R16–R18 out-of-the-box-but-overridable, "renting the
kernel", "renting the wall", pre-approved OAuth clients). Today's sharpening is
the _bare_ end and the _unification_:

| point of contact                | self-hosted (bare)                                                      | hosted (managed + metered)                                   |
| ------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------ |
| events (streams)                | you push events onto the log yourself                                   | our approved integrations push them for you                  |
| secrets                         | you write your own keys                                                 | we deposit _leased_ credentials (pre-approved OAuth clients) |
| egress door                     | open; you bring your own API keys                                       | metered, capped, billed — we are the single counterparty     |
| perimeter (in front of `fetch`) | **none** — Raspberry Pi + miniflare, no auth; you BYO Cloudflare Access | we are the wall                                              |

The claim to lock: **the inner core is byte-identical across the two, and can't
tell which it's in.** Self-hosted = the three points are bare and you wire them.
Hosted = the three points are managed and metered and we bill you. "Hosted" is a
configuration, not a build.

Consequence for the kernel: it must ship **unprotected by default**. Auth is
never a kernel feature; it is always a wall you rent (hosted) or BYO
(self-hosted). "Runs on a Raspberry Pi under miniflare with no auth" is the
literal reference target, not an afterthought.

## 2. Integrations vanish into (events + secrets) — a stronger claim than "overridable"

The pile frames first-party integrations as _referenced through `itx`, and
overridable_ (R16, D17). Jonas's framing today is sharper: **the entire
observable effect of using our Slack integration is that (a) some events appear
on a stream and (b) some secrets appear in the secret system.** Nothing else.

That is a bigger collapse than "overridable":

- An integration is **not a kernel concept, and not even a std-lib service you
  reference.** It is a _producer_ of the two things the kernel already has.
- The merged code confirms the landing pads exactly: `processEvent` consumes the
  events; `this.env.SECRETS` holds the secrets. Hosted Slack and a hand-rolled
  self-hosted Slack are **indistinguishable from `processEvent`'s point of view.**
- So there is **no "integration API" to design.** "Connect Slack" (hosted) and
  "I registered my own Slack app and wrote the token myself" (self-hosted) reach
  the same state.

**The one sharp edge: authenticity / provenance.** If anyone can make
`slack/message-received` appear, a self-hosted forgery is possible. So an event
has to carry _who appended it, under what capability._ Hosted Slack appends under
a verified-ingress capability; your hand-rolled producer appends under "you";
`processEvent` decides how much to trust each. De-privileging stays honest only
because provenance is preserved. (This is capabilities doing the work — already
the pile's trust primitive.) → **Open decision: make "appended-by-capability" a
first-class, visible field on every event.**

Outbound + token refresh footnote: an integration isn't only inbound events + a
static secret — Slack also needs outbound posts and OAuth refresh. Outbound = the
one egress door with `getSecret` placeholders (already how egress works). Refresh
= a keeper that is itself just a `processEvent` + an egress call (hosted runs it
because it owns the client secret; self-hosted you run it). So a secret can be a
_living_ credential with a keeper, and the keeper is nothing new.

## 3. Money — one wallet, enforced at the one egress door; the boundary is just R1 again

Already locked in the pile: B5 (the spend ceiling is a human-world input), R14 (a
uniform money-spent event that rides any stream, tagged, aggregated, with a cap +
kill switch, and **transitive sub-budgets**). Today's addition: **one organism =
one bank account, hard-capped at its seed, non-transferable across projects.**

Two collapses fall out:

1. **Non-transferability across projects is not a new rule — it is R1**
   ("one project can never access another") applied to the wallet. The money edge
   and the information edge are the _same_ edge. One hard boundary, double duty.
2. **The cap lives at the one egress door.** All spend is outbound — LLM calls,
   third-party APIs, virtual cards are all egress. So money is: a `processEvent`
   that folds spend (R14's event) + a gate that refuses egress over-cap. **No
   wallet subsystem** — reuse R14 + the one door.

Hosted vs self-hosted on money = _who runs and trusts the spend-fold._ Hosted: we
run it because we hold the money — the single billing counterparty is the whole
point ("one relationship with us; we bill you for everything your agent spends").
Self-hosted: no enforced cap unless you run your own spend-fold (Anthropic bills
your card directly).

**Falls out for free (worth mining):** because a step's LLM answer is written to
the log and replay _reads_ it rather than _recomputes_ it, replay is free — you
are charged once per _novel_ external effect. The spend events on the log are the
itemized bill, and the log never double-charges. (An observation about the model,
not a new primitive.)

## 7. Further reduction (same session) — the only scarce endowments are money + secrets

Jonas pushed harder: _from the outside, the two things that define an organism
are just **money and secrets**. It starts with an empty balance and no secrets.
Secrets (incl. OAuth) and money let it access data and services and enact change
on the world. In the limit a project starts with literally nothing and creates
something for itself — maybe a token offering._

This survives scrutiny and is sharper than §4's "information + money":

- **Why only these two: they're the only _scarce / rivalrous_ things an organism
  holds.** Money is fungible (permission to _consume_ — inference, compute,
  storage, paid APIs, cards). Secrets are non-fungible (permission to _access /
  be an identity_ — OAuth tokens, keys). Both empty at birth.
- **Everything else is non-rivalrous, so it _accrues_, it isn't _endowed_.** The
  log / information is born empty and grows only by spending money + using secrets
  through the door. The code / genome is born from a free template and rewritten
  by spending. Code and data are copyable → they don't _constrain_, so they don't
  _define_. (This reframes §4: information isn't an endowment, it's the residue.)
- **Reconciles with §0's three points of contact.** The egress door is the
  _mechanism_ money + secrets flow through; the log is the _residue_ that piles up
  inside. Money is metered at the door; secrets are wielded at the door; events
  are what comes back. (Note the code-grounding gap: `core-model-grounding.md` §C
  flags egress observability as "a real gap" — and egress is exactly where money
  must be metered, so that gap is now load-bearing.)

**The organism is a startup.** Born broke, no credentials. It **survives iff its
balance stays positive** — death = bankruptcy → _freeze, not delete_ (the log is
durable; a benefactor can revive it by funding). It grows its balance two ways:
**earn** (sell a service via egress + a payment processor — the pile's
self-funding organism; the multiplayer-self-rewriting-game's "charge players →
self-funding") or, in the limit, **mint** (a token offering — it raises its own
seed). Alive in an economic sense.

**The bootstrap catch:** "start with literally nothing" is never zero — the first
thought costs inference. Someone always provides the first spark (a grubstake):
hosted hands a newborn a trial balance; self-hosted you point it at your own key.
_What is the minimum viable spark, and who lights it_ is a real design + product
question.

**Strategic kicker (the moat, sharpened):** money is **self-mintable** (earn, or
a token offering); certain secrets are **not** (a CASA-approved Gmail client, a
verified Slack app — an individual can't mint these at any price). So the more
self-funding an organism can be, the more the hosted moat narrows to exactly one
irreducible thing: **un-self-mintable _root_ secrets** the federation holds and
leases out as _leaf_ tokens. The OAuth-broker role isn't a feature; it's the
business. (Money in §5.5 was "single billing counterparty"; this says billing is
_erodable_ by self-funding, but the root-secret broker is _not_.)

**Open from this reduction:**

- **Grubstake policy** — does the platform give every newborn a tiny free balance
  so it can take its first breath and pitch for its own funding?
- **Is money a pure scalar or earmarked?** A scoped budget ("$20, inference only")
  blurs toward a secret — permission-to-spend. Money and secrets may be two ends
  of one "permission" spectrum (consume ↔ access), with earmarked budgets between.
- **Death semantics** — freeze-and-revive vs garbage-collect when balance hits 0.

## 8. Money resolves into secrets + capabilities — no third primitive (the budget tree)

Jonas: funding is the genesis event ("the first events need to be basically an
inbound money transfer"); money is dished out as **budgets to sub-agents down the
stream tree**; and he wants to explore "it's all just scoped permissions" —
noting money-in-a-bank or Bitcoin is _held via a secret_ that authenticates you
as the balance's controller. Worked out, this closes the model:

**Genesis = an inbound-money event.** The first meaningful entry on an organism's
log funds the root. Hosted / customer-funded / self-funded differ only in **who
signs that first event** (platform grubstake / a customer / later the organism
itself via revenue or a token sale). Before it, no capability can be honored → no
thought affordable → born broke. Revival = another inbound-money event; death
(balance 0) = freeze, since the log persists.

**The budget tree (Jonas's structure).** The stream tree _is_ the org chart. The
**root stream holds the real money**; nothing anywhere can act if root is out.
The root delegates **budgets** down to sub-paths (an agent + its sub-agents =
a subtree). To spend, **two independent gates** must both pass:

- **Authority** — every budget from your stream up to root has headroom.
  Distributed down the tree; _attenuation_ guarantees a child's budget ≤ parent's
  ($100 parent → at most a $20 child, never $200).
- **Availability** — root's real external balance actually has the funds.
  These fail independently (budget under-cap but account drained by a sibling; or
  account flush but your budget spent). Raising a cap = walk **up** the ancestor
  chain to an authority that can widen it, possibly via **human-in-the-loop**
  approval — reuses the existing egress-approval machinery.

**The resolution — money is not a third thing:**

- **Root money = a _secret_.** A bearer key to an external balance (Bitcoin
  private key / Stripe / bank API key / — hosted — a platform-root credential).
  Held once, at the root, never delegated. (Jonas's own intuition, correct.)
- **Budgets = _capabilities_ attenuated from that secret's spending power.** A
  sub-agent holding a $20 budget can spend _without ever seeing the key_: it hits
  the one egress door, the door validates the budget chain, then asks the **root**
  to sign the real transaction. **This is already the codebase's
  `getSecret`-placeholder pattern** (`itx.remoteCapability.get(url, {headers:
getSecret(...)})` — a capability that _uses_ a secret it can't read, substituted
  at the egress door) with **one added attribute: a depleting quantity.** Normal
  capabilities are non-depleting (access); money capabilities deplete (consume).
- So the "consume ↔ access spectrum" from §7 collapses to: **one primitive
  (capability), anchored by secrets at the root; money = a capability carrying a
  quantity that goes down.**

**Settlement — the real engineering fork.** Authority is distributed, but
availability **cannot** be (no eventually-consistent bank balance, or you
overdraw). So the actual decrement of real money must be **serialized at the root
stream** — free, because the root is a single DO (atomic check-and-decrement).
Like a company: departments hold spending authority; cash leaves one account,
serialized. Open axis: **synchronous settle** (every egress round-trips to root to
debit — hard caps, higher latency) vs **optimistic budget** (spend against a local
budget, reconcile to root after — lower latency, soft caps, needs a clawback).

**The one irreducible money-specific piece:** the egress door must **price** each
call ("this LLM request = $0.03") to know how much to decrement — a cost oracle.
Everything else is secrets + capabilities. (`core-model-grounding.md` §C already
flags egress observability as "a real gap"; pricing is part of closing it.)

**Falls out:** the log is also the account statement — inbound credits + outbound
priced debits folded into the running root balance. (Observation, not a new
primitive.)

**Open from this section:**

- Auto-grubstake every newborn vs require an external funder before first breath.
- Synchronous settle vs optimistic-budget-and-reconcile at the root.
- Is the root one pool or a _set_ of secret-controlled pools (bank + BTC +
  platform credit), which would pull in denomination / FX at the door.

**Resolution (Jonas, 2026-07-28) — don't tie ourselves in knots here.** The right
lens isn't sync-vs-optimistic settlement; it's **credit**. Letting a spend proceed
without knowing its cost in advance = iterate _extending credit_ to the organism
(and LLM calls are inherently this — you don't know the exact cost until the
tokens come back). So the only real question is _how much credit we float per
organism_, and the answer is "a small, bounded amount" (≈ in-flight cost + the
metabolic sliver it takes to append the inbound-money event to the root stream).
Rule: **balance goes negative → nothing is possible until it's positive again.**
It's inherently soft at the very margin and that's fine. The sync/optimistic
mechanics above are downstream detail, not a founder decision — banked, move on.

## 9. Userspace imports the core; type errors as the fleet-update tripwire

Jonas: the merge presented "a way for userspace to import the core," and a design
philosophy — _you should get type errors in your userspace config repo if
something non-backwards-compatible has updated in the core._ How, exactly, is open.

**Grounding (merged code).** Userspace no longer copies the core — it **imports a
published package**:

- `apps/os/config-repo-template/worker.ts:1-3`:
  `import { IterateWorkerEntrypoint, type StreamEvent } from "iterate/sdk"`
  (+ `iterate/starter-apps/*`). The file comments the thesis verbatim: _"the
  essence of an iterate project can be expressed as two functions: { fetch,
  processEvent }."_
- `config-repo-template/package.json`: `"iterate":
"https://pkg.pr.new/iterate/iterate/iterate@main"` — the dep **floats to live
  core** (`@main`), not a frozen version. `iterate/sdk` re-exports the generated
  `itx-api` type graph.
- Typecheck: a **wasm TypeScript sidecar** (`apps/os/src/typechecker.ts`,
  `domains/typecheck/*`) checks scripts + capability types against the **live**
  `ITX_API_DECLARATIONS` (re-projected each run). The typecheck gate output is
  what runs (`#1978`). A just-merged "fail closed on imports" wave (`#2292`,
  `#2275`, `#2160`) = same instinct: break loudly at build, never ship broken.
- **Gap:** the check fires only when a repo **rebuilds**. Deployed-dormant repos
  run frozen bytecode, so a breaking core change fails _new_ builds loudly but
  **silently strands the sleeping fleet** until each redeploys. No batch
  re-typecheck of deployed repos exists.

**The philosophy is ~90% already the architecture.** Because userspace imports the
core's _types_ (referenced, not copied — pile D17) and floats to live, a
non-backwards-compatible core change _is_ a structural type error at the userspace
call site, for free. Nothing to build; three things to decide — _when the check
runs, and what happens to the failure._

**This is the fleet-update answer (the parked "1M-repo" question), from the type
end:**

> Ship core vX+1 → re-typecheck every config repo against it → each repo that now
> errors emits `worker/typecheck-failed` → **the organism's own agent wakes and
> rewrites its config to compile again.** Type checker = alarm; agent = mechanic;
> iterate touches zero userspace repos. (`worker/build-failed` /
> `worker/typecheck-failed` is already on the Tier-1 "missing facts" list.)

Make self-migration reliable with: **deprecate-then-remove** (a `@deprecated` soft
window before the hard break, so most migrate before the error) + a **legible
core-version headline** (a nominal version token so the agent sees "targets core
v2, platform is v3 — migrate" instead of only a deep structural mismatch).

**The commitment it forces: float, don't freeze.** Track the live core, break
loudly, self-migrate. The alternative — pin each repo to its birth core — never
breaks but leaves you maintaining N core versions forever and a fleet that never
improves. Jonas's philosophy _is_ the float choice.

**Honest boundary — two classes of "non-backwards-compatible":**

- **Code-shape break** (removed method, changed signature) → caught by structural
  typing. Solved by the above.
- **Behavior break** (same type, different meaning — e.g. delivery semantics) →
  invisible to types; needs contract tests.
- **Stored-data break** (event/state shape changed; an old log no longer folds) →
  invisible to types (old data predates the new type). Needs **state-adapter
  discipline** (pile's Urbit lesson): version event payloads as a discriminated
  union so the reducer _must_ handle every historical version — an unhandled one
  becomes a compile error too — plus migration/tests.
  So types fully cover the _code_ half, partially the _data_ half (via versioned
  unions), and miss pure _behavior_.

**Open:** commit to float-and-self-migrate as THE model? re-typecheck cadence on
core release (push) vs each organism polling (pull)? length of the deprecate window?

## 11. Kernel ↔ OS-worker ↔ userspace: collapse first-vs-third-party, find the real cut

Two refinements from Jonas, then the research question.

**(a) The core/userspace line = the _breakable-from-config_ line.** Ratified: the
agent is first-party userspace. Sharp test for "is it core?": **can you break it
from your own config?** Yes → userspace (visible, replaceable). No — the kernel
enforces it regardless of your config → core. The core's _unbreakability IS the
security model_ (D1/R1: the only security is the egress door; one project can't
reach another). Everything else should be **visible and breakable in your config**
— that transparency is the value (you and your agents read exactly how the project
is wired, and change it). Grounding: the template `worker.ts` already wires starter
apps as visible npm imports (`iterate/starter-apps/*`), but the **agent + `itx.ai`
are still hidden platform machinery** (`domains/agents` hosts a platform singleton
processor; nothing in the template). Jonas: make the foundational stuff visible too
— "the stuff that makes agents exist is visible to you inside your config and you
could, in theory, break it."

**(b) First-party vs third-party userspace may not be a real architectural line** —

## 12. Candidate clean cuts — kernel / OS-worker / userspace / deployment

**Grounding (true today):**

- `apps/os/src/worker.ts` is a 334-LOC entrypoint, but ~82k LOC of `domains/*`
  hang off it. **The kernel is NOT extracted** — it's tangled inside
  `ProjectDurableObject`, which is simultaneously the stream registry, the egress
  gateway, the Slack/Telegram/email processor host, AND the capability
  orchestrator. The SDK base classes (`IterateWorkerEntrypoint`/`…DurableObject`)
  are reusable _surface_ (RPC, processor protocol, event schema), **not a
  detachable kernel implementation**.
- **The pile already specced the kernel:** ~6k LOC — identity/confinement, journal
  engine, processor + obligation supervision, delivery, capability tree + expr
  eval, egress door + secret substitution, repo build/load of the config worker
  (`explain-operating-system.md` §3). Irreducible seed = _"confined code + durable
  storage + one exit."_ And: **"the kernel is exactly what userspace cannot
  express"** — i.e. our §11 breakable-from-config test, already written down.
- The pile's _current_ position is **three rings** (kernel / iterate-governed
  std-lib / packages), treating first-vs-third-party as a real **governance** line.
  Jonas's new instinct dissolves that to provenance.
- Self-deploy is LOCKED in principle (`DESIGN.md` R17/R18 "rent the kernel / rent
  the wall", capnweb link) but the pile admits _"not at all clear what the rent
  boundary even is once you own Cloudflare"_ — exactly the murk Jonas named.

**The reframing — two orthogonal axes, not three rings:**

- **Axis 1 — breakability:** kernel (unbreakable, ~6k, = what userspace can't
  express) vs userspace (everything else, visible + breakable in config).
- **Axis 2 — deployment:** hosted (iterate holds un-mintable root secrets + is the
  billing counterparty + provides the walls) vs self-hosted (your CF account, BYO
  auth via Cloudflare Access, no leased OAuth).
- **first-party vs third-party is not a third axis** — it collapses to _provenance_
  (which npm package + seeded in the template). The only thing that doesn't
  collapse is the **un-mintable root secrets**, and those live on Axis 2
  (deployment), not in a code ring.

**Three candidate models:**

- **Model 1 — Three rings** (the pile's position): kernel / governed std-lib /
  packages; first-vs-third-party is a real governance line. _Pro:_ audit burden
  managed, iterate owns the deep modules. _Con:_ the middle ring is privileged
  magic; fails the "breakable in config" test.
- **Model 2 — Two layers, OS = deployment shell:** kernel extracted (lib + worker);
  everything above is npm packages (first-party = seeded); the OS worker is a thin
  shell that instantiates the kernel + wires hosted-ops. Self-deploy = a stripped
  shell. _Pro:_ first-vs-third dissolves; kernel clean. _Con:_ the OS is still a
  special "platform" thing.
- **Model 3 — Two layers, OS dissolves into a first-party project** (the maximum
  clean): kernel extracted; the OS app becomes `{ projectId: "os", fetch,
processEvent }` on the kernel — dashboard/agent/integrations/billing/OAuth all
  userspace in the os project's config. Only the kernel is privileged. Self-deploy
  tiers: bare kernel (BYO auth) → kernel + run the os project → full hosted. _Pro:_
  maximally clean; one privileged layer; iterate becomes a platform, not a service;
  directly satisfies "the stuff that makes agents exist is visible + breakable."
  _Con:_ (a) auth + billing dissipate into userspace (per-deployment wall +
  event-reactive credit — but Jonas already accepted both, §8 + R2/R3); (b) the
  moat (leased OAuth roots, billing-counterparty) needs a home on Axis 2, not a
  code ring; (c) real extraction needed — the kernel is currently tangled in
  `ProjectDurableObject`.

**Recommendation: Model 3.** It's the maximum-clean cut and it's consistent with
the whole jam — breakable-from-config = the kernel test; hosted-vs-self = Axis 2;
money-as-credit; agent-as-userspace. It shrinks "what is privileged" to the
smallest possible set: the kernel + the un-mintable root secrets on the hosted
deployment.

**Decisions for Jonas:**

1. **Overturn the governance ring?** Collapse first-vs-third-party to pure
   provenance. Devils-advocate counter (in the pile): npm is a CDN not a trust
   boundary; a non-technical founder can't audit 20 strangers' packages; moving
   integrations to packages relocates on-call, doesn't delete it. Acceptable that
   "iterate owns the deep modules by _convention_ (it publishes + seeds them), not
   by _architecture_"?
2. **Commit to extracting the kernel from `ProjectDurableObject`** — factorize
   streams / egress / capability-host / auth into a standalone kernel that dynamic
   workers reference. Same shape as built-ins→mounts, larger. The big lift.
3. **Confirm the moat lives on Axis 2** (hosted deployment holds un-mintable root
   secrets + is billing counterparty), not in a privileged code ring.

## 13. Refinement (Jonas, Plannotator on `os-as-a-project.html`)

Four corrections that sharpen Model 3 and pull it back from "the OS is a literal
dynamic project."

1. **The OS is NOT a dynamically-built confined project. It's a conventionally-
   deployed edge worker that _consumes the kernel through the project capability
   interface_.** Three concrete reasons the literal-project version fails: (a) the
   config-worker bundler can't build TanStack Start apps — the dashboard is one; (b)
   they want the OS deployed properly to the CF edge (cheaper/faster), not run as a
   dynamic worker all the time; (c) bootstrap fragility — _"should `@iterate` be
   required to run `iterate`?"_ a kernel bug shouldn't be able to irrecoverably brick
   the control plane. → **OS = a normal `wrangler deploy` worker** whose _data_ lives
   in the kernel (streams under `projectId:"os"`) and which _talks to the kernel via
   the same capability tree a project gets_, but whose _code deploys conventionally_.
   "Like a project" at the **interface**, "a normal worker" at **deployment**.

2. **Define the boundary by the self-hosting user story** (Jonas: back up to user
   stories). Self-host = clone, set your CF account, `wrangler deploy` → your own
   iterate, using your CF account + billing + AI bindings + R2, auto-created. **What
   remains in the box** = the kernel + the OS control-plane worker; agents /
   integrations / apps arrive as `iterate/*` npm packages referenced by config
   workers (seeded in the template). **What you lose** = leased-OAuth roots +
   iterate-as-billing-counterparty. Open (Jonas unsure): is the agent "in" the
   self-host bundle or does it arrive via the config worker? → It's an npm package;
   the template seeds the import — so it's available + wired, but not baked into the
   kernel.

3. **The kernel↔consumer interface = a capability tree, over Workers RPC (not Cap'n
   Web) on the hot path.** Jonas agrees "obtain a capability tree by authenticating."
   But performance: HTTP + Cap'n Web ≪ Workers RPC + native bindings. So: **internal
   (same-deployment) kernel↔OS↔project = Workers RPC** (already true — `env.ITX` is a
   Fetcher/`WorkerEntrypoint` RPC stub, `itx/utils.ts:123`); **external / cross-
   deployment** (browser→OS `/api`, or a self-hoster→iterate's hosted moat services)
   = Cap'n Web over WS. Two interfaces; the hot path stays fast.

4. **Confirmed kernel contents:** the streams system, the files system, the secret
   system, the ingress+egress fetch system — all in the kernel. (Settles the pile's
   open "are streams kernel-by-necessity?" → yes, kernel.)

**Refined Model 3:**

- **Kernel worker** — raw bindings + streams / files / secrets / ingress+egress /
  capability resolver / identity+addressing / LOADER; holds _all_ durable state
  incl. every project's streams; exposes a scoped capability tree via **Workers RPC**.
- **OS worker** — conventionally deployed edge worker; TanStack dashboard + agent +
  integrations as first-party code; obtains a `projectId:"os"` capability tree +
  `itx.operator` from the kernel via RPC; stateless compute, state in the kernel.
- **User projects** — dynamic bundled config workers in LOADER isolates; obtain
  their scoped capability tree.
- OS and projects **share the interface**, differ in **deployment** (conventional
  edge vs dynamic isolate) and **privilege** (`itx.operator`).

Next: pin the self-host user story precisely — it's the cleanest definition of the
kernel/OS line.

## 14. The OS front-end is a stateless proxied app; integrations = kernel engine + userspace providers; where MCP sits

Jonas's moves (recording, per his ask):

**(a) Split the OS into a stateless front-end + back-end capabilities.** The
`apps/os` dashboard is large and "not like the other mini-apps" — that's the murk
between "OS" and "kernel." Resolution: make the dashboard a **stateless front-end
worker** deployed to the edge that renders the capability tree, and reach it by
**proxy** — exactly like the `tasks` app already does
(`config-repo-template/worker.ts:45–66` member-gated reverse-proxies `tasks` to a
separately-deployed board). So **`os--<proj>.iterate.app`** (or
`os.<yourdomain>`) proxies to a stateless **`os.iterate.com`** front-end worker.
Consequences: front-end cleanly split from back-end/kernel; the dashboard stops
being special/large; **you could swap in a different OS front-end.** Not crazy —
it's the proven tasks-app pattern applied to the dashboard.

**(b) Front-end protocol adapters over the capability tree (the generalization).**
The dashboard is one stateless adapter (HTML, for browsers). The **inbound MCP
server** is another (MCP, for Claude Desktop / MCP clients). The **Cap'n Web
`/api`** is another (for SDK clients). All three are stateless, proxied at
hostnames, expose the _same_ capability tree, and are replaceable. → "front-end" is
a category: **stateless protocol adapters over the capability tree**, reached by
proxy, over the _external_ interface (Cap'n Web / MCP / HTTP; kernel-internal stays
Workers RPC). **Answers "where do MCP server APIs sit":** inbound MCP = a front-end
adapter (like the dashboard); outbound MCP client (`itx.mcp`) = a kernel capability
(like integrations).

**(c) Integrations = a kernel engine + userspace providers + renderers.**
Integrations are "like the secrets system": the engine (OAuth dance, token storage
in Secret DOs, webhook ingress→event routing) touches secrets/egress/ingress — all
kernel — so the **engine is a kernel capability** (`itx.integrations`). But
**providers** (Google, Slack, + user-added) are **userspace registrations** that
contribute config (endpoints/scopes) + a **renderer** to the shared `/integrations`
view. So "add your own integration provider in userspace and it renders in that
space" = an instance of **userspace modifying the UI** (renderers-from-events,
§11/§3). Kernel = mechanism; userspace = providers + renderers; a front-end renders
them.

**Net: the murky "OS" dissolves.** OS = (stateless front-end adapters —
dashboard / MCP / api, proxied, replaceable) + (kernel capabilities — the
integration engine, `itx.operator`). No large special "OS app" remains — just the
kernel + stateless adapters + userspace.

Open: does the stateless front-end reach the capability tree over Cap'n Web `/api`
(external, simplest for a separately-deployed worker) or a Workers RPC service
binding (faster, needs co-deployment)? Likely Cap'n Web for the replaceable case —
a UI isn't hot-path.

## 15. The stateless OS app collapses authentication (Jonas: "it connects to how auth works")

Grounding: today there are **two** auth systems. The dashboard (the `os` host lane)
uses **bespoke operator-sessions** — `/api/operator-sessions`,
`auth/operator-session.ts`, browser cookies, the auth worker (`ingress.ts:42,154`).
Project apps (`tasks`, `todo`) use a **different** gate:
`itx.auth.get({ policy: "project-member" }).fetch(req)` in their own `fetch`
(`config-repo-template/worker.ts:38,51`).

Making the OS a **stateless proxied front-end** (§14a) collapses these into one:

- **The dashboard authenticates like every other project app** — a proxy gates the
  visitor with `itx.auth.get({ policy })` (member/operator), then forwards to the
  stateless front-end. The bespoke operator-session machinery goes away.
- **Split auth into two clean halves, both flowing through the proxy:**
  - **Identity** ("who are you") — established _at the wall_: hosted = iterate's
    OIDC / operator-session; self-host = **Cloudflare Access** (`cf-access-jwt`) or
    your own OIDC. This is the deployment-axis knob (identity authority).
  - **Authorization** ("are you a member of this project") — `itx.auth` at the
    proxy. **Kernel, identical in both.**
- **The front-end holds no session** — it's stateless, so it _can't_ be the auth
  authority; auth must live at the proxy. That's exactly what keeps it swappable.
- **Uniformity:** dashboard, inbound MCP, `tasks`, user apps — every front-end is a
  stateless adapter behind a proxy that gates via `itx.auth`. One auth story.

So Jonas's instinct is right: the stateless-OS move isn't just tidy packaging — it
_forces_ the clean auth split (identity-at-the-wall / authorization-via-`itx.auth`),
and deletes the dashboard's one-off session system. Self-host auth becomes "put
Cloudflare Access in front"; nothing else changes.

## 16. "Integration engine" is NOT a kernel primitive — it's a connector (corrects §14)

Jonas double-clicked: integrations feel least like files/secrets on the kernel
list; it feels arbitrary; maybe it's "part of the secret system"; is it an instance
of something general? He's right — **it's a composite, not a primitive.**

"Connect Gmail" decomposes into things we already have:

- a **renderer** painted into the OS UI (the Connect button + the status card) —
  the userspace-modifies-UI primitive;
- **fetch handlers** (the OAuth callback, the webhook receiver) — ingress;
- a **self-obtaining, self-refreshing secret** (the OAuth token) — a richer _kind_
  of secret than a static pasted one;
- which yields **events** on a stream (the webhooks).

= `renderer + routes + a living secret + events`. Nothing new.

**"Part of the secret system" is the sharp half:** the credential is a
**self-refreshing secret**; the other half (the webhook) is just an inbound
fetch-handler→stream append. So an integration = _a self-refreshing secret + an
inbound event route + a card painted into a shared view._

**The general pattern = a "connector":** a userspace package that paints a card
into a shared surface, registers routes, and yields (a secret + a stream of events).
Slack/Gmail are the first two; Stripe, a database, any webhook/OAuth source are the
same shape. "Integration" isn't special.

**Corrections this forces:**

- Integrations move **out of the kernel → userspace** (correcting §14, which wrongly
  parked "the integration engine" in the kernel). Consistent with agent = userspace.
- The kernel shrinks further: even `files`/`kv` are userspace **wrappers over raw
  bindings** (R2/KV). True floor = raw bindings + the log + the capability resolver +
  the one egress door + identity + the confined runner.
- **Userspace is a gradient, not flat** (Jonas's "concentric circles"): SDK/base →
  deep std-lib (agent, secret helpers) → connectors → leaf apps. A dependency
  gradient, not a hard ring — consistent with dropping first-vs-third-party.
- **The one reusable kernel-support worth keeping:** a mechanism for userspace to
  **paint a renderer into a shared view** (the userspace-modifies-UI primitive,
  §11/§3).

**Decision (Jonas) — supersedes the "move to userspace" bullet above:** _keep
`integration` as a named feature in the kernel for now,_ with an acknowledgement it
may later be treated more generically (dissolved into the decomposition above). The
rename to "connector" was a relabel, not a simplification (and a coined noun —
dropped). Rationale: dissolving `integration` into "self-refreshing secret + inbound
event route + render-into-a-shared-view" buys generality we don't need until there
are several connectors, and costs indirection now. So: **integration stays named and
in the kernel; the decomposition is carried as the future-generalization note, not a
now-change.** (`files`/`kv`-as-userspace-wrappers still stands as a separate,
smaller point.)

## 17. One `invokeCapability` envelope across every RPC boundary (Jonas — big idea)

Hold this: whenever a capability call crosses a worker RPC boundary (Workers RPC or
capnweb) — **including built-in kernel capabilities**, not just dynamic mounts —
route it through a **single `invokeCapability({ path, args, context })` method**
rather than invoking member methods directly. Member methods (`stub.kv.get(k)`) have
no slot for the extra context we must thread; a single envelope does.

What the envelope carries on **every hop**:

- **caller context** (who's asking — principal + credentials + assurance; §15 /
  `identity-and-actors.md`), so it propagates instead of being lost at the first RPC.
- **call-trace metadata** (the chain of capability invocations) — for provenance,
  audit, and distributed tracing.

The single `invokeCapability` **falls back to the member methods** for actual
dispatch (path → the real method), so it's a uniform _envelope_, not a new dispatch
model. Ergonomics resolution: the nice member-method API (`itx.kv.get(k)`) stays as
sugar that, _at an RPC boundary_, compiles into an `invokeCapability` envelope
carrying the ambient caller context + trace — you get both the ergonomic call and the
context threading. Same shape the mount `invokeCapability` already has
(capability-host), generalized to be the one choke point for all cross-boundary calls.

**Why it's load-bearing, not just nice (surfaced by the `apps/kernel` build):** the
Worker Loader's `env` bindings + `ctx.exports` props are set **per worker instance,
not per request**. So per-request caller context _cannot_ live in the binding props —
it has to be threaded **per call**. That is exactly what this envelope is for. The
walking skeleton hits this the moment auth is added (see §M2 below / `kernel.ts`),
which is the concrete proof this idea is necessary.

**Caveat (Jonas) — `fetch` is exempt, and the caller does NOT go in props.** Two hard
constraints: (1) On Cloudflare a **WebSocket upgrade can only be returned from an RPC
method literally named `fetch`** — nothing else. So `fetch` (the project's ingress
handler AND the egress door) must stay a first-class `fetch` method; **never** wrap it
in `invokeCapability`, or apps lose WebSockets. The envelope is for _non-fetch_
capability calls only. (2) The caller context must **not** live in the binding props
(props are per-instance; the cache-key smuggling that forced was rightly rejected).
Instead: on the **fetch path**, the kernel injects the verified caller as a **trusted
HTTP header** (per-request, natural, rides straight through `fetch`/WS); on the
**non-fetch RPC path**, the caller rides the invoke envelope. Props carry only stable
per-project scoping (`projectId`). Fixed in `kernel.ts`.
