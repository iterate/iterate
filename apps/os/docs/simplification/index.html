iterate · the simplification

How to make apps/os beautifully simple

One page, pyramid-style: the tip first, then wider sections you can skip. Concrete examples, not abstractions. Includes a real vote — six independent judges (3 Claude, 3 codex) rating which bold ideas to build, shelve, or kill. Compiled 2026‑07‑14.

The whole thing in one breath

An iterate project is a fenced-off computer that writes down everything that lastingly happens, runs code in response, can rewrite that code, and can only touch the outside world through one door you’re watching.

It feels heavy because the whole idea is ~5 words but the front door makes you learn 33, and the same handful of jobs got built five times over. Almost everything else is a library you could’ve written yourself.

Watch one thing actually happen

A customer messages your support agent on Slack. Here is literally what the system does — it just adds lines to a log, and everything else is a way of reading that log.

The log at /agents/support — each line is one event (a fact that happened)
#1  agent/created            { parent: "/agents" }
#2  slack/message-received    { text: "my order is late", user: "U123" }
#3  agent/llm-requested       {}          ← the request is "event #3"; the prompt is rebuilt by
                                             folding #1..#2, so we don't copy it into the row
#4  agent/output-added        { text: "Sorry! Let me check your order…" }
#5  slack/message-sent        { text: "Sorry! Let me check your order…" }

State is just those lines added up. “Add them up” = reduce, the same Array.reduce you already know:

state = fold(the log)
state = events.reduce((s, e) => {
  if (e.type === "slack/message-received") s.messages.push(e.text)
  if (e.type === "agent/output-added")     s.lastReply = e.text
  return s
}, { messages: [], lastReply: null })

// → { messages: ["my order is late"], lastReply: "Sorry! Let me check your order…" }

That’s the whole engine. The only way to change anything is to add a line (append). The only way to read anything is to replay the lines (follow & fold). Delete the computed state and you rebuild it by replaying — the log is the truth, the state is a throwaway cache.

Everything durable is a line you add. Everything alive is someone reading the lines.

1 · The five words (each with a real example) Project = a company · Stream = a log · Processor = something that reads a log and reacts · Capability = a phone number · Repo = a git repo.

The rule that outranks everything: each word must be explainable in one line using words a programmer already owns. No new vocabulary to do your first useful thing.

WordIn one lineA concrete instance
Projecta company / a fenced-off world acme — its own logs, its own code, its own secrets. Code in acme can never touch globex.
Streama log (append-only list at a path) /agents/support is a log; every Slack message is a new line. So is /scheduler, /integrations/slack, and the repo’s history.
Processorsomething that reads a log and reacts The support agent: it folds the log into a conversation, calls a model, and appends the reply. An agent is just a processor with a prompt. So is the scheduler, the Slack router, repo-sync.
Capabilitya phone number you can call (a reference) itx.slack.postMessage(...). You can do it because you hold the reference, not because a permission check waved you through. Can’t hold it → can’t call it.
Repoa git repo — the project’s own source worker.ts that the project can read and rewrite. This is how it improves itself.

A processor is really three small functions: reduce (fold the log into state), processEvent (do a side effect — send the Slack reply), and reconcile (after a crash, finish any half-done work). That’s the entire programming model.

2 · The one shape everyone converged on A tiny “seed” you can’t avoid, the five words as a library on top, packages for the rest — and three honest ways to name the whole thing.

Six independent reviews (parallel code-readers, four rounds of a second model, a skeptic, prior-art scholars) all landed here: there’s a tiny core you truly can’t build in userspace, and everything else sits on top of it.

The kernel isn’t the hero. It’s the floor.
LayerWhat it isCould a user write it themselves?
The seedRun untrusted code · give it storage that survives crashes · watch the one door bytes leave by · know which project owns what. No — it’s the thing that runs user code. This, and only this, is the real kernel.
The five wordsproject · stream · processor · capability · repo In principle yes — a “log” is just storage + a rule. Kept fast & built-in so nobody has to reinvent crash-safety.
Packagesagents, integrations, scheduler, tasks, dashboards Yes — leaf features. iterate ships the good ones but keeps none of them privileged.

This answers the question “if streams aren’t in the kernel, is the kernel even the point?” — no. “Kernel” answers a security question (what can’t be userspace). It doesn’t answer what is this. That has three good answers, for three different people:

Who’s askingBest answerSaid plainly
A recruit / the websiteAn intelligent-entity runtime “A program whose loop lives in storage and survives its own crashes. A normal program’s loop dies with the process; this one keeps going.”
An engineerOne log and a fold “One write: add a line. One read: replay the lines. State is the replay; the database is a cache you can throw away.”
Security / opsAn operating system “A tiny locked kernel, a few modules we run, packages for the rest — with two screens: one to run a company from outside, one where the company lives.”

A referee scored these and refused to crown one: “any framing claiming to be universal loses — they’re three photos of one building.”

3 · Why it feels heavy (the honest diagnosis) The same five jobs got built five separate times, and the front door shows you all the plumbing.
Every new feature arrived as a new thing, instead of another use of the old things.

That was reasonable one feature at a time. But look what happens when you count how many times the same job got solved:

One jobTimes it’s built
“fold a log into state”2 engines (a generic one, and a hand-written copy inside the stream itself).
“deliver events to a reader”4 lanes (wake, push, webhook, and the browser hand-rolls a 5th).
“a durable job that must finish after a crash”5 hand-rolled copies (LLM calls, scripts, scheduler, repo-create, sends) + 2 more recovery machines.
“a chat channel → an agent”4 near-identical copies (Slack, Telegram, email, GitHub) — the files literally say “shaped after the Slack one.”
“a place to keep files”3 (repo, workspace, sandbox) that dial each other in a circle.
“walk a dotted path and call it”4 copies + 3 different “reserved word” lists, held together by matching error-message text.

Then the public API shows you all of it. The project object has 33 members; the contract has 46 interfaces; the vision needs 5. And the file that lists them, rpc-targets.ts, is 6,014 lines — 2.35× its size three weeks earlier, when a review already said “split this up.” The “elegant” streams layer is the biggest directory at ~17k lines — which the skeptic calls a gotcha and the design calls the point (streams are a library, not the kernel).

And three things that should be facts aren’t: a repo commit, a file write, and a build failure all happen with no event — so nothing can react to them or trace them. That’s the one hole that makes the log feel like a lie.

4 · What to actually do — three tiers Tier 1 needs no decision (delete + add the missing facts). Tier 2 is the real collapse. Tier 3 needs your call (§8).
just do it Tier 1 — everybody agreed, no philosophy needed
  • Add the 3 missing facts. repo/commit-landed, file/put→pointer-landed, build→succeeded|failed. Now commits, writes, and failures are traceable and reactable. Cheap.
  • Make email a two-step fact (request → sent). Today it sends first and maybe records after — a crash in between = a lost email with no trace.
  • One egress door. Slack goes through the door; gmail and github secretly don’t. Route them through it.
  • Fix the build-cache bug. “Immutable” builds re-resolve npm versions at build time, so the same input can produce different bytes. That quietly breaks replay.
  • Delete the dead docs (a 951-line doc teaching class names that no longer exist, plus a QA playground shipped as a real route).
  • Collapse the duplicates from §3: 2 fold engines → 1; 4 delivery lanes → 1; 5 durable-job recoveries → 1 primitive — and make a -requested event refuse to compile without its “how do I finish this after a crash” handler.

This is most of the felt heaviness gone, with zero framing decisions. Could start Monday.

bigger Tier 2 — the real collapse (most leverage first)
  1. Make built-in tools ordinary mounts on the one capability table → dissolves most of the 6k-line god-file and the whole code-generator that exists to document it.
  2. One channel mechanism — Slack/Telegram/email/GitHub become one small parameterized thing (ideally living in the project’s own repo). ~2,500 lines.
  3. Repo becomes the one filesystem — workspace & builder fold in; a sandbox becomes just a mounted computer.
  4. Fewer hops on the hot path — merge two durable objects that fold the same log; resolve mounts in-process (6 network hops → 2).

Honest target: the core lands near ~6k lines, not 5k. “5,000” was always shorthand for small enough that one person holds the whole thing in their head.

5 · The three ways to explain it, scored (pros & cons) Runtime wins the pitch, one-log wins engineering, OS wins governance. Don’t pick one — use each where it fits.

Three full write-ups exist, each committing to one framing and attacking the other two. They’re not rivals to choose between; each leads for a different audience.

“Intelligent-entity runtime” — the vision pitch

Plain version: a normal program’s loop runs inside one process and dies with it. This loop lives in the log, so the program can crash, restart, and keep going — and some of its steps are a model being asked a question. A normal loop is around promises; this one is around lives.

Pro

  • The only framing that names what’s actually new.
  • Explains the key trick: a model answer is written down as a fact, so a replay reads it — a program with a random step is still perfectly repeatable.

Con

  • “A story about the interesting 5%” — silent on updates, billing, recovery.
  • Its weak word is “intelligent”: rip out the model and the same runtime remains.
“One log and a fold” — for engineers & the LLM

Plain version: it’s a database turned inside out. Normally the table is the truth and the log is a backup; here the log is the truth and the table is the backup. One write (add a line), one read (replay). A quick call is a line you don’t keep; a workflow is a line you do.

Pro

  • The words become API calls immediately — the most plain of the three.
  • Best for the model that has to use it: “add a fact, follow for the result, fold for state.”

Con

  • Taken literally it’s false: audio, big files, and live connections can’t all be log lines (the honest fix: one log of truth + a few typed “devices”).
  • “A log says what happened; a runtime is still happening” — it hides the crash-recovery work.
“An operating system” — for security & ops

Plain version: a tiny locked kernel, a few modules iterate runs, and packages for everything else — plus two screens: os.iterate.com to run a company from the outside, and the company’s own domain where it lives.

Pro

  • The only framing that answers who-owns-what, security patches, and updating a million projects — with real arithmetic.
  • Clean rule: “if it has to work when the project is broken, it lives outside the project.”

Con

  • Doesn’t explain the special part (a filesystem that’s append-only, a scheduler that asks a model).
  • Familiar words that secretly mean something different = highest confusion risk.

Verdict: pitch with the runtime, teach with the log, govern with the OS. And for all three: first say what the programmer does, then reach for the metaphor.

6 · The directional ideas, with concrete examples Just-fetch · the one-door security model · config-as-code · births · expressions-as-grants · sandboxes-as-mounts · the three rings · updating a million projects.
One fetch for everything — and it’s the whole security story

Instead of separate “incoming” and “outgoing” machinery, there’s one fetch. The hostname decides what happens:

the same verb, two destinations
fetch("http://billing.iterate/invoices")            → stays inside the project. free. no checks.

fetch("https://api.stripe.com/charges", {
  headers: { Authorization: getSecret("stripe") }   → leaves the project → THE ONE GATE:
})                                                     swap the real key in, check it's allowed
                                                       to reach stripe.com, maybe ask a human, log it.

Why this matters: an agent can run any code, message anything internal, read any internal state — and none of it can hurt anyone until bytes try to leave. So security isn’t 33 scattered checks; it’s one guard on one door.

Inside the house is free. The only thing that matters is what goes out the door.
Config is a worker.ts that can override any default

Every project is born with a worker.ts that already sees every event and can react. The clever part is how it overrides platform defaults without a fight — both the platform and your code append with the same key, and the log keeps the last one:

how "override the default model" actually works
platform appends:  agent/config { model: "gpt-5.6", key: "defaults@birth" }
your worker adds:  agent/config { model: "claude",  key: "defaults@birth" }  ← same key

fold keeps last-by-key  →  model = "claude".   No callback, no waiting, no fight.
To override: just append first, or re-append. To keep the default: do nothing.

Pro

  • Every default is overridable in the project’s own code, without shipping code into a million repos.

Con

  • The dumb version — platform calls your code and waits — is wrong; your code reacts after the fact and can never block the log.
  • Two judges warned: don’t run user code on every event (fleet tax); make it react only to events it selected.
Expressions + “bind” = a safe way to hand out narrow powers

Today a stored “call this later” is an ugly nested array. Make it writable as normal code, and let you bind an argument to narrow it:

give a helper the power to post to ONE channel, nothing else
const postToSupport =
  grant( itx.slack.postMessage ).bind({ channel: "#support" })

// postToSupport({ text: "hi" })   ✅ works
// postToSupport({ text: "hi", channel: "#ceo-private" })   ❌ rejected — channel is fixed

Now one format works for stored subscriptions, tool grants, egress rules, and secret placeholders — “everything is an expression.”

Pro

  • One readable, inspectable, revocable way to hand out a slice of a capability.

Con

  • “Bind” must be an enforced constraint, not a merge-the-objects (that’s a security hole). Keep the grammar tiny: get + call, no loops, no eval.
  • An expression is a name, not authority — power still comes from who runs it.
Sandboxes are nothing special — just a mount

A “sandbox” is a computer you plug in. There’s no reason it needs its own subsystem — it’s a capability like any other, and the provider is just which one you mounted:

the whole world's compute, one grammar
itx.mount("machines/fly",   { region: "lhr" })
itx.mount("machines/e2b",   {})
itx.mount("machines/my-mac", {})   // a laptop in a menu bar
// then: box.exec("python train.py")   — egress still goes through the one door

Deletes a whole “domain.” All the world’s machines become addressable the same way all the world’s SaaS is.

Everything in userspace? — the reversal, and “three rings”

The night’s biggest course-correction. The dream: ship everything (even agents) as npm packages in each project. The counter is strong enough that the panel killed the mandate 6–0.

Pro (the dream)

  • Userspace-first is the vision: self-improvement, portability, a real marketplace.

Con (why 6/6 judges killed the mandate)

  • npm is a file-download service, not trust or billing or support.
  • A non-technical founder can’t audit 20 strangers’ access grants — that’s trusting 20 employees you never met.
  • The agent code is a deep, cohesive module — splitting it up buys a support nightmare, not simplicity.

The survivor — three rings: ① a locked kernel · ② a few deep modules iterate runs (agents, repo, secrets, scheduling) · ③ packages for leaf apps. “Everything in userspace” survives as a test (“could a stranger rebuild this without secret backdoors?”) — not as a rule that everything must ship as a package.

Updating a million projects without breaking them

You can’t re-edit a million git repos every time you fix something. The math is brutal, but the answer is the one every OS already uses.

the numbers
Rebase every repo on each change:   1 weekly update × 1,000,000 repos = 52,000,000 repo edits/year
                                    even at 99.999% success = 10 broken projects EVERY release.

Give each project its own worker:   ~$20,000/month just to hold a million scripts,
                                    ~69 hours to upload them all.

Publish a version + a "channel":    projects that follow "stable" pick it up on their next build.
                                    Pinned projects don't. Nobody rebases. ← this is apt / the App Store.

Verdict: per layer — kernel updates ship instantly (one deploy); third-party things follow a channel + version-lock; only the code a project truly owns lives in its repo. Don’t build the million-repo rebaser.

7 · The vote — build / shelve / kill the wild ideas 6 independent judges (3 Claude + 3 codex, each a different stake). Unanimous: BUILD “just fetch” & “expressions-as-grants”; KILL “everything-as-a-package.”

Six judges voted independently, each with a different job to protect: a shipper (what a small team can build this quarter), a security reviewer, a developer-experience judge (can an LLM and a normal dev use it day one), a distributed-systems skeptic (does it survive crashes & replay), a ten-year founder (the vision), and a cost/ops judge (what happens at a million projects). Green = build now, amber = shelve as a north-star, red = rule out.

What that means, idea by idea

Build now. Just fetch (every judge’s #1 — fewer verbs, one security door, half-built already). Expressions + bind-as-grant (one readable, revocable way to hand out a slice of a power). Config-overrides-defaults (already shipped; just make overrides selective and loud). “The model is a step you write down” — not really a build, more a rule to make sacred: journal every model answer so replay reads it.
Build, but only the tame slice. Present the project as a filesystem (ls/cat/grep is the most LLM-legible front door there is) — but as a view, where a log is a folder, a fold is a generated file, and live audio is a pipe, not a stored file. And a read-only “rewind to any past moment” debugger (the safe half of “time is a place”).
Shelve as north-stars — real, but not now. The entity is a file (portability moat; needs exact-replay first). The Last RPC (keep it as a way to compile calls, not a promise that a call and a workflow are identical — they aren’t). Shadow-self self-improvement (a testing tool, never an auto-promote button — it can’t simulate how the real world would have replied). Hire software companies (the most beautiful long game — and the one the cost judge singled out as the real fix for fleet updates — but it turns a platform into an economy, with vendor bankruptcy and supply-chain risk).
Rule out. Everything-as-a-package as a mandate (D3) — killed 6–0, the “kill hardest” pick of four judges: it hands a non-technical founder 20 strangers to trust and turns one coherent company into an un-auditable dependency graph. Moving streams out of the kernel (D2) — killed 4–2 as a code move: the razor is right that streams could be userspace, but doing it makes every processor re-implement crash-safety, and the log’s correctness is exactly what must survive a broken userspace. Keep it as a true statement, not a migration.

My own read (where I’d come down)

Include immediately: D1, D5, D4 (selective), and the C6 invariant — these are cheap, they reduce concepts, and every seat at the table wanted them. Include as a view: C5 (the filesystem face) — it’s the single biggest legibility win for the LLM that has to use this, and it pairs perfectly with “just fetch.” Rule out for real: D3 and D2-as-a-move — not because they’re wrong in spirit, but because they trade a working thing for a purity that the panel showed costs more than it saves. Keep alive but off the roadmap: C2, C1, C7, C3, C4 — they’re the vision’s soul; they just shouldn’t touch production until the boring facts (Tier 1) and one exact-replay foundation exist. The one I’d most want to prototype small is C7’s read-only rewind — it’s a killer debug tool and it falls out of “state is a fold” almost for free.

What the judges said was MISSING from the ballot

  • Ship judge: the Tier-1 deletions themselves deserve a vote — they’re the highest-leverage, lowest-risk work and they weren’t even on the list.
  • Security: a tamper-proof, hash-chained record of every access granted, narrowed, or revoked, and every egress decision — “the one door is only trustworthy if its history can’t be forged.”
  • DX: a build-breaking lint that fails CI if any concept or public name can’t be explained in one line of ordinary words — Urbit’s lesson turned into a merge gate.
  • Skeptic & Cost (agree): first-class durable jobs + fleet-native version channels with content locks, staged rollout, and auto-rollback — i.e. bless the obligation primitive and the “publish-a-channel” update model as real features, not afterthoughts.
  • Founder: “collective evolution” — let entities distill proven improvements into signed, privacy-preserving patches that other entities can choose to inherit.

Two of these (durable jobs, version channels) are already Tier-1/§6; two are genuinely new and good (the audit log; the CI legibility lint); one is a fresh north-star (collective evolution).

8 · The wild ideas in full (with a concrete example each) The vote in §7 rated these; here’s what each one actually is, plus why it’s beautiful and how it bites.

A call is a line you don’t keep; a workflow is a line you do. shelve

quick call:   add EPHEMERAL {invoke:"getUser", args:[7]}  →  wait for {result}  →  line is dropped
workflow:     add DURABLE   {invoke:"getUser", args:[7]}  →  wait for {result}  →  line kept forever
the only difference: one boolean, "keep it or not."

Beautiful

  • One mechanism for calls and workflows; replay, audit, and history come free.

But…

  • A call also needs timeouts, cancellation, streaming, backpressure — “keep it or not” isn’t the only difference. Use it as a compiler, not a law.

The entity is a file. shelve

what's literally in the tarball
acme.tar
├── repo/       the code (git: worker.ts, package.json)
├── streams/    the logs (/agents/*, /integrations/*, …)
├── blobs/      big files, by hash
└── lock.json   exact package versions + which code-hash processed each event
NOT inside: secrets, live Slack sessions, emails already sent.

Beautiful

  • Backups, staging, and “leave for a competitor” all become “replay the file.” The deepest trust moat there is.

But…

  • It holds state, not consequences — the sent emails and moved worlds aren’t in the tar, only the receipts.

Rehearse new code against your own past before it goes live. shelve

Before promoting a change, replay the entity’s last week of real events through the new code with the outside world blocked, and compare what it would have done.

Beautiful

  • Turns “the agent edited its own code and we prayed” into “we checked it against real life.”

But…

  • It can’t know how the customer would have replied differently; the judge shares the agent’s blind spots. A test tool, never an auto-promote button — always end with a small live trial.

Don’t install software — hire a company. shelve

A tasks app isn’t a tarball; it’s a live provider at tasks.vendor.com. You don’t install it — you hire it with a contract made of signed events, and it runs in its project, not yours.

Beautiful

  • Solves fleet updates outright: the provider patches one running service, not a million repos. Vendors become accountable companies, not anonymous package names. (The cost judge’s favorite idea.)

But…

  • Turns a platform into an economy — bankruptcy, correlated failure, supply-chain concentration.

The whole project is one tree — but not every leaf is a stored file. build as a view

/acme
├── agents/support/log/…      ← real files (durable events)
├── agents/support/state.json ← a generated file (a fold; recomputed, not stored)
├── repo/worker.ts            ← editable code
├── secrets/stripe            ← write-only, can't be read back
└── calls/42/audio.pcm        ← a PIPE (live audio flows through; nothing is kept)

Beautiful

  • One namespace; ls/cat/grep/watch — the tools every human and every model already knows. The most legible possible front door.

But…

  • Not a real filesystem underneath — a typed view hiding several kinds of storage. “Everything has a path; not everything is a file.”

Rewind to any moment of the entity’s life. shelve (build the read-only half)

Because state is just the log replayed, every past self still exists. Make it addressable: itx.at(offset:#3) gives you the entity exactly as it was after event #3 — debugging becomes time travel.

Beautiful

  • The trace panel and inspector are just special cases of this; “show me the moment before it broke” becomes a verb.

But…

  • Replaying 10M events isn’t free (needs snapshots), and the outside world isn’t in the log, so “what if” hits a wall at every external call.
9 · The case against all of this (steelmanned) The boring-tech skeptic, the “code as content-addressed values” lens, and Urbit — the warning that outranks the architecture.
The skeptic: “just use Postgres, a queue, and cron”
  1. “Log-everything” is a known trap, and the repo is already in it: 122 event types you can now never change; the core format is on version 14 (each bump replays everything); and mutable caches are quietly creeping back in — the classic tell that pure event-sourcing didn’t hold.
  2. The 5,000-line kernel is an accounting trick: the honest number is ~6k, reached by relabeling 63k lines of other code as “packages.” Moving it isn’t deleting it.
  3. A startup wants boring parts: Postgres + a durable queue (Temporal is the durable-job primitive) + cron + an LLM API, with hireable engineers and a debugger that shows a table — not a home-grown system only its authors can run.
  4. “Any SaaS as an npm package” buys a supply-chain attack surface for a marketplace that may never have sellers.

Even the skeptic keeps: the durable-job pattern (maybe via Temporal), config-as-overridable-data, and log-sourcing the one thing that truly fits — the agent conversation.

Content-addressed code (Unison/Nix): the fleet-update answer

Make the repo point at code by hash, like a lockfile. A platform update publishes new hashes; a project follows a channel or pins a version; nobody rebases, because behavior is a name you follow, not code copied into your repo. iterate already does ~60% of this (its build key is a content hash that collapses a million identical repos to one build).

Catch: the pure version is hostile to humans and to an LLM trained on files-and-git. Answer: content-address inside, keep git outside.

Urbit: the warning that outranks the architecture

Urbit is the closest thing that already exists (state = a fold of a log, boot = replay, upgrades = events) and it’s been technically beautiful and adoption-irrelevant for 20 years. It didn’t die of bad architecture.

Urbit died of a private language only its authors spoke.

This exploration is already growing one (organ, attenuation, worldline…). Fine as private notes; never at the front door.

The one discipline that outranks everything: every concept explains in one line of ordinary words, and nobody learns a new word to do their first useful thing. (The DX judge wants this as a build-breaking CI check.)

10 · The decisions that are yours to make The forks where analysis runs out and it’s a judgment call — each with the options and a recommendation.

Which one-liner leads the website?

Recommend: “intelligent-entity runtime,” grounded immediately by the plain version. But decide: is “intelligent entity” the category you sell, or the first use of a more general durable runtime?

How far toward packages?

Recommend (and the vote backs it): three rings; “everything in userspace” as a test, not a mandate. Decide out loud where iterate will never be extensible (auth, the log, crash-recovery, grants, secrets, the door, billing, recovery).

Is the model a first-class part of the runtime, or just another tool?

Decide: does the runtime know what a model call is (and give it request-ids, streaming, accounting), or just enforce the general rule “write down anything you can’t recompute”?

Streams: privileged and built-in, or replaceable userspace?

Recommend: “privileged, with a public replacement seam.” The vote killed actually moving them. Pick your poison: a slightly bigger trusted core, or a smaller one with crash-safety re-implemented above it.

Is the substrate overengineered?

The test: can you defend it to a skeptical senior hire? If not yet, close the gap by adopting Urbit’s version-migration discipline (the concrete answer to “the log format changed”).
