OS as a project — what it actually means

Grounded in today's real code. Scribble on anything confusing. Colours: kernel the "os" project user projects stays global (in kernel)

The one fact that makes this un-scary: user projects already work this way today. A user's config worker runs confined in a WorkerLoader isolate and only sees env.ITX — never raw Cloudflare bindings (worker-loader.ts:226). The OS is the odd one out: its own features live inside the worker with full access. "OS becomes a project" = run the OS's own code across the boundary that already exists.

5 · Why this is safe & incremental (not a rewrite)

Each step ships on its own and moves toward the picture in §2:

1. Built-ins → mounts (start with kv). The mechanism. Nothing user-visible changes.
2. Move agent + integrations to iterate/* npm packages the config imports (already done for the review bot & starter apps).
3. Add itx.operator — name the handful of cross-project powers explicitly.
4. Factor the kernel out of ProjectDurableObject, one subsystem at a time. It shrinks toward ~6k as features leave.

At no point is there a big-bang rewrite. The scary part (step 4) comes last and is gradual.
