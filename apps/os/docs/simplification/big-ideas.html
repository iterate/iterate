How to use this page

Each card carries: what the idea actually is (with a tiny worked example), how it fits the locked foundation (which beliefs/decisions/requirements it serves or violates — the B/D/R/Q IDs), six one-line perspectives, the earlier 6-judge vote, the sharpest objection, and a recommended verdict with where it would land. Where an idea is already substantially locked by the foundation, the card says so and stays short — it's really just asking you to confirm.

Plain-word glosses (no jargon at the front door): attenuation = handing out a narrower version of a power (e.g. "post to this one channel, nothing else"); fold / reduce = adding up a log into current state, like Array.reduce; ephemeral append = a log line you don't keep; egress = bytes leaving the project.

Recommend ADOPT — pull into the foundation

Just fetch — collapse ingress + egress into one verb "Ingress fetch" and "egress fetch" become one fetch; the hostname decides everything. substantially locked → confirm 6-judge: BUILD 6–0

What it is. There is exactly one network verb. The stateless handler routes by hostname: an internal name is free and un-gated; any external origin passes through the single egress gate.

the same verb, two destinations
fetch("http://billing.iterate/invoices")          → stays inside the project. free. no checks.

fetch("https://api.stripe.com/charges", {
  headers:{ Authorization: getSecret("stripe") }  → leaves the project → THE ONE GATE:
})                                                   swap the real key in, check stripe.com is
                                                     allowed, maybe ask a human, log it.

Security stops being 33 scattered checks and becomes one guard on one door: an agent can run any code and read any internal state, and none of it can hurt anyone until bytes try to leave.

Fit with the locked foundation.
Serves / IS: D6 (the only real security is the egress door) — this idea is D6's mechanism. Also serves D8 (one universal event/interface), R1 R2 (which D6 says reduce to the egress door), and folds the two-door §7 architecture note into one.
Violates: nothing. It strengthens the trust model rather than bending it.
Status: already substantially locked — D6 and the §7 "one fetch-shaped door" text state it. This card is a confirm, not a debate.
Feasibility — high; the internal-name routing already half-exists (use-my-computer URL-addressable capabilities).
Value — very high; fewer verbs and a sharper security story at once.
Security — the whole point: confinement becomes one gate on one verb, auditable in one place.
Cost @1M — neutral-to-positive; one chokepoint is cheaper to operate than many.
DX / legibility — excellent; every dev already knows fetch, nothing new to learn.
Vision — pure; "the only way it influences the world is HTTP out" (§1) becomes literally one door.

6-judge vote: BUILD 6–0 — every judge's #1: fewer verbs, one security door, half-built already.

Sharpest objection / failure mode. Very little bites. The one nuance: internal "free, no gate" must genuinely mean the confinement boundary is airtight — an internal hostname that could be tricked into reaching another project would collapse R1. And the "is it a human" enclave-attestation question (a special egress requirement) is unresolved — kernel or a very-trusted mount.
Recommended: ADOPT. It's already D6; adopting here means keeping the wording as one verb throughout the architecture rather than "ingress + egress."
Where it lands: confirms D6; sharpens the §7 architecture line to "one fetch, routed by hostname." No new decision needed.
Your verdict recommended: ADOPT
Expressions-as-grants + bind-as-attenuation A stored "call this later" is written as normal TypeScript; binding an argument hands out a narrower power. 6-judge: BUILD 6–0

What it is. Today a stored capability is an ugly nested array (["integrations","slack","chat","postMessage"]). Make it writable as ordinary code via a recording proxy, and let you bind (fix) an argument to narrow it. Attenuation = handing out a slice of a power, nothing more.

give a helper the power to post to ONE channel, nothing else
const postToSupport =
  grant( itx.slack.postMessage ).bind({ channel:"#support" })

// postToSupport({ text:"hi" })                       ✅ works
// postToSupport({ text:"hi", channel:"#ceo" })       ❌ rejected — channel is fixed

Now one format serves stored subscriptions, tool grants, egress rules, scheduler payloads, and the getSecret placeholder (which is secretly secrets.get(path).material quoted and deferred to the one place allowed to evaluate it). "Everything is an expression."

Fit with the locked foundation.
Serves: R7 (the capability/grant surface should look like TypeScript) — this is exactly its answer, and directly resolves Q9 (make expressions look like TS while keeping the grammar tiny). Also serves D10 (the secret placeholder is a bound, deferred expression) and R2 (a narrow grant can't over-reach).
Strengthens: D1 R1 — evaluation authority comes from the evaluating scope and never travels with the expression, so a persisted grant can't smuggle cross-project reach.
Violates: nothing — but only if bind is an enforced constraint, never an object-merge (see objection).
Feasibility — high; the recording proxy is ~50 lines and the codebase already has proxy competence.
Value — very high; collapses five grant formats into one readable, revocable, inspectable one.
Security — strong if bind = constraint; it's the object-capability "facet" move in the system's own grammar.
Cost @1M — neutral; expressions are by-value data, cheap to store and replay.
DX / legibility — excellent; itx.foo.bar().bind(...) reads like the live call it quotes.
Vision — high; "the events ARE the API" + "everything is an expression" compose cleanly.

6-judge vote: BUILD 6–0 — one readable, revocable way to hand out a slice of a power.

Sharpest objection / failure mode. "Bind" is a security hole if it means deep-merge (a caller could re-open a fixed field). It must be an enforced constraint. Keep the grammar tiny — get + call, JSON args, no loops, no eval. And remember: an expression is a name, not authority — power comes from who evaluates it. Codex round 2 verdict: "excellent intermediate representation, terrible naked grant" — so pair it with a separate revocable grant object.
Recommended: ADOPT. Cheap, reduces concepts, and every judge wanted it.
Where it lands: promotes Q9 into a Decision ("the capability/grant grammar is a small quoted-expression algebra: get + call, JSON args, bind-as-constraint"), landing under the future capability domain object. Satisfies R7.
Your verdict recommended: ADOPT
How far toward userspace — the "three rings" Kernel (can't be userspace) · a few deep first-party modules iterate operates · packages for the leaves. "Everything in userspace" survives as a test, not a mandate. partly locked (D2) the reconciliation, not a single vote

What it is. The night's biggest course-correction. The dream ("ship everything, even agents, as npm packages in every project") lost 6–0 as a mandate. The survivor is a three-layer cut:

RingWhatCould a stranger rebuild it without private backdoors?
① KernelThe seed: run confined code · durable named storage · the one exit · identity/confinement · billing veto. No — it's the thing that runs userspace.
② Deep first-party modulesagents/conversations · repo/artifacts · secrets/egress · scheduling/obligations · core integration machinery. In principle yes — but iterate operates them centrally, with override seams. This is the "userspace test."
③ Packagesleaf apps, vertical workflows, custom UIs, narrow integrations, remote processors. Yes — iterate ships the good ones, privileges none.

"Everything in userspace" demotes from a deployment rule to an implementability test: could a third party build this Ring-2 module without secret bindings?

Fit with the locked foundation.
Serves / IS: D2 (everything except a tiny kernel is overridable in userspace) — three rings is the concrete shape of D2. Directly resolves Q7 (how far toward userspace / what to call the layer). Consistent with the B2 "userspace test" spirit.
Strengthens: D2 by naming which pieces are Ring-1 vs Ring-2 vs Ring-3 — the "kernel razor" says even streams could be Ring-2 by necessity, kept privileged by choice.
Open naming: Q7 still wants a word for Ring-2 that isn't "packages" (implies npm). This card adopts the structure; the name stays flagged.
Feasibility — high; it's a labelling and boundary discipline more than new code.
Value — high; tells you exactly where iterate will never be extensible (auth, log, recovery, grants, secrets, the door, billing).
Security — strong; a non-technical founder trusts iterate's Ring-2, not 20 anonymous strangers.
Cost @1M — favourable; Ring-1/2 updates ship once (a deploy), only Ring-3 follows channels.
DX / legibility — good; "could a stranger rebuild this?" is a crisp, testable line.
Vision — high; "apps/os becomes an OS in the literal sense" without abdicating the deep modules.

6-judge vote: the extreme forms were voted — everything-as-a-package KILLED 6–0 and moving streams to userspace KILLED 4–2. Three rings is the reconciliation both votes point at.

Sharpest objection / failure mode. Codex round 3: "extensibility ≠ abdication; npm is transport, not governance." The risk is Ring-2 quietly swelling until "small number of deep modules" stops being small — and the honest ~6k-LOC core becoming an accounting trick (relabel, don't delete). Draw the Ring-1/Ring-2 line in blood, and price the Ring-2 modules honestly.
Recommended: ADOPT. It's the settled reconciliation and it's the mainline the synthesis recommends.
Where it lands: resolves Q7 into D2 as three named rings, with "everything in userspace" recorded as a test, not a mandate. Still leaves the name of Ring-2 open (flagged ambiguity).
Your verdict recommended: ADOPT
The mind is a fold — the LLM as a journaled step There is no "model integration." An LLM is a reducer with temperature; personality is a fold of lived history; compaction is sleep. substantially locked → confirm the invariant 6-judge: BUILD 4–2

What it is. Say out loud what the agent processor already does: the prompt is rebuilt by reducing committed history up to an offset, the request id is the offset, the response becomes events. So an LLM is a stream processor's fold step whose transition function is stochastic and whose contract is natural language. Personality = the residue of compactions; compaction = sleep (consolidate episodic events into a semantic prefix, wake shorter with the same self).

the sacred invariant that makes replay survive a random step
#7  agent/llm-requested   {}                    ← request id = offset #7
#8  agent/llm-completed   { text:"Sorry! …" }   ← the stochastic answer, WRITTEN DOWN as a fact

// replay READS #8. it never RE-ASKS the model.
// → a fold over a history that contains non-deterministic facts is still perfectly deterministic.
Fit with the locked foundation.
Serves / IS: B3 (optimize the substrate for AI-authored, self-modifying code), D3 (event-sourcing purists — the model output is an event on the normal path), D5 (agents produce only code / respond to events). The "journal the answer, replay reads it" rule is already the locked practice (compaction sits in D3's world; the code commits llm-request-completed).
Strengthens: D3 — it's the reason the purist equation (state = fold of log) survives a stochastic step.
Status: substantially locked. The card asks you to bless the invariant as sacred, and (optionally) to accept the framing "the LLM is a reducer" as canonical language.
Feasibility — already built; this is naming, not new machinery.
Value — high; makes any coding agent (claude/codex/pi) trivially hostable — they're all "stateful processor + stochastic reducer."
Security — neutral; the model is inside the trust boundary like everything else.
Cost @1M — neutral; compaction is already prompt-cache-coherent, so consolidation is cheap.
DX / legibility — mixed; beautiful to a systems mind, but "personality = a fold" is poetry that must stay out of the front door.
Vision — pure; "history is the only substance" — minds are just another view of the journal.

6-judge vote: BUILD 4–2 — the two shelve votes (security, DX) worried the poetic framing over-promises; the invariant itself is unanimous.

Sharpest objection / failure mode. The equation breaks the instant a model output is recomputed rather than read — so the invariant is load-bearing, never optional. Also "personality is a fold of experience" means trauma is too: one poisoned stretch of journal compacts into a permanently-weird entity, and the fix (editing memory) violates append-only — you'd build "therapy" (re-fold the past as new events). Keep the poetry in the vision doc, not the manual (the Urbit idiolect warning).
Recommended: ADOPT. The invariant is non-negotiable and already how the code works; adopting means writing it down as a first-class rule.
Where it lands: a Decision under D3/D5: "a stochastic (LLM) step's output is always a journaled fact; replay reads it, never recomputes it." The "mind = fold" framing stays in the vision doc, off the front door.
Your verdict recommended: ADOPT
The project is one virtual filesystem — as a view Everything has a path; not everything is a stored file. ls /agents/foo/, cat state.json, grep the history — the most model-legible front door there is. 6-judge: BUILD as a view 3–3

What it is. Present the whole project as one navigable tree — a stream is a folder, a durable event is an immutable file, a fold is a generated read-only file, a secret is write-only, live audio is a pipe. The key mutation (from the codex run): "everything is a *file*" KILLED; "everything has a *path*" KEPT. It's a typed namespace whose filesystem interface hides several radically different storage/transport implementations — like Unix's /proc, not a real disk.

one tree — but each node has the storage it actually needs
/acme
├── agents/support/events/…      ← regular files  (durable events, retained)
├── agents/support/state.json    ← generated file (a fold, recomputed — not stored)
├── repo/worker.ts               ← mutable content-addressed tree (editable code)
├── secrets/stripe               ← write-only, pinned-egress (can't be read back)
└── calls/42/audio.pcm           ← a PIPE / device (live PCM flows through; nothing kept)

The primary user is an LLM trained on files and folders, not a capability DSL. ls/cat/grep/watch are tools every human and model already own — the same adoption insight Urbit died for lacking.

Fit with the locked foundation.
Serves: B2 (the primary API user is an LLM; legibility-to-a-model is first-class) — this is arguably its single biggest win. R5 (traceable — "the trace is the events subtree, sorted, with causation as link structure"). D8 (one universal interface). The path is exactly what itx already is (streams live "at a path").
Fills a hole: §4 lists only four concepts; the fifth — Project as the one navigable namespace — is precisely the tree. It names the runtime instance.
Respects: D11 (durable vs ephemeral) — durable events are files, PCM is a pipe; R4 (voice) survives because audio is a device, not a stored file. D10 — secrets stay write-only.
Careful with: D3 — a filesystem tree gives a node one parent, but traceability needs a directed graph (causation via symlinks / a caused-by xattr).
Feasibility — the view is feasible (a projection); a literal POSIX FS on Cloudflare is not (no shared persistent FS in Workers).
Value — high as legibility; it's a face, so it doesn't change the substrate.
Security — fine if secrets stay write-only and capabilities aren't naively "readable files."
Cost @1M — modest; it's rendering over existing streams, not new storage (avoid materializing millions of tiny files).
DX / legibility — best-in-class; the most LLM-legible front door the system could have.
Vision — high; pairs perfectly with "just fetch" (read a file = GET, append = write).

6-judge vote: BUILD as a view 3–3 — split down the middle on the literal version, unanimous that the view (path-not-file) is the win; ship the tame slice.

Sharpest objection / failure mode. A literal regular-file model makes secrets readable, capabilities awkward, folds write-heavy, and live media impossible — and callers expect POSIX guarantees a projection can't give (atomic rename, fs.watch, one-parent hierarchy). Keep it a typed view, never claim a real filesystem underneath. "Everything has a path; not everything is a file."
Recommended: ADOPT (as a view). The single biggest legibility win for the LLM that has to use this, and it costs nothing structurally because it's a face over what already exists.
Where it lands: adopt Project as the fifth concept — the one stable navigable namespace/tree — into the taxonomy; the filesystem interface becomes a projection over itx (D8). Do not adopt a literal VFS as substrate.
Your verdict recommended: ADOPT (as a view)

Recommend SHELVE — real north-stars, not now

Time is a place itx.at(offset) — the entity at any moment of its life, live and queryable. Fork it, feed it a different event, watch the life it didn't lead. 6-judge: SHELVE 4·1·1 (build read-only half)

What it is. Because state is a fold, every past self still exists in the journal. Make it addressable: itx.at(#3) returns a real itx whose folds stop at event #3 — a live scope you can __describe(), run scripts against, ask questions of. The counterfactual half: fork at an offset, append the event that didn't happen, replay with egress jailed, diff the two lives.

two halves — one safe, one hard
SAFE (read-only rewind):   itx.at(#128) → "show me the entity the moment before it wedged"
                           the trace panel + stream inspector are special cases of this.

HARD (counterfactual):     itx.at(#128).fork().append(reply:"yes") → replay → diff
                           but the outside world isn't in the log, so it hits a wall at every egress.
Fit with the locked foundation.
Serves: R5 (everything is traceable — "show me the moment before it broke" becomes a verb) and follows straight from D3/D9 (state is a fold; reduced state is disposable). The read-only half is almost free.
Tension with: the counterfactual half — the external world isn't in the journal (D9 is explicit: you replay streams and resolve references, but effects that left the project are gone), and LLM nondeterminism smears the branches.
Needs first: checkpoint snapshots for cheap at() on long journals — engineering, not conceptual.
Feasibility — read-only half: high (falls out of "state is a fold"). Counterfactual half: hard (needs snapshots + a frozen world).
Value — high for debugging/support ("every incident report is an offset"); speculative for training.
Security — read-only is safe; the fork/replay path must keep egress jailed or it acts for real.
Cost @1M — replaying 10M events isn't free; needs snapshotting to be affordable.
DX / legibility — excellent as a debugger; "rewind to any moment" is instantly graspable.
Vision — high; the trace panel and inspector are just renderings of itx.at().

6-judge vote: SHELVE 4·1·1 — build the read-only rewind now; shelve the counterfactual engine.

Sharpest objection / failure mode. The deeper lie: the external world isn't in the journal, so counterfactuals hit a wall at every external call — you're replaying decisions against a frozen world, and LLM nondeterminism smears the branches. It's a divination tool, not a physics engine — sell (and build) it as the former.
Recommended: SHELVE — but the read-only rewind is the one thing I'd most want to prototype small, because it falls out of "state is a fold" almost for free and is a killer debug tool.
Where it lands: the read-only half becomes tooling serving R5 (a rendering of D9); the counterfactual engine stays off the roadmap until an exact-replay foundation exists. Not a new decision yet.
Your verdict recommended: SHELVE (build the read-only half)
The entity is a file A project is exactly (repo, streams, blobs). Tar those and you're holding the entire living entity — movable to another account, cloud, laptop, USB stick. 6-judge: SHELVE 4·1·1

What it is. The Smalltalk image done right: genome = repo (diffable, forkable, git), memory = streams (append-only, replayable), body = folds (disposable). The one missing piece to make it real: stamp every event with the config-repo commit that processed it, so replay is deterministic across self-modification.

what's literally in the tarball
acme.tar
├── repo/       the code (git: worker.ts, package.json)
├── streams/    the logs (/agents/*, /integrations/*, …)
├── blobs/      big files, by hash
└── lock.json   exact package versions + which code-hash processed each event
NOT inside: secrets, live Slack sessions, emails already sent.

Export-to-competitor becomes a product feature and the deepest trust argument: iterate is the only agent platform where a customer can pick up their whole entity and leave. That's the moat, not a risk.

Fit with the locked foundation.
Serves / IS: R10 (full durable state must be exportable — streams, git repo, referenced blobs — and a project must be able to run on its own dedicated deployment). This idea is R10 taken to its literal conclusion, plus D9 (two stores: streams + git; events reference bigger objects).
Respects: D10 — secrets correctly can't ride along; R1 — the tar is one project's state only.
Blocked by / needs first: exact replay — build keys currently re-resolve npm ranges and artifacts expire (30 days), so "old images replay forever" needs an immutable lock + longer retention. The codex salvage: downgrade "Organism Image" to an Organism Lock (a small immutable manifest + refs to shared signed artifacts + separate policy/grants/state), materializable into a tarball on export.
Feasibility — the export tar is feasible; bit-identical replay across self-modification needs immutable locks + toolchain retention.
Value — high; backups, staging, and "leave for a competitor" all become "replay the file."
Security — good; secrets excluded by design, one project's bytes only.
Cost @1M — the naive "immutable per-project image" is expensive; the Organism Lock is cheap (shared artifacts + tiny manifest).
DX / legibility — "your company is a tarball" is a great story once replay is exact.
Vision — the deepest trust moat there is; the founder judge's favourite.

6-judge vote: SHELVE 4·1·1 — real portability moat; needs exact-replay first (the skeptic voted kill on the "monolithic image" reading).

Sharpest objection / failure mode. The file holds state, not consequences — the sent emails and moved worlds aren't in the tar, only the receipts. And "portable" is only true if iterate/sdk is stable enough to be the entity's POSIX. The immutable-image reading collapses at 1M projects (relinking 12M unique executable graphs); the Organism Lock avoids that.
Recommended: SHELVE. A real north-star that R10 already commits us not to foreclose — but it needs the exact-replay foundation (Tier-1 facts + immutable build keys) first. Don't build the monolithic image.
Where it lands: stays a future feature satisfying R10; the concrete near-term step is the Organism Lock (stamp events with the processing commit + immutable package locks), which unblocks it. Not a new decision.
Your verdict recommended: SHELVE
The Last RPC A call is an ephemeral append; a workflow is a durable one. Retention is the only difference. capnweb stops being a transport and becomes a compiler. its endpoint is locked (D7/D3) 6-judge: SHELVE 4·0·2

What it is. Every invocation becomes an event — invocation-requested {path,args} appended, invocation-completed {result} appended back — and the only thing separating "RPC" from "durable workflow" is the retention flag on the row. The ephemeral event lane (already built) makes ephemeral-append-with-a-live-tail-subscriber into request/response at socket latency. Flip the flag and the same call becomes a replayable, audited durable workflow for free. capnweb becomes sugar that compiles itx.foo.bar(x) into appends and folds the completion back into a promise.

the entire difference is one boolean
quick call:  append EPHEMERAL {invoke:"getUser", args:[7]} → await {result} → row dropped
workflow:    append DURABLE   {invoke:"getUser", args:[7]} → await {result} → row kept forever
Fit with the locked foundation.
Serves / aligns with: D7 (one stream + processor abstraction does everything — db, queue, workflow, live streaming), D3 (event-sourcing purists), D11 (events are durable or ephemeral — which is exactly the retention flag this needs), and §2's "the events ARE the API." The endpoint — "in principle the only interaction is appending events" — is already the locked design.
Tension with: the honest failure mode below — a call needs timeouts, cancellation, streaming, backpressure; retention isn't the only real difference. So adopt it as a compiler, not a law.
Feasibility — the load-bearing piece (ephemeral lane) exists; making every call route through it is a large, risky refactor.
Value — high in principle (one mechanism for calls + workflows; replay/audit free), but only if the ephemeral lane is genuinely free.
Security — clean; "capability = the right to append to a path" is one invariant instead of a proxy + fallback chain + auth adapter.
Cost @1M — the danger zone: one slow fold on the hot path taxes every "call" in the project.
DX / legibility — mixed; debugging a promise pipeline through event offsets is its own hell.
Vision — pure; it's the most literal form of "history is the only substance."

6-judge vote: SHELVE 4·0·2 — beautiful, but the skeptic and cost judge voted kill on a literal "every call is an append" rewrite.

Sharpest objection / failure mode. Kafka-as-database syndrome. Chatty pipelined call graphs become journal choreography; you'd need the ephemeral lane to be genuinely free or this is a 10× latency regression wearing a philosophy costume. A call also needs timeouts, cancellation, streaming, backpressure — "keep it or not" isn't the only difference.
Recommended: SHELVE. Keep it as a way to compile calls into appends where it pays, not as a promise that a call and a workflow are identical — they aren't.
Where it lands: a mechanic under D7/D11 — capnweb-as-compiler over the append/fold substrate, applied selectively. Don't rewrite the whole invocation path onto the log as a law.
Your verdict recommended: SHELVE
Shadow selves — the journal is the fitness function Self-modification ships as a shadow fold: the mutated worker.ts relives the entity's real recent history, effects jailed, and is promoted only if its life would have gone at least as well. 6-judge: SHELVE 3·1·2

What it is. Everyone says "the agent improves its own code" and means "the agent edits a file and we pray." Instead: agent commits a mutation to a branch → builder produces a keyed artifact → a shadow processor subscribes to the live stream and replays the recent past with side effects intercepted → an LLM judge diffs shadow behavior against lived history → genome/promoted or genome/culled is appended, with the diff as evidence. Regression testing without tests, because the test suite is the entity's actual life. A foreign third-party processor auditions as a shadow before it's ever allowed to act.

Fit with the locked foundation.
Serves: B3 (AI-authored, self-modifying code — this is how you make it safe) and B4 (verification flips — humans review promotions with evidence attached, not diffs in the dark). Leans on D3/D9 (replay is free because state is a fold) and R11 (a third-party processor auditions as a shadow first).
Depends on: the egress jail (D6/D10) being airtight — the shadow's "I would have sent this email" must be capturable data, never a sent email.
Blocked by: exact replay (same prerequisite as "the entity is a file").
Feasibility — the primitives exist (fold-replay, egress intercept, requested/completed pairs); wiring them into a promote/cull loop is real work.
Value — high as a test tool; dangerous as an auto-promote button.
Security — the ship & security judges voted kill: one effect lane that doesn't route through egress and the shadow bites for real.
Cost @1M — replaying weeks of history per candidate is not free; needs snapshots.
DX / legibility — appealing ("checked it against real life") but the LLM judge's taste becomes the real fitness function.
Vision — the founder judge's build: natural selection over genomes, the soul of self-improvement.

6-judge vote: SHELVE 3·1·2 — ship + security voted kill (jail risk); founder voted build (the vision); the rest shelve.

Sharpest objection / failure mode. Move streams to userspace — the kernel razor, taken literally The kernel is only what userspace cannot express. A stream is a library on the seed — so move the ~12k-line streams domain out of the kernel. the razor is true; the move is rejected 6-judge: KILL (as a move) 4–2

What it is. The kernel razor (§6.12): the kernel is exactly what userspace can't express. Apply it honestly and a stream — durable ordered append + fold + delivery + alarms — is buildable in userspace given confined durable storage, wakeability, and fetch. The genuinely un-userspace-able part isn't the log; it's the confinement of the storage. So, the literal reading goes, the streams domain could move out of the kernel — which is most of how you'd hit a ~5k-LOC core.

The distinction that matters (from §6.14): the razor answers "where is the security wall?" (the seed). It says nothing about what the system IS. Streams being userspace-expressible makes them fundamental and portable, not minor — a linked list is expressible in userspace and is still the data structure. So: keep the true statement, reject the migration.

Fit with the locked foundation.
The statement serves: D2 (clarifies the kernel/userspace cut — the load-bearing wall is the seed, and everything above it is negotiable).
The move violates: R6 (assume any part can fail and recover uniformly — if streams are userspace, every processor re-implements crash-safety/at-least-once/park-revive), R4 (the substrate must carry real-time PCM — performance the kernel guarantees), D7 (one privileged stream abstraction does everything), B2 (the primary user is an LLM that shouldn't have to reimplement at-least-once). The log's correctness is exactly what must survive a broken userspace.
Status: the razor is a true, clarifying statement to keep; the literal code migration is rejected.
Feasibility — technically possible; the confinement of storage is the only truly un-userspace bit.
Value — negative as a move; it trades a working, correct substrate for purity.
Security — worse; the delivery/obligation correctness must hold even when userspace is the thing that crashed — so it can't be userspace.
Cost @1M — worse; every processor re-implementing at-least-once is a fleet-wide tax and a bug farm.
DX / legibility — worse; the LLM primary user would have to reimplement crash-safety to do anything.
Vision — the statement is clarifying (streams are fundamental + portable); the move adds nothing the razor doesn't already say.

6-judge vote: KILL as a code move 4–2 — ship/DX/skeptic/cost killed the migration; security & founder shelved. Nobody wanted to actually move it.

Keep it as a true statement, not a migration.
Recommended: KILL (as a move). Keep the razor as an analytic tool that tells you the security wall is the tiny seed; keep streams privileged by choice, with a public replacement seam. Don't move the code.
Where it lands: a clarifying line under D2/D7 ("streams are userspace-expressible but kept kernel-privileged by choice, for R4/R6"). The migration is ruled out. The hero framing (§6.14) also retires "kernel" as the hero noun in favour of "intelligent entity runtime."
