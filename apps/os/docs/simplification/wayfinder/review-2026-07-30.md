# Whole-map review — self-hosting the kernel

A step-back review of where the design landed after this session's sweep. Annotate freely — I've put
explicit questions at the end, but comment anywhere. Detail lives in the `wayfinder/` folder
(`DECISIONS.md`, `topologies-and-axes.md`, the `questions/` tickets, `phase-0-runbook.md`); this is the
one-page shape.

---

## 1. The destination

A **clean-room lab in `apps/kernel`** where each deployment permutation is a minimal, runnable, provable
profile — skeletal but structurally real (real DOs, real bindings), the beginning of a future rewrite.
Not productionising `apps/os` yet; that's a later track.

---

## 2. The architecture in one picture

- **The runner = `ProjectWorkerEntrypoint`** — one props-parameterised `WorkerEntrypoint` class. It's
  what every dynamic userspace worker binds to as `env.ITX`, and it can be the default export of a worker.
  = **compute** (runs the loaded userspace) + **data** (the DOs) + its **own local bindings**.
- **The control plane = the network edge** — authentication (the wall) · ingress routing · webhook
  ingress · **egress** · email · **MCP**. Holds no project data.
- **One worker for now** (loader + entrypoint must be co-located via `ctx.exports`); the two roles are
  logical, the split is deferred but cheap (clean seam = the ITX/`authenticate` interface).
- **Reach is a binary:** Workers RPC to a **loopback** binding (co-located) OR **capnweb over HTTP** (a
  public hostname). **No NAT dial-out** — a homelab makes itself findable with a tunnel.
- **Egress always flows through the control plane** — the project worker never touches the public
  internet directly.

---

## 3. The four archetypes

The two **ends** are the same shape (control plane + project worker co-located, loopback), opposite
owners. The two **middles** are "your project worker, our control plane, over capnweb/HTTP."

| axis                             | **iterate-hosted**       | **project worker · your CF account** | **project worker · your box** | **self-hosted**               |
| -------------------------------- | ------------------------ | ------------------------------------ | ----------------------------- | ----------------------------- |
| control plane                    | ours                     | ours                                 | ours                          | **yours**                     |
| project worker runs              | our account (co-located) | your CF account                      | your box (Miniflare + tunnel) | your account/box (co-located) |
| CP → project worker              | RPC **loopback**         | **capnweb/HTTP**                     | **capnweb/HTTP**              | RPC **loopback**              |
| `env.AI` / `env.ARTIFACTS` / DOs | our account              | **your** account                     | **your** box                  | your account/box              |
| egress leaves via                | our CP                   | our CP                               | our CP                        | your CP                       |

So the whole lattice is **two reach mechanisms + config**. iterate-hosted and self-hosted need zero new
transport; capnweb is only "reach someone else's worker." _(Cell = one account per project = a stretch
variant of the same, parked.)_

---

## 4. The capability model

A capability has **three orthogonal properties** (we'd been conflating them):

1. **Presence** — _does it exist here?_ **Environment-determined** (ADR 0021). Slack/metered-AI exist
   only if the control plane wired them. Config, not a code fork.
2. **Sourcing** — _where is it served from?_ (deferred). Local binding vs remote proxy. For now bindings
   just **follow the project worker**.
3. **Shadowing** — _what does a name resolve to?_ **Config-shadow** (trusted, may override a builtin) vs
   **event-shadow** (userspace `provideCapability`, fallback-only, never shadows a builtin).

Plus: **storage-shaped** capabilities (streams/repos/secrets/files DOs) _follow the worker, never
sourced_; **service-shaped** (ai/egress/browser) are the sourceable ones. And the standing constraint:
**no `rpc-targets` god-object** (today it's 7,667 LOC / 87 imports; even leaf DOs import it — the rewrite
must not reproduce that).

## 5. Dimensions swept this session (each grounded in real code)

| dimension                    | where it landed                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Routing / DNS** (ADR 0020) | Ingress = a `hostname → {projectId, app}` table. Wildcard base optional: **single-project self-host needs no wildcard** (control plane on `workers.dev`, one explicit routing row for the one domain). We provide `*.iterate2.app` for the three control-plane-is-ours archetypes. **Gap:** the routing table isn't built (kernel only slug-parses) — that's M2.                       |
| **Email**                    | Rides the **same base domain** as HTTP ingress (`emailDomainForDeployment = projectHostnameBases[0]`) — **no extra domain burn**. Escape hatch: a shared `mail.iterate.com` even in self-host. Outbound = Cloudflare `send_email` (paid plan — accepted).                                                                                                                              |
| **Integrations** (ADR 0021)  | Slack etc. are control-plane concerns (OAuth receiver at the CP host; one Slack app per deployment). Two metered-secret lanes, **but only the Secret-DO lane meters** — the platform-key lane (Exa/Parallel) has **no metering** (a real gap). Presence is ad hoc today; needs one shared `requirePlatformIntegration()` primitive.                                                    |
| **MCP** (ADR 0022)           | Deliberately control-plane (creates projects, spans projects). Today os uses a bespoke `auth.iterate.com` OAuth resource-server — **not** the wall, **no** wide-open mode; kernel has **no `/mcp`** at all. The kernel **wall simplifies it**: Access-fronted (Managed-OAuth→wall) and no-auth `/mcp` both fall out. Battery: prove unauth + auth per topology, incl. Miniflare-local. |
| **Dev modes** (ADR 0023)     | `pnpm dev` means two things: **project-worker-only** (behind our CP) vs **full-stack** (your own CP, the Pi floor). Disambiguate.                                                                                                                                                                                                                                                      |

## 6. The build plan

- **Phase 0 — topology playbook** (`phase-0-runbook.md`): stand up each archetype, prove ingress + auth +
  confinement + **MCP** (unauth + auth), across our account / a separate account / Miniflare. Mostly
  _writing a repeatable harness_ over profiles that already work; the one new thing is **deploying to a
  separate account** (Jonas personal `05958…`, domain `iterate-e2e-test-custom-cloudflare-domain.com`).
- **Phase 1 — streams prove the reach paths**: reuse the stream **engine** verbatim (~1,750 LOC, cleanly
  factored) behind a thin kernel-owned `StreamDurableObject`; wire `streams` into the ITX tree; then
  prove loopback then **capnweb-over-HTTP** with real events crossing the wire.
- **Phase 2 — the capability tree, natively** (no god-object): repo, capability host, dynamic-worker
  building, the presence primitive, config-shadowing sourcing. "Break up the RPC targets" done properly.

---

## 7. Open frontier / known unknowns

- **The capnweb serve/streaming lane** — HTTP serving can't ride RPC method-replay (what #2156 removed);
  needs a dedicated streaming fetch adapter. The Phase-1 risk.
- **The routing table (M2)** — not built; needed for custom domains + single-project self-host.
- **The metering gap** — platform-key egress lane doesn't meter; must close for "metered first-party
  secret."
- **Presence mechanism** — absent-getter vs typed-"unavailable"; one shared primitive.
- **MCP kernel build** — reserved `/mcp` route + auth-via-wall + config-driven URLs.
- **Dev-mode CLI shape** — how the two `pnpm dev` modes are actually invoked.
- **Parked:** account-per-project (Cell), data migration, multi-user self-host, versioning/upgrades.
