Design proposal · apps/os · approval required

References that survive the composer

Brief

Let a user select config-repo files from @ suggestions, render the selections as inline pills, store resolvable references in the user message, and materialize the selected file contents before the agent’s first LLM call. The same mechanism should later support people, streams, agents, and slash commands.

1 Message API
2 Durable events
0 Extra LLM turns
1 Extensible codec
Proposed decision

A mention is a typed inline reference, not an attachment and not merely decorated text. Persist versioned nodes beside a required plain-text projection. The server derives refs, resolves immutable targets, and durably records the bounded result before scheduling one model turn.

Resolve A missing or unreadable target marks the sent pill with a warning and gives the model an explicit resolution result.
02

One flow from keystroke to model context

Solid arrows are durable message processing; dashed arrows are repository queries.

What touches the Artifact?

Search and resolution both use the Repo Durable Object’s lazy HEAD snapshot and durable head-tree cache. Resolution asks that same object for { path }, deliberately meaning the latest committed version when the message is processed.

Why two events?

The user event is the transcript and does not trigger. The processor commits the exact resolution outcome next. That second event triggers one model call, making retries fold the same bytes instead of re-reading mutable external state on each attempt.

content

Required, immutable, searchable fallback. It must equal the concatenation of text and reference display values.

richContent

Owns inline placement, occurrence identity, display text, and the typed target. Unknown or invalid data falls back to content.

refs

Server-derived retrieval coordinates for processors and agents. They never determine where a pill is rendered.

const configFileProvider: ComposerSuggestionProvider = {

  trigger: "@",
  cacheKey: [projectId, "/repos/config"],
  async search(query) {

    return paths.map((path) => ({

Editor implementation

Use the already-installed CodeMirror 6 client bundle with atomic reference ranges and decorations. Keep it behind the same lazy browser-only import pattern as the existing code editor to avoid increasing the Worker bundle. The parent owns nodes, not raw editor ranges.

Extension rule

Adding people, streams, or agents means adding a target variant, one provider, one resolver, and one rendering label. It does not add another composer or message API. Slash commands share the provider registry but complete as text/actions, not refs.

06

Risks and explicit outcomes

A reference starts a turn before its file is committed
High
The source event never triggers; its blocked, idempotent materialization append is the only trigger.
Repo changes between selection and resolution
High
Latest is the explicit product contract. The derived event records the resolved OID and exact bounded bytes before the model request exists.
Large or binary files flood model context
Medium
Text detection, per-file and total budgets, explicit truncation metadata, and one classified outcome per occurrence.
Rich editor increases server bundle
Medium
Load CodeMirror only in a browser client module, matching the existing CodeEditor wrapper.
New clients write data old clients cannot decode
Low
The canonical plain projection is always present; invalid/unknown nodes become ordinary text, never dropped content.
07

Decisions to annotate

Which config-file version does a mention resolve?

Decision: latest. The durable target intentionally omits an OID. Resolution records the exact OID and bytes in the derived event, so subsequent model retries remain deterministic.

Accepted: latest

What are the first materialization budgets?

Recommendation: 64 KiB of decoded text per file, 128 KiB across one message, with explicit truncation metadata. The values should be configuration constants covered by tests.

Proposed default: 64 KiB / 128 KiB

Should duplicate mentions duplicate file content?

Recommendation: preserve every occurrence in richContent, derive every occurrence outcome, but read and materialize each unique coordinate once for the model.

Accepted: deduplicate bytes

Should a typed but unselected @path become a reference?

Recommendation: no. Only a selected candidate has server-verified identity; raw @text remains plain text.

Proposed default: selection required
Acceptance checklist
CodecRepeated identical mentions round-trip with distinct occurrence IDs; projection mismatch and unknown versions visibly fall back.
ServerThe message boundary rejects forged paths, derives refs, resolves under project authority, and schedules exactly one request.
RetryThe same requested event always folds identical materialized bytes even after config HEAD moves.
CacheLatest reads use the Repo DO’s verified lazy HEAD snapshot and bounded fallbacks; the Artifact is not the steady-state read path.
UIKeyboard, pointer, touch, IME, copy/paste, atomic deletion, screen reader labels, and narrow mobile layouts work.
FailureMissing, denied, binary, oversized, and failed reads are classified and observable; no reference silently vanishes.
