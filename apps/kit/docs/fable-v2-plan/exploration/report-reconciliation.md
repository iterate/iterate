## 2. Prose on the interesting rows

### 2.1 The report's biggest blind spot: `AFE_TYPE_FD` doesn't exist in it

The report's DSP recommendation (KF-2b, D§3-1) is "use the VC profile — the one
you want for full-duplex calling." Live esp-sr v2.4.6 has a _fourth_ type,
`AFE_TYPE_FD` — "full-duplex conversation, linear + nonlinear, tuned for
barge-in" — added in 2.4.3 (2026-04), i.e. after the report's training
horizon. Espressif's own AEC doc recommends `AEC_MODE_FD_LOW_COST` as the best
balance, and its feed-side CPU is less than half of VC's (12.1 % vs 30.6 % in
the full-AFE table). Our plan already stands on FD_LOW_COST (PLAN Stage 5,
G13, brief hard constraints). The report's advice here is not wrong so much as
generationally stale — and it is the clearest demonstration of why its
self-declared "verify before committing" caveat was warranted.

### 2.2 The flash-stall rule is real — and stronger than the report says

The report claims flash writes "disable the flash cache, stalling any non-IRAM
code." The official mechanism (`spi_flash_concurrency.rst`, v5.5.3) is more
drastic on multi-core chips: during any SPI1 flash operation (OTA write, NVS
commit, SPIFFS/FATFS-on-flash I/O), the APIs **suspend all other tasks, park
the other core in a busy-poll loop, and disable every non-IRAM-safe
interrupt** until the operation completes. That means an NVS commit freezes
the core-1 audio owner _entirely_, no matter how it's coded; only IRAM-safe
ISRs (our I2S ISR qualifies — v1 sets `CONFIG_I2S_ISR_IRAM_SAFE=y`) keep
running. Three consequences for the plan:

1. **Rule** (D-level, applies to stages 2/4): no NVS writes, no OTA, no
   flash-filesystem I/O while an audio session is active. The D5 boot counter
   is written at boot; provisioning writes happen outside sessions; deferred
   flash writes queue behind session teardown.
2. **SD logging is exempt**: the Waveshare SD path is native SDMMC (verified
   pins CLK=2/CMD=1/D0=3), a different bus — the concurrency constraint
   explicitly applies only to SPI0/1. Stage 4's "write logs while nobody is
   listening" does not conflict with live audio.
3. **Escapes exist if the rule must ever break**: flash auto-suspend
   (`CONFIG_SPI_FLASH_AUTO_SUSPEND`, S3-capable but flash-chip-dependent) and
   XIP-from-PSRAM (§2.4).

### 2.3 The Wi-Fi IRAM options: the report has the sign backwards for us

`CONFIG_ESP_WIFI_IRAM_OPT` and `CONFIG_ESP_WIFI_RX_IRAM_OPT` (the report's
`ESP32_`-prefixed spellings are the pre-v5 names, now deprecated aliases) are
already **on** in v1 — they're IDF defaults. Since our image has exactly one
byte of IRAM free, "enable them" is a no-op; the actionable insight is the
inverse: these two options are among the largest single IRAM consumers, so
they are the documented **emergency IRAM-reclaim lever** (trading Wi-Fi
throughput) if Stage 1's headroom chore comes up short. That option should be
recorded in the Stage 1 IRAM audit, not exercised blindly — Wi-Fi RX
throughput protects the PCM lanes.

### 2.4 SPIRAM XIP: reconciling the report's caution with Voice PE's YAML

The report says avoid `SPIRAM_FETCH_INSTRUCTIONS`/`SPIRAM_RODATA` ("running
code from PSRAM hurts real-time"). HA Voice PE's shipped YAML enables both.
Both positions are rational because the feature trades two different risks:

- **Cost**: instruction/rodata fetches now compete with data traffic on the
  PSRAM bus — the exact contention the report warns about.
- **Benefit** (the half the report misses, straight from the Kconfig help and
  the concurrency doc): with both enabled, code no longer needs IRAM residency
  to survive flash operations, and the flash APIs **stop disabling the caches
  altogether** — OTA/NVS during playback stops being an outage. It also
  relieves IRAM pressure (the 1-byte problem) because flash-safety stops being
  a reason for `IRAM_ATTR`.

Voice PE can afford the PSRAM contention because its hard-realtime DSP lives
on the XMOS; the ESP32 just shuttles pre-cleaned audio. On our S3 boards the
AEC math will live on-chip, so the contention cost is real. Disposition:
keep both options **off** as the default (v1 already has them off), and add a
bounded **Stage 1 experiment**: enable `CONFIG_SPIRAM_XIP_FROM_PSRAM` (the
helper that selects both) on a rig build, measure IRAM freed and
tone/PRBS/endurance regression, and record the verdict in the plan. If it
passes, it retires both the flash-stall rule and part of the IRAM crisis at
once; if it fails, the rule from §2.2 stands. Prerequisite either way: bump
PSRAM from 40 MHz to 80 MHz (§3 item 3) so the experiment isn't handicapped.

### 2.5 What v1's sdkconfig already gets right (report's Stage-2 bundle)

Verified against the effective `sdkconfig` (read-only): Wi-Fi task pinned to
core 0 (default), both Wi-Fi IRAM opts on, task WDT on (5 s, both idle tasks),
octal PSRAM on, `I2S_ISR_IRAM_SAFE` on, FreeRTOS runtime-stats counters
compiled in, ISR→task handoff already via direct-to-task notification
(`m5sticks3_direct_audio.cpp:304`). The genuinely missing pieces from the
report's load-isolation bundle are exactly three: lwIP affinity (unpinned
today), the flash-write rule (§2.2), and the PM-lock tripwire (moot today,
PM disabled). Everything else in that bundle is either already in v1 code, in
PLAN stages 1–2 (capture off the main task, event-driven wakeups), or is an
experiment to run on the rig rather than a config to flip.

### 2.6 P4+C6: does our hardware-plugability design preclude it?

No. Checked against the plan's interfaces: portable `components/` have zero
platform includes (grep-verified in the review §2.1); every hardware surface
is a caller-owned vtable wired at init by the composition root
(`exploration/hardware-plugability.md` — no runtime discovery, no
chip-family assumptions); per-board profiles are plain data with capability
flags (PLAN Stage 3). The Wi-Fi side lives in `platforms/iterate_esp_idf/`
(`wifi_station.c` on `retry_gate`, Stage 1), and ESP-Hosted on a P4 host
presents the standard `esp_wifi` API via `esp_wifi_remote` — so even the
platform layer largely carries over; a P4+C6 board is a new `devices/` +
`platforms/` composition, which is precisely the extension point the design
sells. The one budget-level difference: SDIO transport latency would need its
own line in the latency budget doc. No plan change needed; recorded as a
future board class in §4.3.
