## 1. Module inventory

### 1a. `vendor/capnweb` — bounded C99 Cap'n Web peer (~3.0k LOC src, 451-line public header)

A vendored, first-party ("Copyright (c) 2026 Iterate", MIT) allocator-independent Cap'n Web implementation, not a wrapped third-party library. `vendor/capnweb/README.md` describes it as "a compatibility profile, not a second full runtime": supported messages are `push`, `pull`, `resolve`, `reject`, `release`, `abort`; supported expressions are JSON scalars/arrays/objects, exported capabilities, pipeline calls, and a bounded `bytes` form. Explicitly unsupported: `stream`, pipe/Blob streaming, imported expressions in inbound calls, calls queued on unresolved results. A typed known-failure ledger lives in `apps/kit/firmware/__tests__/c-interop-known-failures.ts` and an interop test drives the compiled C peer against the real `@iterate-com/capnweb` TS runtime.

- Public API: single header `vendor/capnweb/include/capnweb/capnweb.h`. The session (`capnweb_session`, init at :288) takes _all_ storage via `capnweb_session_options` (:251–275): caller-allocated `pending_calls`, `exports`, `imports`, JSON `tokens` scratch, and a small `output_buffer` used only to coalesce outbound DATA fragments. Exhaustion is `CAPNWEB_E_LIMIT`, never heap growth.
- Values are borrowed token-tree views (`capnweb_value`, :109–114) valid only during a dispatch/completion callback. Outbound text is emitted as BEGIN/DATA/END fragments through one `capnweb_send_text_fn` (:152); a transport failure mid-message is terminal by design (:141–145 comment).
- Calls: `capnweb_session_call_path/_call/_call_expressions` (:401–426) with a completion callback; replies via `capnweb_reply_*` / deferred `capnweb_responder_*` setters; capability export/release with explicit single-owner transfer semantics (:428–445).
- Files: `session.c` (1010 LOC — session state machine, terminalization, import notification), `json.c` (479 — bounded tokenizer), `value.c` (431), `expression.c` (344 — expression serializer), `writer.c` (225), `call.c` (215), `responder.c` (149), `reply.c` (127).
- Depends on: libc only. Everything above depends on it.
- Built three ways: host static lib via `vendor/capnweb/CMakeLists.txt` (with optional ASan/UBSan and a fuzzer), ESP-IDF component via `idf-components/capnweb/CMakeLists.txt` (which registers the same vendored sources), and standalone with the TS interop suite (`pnpm --dir apps/kit firmware:test:capnweb`).

### 1c. `components/capabilities` — reusable Cap'n Web capability modules (~2.6k LOC)

IDF component `capabilities` / host lib `iterate-kit-capabilities`, `REQUIRES core`. Each module exposes an `iterate_kit_module` (method table + poll/close/session_ended) and a `_init` that borrows caller storage:

- **`metrics`** (1510 c / 391 h — the largest file in scope). Three methods: `subscribeToMetrics`, `subscribeToPlaybackMetrics`, `getDiagnostics` (`metrics.c:1496–1500`). Latest-state subscription scheduler: samples the driver once per interval, builds a capnweb expression tree in a ≤4 KiB stack workspace (`metrics.c:129–175` `_Static_assert`s), fans one coherent sample to all ready subscribers, never overlaps calls to a callback, drops dead subscribers instead of retrying (`metrics.c:1224–1243`). `getDiagnostics` snprintf-formats a retained control-transport incident into a caller-owned 1536-byte buffer with truncation treated as a schema defect (`metrics.c:1054–1206`), guarded by a one-in-flight latch (`metrics.c:1027–1035`).
- **`device_event_stream`** (529/100). Single-subscriber `subscribeToEvents` push stream of push-to-talk edges with boot-local sequence, a coalescing bounded queue that replaces the newest entry on overflow and counts it (`device_event_stream.c:90–108`), and a post-subscribe state snapshot notification (:159–178).
- **`push_to_talk`** (83/36). `pushToTalk.start/stop` → publishes into the shared `device_events` queue rather than calling audio directly, so remote and physical edges share one total order (`push_to_talk.c:7–13`).
- **`leds`** (127), **`servos`** (90), **`screen`** (78), **`camera`** (92): thin validated RPC → synchronous driver-vtable adapters. Servos copy their limit snapshot at init to freeze the safety envelope (`servos.c:65–69`); camera is an ownership boundary transferring a driver-produced frame into `capnweb_reply_set_bytes` with exactly-one-release semantics (`camera.c:52–59`).
- **`callback_budget`** (43/48). Trivial in-flight counter shared across modules to bound the total concurrent outbound callback burst; underflow is a latched module failure, not a clamp (`callback_budget.c:29–43`).
- **`rpc_internal`** (63/26, private header). Shared status→RPC-error mapping (`iterate_kit_reply_status`) and strict argument readers, keeping "hardware rejected the arguments" vocabulary uniform across modules.

### 1d. `devices/` — composition roots (m5sticks3 284 LOC, stackchan 131 LOC)

`devices/m5sticks3/m5sticks3.c` is explicitly "a composition root, not an M5 hardware driver" (:5–17). It wires five modules in a fixed order — event_stream, metrics, screen, push_to_talk, audio (`m5sticks3.c:158–165`, count fixed by `ITERATE_KIT_M5STICKS3_MODULE_COUNT = 5` in the header) — around one device event queue whose handler drives the audio controller and whose observer mirrors into the event stream (:41–87). It also embeds the static `__describe` JSON description (:18–33). Depends on capabilities + core; zero platform includes.

### 1e. `platforms/iterate_esp_idf` — ESP-IDF adapters (~3.6k LOC)

- **`itx_transport.c`** (1624). The control-plane scheduler. Three execution contexts (:14–35 comment): ESP-IDF Wi-Fi/IP event callbacks publish only atomic flags (`wifi_event`/`ip_event`, :385–428); one statically-allocated network task pinned to core 0, priority 5, owns the socket, reconnect policy and all I/O (`network_task`, :707–907); the application task alone parses capnweb and dispatches device code (`_poll`, :1167–1408). Handoff is exclusively the two SPSC rings + acquire/release `uint32_t` flags. Reconnects are _generation_ replacements: five generation counters (`socket_generation`, `accepted_`, `ready_`, `handled_`, `protocol_failure_generation`) implement a handshake in which the network task refuses to send an outbox built for another epoch (:608–620), READY is published only after mount so a handshake alone cannot reset backoff (:738–748), and `protocol_failure_generation` is monotonic and never cleared (`esp_idf_itx_transport.h:179–186`). Also owns Wi-Fi bring-up: NVS init/erase, netif/event-loop, WPA config, `WIFI_PS_NONE` for voice latency (:1010–1164), and a rich atomic metrics snapshot (:1489–1603).
- **`websocket_connection.c`** (685). "Taskless" lower WebSocket: uses ESP-IDF `esp_transport` for DNS/TLS/HTTP upgrade only, then sets `O_NONBLOCK` + `TCP_NODELAY` on the raw descriptor (must succeed or the connection is rejected, :301–334), and drives the portable `websocket_tx`/`websocket_rx` over zero-timeout `esp_transport_write/read`. TLS `WANT_READ/WANT_WRITE` map to WOULD_BLOCK, not disconnect (:209–222). PONG/CLOSE replies are queued into the tx control slots, never written inline from the receive path (:539–556). Uses the private `esp_transport_get_socket` symbol (:49–55).
- **`itx_transport` header** (386 lines) documents the full cross-task contract; **`esp_idf_websocket_policy.h`** (139) centralizes shared control/PCM constants with C99 negative-array-size compile-time proofs of deadline ordering (:66–109) and pins PCM network priority = control + 1 (:36–52).
- **`configuration.c`** (137). Reads the `iterate_kit` custom flash partition (type 0x40) via `esp_partition_mmap`, feeds the portable decoder, zeroes on any failure (:60–65).
- **`pcm_transport.c`** (1181) — PCM twin of itx_transport (out of scope). **`idf_overrides/tcp_transport/`** — an ESP-IDF component _override_ that applies guarded, exact-match source patches to upstream `tcp_transport` (whose WebSocket reader treats a nonblocking payload stall as end-of-frame); a mismatch after an IDF upgrade fails at configure time (override `CMakeLists.txt:1–13`).

### 1f. `simulator/` (~900 LOC) and `targets/m5sticks3/main/main.cpp` (1349)

The simulator is "a deterministic control-plane model … deliberately does not synthesize sound or imitate I2S/DMA/FreeRTOS/WebSocket buffering" (`simulator/devices/m5sticks3.cpp:10–23`): a stdio runner drives the real device profile + peer synchronously. `main.cpp` is the target composition: all storage static (`runtime` struct), boot order provision→rings→device→connection→transport-start (:1149–1170), then a single cooperative main loop (device poll → button edge → itx transport poll → PCM transport poll → playback status), with PCM started only after first control READY (:1259–1283).

## 2. Layering as it actually exists

Four clean strata, enforced by both include direction and the two build systems:

1. **Vendor portable**: `vendor/capnweb` (libc only).
2. **Portable core**: `components/core` → capnweb. **Verified: no file under `components/`, `devices/`, or `vendor/` includes any `iterate/kit/platforms/*` or `esp_*` header** (grep returned zero hits). The only ESP mentions in core are comments (e.g. `websocket_text.h:63` describing the ESP-IDF event API shape the ingress contract was designed for).
3. **Capabilities** → core (+capnweb via `rpc_internal.h`); **devices** → capabilities.
4. **Platform** (`iterate_esp_idf`, `iterate_m5unified`) → core + ESP-IDF; **target** (`targets/m5sticks3`) → everything.

`#ifdef` hygiene is excellent: the only conditionals in portable code are `__cplusplus` extern-C guards; there is no `#ifdef ESP_PLATFORM` anywhere in core/capabilities.

Where the layering is _softened_ rather than violated:

- **Audio lives inside the same component as networking.** `components/core` is one library containing both the WebSocket/capnweb stack and the entire PCM lane (`pcm_lane.c`, `pcm_uplink_*`, `audio.c` — ~2.7k LOC). Files are disjoint, but the component boundary isn't: you cannot link the control stack without the audio lane, and `device.h:4` includes `audio.h` so even the type-erased device concept carries `iterate_kit_audio_mode`. Conversely the network modules themselves stay audio-free (websocket_tx/rx/text never mention PCM except in comments); `pcm_websocket.h` is just wire constants.
- **Platform error domains leak upward into the portable capability schema — deliberately.** `iterate_kit_control_diagnostics_sample` (`capabilities/include/.../metrics.h:134–165`) carries `last_websocket_tls_error`, `last_websocket_handshake_status_code`, etc., with the comment "the remaining integer domains deliberately mirror ESP-IDF rather than inventing a lossy common error code in the capability layer." The struct even preserves dead fields from the abandoned managed-client design that "remain zero" under the current taskless adapter (`esp_idf_itx_transport.h:144–158`). This is documented and honest, but it means the portable capability schema is shaped by one platform.
- **`websocket_policy.h` (platform) includes a core PCM header** (`esp_idf_websocket_policy.h:4` includes `pcm_uplink_conductor.h`) so control-transport code that includes the policy header transitively pulls audio-lane types — a small control↔audio coupling at the platform layer.
- Root host `CMakeLists.txt:180–183` adds `-UNDEBUG` globally _after_ library definitions with the comment about MinSizeRel asserts — a build-level subtlety, not a layering issue, but it applies to all subsequently defined targets only.

## 3. itx/capnweb RPC surface, capability mounting, metrics/diagnostics wiring

**The RPC stack, bottom-up on device:**
`esp_transport` (TLS) → `websocket_connection` (nonblocking framing via portable tx/rx) → network task in `itx_transport.c` → `websocket_text_inbox/outbox` over two SPSC rings → application task: `itx_transport_poll` → `itx_connection_receive_text` → `capnweb_session_receive` → `peer.dispatch` → capability module → reply/responder → capnweb `send_text` → `itx_transport_send_text` (`itx_transport.c:987–1008`) → outbox ring → network task write. capnweb never blocks on the socket (fragments are assembled directly into a reserved ring slot; only END publishes, `websocket_text.c:370–388`), and the network task never executes device code (`esp_idf_itx_transport.h:83–90`).

**Mounting** (`itx_mount.c`): sequential, non-pipelined by explicit decision (:347–351): `authenticate({type:"project-secret", projectId, secret})` on the bootstrap capability → session capability → `projects.get(projectId)` → project capability → `provideCapability({type:"live", path, capability, flattenNestedPaths:true, instructions?, types?})` → provision capability. Each stage sheds the previous remote handle (:281–294); in READY only the provision handle is held — it is the revocation handle. Failures carry a two-dimensional classification (semantic stage enum × capnweb status, :54–68). No retry inside the mount; retry belongs to a fresh connection generation (header :68–74). `flattenNestedPaths` exists because an exported capability is a path proxy, not an object tree — the OS-side host preserves the full dotted path as one `invokeCapability({path, args})` envelope, which `peer.c:159–207` unwraps allocation-free into the same static method table, with explicit defense against recursive envelope unwrapping (:202–206).

**itx_connection** is the ownership seam between transport and protocol: `open()` after socket connect (advances a diagnostics `generation`, hard-fails at UINT32_MAX rather than wrap, `itx_connection.c:130–139`), `lost()` for network death (local teardown, no writes), `close()` for deliberate shutdown (releases the provision while writable) — the header explains why merging these paths is wrong (`itx_connection.h:54–66`). `session_ended` fires exactly once per generation after capnweb settles callbacks (:41–57) and fans out through `peer_session_ended` → each module's `session_ended`, which drops session-scoped imports without touching hardware (`peer.h:44–58`).

**Metrics/diagnostics wiring — three parallel paths:**

1. **Cap'n Web pull/push** (`capabilities/metrics.c`): platform supplies a synchronous `iterate_kit_metrics_driver.sample()`; the module samples only when a subscriber can accept, builds expressions on the stack, and delivers via callback capabilities under the shared `callback_budget`. `getDiagnostics` returns the retained latest control-transport incident so the _replacement_ session can explain why its predecessor died (`metrics.h:123–133`).
2. **Console exporter** (`core/runtime_diagnostics.c`): owner-built snapshot → three fixed-format lines (system/control/pcm families) pumped through a nonblocking byte sink with a per-call byte budget — for physically-attached endurance evidence, fully independent of the network.
3. **Raw platform counters**: `iterate_kit_esp_idf_itx_transport_metrics()` (atomic snapshot, `itx_transport.c:1489–1603`) and `websocket_connection_metrics`/`websocket_tx_metrics`/`spsc_ring_metrics` feed both of the above via the platform's sampler.

**Separability verdict:** metrics/diagnostics are cleanly separable from the transport in the _mechanism_ sense — the transport never calls into metrics; producers only bump owner-local atomics, and samplers pull. The capability module is generic over a driver vtable. What is _not_ separable is the schema: the capability-layer sample struct hard-codes the ESP transport's field inventory (see §2), and the same field families are duplicated by hand in three shapes (transport metrics struct, `runtime_diagnostics_snapshot.control/pcm`, `control_diagnostics_sample`) that must be kept in sync manually.

## 4. Concurrency model

**Tasks on the real target** (from `main.cpp:35–52` and platform code):

- **Application task** (`app_main` loop): device events, all capnweb parse/dispatch, capture submission, transport `poll()`s. Sole owner of session/mount/peer/module state.
- **Control network task** `iterate-net`: core 0, priority 5, statically allocated stack (`itx_transport.c:1135–1148`), sole owner of the control socket; woken by `xTaskNotifyGive` with a 20 ms timed-poll liveness floor and bounded per-pass budgets (`NETWORK_RECEIVE_BURST=8`, `NETWORK_SEND_BURST=4`, :36–83).
- **PCM network task**: core 0, priority 6 (one level above control — a deliberate, physically-motivated lane priority, `esp_idf_websocket_policy.h:36–52`).
- **Audio playback owner**: core 1, priority 19 (m5unified direct-I2S layer; out of scope).
- ESP-IDF system tasks (Wi-Fi, event loop); Wi-Fi/IP callbacks only store atomic flags and wake the network task (`itx_transport.c:392–414`).

**Cross-task primitives:** exactly two kinds — SPSC rings (payloads) and word atomics (flags/counters). The ring uses release-store on the producer sequence as the sole publication point and acquire-load on the consumer side (`spsc_ring.c:152–166` with the comment explaining why weakening it is wrong). Lifecycle flags in the transport use acquire/release (`itx_transport.c:85–104`); diagnostics counters are relaxed saturating increments/maxes, and `atomic.h:22–32` documents _why_ relaxed is sufficient for them and forbids extending the API ambiguously. There are no mutexes, no allocation, no blocking anywhere above the ESP handshake.

**Documented vs implicit boundaries:** unusually well documented. Every struct states its owner (`websocket_tx.h:82–101`, `esp_idf_itx_transport.h:165–189`, `metrics.c:16–20`, `device_events.h:75–85`). The generation-ordering argument (store status before generation publication so a snapshot can't pair new generation with old status) is written down at `itx_transport.c:352–371`. The subtle points that remain _convention-only_: (a) capnweb's session is single-threaded purely by the "callers must serialize" sentence in `capnweb.h:292–295`; (b) the `iterate_kit_device_event_queue` is not ISR-safe and relies on platforms marshalling GPIO edges onto the owner task — stated in the header but unverifiable by the compiler; (c) `websocket_tx`'s "exactly one caller/task owns this object" while its metrics fields are read cross-core — safe today because the itx network task both owns tx and services control, but nothing structural prevents a second caller.

**Backoff:** WebSocket reconnect uses the portable `retry_gate` (250 ms → 30 s, policy header :62–63); Wi-Fi reconnect uses a hand-rolled doubling backoff inline in the network task (see smell list).

## 5. Configuration

Three distinct tiers:

1. **Provisioning (runtime, per-device, flash):** the `ITERKIT1` TLV image on a custom partition — Wi-Fi SSID/password, OS base URL, project id, project API key — written by the shared CLI/web flasher, decoded by the portable `configuration.c` (magic/version/CRC32/duplicate-tag checks, transactional zero-on-failure). Field capacities are fixed enums (`configuration.h:11–28`) so decoding never allocates; the same decoder runs in host tests and in the browser-flasher pipeline (`configuration.c:44–50` keeps CRC portable for that reason). Unprovisioned boot is terminal for the boot ("Needs provisioning", `main.cpp:1128–1146`). WS URLs are derived (`https→wss` + `/api` or `/pcm`).
2. **Policy constants (compile-time, shared):** `esp_idf_websocket_policy.h` — retry ranges, PCM barrier/ping deadlines, task priorities — with compile-time relationship proofs; message-size ceilings like `ITERATE_KIT_ESP_IDF_CONTROL_MESSAGE_CAPACITY = 2048` and stack sizes in `esp_idf_itx_transport.h:43–58`.
3. **Profile storage (compile-time size, init-time wiring, per-device):** every module takes caller-owned arrays through its options struct (ring slots, subscription slots, event storage, diagnostics buffer, URL scratch). The _sizes_ are chosen by the composition layer — target `main.cpp` for the real board, simulator for host — so a device profile's total RAM is `sizeof(runtime)` and is logged at boot as a memory-regression bridge (`main.cpp:1173–1196`). There is no runtime tuning surface beyond the provisioning image; buffer sizes are per-target compile-time decisions, which fits the "RAM ceiling is part of the device profile" doctrine (`itx_connection.h:25–30`).

## 6. Testability assessment

**What runs on host (very high coverage of in-scope code):** 38 `add_test` entries in the root `CMakeLists.txt`, all plain-C/C++ executables with an abort-on-fail `assert` macro and zero test framework for the portable tests. Every in-scope core module has a dedicated test (`itx_connection_test`, `itx_mount_test`, `websocket_{frame_writer,tx,rx,text,mailbox}_test`, `spsc_ring_test` (threaded, links pthreads), `atomic_test`, `retry_gate_test`, `cpu_usage_test`, `configuration_test`, `device_events_test`, `runtime_diagnostics_test`, `metrics_subscription_test` (1169 LOC), `m5sticks3_events_test`).

- **Test style:** fixtures hold real capnweb sessions with tiny bounded tables and a `capture_fragment` send-text fake that reassembles outbound messages for string-level assertion (`tests/itx_mount_test.c:44–92`, same pattern in `metrics_subscription_test.c`). Tests are behavior-named (`pong_waits_until_the_pcm_frame_boundary`, `close_replaces_a_pending_pong` in `websocket_tx_test.c:139–342`) and per AGENTS.md each documents the real failure mode it models. The mount/connection tests exercise the protocol through real JSON round-trips, not mocks of capnweb.
- **Platform adapters are host-tested too — the standout feature.** `tests/fakes/` contains header shims for `esp_wifi.h`, `esp_timer.h`, `nvs_flash.h`, `freertos/`, etc., plus `fake_esp_idf_platform.c` implementing FreeRTOS tasks over pthreads with pause/notify control and a virtual clock offset. The _real_ `platforms/iterate_esp_idf/itx_transport.c` is compiled against these fakes (root `CMakeLists.txt`, `iterate-kit-esp-idf-itx-transport-test` target) — so the generation handshake, discard policy, and restart logic (the riskiest concurrent code in scope) run under host CI, including a sanitized build tree (`build-host-sanitized/`).
- **Even the vendored-IDF patch is tested:** `tests/esp_idf_tcp_transport_host/` is an ESP-IDF host-target Catch2 project that runs the actual patched `tcp_transport` WebSocket parser against scripted byte streams ("the upgrade, frame header parser, payload bookkeeping, and project override are real", its main test comment).
- **Other lanes:** capnweb's own native tests + fuzzer + TS interop suite with a typed known-failure ledger; the simulator binaries for protocol-level device behavior; CMake-script tests for the post-link realtime ELF audit (root `CMakeLists.txt` bottom, including WILL_FAIL negatives).

**What is not host-testable:** real TLS/lwIP/Wi-Fi timing, actual `esp_transport` semantics beyond the scripted host component test, DMA/I2S, and multi-core memory-ordering behavior (host x86/ARM is stronger-ordered than the honesty of the code assumes; the relaxed/acquire-release discipline is argued in comments, not model-checked). The team knows this — comments repeatedly defer to "physical-device evidence" for those properties.

**Quality of fakes:** high. Fakes model contracts (short writes, deferred connects, notification coalescing) rather than happy paths — `fake_esp_idf_platform.c` exposes `defer_connected` / `short_next_send` knobs; the simulator's PCM egress deliberately withholds completion to force the backpressure interval (`simulator/devices/m5sticks3.cpp:55–60`).

**Gaps:** no host test compiles `websocket_connection.c` itself (its logic is partially covered indirectly via the tcp_transport host suite and via tx/rx unit tests, but the errno-classification switch at :209–237 and the URL parser at :80–163 appear untested on host — the URL parser especially is security-relevant input handling). `peer.c`'s `invokeCapability` unwrapping is tested only through device-level tests. I found no dedicated `peer_test.c`.

## 7. Architectural smells & risks (candid)

Ordered roughly by importance:

1. **`capabilities/src/metrics.c` is a god file (1510 LOC) with two serialization mechanisms and hand-counted literals.** The subscription path builds capnweb expression trees with per-field helpers where key lengths are sometimes bare integers (`"sent", 4U` at `metrics.c:352`, `"consecutiveSendDeferrals", 24U` at :405–407) and sometimes `sizeof("...")-1U` (:424 onward) — the numeric ones silently break if a key is renamed. Meanwhile `getDiagnostics` hand-formats a ~40-field JSON object in one snprintf format string (`metrics.c:1054–1132`) plus a second conditional snprintf for the network sibling (:1154–1182). Three schema representations (struct, expression builder, format string) must be kept in sync by hand; the maximum-width regression test is the only guard. A tiny schema-table generator (or at least uniform `sizeof`-based lengths) would remove a whole class of drift.

2. **Diagnostic schema triplication across layers.** The same counter families exist as `iterate_kit_esp_idf_itx_transport_metrics` (`esp_idf_itx_transport.h:108–163`), `runtime_diagnostics_snapshot.control` (`runtime_diagnostics.h:81–101`), and `control_diagnostics_sample` (`capabilities/metrics.h:134–193`), with slightly different field name spellings (`websocket_errors` vs `lastErrorType` vs `control_receive_failures`). Every new transport counter must be threaded through up to three structs, two serializers, and the platform sampler. Nothing detects a missed hop except review.

3. **ESP-IDF error domains and dead managed-client fields baked into the portable capability schema.** `metrics.h:147–158` (`last_websocket_tls_error` etc.) are documented as mirroring ESP-IDF, and `esp_idf_itx_transport.h:144–151` admits several fields "remain zero" since the managed-client was replaced — schema compatibility cruft in a pre-1.0 firmware whose wire consumers are in the same monorepo. This contradicts the repo-wide no-backcompat-cruft preference and should be cleaned before external consumers exist.

4. **Hand-rolled Wi-Fi backoff duplicated twice inside `network_task` while `retry_gate` exists for exactly this.** The doubling-with-saturation block appears verbatim at `itx_transport.c:757–768` (on Wi-Fi loss) and again at :775–784 (on `wifi_retry_later`), alongside a `retry_gate` used for the WebSocket in the same function (:709–717). Two backoff idioms in one loop invite divergence (they already differ: the Wi-Fi variant halves-then-caps using `WIFI_RETRY_MAX_MS / 2U` comparisons, the gate saturates internally).

5. **Five generation variables spread across two tasks are the correctness core, and the invariants live only in comments.** `socket_generation` / `accepted_` / `ready_` / `handled_` / `protocol_failure_generation` (`esp_idf_itx_transport.h:244–296`, logic at `itx_transport.c:468–494`, :608–620, :1201–1306, :1355–1374). The reasoning comments are excellent and the host transport test hammers this, but the state machine is not expressed as a state machine — it's emergent from ~15 atomic compare sites. This is the highest-cognitive-load area of the codebase; a follow-on defect here (e.g. a new flag added without generation stamping — a risk the code itself calls out at :440–445) would be hard to spot. `itx_transport.c` overall (1624 LOC) mixes Wi-Fi provisioning/NVS bring-up (:1010–1132), task lifecycle, generation logic, ring discard policy, and metrics into one file; the Wi-Fi station management is a separable ~250-line module.

6. **Duplicated atomic helper implementations instead of using `atomic.h`.** Local static copies of saturating-increment/update-max exist in `spsc_ring.c:42–67`, `websocket_tx.c:38–59`, and `itx_transport.c:139–169`, while `websocket_connection.c` correctly uses `iterate/kit/atomic.h`. The itx_transport acquire/release variants are justifiably different, but the relaxed counters are copy-paste; per `atomic.h:28–32`'s own rationale ("centralizing the compare/exchange loops prevents…"), these should be the shared header.

7. **Host CMakeLists duplication — two source-of-truth lists per component and ~40 copy-pasted test stanzas.** Root `CMakeLists.txt` re-enumerates every core/capabilities source that `components/*/CMakeLists.txt` also lists (a new file must be added in both, silently missing from one build otherwise), and 900+ of its lines are identical per-test boilerplate that an `add_iterate_kit_test(name lib...)` function (the pattern already exists as `add_iterate_kit_simulator`) would collapse tenfold.

8. **Inconsistent RPC argument strictness across capability modules.** `device_event_stream.subscribe` requires exactly one argument (`device_event_stream.c:129–134`), while `metrics.subscribe_view` only checks argument 0 exists and ignores extras (`metrics.c:932–935`); `getDiagnostics` requires exactly zero (:1016–1019). Harmless today, but the strict/lenient mix will fossilize into observable API behavior.

9. **Positional struct initialization for capnweb options.** `itx_connection.c:140–154` and `itx_mount.c` fill `capnweb_session_options`/`mount_options` positionally in a codebase that otherwise uses designated initializers; a field reordering in `capnweb.h` would compile and misbind (all pointers/sizes, several adjacent same-typed fields). Same pattern in the test fixtures (`tests/itx_mount_test.c:104–118`).

10. **Dead/duplicated control-frame validation in `websocket_text_ingress`.** Ingress validates and ignores interleaved control frames (`websocket_text.c:174–189`), but in the current ESP path the lower `websocket_connection`/`websocket_rx` already consumes control frames and the transport never feeds them to the inbox (`itx_transport.c:571–573` `continue`s on CONTROL). The ingress path is kept for the old `esp_websocket_client` event shape — reasonable during migration, but now two layers own control-frame policy and the ingress branch is unreachable in production.

11. **Minor naming drift.** The `websocket_text` outbox/inbox are tested by `websocket_mailbox_test.c` (a name that appears nowhere in the source); `runtime_diagnostics.h:14–23` documents its capacity in terms of the PCM family's width — the module names and test names don't always track the concepts.

12. **`peer` duplicate-path check is O(methods²) at init and dispatch is a linear scan per call** (`peer.c:69–73`, :126–141). Documented and fine at current table sizes (~10 methods), but there is no bound preventing a future profile from making per-RPC dispatch cost noticeable; noting because dispatch happens on the same task budgeted for audio-adjacent work.

**What is notably _not_ a smell:** ownership discipline (every buffer caller-owned, every transfer point commented), error taxonomy (two-dimensional failure classification throughout), zero heap after boot, the fail-closed bias (truncation, invalid enums, budget underflow all become loud classified errors instead of coerced defaults), and the host-testing of real platform adapter code through pthread fakes — these are all considerably above typical embedded-firmware practice.
