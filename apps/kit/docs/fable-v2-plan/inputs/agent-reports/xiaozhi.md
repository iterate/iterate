# xiaozhi-esp32 Architecture Study — Transferable Lessons for Our ESP32-S3 Firmware

Repo: `~/src/github.com/78/xiaozhi-esp32` at commit `e0074e90` (2026-07-28, "add ESP32-S31-Korvo-1 Board support"). All paths below are relative to the repo root; the interesting code is all under `main/`.

## 1. Module decomposition

The layering is strict and small — five layers, each with one owner class:

| Layer            | Class / files                                                                                                                                                                                                                                                                                  | Responsibility                                                                                                                                                                                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Hardware I/O     | `AudioCodec` (abstract) — `main/audio/audio_codec.{h,cc}`; implementations in `main/audio/codecs/` (`es8311_audio_codec.cc`, `box_audio_codec.cc` = ES8311 DAC + ES7210 4-ch ADC, `es8388/74/89_audio_codec.cc`, `no_audio_codec.cc` = raw I2S std/PDM simplex/duplex, `dummy_audio_codec.cc`) | Blocking `Read()/Write()` of int16 PCM at the codec's native rate; owns I2S channels, `esp_codec_dev`, volume, `EnableInput/Output` power gating. Exposes properties: `duplex()`, `input_reference()`, `input_channels()`, `input_sample_rate()` (`audio_codec.h:41-50`) |
| Speech pipeline  | `AudioEngine` (interface, `main/audio/audio_engine.h`) — `AfeAudioEngine` (`main/audio/engines/afe_audio_engine.{h,cc}`, S3/P4/S31) or `LiteAudioEngine` (`lite_audio_engine.cc`, ESP32/C3/C5/C6)                                                                                              | AFE (AEC+VAD+WakeNet), wake-word, VAD events, emits exactly 16 kHz mono Opus-frame-sized PCM via `OnOutput` callback                                                                                                                                                     |
| Service / queues | `AudioService` — `main/audio/audio_service.{h,cc}`                                                                                                                                                                                                                                             | Owns the 3 audio tasks, 5 queues, Opus encoder/decoder, resamplers, power timer, wake-word packet retrieval. The only audio API `Application` sees                                                                                                                       |
| Protocol         | `Protocol` (abstract, `main/protocols/protocol.{h,cc}`) — `WebsocketProtocol` (`websocket_protocol.cc`), `MqttProtocol` (`mqtt_protocol.cc`, control over MQTT + audio over AES-CTR-encrypted UDP)                                                                                             | `AudioStreamPacket` in/out, JSON control messages, hello handshake, session                                                                                                                                                                                              |
| Application      | `Application` (singleton, `main/application.{h,cc}`) + `DeviceStateMachine` (`main/device_state_machine.{h,cc}`)                                                                                                                                                                               | Event-loop FSM wiring everything together; also `mcp_server.cc` (device MCP tools), `ota.cc`, `display/`, `led/`                                                                                                                                                         |

Board abstraction is a parallel axis: `Board` (`main/boards/common/board.h`) with `WifiBoard`/`Ml307Board`(cellular)/`EthernetBoard` mid-layers and ~180 concrete boards in 45 vendor directories.

Key structural decision, quoted from their own `main/audio/README.md`: "`AudioService` owns one input engine and keeps codec I/O, Opus encoding/decoding, and network queues independent from the chip-specific speech pipeline." The chip-specific stuff (AFE, WakeNet) is entirely behind `AudioEngine`; everything above it is portable across all 7 ESP32 variants.

## 2. Task model

All audio tasks are created in `AudioService::Start()` (`audio_service.cc:122-165`) and torn down cooperatively via an `service_stopped_` atomic + event-group bits.

| Task                | Priority     | Stack                                    | Core                               | Created at                    | Job                                                                                                  |
| ------------------- | ------------ | ---------------------------------------- | ---------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| `audio_input`       | 8            | 6 KB (AFE build) / 4 KB                  | **pinned core 0** (AFE build only) | `audio_service.cc:131-135`    | Blocking-reads 10 ms (160-sample) chunks from codec, resamples to 16 kHz, `engine->Feed()`           |
| `audio_output`      | 4            | 4 KB / 2 KB                              | any                                | `audio_service.cc:138-142`    | Pops decoded PCM, blocking-writes to codec                                                           |
| `opus_codec`        | **2**        | **24 KB**                                | any                                | `audio_service.cc:160-164`    | One task does both Opus encode and decode                                                            |
| `audio_afe`         | 3            | 4 KB                                     | any                                | `afe_audio_engine.cc:173-177` | `afe_iface_->fetch_with_delay()` loop; WakeNet result handling, VAD edge detection, framing to 60 ms |
| `encode_wake_word`  | 2            | 24 KB (**static, stack in PSRAM**)       | any                                | `afe_audio_engine.cc:479-556` | One-shot: Opus-encodes the 2 s pre-wake ring buffer, then self-deletes                               |
| main task (`Run()`) | raised to 10 | 8 KB (`CONFIG_ESP_MAIN_TASK_STACK_SIZE`) | —                                  | `application.cc:170`          | Event loop; also drains send queue to network                                                        |
| `activation`        | 2            | 8 KB                                     | any                                | `application.cc:287-294`      | One-shot OTA/activation at boot                                                                      |

How they keep I2S fed and network from starving audio — the priority ladder is the whole story:

- **Input is highest (8) and pinned to core 0**, away from the Wi-Fi/LwIP tasks; a missed 10 ms mic read is unrecoverable, so it outranks everything.
- **Playback (4) > AFE (3) > Opus (2)**: Opus encode of a 60 ms frame is the biggest CPU burst, and it is deliberately the _lowest_ priority — it can be late, because the queues in front of and behind it absorb jitter. Note Opus complexity is set to 0 (`audio_service.h:72`) so even at prio 2 it keeps up.
- **Network sending is not a task at all.** The Opus task pushes to `audio_send_queue_` and fires `on_send_queue_available`, which just sets `MAIN_EVENT_SEND_AUDIO`; the main loop drains the queue and calls `protocol_->SendAudio()` (`application.cc:226-238`). Blocking websocket writes therefore happen in the main task, never in an audio task.
- `TaskPriorityReset` RAII helper (`application.h:184-196`) exists to temporarily change the calling task's priority for heavy sections.

## 3. Buffering and backpressure

The pipeline (comment at `audio_service.h:28-37`):

```
(MIC) -> [AudioEngine] -> {encode_queue} -> [OpusCodecTask] -> {send_queue} -> (Server)
(Server) -> {decode_queue} -> [OpusCodecTask] -> {playback_queue} -> [AudioOutputTask] -> (Speaker)
```

All five queues are plain `std::deque<std::unique_ptr<...>>` guarded by **one mutex + one condition_variable** (`audio_queue_mutex_`/`audio_queue_cv_`, `audio_service.h:170-176`) — no FreeRTOS queues at the service layer, which lets one CV wake express compound predicates like "decode queue non-empty AND playback queue below limit" (`audio_service.cc:366-370`).

Sizes (`audio_service.h:39-45`):

- `MAX_ENCODE_TASKS_IN_QUEUE 2` and `MAX_PLAYBACK_TASKS_IN_QUEUE 2` — **PCM queues are tiny** (2 x 60 ms) because PCM is big;
- `MAX_DECODE_PACKETS_IN_QUEUE` and `MAX_SEND_PACKETS_IN_QUEUE` = 2400/60 = **40 packets = 2.4 s** — Opus queues are the deep jitter buffers because Opus frames are ~100-200 bytes. Their comment: "Decode Queue and Send Queue are the main queues, because Opus packets are quite smaller than PCM packets."
- `MAX_TIMESTAMPS_IN_QUEUE 3` for the server-AEC timestamp echo path.

Backpressure policy is direction-dependent:

- **Uplink drops, never blocks.** `PushTaskToEncodeQueue` (`audio_service.cc:556-564`): "Microphone audio is realtime, so drop the oldest frame instead of blocking. Blocking here would stall the audio engine task (AFE fetch) and deadlock the whole input pipeline when the send queue stops being drained (e.g. network congestion or a failed UDP send)." Same at the send queue (`audio_service.cc:471-475`): full send queue pops the oldest. And in the main loop, if a websocket send fails they drain and discard the entire send queue (`application.cc:228-236`) with a comment explaining the deadlock chain they are avoiding. Drops are counted (`DebugStatistics.encode_drop_count`) and logged rate-limited (max 1/s) **outside the lock** because "UART writes are slow and would starve the codec task" (`audio_service.cc:569-577`).
- **Downlink blocks (optionally).** `PushPacketToDecodeQueue(packet, wait=true)` waits on the CV when 2.4 s of audio is queued (`audio_service.cc:580-599`) — used by `PlaySound` for local OGG assets; the network path uses `wait=false` and drops.
- **Drained tracking:** `decode_in_flight_`/`output_in_flight_` booleans plus `playback_generation_` counter give an exact "playback fully drained" edge event (`IsPlaybackDrainedLocked`, `audio_service.cc:765-776`) that fires `on_playback_drained` exactly once — used by the FSM to defer mic-open until the speaker is done (see §4).
- **Warmup:** `audio_input_need_warmup_` causes the input task to sleep 120 ms and discard the first read after enabling voice processing (`audio_service.cc:269-272`) — mic settle time.

PSRAM vs SRAM: bulk audio buffers deliberately go to PSRAM — the AFE is configured `AFE_MEMORY_ALLOC_MORE_PSRAM` (`afe_audio_engine.cc:150`), the 64 KB 2-second wake-word ring is `MALLOC_CAP_SPIRAM` (`wake_word_audio_cache.cc:26-27`), and the wake-word encoder task's 24 KB stack is a **static task with its stack in PSRAM** and only the TCB in internal RAM (`afe_audio_engine.cc:481-489`) — a trick worth remembering. `sdkconfig.defaults.esp32s3` reserves 96 KB internal (`CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL=98304`) and forces allocations ≤2 KB internal (`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048`), plus `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` to push TLS to PSRAM.

Timestamps: `AudioStreamPacket{sample_rate, frame_duration, timestamp, payload}` (`protocol.h:10-15`). Timestamps only flow when server AEC is on: the output task records each played packet's timestamp into `timestamp_queue_` (`audio_service.cc:344-349`), and the encode path stamps outgoing mic frames with the front of that queue (`audio_service.cc:547-553`) — i.e. "this mic frame was captured while the speaker was playing server-timestamp T", which is exactly what a server-side AEC needs to align its reference.

## 4. AEC / VAD / duplex-mode switching

**One AFE instance for everything** — this is the centerpiece. Their README: "`AfeAudioEngine` owns a single FD AFE instance. WakeNet and voice uplink share that instance, so enabling both no longer creates two AFE pipelines."

Configuration (`afe_audio_engine.cc:128-151`): `afe_config_init(input_format, models, AFE_TYPE_VC, AFE_MODE_HIGH_PERF)` with:

- `aec_init = codec_->input_reference()` — AEC exists only if the board has a hardware reference channel;
- `aec_mode = AEC_MODE_VOIP_HIGH_PERF`, `aec_nlp_level = AEC_NLP_LEVEL_VERYAGGR` (the README still says FD_LOW_COST — the code has since moved to VOIP_HIGH_PERF; NLP "very aggressive" retained);
- `ns_init = false` ("WebRTC/NSNet noise suppression is intentionally disabled because the project does not ship an NSNet model");
- `vad_init` only when the audio processor is enabled, `VAD_MODE_0`, `vad_min_noise_ms = 100`, VADNet model if present;
- `agc_init = false`; `memory_alloc_mode = AFE_MEMORY_ALLOC_MORE_PSRAM`.
- Input format string is built as `"M...R"` from `input_channels - ref_num` mics + ref channels (`afe_audio_engine.cc:116-123`) — e.g. `"MR"` on a box.

**Reference signal is always hardware loopback**, never software mixing: on ES7210 boards one TDM slot is wired to the amplifier output (`BoxAudioCodec` opens channel mask slot 0 + slot 1 when `input_reference_`, `box_audio_codec.cc:196-206`, with a separately configurable reference gain channel). Kconfig hard-gates `USE_DEVICE_AEC` to an explicit allowlist of boards known to have that loopback plus acoustic isolation (`Kconfig.projbuild:904-916`, help text: "device-side AEC requires a clean output reference path from the speaker signal and physical acoustic isolation between the microphone and speaker"). ES8311-only boards (like the M5 Stick-S3) set `input_reference_ = false` and simply cannot do device AEC.

**Runtime states, not pipeline rebuilds.** Wake-word detection and voice processing are two independent event-group bits (`kWakeWordEnabled`, `kVoiceProcessingEnabled`) on the same engine; a derived `kAfeActive` bit gates both `Feed()` and the fetch task. Toggling modes never destroys the AFE. Cross-task safety is handled with a disciplined "owner task applies controls" pattern that is worth copying wholesale:

- `enable_wakenet/disable_wakenet/enable_aec/disable_aec` are **never called from the control thread** — control paths only set `afe_control_dirty_`, and `ProcessingTask` applies them between fetches (`ApplyAfeControls`, `afe_audio_engine.cc:317-335`), "WakeNet/AEC toggles are not safe against a concurrent fetch".
- Same for `reset_buffer()`: deferred via `reset_pending_` because "a concurrent reset corrupts the ring buffer state" (`afe_audio_engine.cc:294-300`).
- A `control_generation_` counter rejects a stale `fetch_with_delay` result that unblocks after a disable/re-enable cycle (`afe_audio_engine.cc:360-368`).

**AEC enablement logic** (`ApplyAfeControls`, `afe_audio_engine.cc:326-334`): AEC is on when _wake-word detection_ is active (so you can bargein-wake during playback — the README calls this out: "AEC stays active while wake-word detection is active so playback reference remains available for wake-up during device playback"), or when voice processing is active _and_ device AEC was requested.

**Three-way AEC ownership** (`AecMode` in `application.h:38-42`): `kAecOff`, `kAecOnDeviceSide`, `kAecOnServerSide` (mutually exclusive at Kconfig level, `application.cc:25-33`, runtime-switchable via `SetAecMode` which closes the audio channel to renegotiate). This maps directly onto listening mode: `GetDefaultListeningMode()` returns `kListeningModeRealtime` iff any AEC is available, else `kListeningModeAutoStop` (`application.cc:1022-1024`). The three `ListeningMode`s (`protocol.h:35-39`) are the whole duplex policy:

- `kListeningModeRealtime` — full duplex: on TTS start, voice processing stays on (`application.cc:954`); echo removed on device (AFE) or on server (timestamp echo, `features.aec=true` in the websocket hello, `websocket_protocol.cc:204-206`).
- `kListeningModeAutoStop` — half duplex: mic off while speaking; when TTS stops, transition to Listening _defers mic-on until playback drains_ (`pending_listening_start_` + `MAIN_EVENT_PLAYBACK_DRAINED`, `application.cc:937-945`) — "prevents audio truncation when STOP arrives late due to network jitter".
- `kListeningModeManualStop` — push-to-talk: server never auto-ends the turn; buttons call `StartListening()`/`StopListening()`. PTT vs click-to-talk is a per-device persisted setting exposed as an MCP tool the _assistant itself_ can flip (`boards/common/press_to_talk_mcp_tool.cc`, tool `self.set_press_to_talk`).

**VAD** is consumed only as an edge signal: `HandleVoiceResult` (`afe_audio_engine.cc:420-428`) converts `result->vad_state` into speaking/not-speaking transitions; `Application` uses it just to update the LED. Turn-taking on `AutoStop` is server-side (server sends `tts start/stop` JSON) — the device does not do endpointing itself.

## 5. Board abstraction

- `Board` is an abstract singleton created via a `create_board()` free function; each board file ends with `DECLARE_BOARD(M5StackStickS3Board)` which defines it (`board.h:87-90`). `Board::GetInstance()` (`board.h:62-65`) is used everywhere.
- The interface (`board.h:68-84`) is a set of lazy accessors: `GetAudioCodec()`, `GetDisplay()`, `GetLed()`, `GetBacklight()`, `GetCamera()`, `GetNetwork()` (returns a `NetworkInterface` that can `CreateWebSocket/CreateUdp/CreateMqtt` — so cellular vs Wi-Fi is invisible to protocols), `StartNetwork()`, `SetNetworkEventCallback()`, `SetPowerSaveLevel()`, `GetBatteryLevel()`, plus JSON self-description (`GetBoardJson`, `GetDeviceStatusJson`) reported to the server.
- Boards return components as **function-local statics** (`static Sticks3AudioCodec audio_codec(...); return &audio_codec;` — `m5stack_stick_s3.cc:193-208`), so hardware is constructed on first use, after board init.
- A new board = one directory under `main/boards/<vendor>/<name>/` with `config.h` (pins, sample rates, display geometry — all `#define`s), `<name>.cc` (the Board subclass: init I2C/SPI/PMIC/display/buttons in constructor, override accessors), and `config.json` (build metadata: target chip plus `sdkconfig_append` per build variant, e.g. Stick-S3 appends `CONFIG_USE_ESP_WAKE_WORD=y`, 8 MB flash partition table). Board selection is **compile-time** via Kconfig choice → `BOARD_DIR` in `main/CMakeLists.txt` (one `elseif` per board, also picking fonts/emoji assets per board).
- Mid-layer classes absorb transport diversity: `WifiBoard`, `Ml307Board`/`Nt26Board` (cellular modems), `DualNetworkBoard`, `EthernetBoard`, plus reusable drivers in `boards/common/` (`button.cc`, `knob.cc`, `power_save_timer.cc`, `adc_battery_monitor.cc`, PMIC drivers `axp2101.cc`/`sy6970.cc`, `system_reset.cc`).
- Behavior differences are expressed by subclassing the codec in the board file — e.g. Stick-S3 wraps `Es8311AudioCodec` just to scale hardware volume to 60% while reporting the unscaled value (`m5stack_stick_s3.cc:25-55`).

## 6. Sample rates and resampling

- **The wire and the pipeline are fixed at 16 kHz mono**; the hello message advertises `format: opus, sample_rate: 16000, channels: 1, frame_duration: 60` (`websocket_protocol.cc:211-216`).
- The codec runs at its natural rate (Stick-S3: 24 kHz in/out, `boards/m5stack/stick-s3/config.h:6-7`; box boards: 16 k in / 16-48 k out). `AudioService::ReadAudioData` (`audio_service.cc:190-234`) computes how many native samples correspond to the requested 16 kHz sample count, reads, then resamples through `esp_ae_rate_cvt` (esp-audio-effects), configured `complexity=2, perf_type=SPEED` (`audio_service.cc:5-14`). Resamplers are `reset()` on every capture (re)start.
- **Downlink is decoded at the server's rate** (default 24000, `protocol.h:77`) learned from the server hello, and only resampled if it differs from the codec output rate; `SetDecodeSampleRate` (`audio_service.cc:500-534`) tears down and recreates the Opus decoder and output resampler on the fly when the server's `sample_rate`/`frame_duration` change mid-stream (each `AudioStreamPacket` carries both, so local sound effects at 24 k and server TTS at 16 k can interleave). They log a warning that resampling "may cause distortion" when server rate ≠ codec rate — resampling is treated as a fallback, and boards are encouraged to run the codec at the server rate.
- AFE always operates at 16 kHz; multi-channel (`M`/`R`) interleaved input goes in, clean mono comes out, and `HandleVoiceResult`/`OutputRawAudio` re-chunk arbitrary AFE output sizes into exact 60 ms frames (960 samples) with a small accumulation buffer and a nice move-vs-copy optimization for the common exact-fit case (`afe_audio_engine.cc:433-445`).

## 7. Other notably clever things

- **Opus settings** (`audio_service.h:65-76`): 60 ms frames (fewer packets, less header/radio overhead, better compression), `complexity = 0` (encode a 60 ms frame cheaply on a 240 MHz S3), **DTX enabled** (near-zero bytes during silence — huge for the always-sending realtime mode), VBR, `BITRATE_AUTO`, mono 16 k. One 24 KB-stack task handles codec both directions.
- **Audio power gating**: a 1 Hz `audio_power_timer` turns off codec ADC/DAC after 15 s of inactivity (`CheckAndUpdateAudioPowerState`, `audio_service.cc:778-796`), with two hardware-gotcha comments: ADC-continuous start/stop must happen in the input task itself (they set a stop-request event bit rather than closing from the timer task), and TX clock must be kept when a duplex codec is still capturing "otherwise RX may stall on some boards". The first `Read`/`Write` after idle transparently re-enables the channel.
- **Power/latency arbitration**: `PowerSaveLevel::{LOW_POWER, BALANCED, PERFORMANCE}` on `Board`; the app goes PERFORMANCE right before opening the audio channel ("Switch to performance mode before connecting to reduce latency", `application.cc:749-751`) and back to LOW*POWER when the channel closes. `PowerSaveTimer` (`boards/common/power_save_timer.cc`) additionally drops the CPU clock and enables light sleep after N idle seconds — but only after asking `Application::CanEnterSleepMode()` (idle FSM + channel closed + `audio_service*.IsIdle()`), and it disables wake-word detection and mic input first, restoring them on wake.
- **Protocol design**: JSON text frames for control (hello/tts/stt/llm-emotion/mcp/system/alert), raw binary frames for Opus. Three wire versions negotiated by a `version` setting sent as a header: v1 = bare Opus payload; v2 = 16-byte header with **timestamp for server AEC** (`BinaryProtocol2`, `protocol.h:17-24`); v3 = minimal 4-byte type/len header. MQTT variant does control over MQTT and audio over UDP with AES-CTR, the 16-byte nonce doubling as the packet header carrying payload length, timestamp, and a monotonic sequence with duplicate/out-of-order detection (`mqtt_protocol.cc:186-211`, `267-334`). MCP (tool calls from the assistant to the device) is tunneled as just another JSON message type.
- **Wake-word preroll upload**: the last 2 s of AFE-processed audio are kept in the single PSRAM ring (`WakeWordAudioCache`), and on detection they are Opus-encoded by a throwaway task and sent to the server ahead of `SendWakeWordDetected` (`application.cc:890-897`) — the server hears the wake word itself plus anything said immediately after, killing the classic post-wake truncation. The consumer streams packet-by-packet with a CV (`GetWakeWordOpus` blocks; an empty sentinel packet marks the end, `afe_audio_engine.cc:549-570`).
- **Deadlock-conscious FSM**: everything funnels into one main event loop (`Application::Run`) driven by a single event group with 14 bits; cross-thread work enters via `Schedule(lambda)` + `MAIN_EVENT_SCHEDULE`. The `DeviceStateMachine` is a pure validated-transition table (`device_state_machine.cc:34-102`) with listeners; invalid transitions are logged and rejected rather than asserted. State handlers contain several "re-check the state after Schedule because it may have changed" guards.
- **Built-in mic loopback test**: in Wi-Fi-config mode, the button toggles `AudioTesting`, which records up to 10 s of encoded mic audio into a queue and, on stop, **moves the testing queue straight into the decode queue** to play your own voice back (`EnableAudioTesting`, `audio_service.cc:679-693`) — a zero-extra-code end-to-end audio self-test in the field.
- **Audio debugger**: `CONFIG_USE_AUDIO_DEBUGGER` streams raw pre-pipeline PCM over UDP to a host (`audio_debugger.cc`, host script `scripts/audio_debug_server.py`) — taps the input right after `ReadAudioData`.
- Debug hygiene: `DebugStatistics` counters for every stage (input/decode/encode/playback/drops), heap stats printed every 10 s from the clock tick.

## 8. Lessons for us (distilled)

Ordered roughly by how directly they apply to our portable C core + device-module firmware (PCM-over-websocket, sometimes PTT, sometimes full duplex):

1. **Split "speech pipeline" from "audio service" with a single-interface seam.** One `AudioEngine`-equivalent interface (feed PCM in; get clean 16 kHz frames, VAD edges, wake events out) is the only chip-specific audio component. Everything else — queues, codecs' I2S I/O, Opus, network — stays portable and thus host-testable. This maps perfectly onto our host-testable C core: the AFE engine becomes a device module; a trivial pass-through engine runs in the simulator.
2. **Four tasks, strict priority ladder, input on top and pinned:** mic read (highest, pinned to the non-Wi-Fi core) > speaker write > pipeline fetch > codec encode/decode (lowest, fat stack). Do CPU-heavy encode at _low_ priority with queues around it; never put a network write in any audio task.
3. **Asymmetric backpressure: uplink drops oldest, never blocks; downlink gets a deep jitter buffer (~2.4 s) of _compressed_ frames and tiny (2-frame) PCM queues.** Keep PCM queues shallow and Opus/encoded queues deep. Count and rate-limit-log every drop, outside the lock.
4. **On network-send failure, flush the whole send queue.** Stale realtime mic audio is worthless and a stuck queue deadlocks the pipeline; their comments document the exact deadlock chain twice. We already learned a cousin of this in our station-outage work — worth encoding as policy.
5. **One AFE instance, mode switches as state bits, all AFE mutations applied by the task that owns the fetch side** (dirty-flag + generation counter + deferred reset). Never enable/disable/reset an AFE (or any DSP with an internal ring) from a control thread while another task is inside fetch. This is the cleanest solution I have seen to a bug class we would otherwise certainly hit.
6. **Model duplex policy as three listening modes** (`realtime` / `auto_stop` / `manual_stop`) picked from AEC availability, and send the mode to the server in `start_listening`. PTT is not a different pipeline — it is `manual_stop` with the same code path; a persisted flag (they even expose it as an MCP tool) flips button semantics.
7. **Support server-side AEC via timestamp echo**: record the play-out timestamp of each downlink frame, stamp uplink frames with the front of that queue, and advertise `features.aec` in the hello. It makes echo-cancelled full duplex possible on reference-less hardware like the M5StickS3 (their Stick-S3 port has `input_reference_ = false` — device AEC is _structurally impossible_ there, so this is the only full-duplex path for that hardware).
8. **Gate device AEC on hardware truth, loudly.** AEC requires a real loopback reference channel and acoustic isolation; they enforce it with a Kconfig board allowlist and a runtime warning. Don't attempt software reference (buffer-the-TX) as a default; they never do.
9. **Defer mic-open until playback fully drains** (edge-triggered `on_playback_drained` event computed from queues + in-flight flags + generation counter) in auto-stop mode, and add a ~120 ms mic warmup discard. This one mechanism removes both self-echo at turn start and truncated TTS tails under jitter.
10. **Keep the wire format at 16 kHz mono Opus 60 ms with DTX + VBR + complexity 0**, resample at the edges with a speed-optimized resampler, and let the _downlink_ rate float per-packet (each packet carries `sample_rate`/`frame_duration`; decoder rebuilds on change). Prefer running the codec at the server rate to avoid resampling entirely.
11. **PSRAM discipline**: AFE in "more PSRAM" mode, preroll ring in PSRAM, big one-shot task stacks as static tasks with PSRAM stacks, TLS/mbedtls external alloc, and a reserved internal pool — with DMA/I2S descriptors sized small (6 descriptors x 240 frames, `audio_codec.h:15-16`).
12. **Ship a 2 s wake-word preroll ring and upload it on wake** — cheap (64 KB PSRAM) and eliminates first-syllable loss. Encode lazily in a throwaway task only on detection.
13. **Single main event loop + validated FSM transition table.** All cross-thread interaction is event-group bits or `Schedule(lambda)`; state changes go through an explicit `IsValidTransition` table that rejects and logs. Audio callbacks _only set bits_ — they never do work inline.
14. **Build in field self-tests and taps**: the record-then-playback loopback test wired to a button in setup mode, the UDP raw-PCM debug tap, per-stage counters, and periodic heap prints. All are ~50 lines each and pay for themselves immediately (we spent days on exactly the acoustic-capture and receive-stall investigations these would have shortcut).
15. **Tie power management to the audio lifecycle at three levels**: codec ADC/DAC auto-off after 15 s idle (with the "stop from the owning task" and "keep TX clock while duplex RX active" gotchas), Wi-Fi/CPU `PowerSaveLevel` toggled PERFORMANCE around an open audio channel, and light-sleep entry gated on an explicit `CanEnterSleepMode()` (FSM idle + channel closed + queues drained) that disables wake-word/mic first and restores them on wake.

One caveat for transfer: their portability axis is "many ESP-IDF chips/boards", not "host-testable" — everything is C++ on FreeRTOS primitives with `std::mutex`/CV on top, and there is no off-device test story at all. Our sans-io/virtual-clock core is a real advantage they don't have; the lesson to import is their _seam placement_ (engine interface, codec interface, protocol interface, board interface) and their _scheduling/backpressure policies_, not their concrete classes.
