# StackChan avatar integration — skeptical embedded review

**Verdict up front.** The architecture is right and the concurrency design is verifiably sound, but the review found one hard blocker and one proof-infrastructure gap that together mean the current source has never run and cannot currently be proven:

1. **BLOCKER — the current source cannot boot.** `stackchan_avatar.c:490` allocates the framebuffer with `MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA | MALLOC_CAP_8BIT`. On ESP32‑S3 under IDF v5.4.2, no heap region carries both SPIRAM and DMA caps — PSRAM is tagged `MALLOC_CAP_SPIRAM|DEFAULT|8BIT|32BIT|SIMD` only (`esp-idf/components/heap/port/esp32s3/memory_layout.c:66`, `esp_psram/esp_psram.c:392`); `MALLOC_CAP_DMA` exists only on internal DIRAM/DRAM. I verified both files directly. The alloc returns NULL → `avatar_start` returns `ESP_ERR_NO_MEM` → `main.c:888` deliberately fails the whole target (avatar is load-bearing by policy). The previously flashed core‑0 build displayed a face, so its binary must predate this caps combination — source files were edited 16:39–17:35 while the six evidence runs (16:01–16:42) ran over the air against the old binary. **No evidence run covers the code under review.**
2. **The one‑slot/semaphore/ownership protocol is sound** — verified against v5.4.2 sources, including the one scenario that could have broken it (chunked >32 KiB transfers; see Q3).
3. **A hidden allocation invalidates the "steady-state allocates nothing" contract.** S3's SPI master cannot DMA from PSRAM in v5.4.2 (`spi_common.c:257-263`: `.access_ext_mem = false`, literal `// TODO: add support to allow SPI transfer PSRAM buffer`). A PSRAM TX buffer triggers a **per-transaction internal `heap_caps_aligned_alloc(MALLOC_CAP_DMA)` + memcpy bounce** (`spi_master.c:1163-1176`), freed on recycle. At 38,400 B/frame this is ~2 internal allocations up to 32,768 B each, ~30×/s — which is precisely where the unexplained ~51 KiB of the 81,307 → ~30,300 B minimum-internal-heap drop went, plus heap-lock churn and fragmentation exposure the design thought it had excluded.
4. **No avatar counter leaves the device.** `sample_runtime_metrics` snapshots the avatar struct (`main.c:256`) but exports only the stack high-water fold-in (`main.c:287-288`); `grep -i avatar apps/kit/src` finds nothing. With the USB/JTAG endpoint gone, avatar motion, display transfers, and timeouts are currently **unobservable** in any proof run.

All six avatar-era evidence runs are network-invalid failures (RSSI −68/−75 dBm vs −57..−55 in the green run; ping timeouts; PCM socket deaths; one AEC fail at 2.69 dB under degraded RF). One correction to the given narrative: the "extra Grok VAD starts" runs show speech fragmenting mid-phrase ("Reply exactly. Production.") alongside `uplink_dropped +62/+84` and RTT spikes — the uplink-gap fragmentation signature, with room noise at most co-causal. Network-invalid either way; not acceptance evidence, and also not avatar-incriminating.

## Q1 — Is core 1 / priority 2 the cleanest affinity?

**Yes. Keep it; refine only the interrupt side.** The full placement picture for this target:

| Work                                      | Core       | Prio    | Source                                                                                                                                                                     |
| ----------------------------------------- | ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wi-Fi task                                | 0 (pinned) | —       | `sdkconfig:1387` `CONFIG_ESP_WIFI_TASK_PINNED_TO_CORE_0=y`                                                                                                                 |
| main task (all init)                      | 0          | 1       | `sdkconfig:1297`                                                                                                                                                           |
| lwIP tcpip                                | unpinned   | 18      | `sdkconfig:1747`                                                                                                                                                           |
| audio io / aec                            | 1          | 23 / 20 | `core_s3_audio_owner.c:29-31,1147-1164`                                                                                                                                    |
| avatar analyzer+render                    | 1          | 2       | `stackchan_avatar.c:47,59,542-550`                                                                                                                                         |
| **SPI3 LCD ISR**                          | **0**      | —       | default `isr_cpu_id=AUTO` → allocated on the core running the first `spi_bus_add_device` (`spi_master.c:302-312,408-413`, `intr_alloc.c:570`), which is `app_main` on CPU0 |
| **I2S GDMA ISR** (incl. the new observer) | **0**      | —       | same mechanism; `initialize_codecs` runs in `owner_start` from `app_main` (`core_s3_audio_owner.c:1171`)                                                                   |

The task-side reasoning encoded at `stackchan_avatar.c:48-68` is correct and matches the only measured-good prior art: the StickS3 experiment ran a single avatar task at **core 1, priority 2** (`firmware-sticks3/main/app_main.cpp:334-335`), and the CoreS3 LVGL experiment ran rendering at core 1 priority 4 below audio. A priority‑2 task on core 1 consumes only the audio owners' idle time by construction; the compile-time guards (`#error` on core count and Wi-Fi pinning, `stackchan_avatar.c:60-65`) keep it from drifting. No simpler architecture exists that preserves the properties: eliminating the task (rendering from the io task or a timer callback) would put visual work inside audio's deadline domain, which is exactly what this design forbids.

Two refinements, not restructurings: (a) v5.4.2 **does** support `spi_bus_config_t.isr_cpu_id` (`spi_common.h:123`) — set `ESP_INTR_CPU_AFFINITY_1` in the first-party override BSP's `bsp_spi_init` (`idf_overrides/.../m5stack_core_s3.c:175-182`) so the ~30/s flush-completion ISRs leave the Wi-Fi core; one line, zero risk. (b) Leave I2S init where it is — its core‑0 ISR placement is part of the proven green baseline, and the observer adds only a bounded ~2–4 µs copy per 8 ms descriptor there.

Note honestly: the 5–10% LAN loss was measured with the **task** on core 0; the core‑1 build has never been flashed, so "core 1 fixes it" currently rests on the prior experiment's affinity plus the priority argument, not on a measurement of this firmware. That measurement is the point of the next proof.

## Q2 — Can the render/byte-swap/SPI-DMA path perturb audio indirectly?

Channel by channel, with the framebuffer question at the center:

- **PSRAM + cache (the real one).** Today's path does three full sweeps of a PSRAM framebuffer per frame — render write, in-place swap read+write (`stackchan_avatar.c:290-304`), then the driver's bounce memcpy read — ≈1.7 MB/s through the shared 64 KiB dcache (`sdkconfig`: 64 KB/8-way/64 B line), plus atlas reads (rodata is **in PSRAM** under `CONFIG_SPIRAM_RODATA=y`). PSRAM is **QUAD @ 80 MHz** on this target (`sdkconfig.defaults`), not octal — modest bandwidth — and the AEC's working set is also PSRAM (`create_aec` caps `MALLOC_CAP_SPIRAM`, `core_s3_audio_owner.c:489`). Dcache eviction and PSRAM bus contention do not respect FreeRTOS priorities; this is the plausible mechanism behind the core‑0 loss beyond mere CPU time. **The fix for Q6 #1 (internal framebuffer) removes this entire channel**: render, swap, and DMA all stay in internal SRAM, which is uncached and directly DMA-readable.
- **Hidden heap churn.** The per-transaction bounce malloc/free (~30/s, up to 32,768 B contiguous internal) is a fragmentation and latency-jitter source inside `spi_master`, and a transient internal-heap consumer competing with TLS spikes. Also removed by the internal framebuffer.
- **GDMA arbitration.** All SPI and I2S GDMA channels run at priority 0, round-robin (`esp_private/gdma.h:227-238`; no driver ever calls `gdma_set_priority`, max prio 5 on S3, `gdma_ll.h:23`). I2S needs 256 B per 8 ms against SPI's bursts; round-robin per-beat arbitration cannot starve it at these rates. Not a risk.
- **SPI bus sharing.** LCD and SD share SPI3 (`m5stack_core_s3.h:359,485`); SD is never mounted on this target, so no contention — but note `bsp_sdcard_unmount` would free the shared bus, and whoever inits first fixes `max_transfer_sz` for both. Keep SD off this target.
- **ISR load on core 0.** 15 Hz × 2 chunks ≈ 30 SPI completion ISRs/s plus the 125 Hz observer copy — microseconds; negligible, and half of it moves with the `isr_cpu_id` fix.
- **lwIP.** The avatar owns no sockets and shares no locks with lwIP; the unpinned tcpip task outranks priority 2 everywhere. No pathway.
- **One residual corner:** esp_lcd's `lcd_spi_post_trans_color_cb` is **not** IRAM (`esp_lcd_panel_io_spi.c:418-427`) while the SPI ISR is IRAM-resident (`CONFIG_SPI_MASTER_ISR_IN_IRAM=y`). A flash write (NVS) coinciding with a color-transfer completion can fault in the cache-disabled window. This firmware does not write flash in steady state; keep it that way while the display is active, and treat this as an upstream watch item.

The audio-side guarantee is structural and unchanged: the observer runs after physical DMA completion, posts to an overwrite-latest mailbox, and audio consumes PCM only on its own physical clock (`core_s3_audio_owner.c:660-681`); nothing on the visual side can insert a wait into the audio path.

## Q3 — Are the ISR callback, mailbox, semaphore, timeout, and framebuffer ownership race-safe and bounded?

**Yes — verified, including the one scenario that would have broken it.**

- **The chunking hazard is closed.** 38,400 B exceeds the S3 hardware limit of 32,768 B per SPI transaction (`spi_ll.h:44`), so `esp_lcd` splits the flush into two transactions — and sets the completion flag **only on the final chunk**, explicitly "to avoid premature completion callback" (`esp_lcd_panel_io_spi.c:354-401, 375-379`). Exactly one semaphore give per `draw_bitmap`; the drain-then-wait protocol (`stackchan_avatar.c:247-276`) is therefore correct. Had the callback fired per chunk, the renderer would have reused the buffer ~6 ms early every frame.
- **ISR side.** `on_i2s_tx_sent` → tap → observer runs in the I2S GDMA interrupt (`i2s_common.c:614-658`), is `IRAM_ATTR` with all touched state in `DRAM_ATTR` statics (`stackchan_avatar.c:142`), does one bounded 268 B staging copy plus `xQueueOverwriteFromISR` — the documented length‑1 mailbox pattern, copying under critical sections, so torn reads are impossible. Single ISR writer serializes `isr_staging`. `CONFIG_I2S_ISR_IRAM_SAFE=y` enforces the IRAM contract. Return-value plumbing to `portYIELD_FROM_ISR` is the standard contract (`gdma.c:822-851`).
- **Timeout policy.** On a 50 ms wait timeout, DMA ownership of the buffer is treated as unknowable: `display_active=0`, no retry, task suspends, buffer never freed or reused (`stackchan_avatar.c:262-276, 423-430`). A late completion's stale give is drained by `xSemaphoreTake(sem, 0)` before the next draw. This is the correct fail-closed shape; audio is untouched.
- **Framebuffer ownership.** Single task renders → swaps → queues → waits; the startup quadrant clear reuses the same buffer only after each completion (`stackchan_avatar.c:527-537`). No second writer exists; the animator seqlock (`face_animator.c:33-43, 314-368`) is same-task today and correctly fails one frame closed if a second writer ever appears.
- **Init order.** `ready` publishes before the audio owner installs the tap (`main.c:888` → `core_s3_audio_owner.c:1183`), so the observer can never see a half-built owner.
- **Two bounded caveats**, both acceptable if documented: `tx_color` can block on `portMAX_DELAY` internals if the bus wedges (`esp_lcd_panel_io_spi.c:361-367, 394`) — the avatar task parks invisibly rather than hitting its own 50 ms timeout; stalled `display_transfers` counters are the detection signal, which is one more reason to export them. And the analyzer task is not on the task watchdog — defensible for a priority‑2 lossy sidecar, but make it a decision, not an accident.

## Q4 — Shortest truthful on-device acceptance proof (no serial, no camera)

The existing harness (`apps/kit/scripts/prove-production-stackchan-grok.ts`) already proves audio, AEC, interruption, resources, and network validity in one ~40 s run with hard gates (silent-ready gate, exactly-one VAD edge pair per turn, interruption byte-ledger with zero unexplained loss, AEC ≥3 dB far-end suppression, delta-zero failure counters, and the RTT/RSSI/timeout network classifier — which is also the no-tolerated-loss Wi-Fi regression detector). The avatar needs three additions, in order:

1. **Recover flashing** via the ROM download strap (hold BOOT through power-cycle) — the endpoint vanished while Wi-Fi stayed up, so this is a USB/CDC recovery problem, not a dead board.
2. **Export an avatar metrics view.** The general sample's 2 KiB control slot has ~120 B of measured headroom — too small for ~10 new fields inline — so follow the AEC pattern: a dedicated serialization view plus a **third device subscription slot** (`STACKCHAN_METRICS_SUBSCRIPTION_CAPACITY` 2→3, `main.c:67`), harness-subscribed like `subscribeToAecMetrics`. Fields: `ready`, `playout_observations`, `rendered_frames`, `display_transfers`, `display_transfer_failures`, `display_transfer_timeouts`, `mailbox_failures`, `malformed_observations`, `maximum_display_transfer_us`, plus one new firmware counter `speaking_windows` (incremented in `finish_analysis_window` when `mouth_open != 0`) as the motion oracle.
3. **Gates on top of the unchanged existing proof**, baseline→terminal: `playout_observations` advances at ≈125/s (continuous physical clock); `rendered_frames` and `display_transfers` advance at ≈13–15 Hz and track each other; timeouts, failures, malformed and mailbox failures all delta-zero; `speaking_windows` advanced during the response window and not during the silent-ready window; existing CPU/heap/stack fields within an explicit new budget (post-fix expectation ≈35–40 KiB min internal heap floor — add an absolute floor gate, since today only delta gates exist and a 51 KiB regression sailed through unflagged).

Boot itself already proves avatar init: the target refuses to start voice without a working avatar (`main.c:888-896`), so a green voice run _entails_ display init, the four-quadrant clear, and one rendered+completed frame. State the residual honestly: wire-level transfer completion is the strongest in-band oracle — the panel ACKs nothing — so "pixels physically appeared" rests on one human eyeball check at flash time until an optical oracle exists.

## Q5 — What should be deleted or simplified

- **The local maximum is the PSRAM framebuffer.** It optimizes the visible metric (internal heap) while secretly spending internal heap through driver bounce buffers, tripling memory traffic, and adding per-frame malloc/free. The internal `MALLOC_CAP_DMA` buffer is smaller total system cost. The comment block at `stackchan_avatar.c:472-481` ("no display queue above ESP-IDF's own DMA transaction", "one explicit PSRAM buffer") describes a machine that v5.4.2 does not implement.
- **Misleading claims/counters** (the header's "Steady-state … allocate nothing" at `stackchan_avatar.h:55-57` is false today at the driver layer — fixed by the same alloc change): `render_failures` also counts display failures (`stackchan_avatar.c:352`), so a panel timeout increments two counters with different names; `malformed_observations` also counts not-ready calls (`:574-578`); the owner-level `playout_observer_frames/shape_errors` nearly duplicate the avatar's `playout_observations/malformed_observations` — pick one layer per fact before dashboards exist. The boot log's "160x120@15Hz" (`:560`) overstates a loop that is actually interval-plus-render-time, ≈13–14 Hz; log the interval instead.
- **Dead device surface from the WASM lab:** `face_render.h` declares a 74-profile enum and five functions (`face_render_frame`, `face_render_profile_*`) with **no definition anywhere in the component** — pure header debt on the firmware include path. `face_driver.c` (algorithm vtable), `face_stage.c` (cue system), and `face_animator_push_event`/`listening_lock`/activity states have zero device callers (the physical-playout envelope makes the listening lock redundant by construction — a genuinely good property). The linker drops the objects, but fence these as lab-only so they can't grow device-side.
- **Three of four atlases are dead flash.** All four are linked via the generated catalog, but no device code ever calls `face_avatar_registry_next/select` — there is no switching input. Either wire selection to a capability soon or ship one atlas for the next proof; don't keep the zombie middle indefinitely. (Only the selected atlas is validated at init, so boot cost is unaffected either way.)
- **Keep:** the exhaustive atlas validation (`face_sprite_sheet.c:843-1124` — every cell fully stream-decoded, palette-bounds-checked, placements and cycle periods validated at init; per-pixel clipping in `emit_scaled_pixel`), the seqlock-with-bounded-attempt (`snapshot_races` can't fire today but guards the future, as its comment says), the no-catch-up render pacing, and the boot-time hard dependency — it is exactly what makes boot itself proof-bearing. Two accepted quirks to document: the physical sample clock wraps after ~74.5 h of playout (`sequence*128` in uint32, `:600-603`), and the override BSP powers the camera feature inside `bsp_display_new` (`m5stack_core_s3.c:460`) for no reason on this target.

## Q6 — Ordered near-term fixes (before the next production proof)

1. **Fix the framebuffer allocation** — `MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL`, drop SPIRAM (one line at `stackchan_avatar.c:487-490`). Unbricks the current source, makes the DMA zero-copy claim true, deletes the per-frame bounce malloc+memcpy, and removes the whole PSRAM/dcache perturbation channel. Keep the 64‑byte alignment (harmless internally).
2. **Export the avatar metrics view + third subscription slot + harness gates** (Q4 #2–3, including the `speaking_windows` counter and an absolute min-internal-heap floor gate). Without this there is no truthful proof at all.
3. **Recover the flasher, flash the core‑1 build, run one full production proof**, and re-measure LAN loss with the face active — every existing avatar number (471–503‰, 27–30 KiB, 5–10% loss) is from the core‑0 build and is now doubly stale.
4. **Pin the SPI3 ISR to core 1** via `isr_cpu_id` in the override BSP's `bsp_spi_init`.
5. **Counter/log tidy** (dedupe the two observer-counter layers, split display failures out of `render_failures`, honest rate in the boot log) — cheap, and it protects the proof's interpretability.

Later, not now: avatar-switching capability or atlas pruning; fencing `face_render.h`/driver/stage to the lab; the watchdog decision for the analyzer task; the endurance ladder with the avatar compiled in; camera-rail removal from `bsp_display_new`; an optical oracle.

One process note: the avatar component and platform were committed to `c-capabilities` mid-review (the review docs are still untracked); given the prior worktree-reset incident, keep committing at each milestone — the blocker fix above should land as its own commit before flashing.
