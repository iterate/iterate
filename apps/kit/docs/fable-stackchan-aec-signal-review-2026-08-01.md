# Fable review: StackChan/CoreS3 full-duplex audio signal path — why Grok VAD hears no speech — 2026-08-01

Read-only review at `c-capabilities`. Sources: firmware/userspace first-hand reads, vendored esp_codec_dev/esp-sr/BSP sources, local ESP-IDF v5.4.2 checkout, the prior-art `iterate/stackchan` checkout (read-only), and first-party web docs (xAI, M5Stack). No hardware was touched; only this file was created.

## Executive verdict (five sentences)

The most likely reason Grok server VAD sees no user speech is that the clean uplink reaches Grok roughly 12 dB below the only proven-detectable level — the kit runs 24 dB analog mic gain with **no digital uplink stage** where prior art proved 24 dB analog **plus 12 dB digital** was required (18 dB analog was measured "Grok never detected speech" at −37.4 dBFS peaks) — while the session runs a bare `{"type":"server_vad"}` whose documented default `threshold` is 0.85 on a 0.1–0.9 scale ("higher values require louder audio to trigger"). The same physical run also suffered an independent uplink-transport starvation failure (≈62 in-place freshness recoveries, 1,930 dropped frames ≈30%, accept age up to 627 ms, close 1006 at ~128 s), which deleted or delayed much of the audio Grok could have judged; both defects must be fixed, but the level defect makes VAD deaf even on a healthy socket. The near/reference channel mapping (near=TDM slot 0, reference=slot 1) is **correct on this hardware** — proven not by the datasheet but by 1,242 one-second per-slot peak telemetry lines from prior art on the same board, where slot 1 is hot only during playback (electrical speaker reference), slot 2 tracks all acoustics at exactly the −37 dB expected of the second mic's PGA delta, and slot 3 is dead — so re-mapping slots or re-tuning the AEC before measurement would be wrong. The minimum instrumentation is to **fill the already-defined but producer-less `iterate_kit_aec_metrics_sample` schema** (`capabilities/include/iterate/kit/capabilities/metrics.h:139-164`, view already built in `metrics.c`) with stride-sampled, position-aligned near/reference/clean interval accumulators in the AEC task plus exchange-to-zero interval slot peaks — integer-only, no logging, no queues. Fix order: export the falsifiers, measure one scripted utterance, then apply +12 dB saturating digital gain in `copy_clean_uplink` plus explicit remote-tunable `turn_detection` parameters, and land the uplink-sender empty-ring/escalation fixes (B1/F3 from the shared-AEC review) before any soak.

## 2. Ranked causes of "Grok VAD sees no speech"

**R1 — Uplink level below the server-VAD trigger. Severity: blocks the goal. Confidence: HIGH.**
Evidence: prior art settled on `STACKCHAN_MIC_GAIN_DB 24` **plus** `STACKCHAN_UPLINK_GAIN_DB 12` (`firmware-ws/main/app_config.h:50-51`) after measuring that at 18 dB analog a loud prompt peaked −37.4 dBFS and "Grok never detected speech" (52 s deaf), while 37 dB analog clipped and self-answered; the kit ships 24 dB analog + **0 dB digital** (`copy_clean_uplink` has no gain stage) ⇒ predicted loud-speech peaks ≈ −31 dBFS (devicePcmPeak ≈ 900), 12 dB under the proven point (≈ −19 dBFS, peak ≈ 3 500); the bare session leaves `threshold` at its documented near-maximum default 0.85. Explains: healthy session/keepalives, frames flowing, zero `speech_started`. Cheapest falsification (zero firmware change): read `devicePcmPeakSample`/`devicePcmRmsSample` from the worker session metrics during one scripted loud utterance. Smallest fix: saturating ×4 (+12 dB) on clean frames in `copy_clean_uplink` + live `setMicGain`/`setUplinkGain` capability knobs + explicit `turn_detection {threshold≈0.5-0.6, silence_duration_ms 1000, prefix_padding_ms 400}` in `providers.ts` (threshold is the docs-proven remote lever needing no reflash).

**R2 — Uplink transport starvation. Severity: fatal to any run. Confidence: CONFIRMED present in the observed run; MEDIUM as the sole VAD cause.**
Evidence: the run's own counters (transport-AEC prompt): ~62 in-place freshness recoveries, ring high-water 31/32, 1,930 dropped frames (~30 % of 128 s), accept age 627 ms, close 1006 — a connected-but-stalled socket purging mic audio every ~500 ms with no escalation (shared review F3) plus the empty-ring fatal latch (B1, `pcm_uplink_sender.c:242-246`). Explains gappy/absent audio at Grok; does not explain deafness for the ~70 % delivered unless speech coincided with purge windows. Falsification: userspace `uplinkFrames` ≈ 50/s sustained while speaking; firmware `uplink_in_place_freshness_recoveries` ≈ 0. Fix: B1 UNAVAILABLE branch + F3 escalate-to-socket-replacement (already specified).

**R3 — AEC suppressing near speech. Severity: would block. Confidence: LOW-MEDIUM.**
The wrong-slot variant (reference = second acoustic mic ⇒ speech cancelled as echo) is **refuted** by the prior-art telemetry (slot 1 does not track speech). Residual: this port is the first to run esp-sr against the hardware slot-1 reference; NLP level 2 could still over-attenuate already-quiet speech, especially during/after playback. Falsification: with the R-instrumentation, speech-only window must show `clean_mean_absolute / near_mean_absolute` ≥ ~0.5 (−6 dB); far-end-only window should show it ≪ 1. Fix if confirmed: lower `nlp_level`, verify reference alignment — only after measurement.

**R4 — Near mic silent this boot (slot 0 dead). Severity: would block. Confidence: LOW.**
Same binary lineage measured a live mic, but nothing in the failing run proves it remotely (slot peaks unexported). Falsification: `near_peak`/`devicePcmRmsSample` ≈ 0 during speech. Fix: ES7210 bring-up debug only if observed.

**R5 — Userspace/provider format or config error. Confidence: VERY LOW.**
16 kHz binary PCM + `server_vad` is docs-legal and code-clean (mode header landed both ends; zero-length markers suppressed in firmware, fatal-if-seen in worker `pcm-proxy.ts:591-599`); the residual tunables (bare threshold, fragmentation) are folded into R1.

## 3. Minimum interval-aligned instrumentation

Everything below fills the **already-shipped** schema `struct iterate_kit_aec_metrics_sample` (`metrics.h:139-164`) whose Cap'n Web view (`build_aec_metrics_expression`, `metrics.c:950-1010`, `subscribe_aec_path`) exists but has **no producer** — `sample_runtime_metrics` (`main.c:213-451`) never sets `has_aec_detail`. Plumbing, not schema design.

**Producer (single writer = AEC task), in `process_aec()` (`core_s3_audio_owner.c:470-508`), where near/reference/clean 512-sample frames are all in scope:**
- Stride-4 walk (128 positions per 512-frame, same indices for all three streams — position alignment is the schema's stated contract): accumulate `near_abs_sum`, `ref_abs_sum`, `clean_abs_sum` (u32, saturating add) and `near_peak`, `ref_peak`, `clean_peak` (relaxed CAS-max, same helper as `tdm_slot_peak`), plus `window_sampled_samples` (+128) and `window_started_at_ms` (set when count==0).
- Overflow bound: stride-4 ⇒ 4 000 samples/s × 32 767 ≈ 1.31×10⁸/s; u32 saturates only after ~32 s of full-scale — 30× headroom over the 1 s interval; saturation is itself the "clipping" signal.
- Cost: ~384 loads+adds per 32 ms ≈ 12 k ops/s (<0.01 % of a 240 MHz core), zero heap, zero logging, no new tasks/queues.

**Snapshot/reset (single reader = the 1 000 ms metrics sampler via the existing subscription, `device_options.metrics.interval_ms = 1000U`, `main.c:576`):**
- Extend `iterate_kit_core_s3_audio_owner_metrics_snapshot` (or add `…_aec_window_snapshot`) to `__atomic_exchange_n(field, 0)` the six level fields + sampled count + window start; monotonically increment `sequence`. Exchange-to-zero is exactly the proven prior-art pattern (`audio_pipeline.c:763-775`). Document single-reader ownership; the writers use relaxed CAS so no torn windows beyond one 512-frame, acceptable for 1 s windows.
- Convert `tdm_slot_peak[4]` to the same interval semantics (exchange on snapshot) — its current max-since-boot value is useless after the first loud event; nothing else consumes it.
- `sample_stride=4`; `frames_processed/recreates/…/capture_bridge_errors` map 1:1 from existing counters; `signal_measurement_failures` counts snapshot-while-capture-failed.

**Wire-side (already exists — read, don't build):** `devicePcmPeakSample`/`devicePcmRmsSample`/`uplinkFrames` (post-provider-accept, `pcm-proxy.ts:659-668`) give the provider-received level; the provider event stream gives `speech_started`/transcription ground truth. Sent-level ≈ clean-level when the turn is active (`frames_accepted` distinguishes gating), so no extra firmware field is needed.

**Optional bounded raw capture (only if aggregates disagree):** a one-shot capability call copying the current 512-sample near/reference/clean static frames (3 KiB, single memcpy on request, may tear across one frame — diagnostic only). No hot-path cost, no streaming.

## 4. StackChan/HAVPE seam verdict

The seam already chosen is right and needs no rework for this proof: the shared surface is "audio owner produces clean 16 kHz mono PCM-v1 frames, consumes playback frames, and exposes uplink-active/interruption/generation-barrier hooks" plus the mode header; everything CoreS3-specific (TDM slots, esp-sr, BSP patch, AW88298) already lives in `platforms/iterate_core_s3_audio` + the patched BSP, and HAVPE's XMOS hardware pipeline slots in behind the same owner interface (per the shared-AEC review's first-party HAVPE audit; not re-verified here). `iterate_kit_aec_metrics_sample` is device-agnostic enough for both (HAVPE reports reference/clean from its hardware tap or zeros). Collapse **now**, because it simplifies the proof: (a) the triple `FULL_DUPLEX_AEC` declaration in `main.c` → one `STACKCHAN_AUDIO_MODE` in `stackchan_realtime_policy.h`; (b) fill the existing metrics plumbing instead of inventing any new export path. Defer (post-proof): `pcm_playback_interruption`/generation-fence merge, `voicelab_stream.c` deletion. Do not add a shared "DSP framework" — the two DSPs are correctly device-specific.

## 7. Uncertainties

1. Which **physical ES7210 pin** carries the speaker divider (MIC2 vs MIC3) — the slot-level mapping is measurement-proven, the label is not; the M5Stack docs page omits it and the ES7210 datasheet TDM channel order was not verified. Electrically irrelevant to current code (reference PGA is 0 dB either way).
2. Grok's `threshold`↔dBFS mapping is unpublished; 0.85 semantics are only qualitative ("louder audio").
3. Whether the failing run's userspace `devicePcm*` metrics were captured — if not, R1 vs R4 needs run A.
4. TX-unit vs RX-unit WS **phase** alignment on the shared pins is measurement-anchored, not docs-proven.
5. esp-sr NLP-2 attenuation of quiet near speech with a near-silent reference is closed-source behavior; the ERLE-proxy run settles it.
6. HAVPE first-party claims are carried from the shared-AEC review's audit, not re-verified here.
7. Slot map could shift on another CoreS3 revision or an esp_codec_dev bump — the F4 boot geometry assert and interval slot peaks are the guards.
