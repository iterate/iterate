## 1. Is userspace coalescing safe under all relevant orderings? (Q1)

**Invariant: while the first purge is pending, no downlink sample associated with a later response can become physically reachable. VERDICT: HOLDS (C), with two bounded device-side qualifiers that concern only *old*-response audio and predate this change.**

Worker leg (C, first-hand): every non-zero-byte device send goes through `#scheduleDownlink` (entry gate: `#closed || #interrupted || #playbackInterruptionPending || timer`) or `#sendDueDownlinkFrames` (re-checks the same three), both in `pcm-proxy.ts`. Enqueue never sends. The only gate-bypassing send is the zero-byte END marker in `#retireProviderAfterDownlinkOverflow` — zero samples, reachable only after 90 s of continuously-gated reservoir fill, which the device's 50 ms ack timeout terminates long before. JS single-threading means the gate cannot flip mid-priming-loop.

Ordering-by-ordering:

- **Second speech cycle while pending (the fixed regression)** — sound, provably: pending was continuously true from edge 1, so the response created between the edges lived entirely inside the gate — zero of its samples were ever admitted — and a second physical purge would have nothing to remove; the ring discard precedes the coalesce return, so leftovers cannot ride out; after the single ack only post-edge-2 content is admissible (C). All shared edge work (interrupted flag, discard+ledger, abandon, speech accounting) happens before the early return. Without the change, the second concurrent Cap'n Web call was rejected by the device (`"playback interruption already pending"`, `conversation.c:109-113`), the rejection matched the bumped epoch, and `#fail → close(4000)` killed a healthy session — the prior review's B2/T4 chain (C). Note honestly: `playbackInterruptionsCoalesced` was **0 in all six physical runs** (M) — every observed echo/speech cycle serialized behind a completed purge (`requested == completed` everywhere: 2/2, 1/1, 4/4, 5/5, 4/4, 3/3). The collision remains host-test-reproduced, not physically observed; the change is a guard, and it was not what unblocked the proof (wave 2 was).
- **Late promise settlement** — the epoch fence in both settlement handlers plus `#invalidatePlaybackInterruption()` at `close()`/`setConversationActive(false)` makes late acks/rejections inert; a conversation always passes through deactivation before reactivation, so `pending` is always false at conversation start. Coalescing correctly does *not* bump the epoch, so ack 1 releases the shared barrier (C).
- **Failure settlement after a coalesced edge** — the single failure kills the session for both cycles; fail-closed, no stale audio (C); untested (§3.2).
- **Provider `response.created`/binary reordering** — the retained record is now strong (M, provider-ordering trawl over kit + prior-art journals): a cancelled `response.done`, when it exists at all, is always a **"ghost"** — a response id with no `created` ever journaled (the post-function-call continuation caught by user speech) — and it always arrives immediately **before** the new `created` (4/4 observations, Stick journals). A **mid-audio** barge-in instead ends the old response with a **ladder-less `done(status=completed)`** (`output:[]`, no transcript/content-part/audio done events), same-millisecond as the interrupting `speech_started` (both retained mid-audio barge-ins, 08:46/08:49 runs); and many superseded responses get **no terminal event at all**. `created` preceded first audio in every measured case (456 ms–2.2 s across kit + prior-art probes); binary-before-`created` and cancelled-done-after-new-`created` are **ABSENT from all retained evidence** — the two hazards I traced in code (old-binary-after-`stopped` misclassified as the new response; late cancelled done discarding the new response's head and emitting an early END) remain **H**, pre-existing, unaffected by coalescing, and visible if ever real (unexplained-loss / early boundary). Do not pre-fix them.
- **Socket closure** — device close ⇒ `close()` ⇒ invalidate. Provider close mid-pendency ⇒ `#detachProvider` discards the ring while `pending` deliberately survives (purge is device-scoped); the replacement generation's audio stays gated until the ack (C). This is not hypothetical: one Stick journal retains a **mid-response provider-socket replacement** — fresh `session.created` in the same continuous journal with the open response never terminated (M). Device side: Cap'n Web `session_ended` drops the responder but keeps the slot (`conversation.c:247-262`); the module poll clears it at the next fence ack, ≤ ~18 ms healthy (C).
- **Conversation boundaries** — end-mid-purge invalidates the worker fence; the device slot self-frees via poll (one 8 ms io pass + one 10 ms main-loop pass). A stale slot can only reject a *new* conversation's first `interruptPlayback` if the audio owner is wedged (§6 latch) (C).

Device-side qualifiers (C, CoreS3 owner read): the purge's `reset_playback_state` clears the retained partial frame and drains the lane ring **but never touches codec DMA — up to 40 ms already written keeps playing**; and the PCM receive path has **no interruption epoch** (`downlink_generation_accepted` checks only the *socket* generation), so a pre-interruption frame still in TCP flight when the reset runs is admitted and played (bounded by the 12-frame/240 ms lead; the lane discard also snapshots depth, so concurrently-published frames survive it). All of these windows contain only *old*-response audio — the worker never sends later-response samples while pending — so the invariant as stated survives; worst case is ~¼ s of residual old audio right after a purge, unheard in any run so far. Coalescing neither adds to nor subtracts from it.

## 2. Should the C capability become multi-waiter/idempotent? (Q2)

**No. Keep the one-slot capability exactly as it is; worker-side coalescing is the bounded near-term design** (already implemented and now sitting under a passing proof).

- The worker is the **only** caller anywhere: `device-control.ts:25` is the sole call site, used only by `worker.ts:291-307`; the harness barge-in is acoustic-only (C). Single caller + single-flight at the caller makes device-side concurrency support dead weight.
- The cost of multi-waiter is not the ~24-32 B per responder slot; it is per-waiter 50 ms deadline clocks, `session_ended` sweeps across slots, and responder lifetime across session replacement — the itx connection reuses one `capnweb_session` across generations, so one missed sweep can answer a *different* deferred call in the next session (C). That is the fatal-latch bug family again.
- The prior review's D2 also carried a semantic trap: a joined waiter would be acknowledged by a purge admitted *before* its own speech edge — the worker's epoch fence exists precisely because such an ack must not be trusted across edges.
- Residual concurrent-call windows (replacement PCM session whose predecessor's RPC survives via `waitUntil`; conversation end→start; a future direct itx caller; DO restart) all reduce to the device's pending interval: milliseconds healthy, unbounded only under the suspended-owner latch — fixed systemically by the watchdog port (§5), after which a collision is fail-closed session recycling, which is designed behavior.
- Keep the rejection loud: post-coalescing it signals a genuinely unexpected caller or a wedged device — exactly what must be visible.

Backlog (next firmware touch, not now): `iterate_kit_conversation_metrics` has **zero callers** — the device-side `playback_interruption_{requests,completions,failures,timeouts,cancellations,backpressure}` counters are dark (C). Exporting them would have let today's runs prove device-side agreement with the worker's 3/3.

## 3. Missing red tests at public seams (Q3)

Worker seam (`pcm-proxy.test.ts`, driving only sockets/callbacks/metrics):

1. **Purge rejection is session-terminal**: `onPlaybackInterruption` rejects ⇒ `playback-interruption-failed` + close 4000 + `closed: true`. §2's safety argument rests on this staying loud; it is only implicit today.
2. **Coalesce then failure**: edge 1 pending, edge 2 coalesced, purge rejects ⇒ session still dies — guards against a future "we coalesced, so soften the failure".

4. **Provider replacement mid-pendency**: purge pending → provider dies → `attachProvider` → new-generation binary stays gated until ack, then plays. Pins that `attachProvider` never resets the purge fence — and the mid-response provider replacement is a measured reality (§1).

## 6. Runtime audit (Q6)

- **Worker**: coalescing adds two counters, zero timers/allocations; under a double edge it *removes* a Cap'n Web round trip and a rejection path. Metrics JSON grows by two numbers. The 2.88 MB reservoir accounting is unchanged; `downlinkInterruptedBytes` is increment-only arithmetic on existing paths.
- **Device (unchanged by this work, audited)**: purge = one-slot SPSC command + `reset_playback_state`: O(1) retained-frame clear + lane-ring walk ≤32 slot items, index traffic only — no sample memcpy, no locks, no logging, no heap, no I2S calls; at most one fence reset per 8 ms io pass, and a socket-generation edge wins the pass over an interruption, delaying that ack ≤8 ms (C). Healthy ack ≈ ≤18 ms (8 ms io + 10 ms main-loop poll) against the 50 ms budget — timeout implies ≥6 missed io passes, i.e. real trouble. Fence+interruption state ≈ ~310 B in the owner's internal-DRAM struct; conversation-module additions ≈ 60-70 B .bss; service runs on the io task's 4096 B static stack (estimates from struct layouts, not `sizeof`-verified) (C).
- **Priorities**: io 23 / aec 20 on core 1; pcm-net 6 / control-net 5 / main 1 on core 0; the purge handshake crosses only bounded mailboxes; nothing on the audio path blocks on RPC (C).
- **The one unbounded item — the latch**: if both codec directions fail 3× the io task suspends itself; the fence starves; `pending` never clears (timeout deliberately keeps the slot); every later `interruptPlayback` in every conversation rejects; the worker kills each session; nothing reboots the device — StackChan has no armed task watchdog (C). Rare trigger, certain latch, remedy is §5's port; §3.8 documents it until then.
- **Discipline reaffirmed**: no DSP conclusion was (or should be) drawn from network-invalid intervals — 08:33's digital "failures" were the purged reservoir (accounting, fixed by wave 2) and two radio-interval counters; the confirmatory AEC number comes from the network-valid 08:54 run.
