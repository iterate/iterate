## 2. What v3 has today for the same need

v3 closed this need last night, differently and in two places.

**In the project worker (commit 773978230, BUILD-LOG 2026-09-06 "identity"; as-built §4 "Who"):** `src/principal.ts` (86 code) — `Principal = { actor: string; email?: string }`, `ProjectTokenClaims = Principal & { projectId, expiresAt }`, `signProjectToken` / `verifyProjectToken` (HMAC-SHA256 over `<base64url payload>.<sig>`, `APP_CONFIG_PROJECT_TOKEN_SECRET`), `stampPrincipal`, `ITX_PRINCIPAL_HEADER = "x-itx-principal"`. `session.ts:92` `async authenticate(credentials?: { projectToken?: string })` → `INVALID_CREDENTIALS` on any bad token; `Session.whoami()`; `ProjectCollection.get` throws `FORBIDDEN` off-project (`session.ts:164-168`). `iterate-context.ts:157` picks `durableObject.invokeAs(principal, …)` over `invoke`; `:209-210` sets the header on a terminal fetch. The DO runs `invokeAs` under an `AsyncLocalStorage` (`iterate-context-durable-object.ts:743-750`), the fetch lane runs the app's invoke under the header's principal (`:777-784`), and the built-in append root stamps `source.principal` (`built-ins.ts:390` dep, `:222`). `worker.ts:77-98` is the `/.itx/session?token=&next=` cookie door on a project host; `:104-110` turns that cookie into `x-itx-principal`; `:163` strips it on `/expression`; `itx-entrypoint.ts:48` strips it for loaded workers. Proofs: `e2e/session-identity.e2e.test.ts` (32 code), the session-door test in `e2e/ingress-project-host.e2e.test.ts` (116 code), `src/principal.test.ts`.

**In the control plane (`packages/v3/control-plane/`, 985 lines):** a full front desk that v4 partly re-implements. `src/index.ts:18-44` — an OAuth 2.1 AS with `apiRoute: "/mcp"`, `/authorize` `/token` `/register`, **CIMD on**, PKCE S256, and `resolveExternalToken` turning a hashed API key into the *same* props. `src/app.ts:114-170` — the consent page, which also lets a caller emerge with an org+project. `src/session.ts` — the HMAC session cookie (30 d, server-side expiry), the shape `principal.ts` deliberately copies. `src/directory.ts` — users, orgs, projects, memberships, `access(userId, projectId)`, hashed API keys with grants. `src/ingress.ts:15-20` — `StampedCaller { actor, email, member, role }`. `src/mcp.ts` — an MCP server with `whoami` / `list_projects` / `create_project`.

**Outbound MCP already exists in v3's library:** `src/library/mcp.ts` (174 code), `itx.connectToMcp(url, { headers })`, a root at `context/built-in-roots.ts:26`, deliberately hand-written "without the MCP SDK: the whole client is the few requests below" (`library/mcp.ts:8`). v4 rewrote the same module onto the SDK and it came out at **177 code lines** — the SDK bought nothing on that side.

**Where v4 conflicts, specifically:**

1. **Two front desks.** v4 puts a login page, a session store and an OAuth AS *in the project worker*. The identity entry is explicit that "membership stays the control plane's: the token is minted after the check, so the worker calls no directory", and defers "the login page (the control plane's)". The control plane already has all of it, backed by D1.
2. **Identity that attributes nothing.** v4's principal stops at `Session.identity()`. On its own `/mcp` door it is dropped entirely (`worker.ts:114-116`), so an OAuth-authorized MCP `itx.kv.put` is indistinguishable in the log from an anonymous one. v3's whole point is `source.principal` on every append.
3. **Authority where v3 has attribution.** In a configured deployment v4's `/api` 401s without a cookie, and the cookie is minted by typing any email-shaped string. That is a gate with zero assurance: it converts identity into authority (against the trusted-client doctrine) while proving nothing, and forces every non-browser client through a login form — the e2e harness has to monkey-patch `fetch` and `WebSocket` to cope.
4. **A second dispatch door.** `/mcp` is a new platform door beside `/api` and `/expression`. `mcp-server.ts:2-3` argues MCP "is not a parallel capability API" — which is the argument for *not* giving it a parallel door.
5. **Routing back in the query string.** `/mcp?project=<id>` re-introduces exactly what `project-host.ts` removed last night (the assessment's Gap 1: the lane "puts the routing in the query string").
6. **A self-asserted project.** The consent page asks the user to *type* a project id; nothing checks membership. The grant scopes, it does not authorize.
7. **Fork lag, not disagreement.** v4 is `CODE_VERSION = "live-47"` (`worker.ts:54`) against v3's `live-53`; its `session.ts` predates `principal.ts` entirely. The `identity()` / `whoami()` split is a fork point, not a considered rejection.
8. **Bundle.** `@modelcontextprotocol/sdk` enters a worker whose deployed upload is 774 KiB with 8 ms startup (BUILD-LOG 2026-09-06).

**Where v4 is better and v3 should take it:** the stateless-per-request Streamable HTTP transport is the right shape and the reasoning at `mcp-server.ts:18-23` is correct; `jsonValue()` (`:84-91`) is an honest JSON boundary v3 has no equivalent of and will need; the CSWSH check (`auth.ts:102-106`) names a real class of bug; and `resourceMetadata` / RFC 9728 discovery is something whichever side hosts MCP must serve.

## 3. Proposed layering on v3

**The MCP server is a LIBRARY member, not a door.** `src/library/mcp-server.ts` exporting `itx.serveMcp()` — a handle whose one member is `fetch(request): Promise<Response>` — with the root added to `context/built-in-roots.ts` beside `connectToMcp`, and the verb + docstring to `library/index.ts`. It passes the litmus test verbatim: it takes only `itx` and a `Request`; it could be a userspace worker. Userspace mounts it with the verb that already exists:

```
itx.provide("itx.apps.mcp", "itx.serveMcp()")
```

and tonight's ingress serves it at `https://mcp--<projectId>.<base>/`. **No change to `worker.ts`'s doors, no `?project=`, no `PUBLIC_ORIGIN`, no `OAUTH_KV`.**

- ONE tool, `itx.invoke({ expression, args? })` → `itx.invoke(expression, ...args)` — the same expression the client would write over `/api`. Borrow v4's JSON boundary.
- It appends **no new event types**. Whatever the expression appends is stamped `source.principal` by the DO's append root, because the fetch lane already runs the app's invoke under the request's principal (`iterate-context-durable-object.ts:777-784`).
- One axiom touched: the module needs to turn a dotted string into steps, so `library/boundary.test.ts:12-16` gains `"../context/expression.ts"` beside `"../context/invoke-handle.ts"` (both pure leaf modules), and `LibraryItx` widens from `Pick<BuiltInScope,"fetch">` to `Pick<BuiltInScope,"fetch"|"cd">` — `library/index.ts:40` already says to widen it there.

**The bearer IS the project token.** One change on the ingress, ~8 lines in `worker.ts` beside the cookie read: a project host accepts `Authorization: Bearer <projectToken>` as an alternative to the `itx-project-session` cookie, verified by the same `verifyProjectToken` against the same project, stamping the same `x-itx-principal`. This is the assessment's Gap 7 machine lane, and it makes every MCP client's bearer a v3 project token with no new credential type, no token store and no OAuth code in the project worker. An unauthenticated MCP request answers 401 with `WWW-Authenticate: Bearer resource_metadata="<control-plane URL>"` so a client can discover where to get one.

**Login, the directory and the OAuth AS stay in the control plane.** v4's `auth.ts` is deleted, not ported. The control plane gains one thing: **mint a project token for a project the caller is a member of.** Two callers, both cheap because the machinery is there:
- a browser — the control plane redirects to `https://<projectId>.<base>/.itx/session?token=…&next=/`, the door that already exists;
- an MCP client — the existing AS (`control-plane/src/index.ts:18-44`) grants as it does today, and its `/mcp` server gains one tool (`project_token`) returning a short-lived project token for the granted project; `resolveExternalToken` means an API key works on the same path with no extra plumbing.

**Deliberately left out:** a project directory or a login page in the project worker; a tool per capability; MCP sessions and SSE; OAuth token storage anywhere but the control plane; a `/mcp` door on the worker's own hostname; any gate on `/api` — it stays anonymous by default (attribution, not authority).

## 7. Risks and questions for Jonas

1. **Library member or platform door?** I recommend the library + project host, because the litmus test is unambiguous and v4's own comment makes the argument. The honest counter: MCP clients expect one stable resource URL with `.well-known` metadata at its origin, and a per-project origin means N resources to register. If you want one endpoint for the whole deployment, it belongs on the **control plane** (which already hosts an AS and an MCP server), not as a third door on the project worker.
2. **Does an MCP bearer get the whole surface?** v4's one tool grants every itx expression to any bearer. Under the trusted-client doctrine that is consistent, but it is the first time an *external* client holds it, so it should be said out loud rather than inherited by accident.
3. **Is the control plane the only login?** This is the one thing the two trees actually disagree about. v4 proves a project worker *can* front users; v3's doctrine says it must not.
4. **Is a deliberately-unverified login acceptable on a URL people can find?** `auth.ts:263-266` renders "shared sandbox data, not a private account" on a page served at `https://v4.iterate2.app`. Preview-only artifact, or a thing to remove?
5. **Could not verify (asserted by v4, not run):** `README.md:180` "Deployed OAuth PKCE and a real MCP ITX write/read also passed" and `docs/preview-proof.md:970-974` "It passed 1/1". I read the test and the harness it depends on (`e2e/support/setup.ts:18-27` patches `globalThis.fetch` to attach the shared demo cookie, which is what makes the un-cookied `/authorize` POST at `mcp-deployed.e2e.test.ts:38-46` return 302 rather than the 303 the source would otherwise give); the path is coherent. Per the brief I did not run v4's tests.
6. **Could not verify:** whether `@modelcontextprotocol/sdk` fits the worker's startup budget. v4's README claims a deployed pass but names no upload size or startup time to compare against v3's 774 KiB / 8 ms.
7. **A coupling to reject explicitly:** v4's auth makes the entire deployed e2e suite run as one logged-in demo identity behind a monkey-patched `globalThis.fetch`/`WebSocket`. If v3 ever gates `/api`, it inherits that. My recommendation is that `/api` is never gated — but it is your call, because it is the same call as (3).
8. **Unnoticed in v4, worth knowing either way:** with `OAUTH_KV`/`PUBLIC_ORIGIN` unbound — the entire local and test posture — `/mcp?project=<anything>` answers with no credential at all (`auth.ts:52` + `worker.ts:111-117`), and no test covers it. "OAuth protects MCP" is true only of a configured deployment.
