# Bundling dynamic workers — v4 vs v3

## 1. What v4 has

Two independent things landed together and should be judged separately: a **build tier** (a sidecar
compiler worker + `itx.build` / `itx.check`) and a **second loader door** (`itx.workers.load`).
**Files** (code lines = non-blank, non-comment; measured):

| file                                                    | lines | what                                                             |
| ------------------------------------------------------- | ----: | ---------------------------------------------------------------- |
| `packages/v4/project-worker/src/build.ts`                |    51 | inert zod shapes: `BundleInput`, `RepositoryBuildInput`, `BuildResult`, `CheckDiagnostic` |
| `packages/v4/project-worker/src/bundler.ts`              |   224 | the sidecar `WorkerEntrypoint`: `build()`, `check()`, KV cache, base64 module codec |
| `packages/v4/project-worker/wrangler.bundler.jsonc`      |    13 | the sidecar's own wrangler config                                |
| `packages/v4/project-worker/build-types.mjs`             |   190 | emits `src/generated/type-files.ts` (**2,730,606 bytes** of `.d.ts` text) for `check` |
| `src/context/worker-loader.ts` lines 33–190              |   130 | `loadNativeWorker` + `NativeWorkerCode` + the cache-value digest |
| `src/context/built-ins.ts`                               |  ~38  | the `workers.load` entry (~30) + the build/check/repos/secrets root declarations (~8) |
| `src/iterate-context-durable-object.ts` :135, :546–7, :616–24 | ~12 | `BUNDLER: Service<Bundler>`, the two delegations, `#resolveSource` |
| `scripts/generate-deploy-config.ts` :71–85, `scripts/deploy.ts` :94 | ~16 | the sidecar's deploy config; sidecar deploys **first** |

v4's whole `worker-loader.ts` is **233** code lines against v3's **106**.

**Public API, as spelled** (`src/context/built-ins.ts:91–94, 188–193`):

```ts
build(input: BuildInput): Promise<BuildResult>;            // BuildInput = BundleInput | RepositoryBuildInput
check(input: BuildInput): Promise<CheckResult>;
workers.load(code: NativeWorkerCode,
             options?: { className?: string; props?: unknown; cacheKey?: string }): InvokeHandle;
```

`BundleInput = { files: Record<path,string>, options: { entryPoint, target?, minify?, sourcemap? } }`
(1–1024 files, ≤1 MiB each, relative paths only). `RepositoryBuildInput = { source: { repo, revision:
/^[a-f0-9]{64}$/ }, options }` — the DO resolves the revision to files via `#resolveSource`
(`iterate-context-durable-object.ts:616`) before the RPC, so the sidecar never sees a project.
`BuildResult` is `{ status:"built", code, key, cache:"hit"|"miss", diagnostics }` or
`{ status:"rejected", diagnostics }`. `NativeWorkerCode` is Cloudflare's `WorkerLoaderWorkerCode`
with `env` widened — the caller supplies `compatibilityDate`, `compatibilityFlags`,
`allowExperimental`, `limits`, `mainModule`, `modules` (js/cjs/text/json/data/wasm/py), `env`,
`tails`. Only `ITX` and `globalOutbound` are forced by the context (`worker-loader.ts:86–95`).

**Events appended: none.** Neither `build` nor `check` writes to the log. The Docs example appends
two *existing* event types (`events.iterate.com/docs/activated`, a userspace type, and
`events.iterate.com/itx/rewrite-rule-configured`, v3's) whose rewrite target inlines
`JSON.stringify(built.code)` — the whole bundle — into core state
(`e2e/docs-app.e2e.test.ts:151`, `src/client/docs.ts:497`).

**Config / bindings / infra:** a **second deployed Worker** (`envs.ts:600`
`iterate-v4-simplification-bundler`) with `nodejs_compat`, `define: {"process.browser":"true"}`, a
`version_metadata` binding and its own KV `BUILD_CACHE` (`envs.ts:616`, 24 h TTL, `bundler.ts:92`);
a `BUNDLER` service binding on the main worker; an ordered deploy (sidecar first); and the generated
2.7 MB `type-files.ts` compiled in. Dependency `@cloudflare/worker-bundler@0.2.1` — measured on disk:
`dist/esbuild.wasm` **13 MB**, `dist/typescript.js` **4.4 MB**.

**Tests:** `e2e/build.e2e.test.ts` (119 lines, 4: build + cache miss/hit, pinned-repo build then
`workers.load`, syntax diagnostics, `check` against the real emitted ITX `.d.ts`);
`e2e/workers-native-input.e2e.test.ts` (162 lines, 7; 137 native — cacheKey reuse, key changes with
code and with JSON module data, live-binding refusal, `env`/props/ITX authority, `globalOutbound`
override); `src/context/worker-loader.test.ts:132–240` (102 lines, 2 unit tests over a fake loader);
plus `e2e/rpc-inert-result-release.e2e.test.ts` and `e2e/docs-app.e2e.test.ts`. **None is named
`*.deployed.e2e.test.ts`** — the lane is steerable at a deployed worker via `WORKER_BASE_URL`
(`e2e/support/global-setup.ts:65–69`), and `README.md` + `docs/preview-proof.md` (:220, :585, :650,
:730 — builds at 456/500/676/774 ms) claim they passed on preview. I read the claim; I did not run it.

**Depends on inside v4:** `src/repos.ts` (275 lines) for the pinned-revision input and
`src/generated/type-files.ts` for `check`. `workers.load` depends on nothing but the loader.

## 2. What v3 has today for the same need

v3 has **exactly one** loading door per host kind and a deliberate hole where the build tier goes.
`itx.workers.get({ source, cacheKey?, className?, props? })` and `itx.facets.get(name, { source,
cacheKey?, className })` both bottom out in `loadConfinedWorker` (`src/context/worker-loader.ts`).
`WorkerSource` is either the modules literally (`Record<string,string>`, `"cap.js"` the main module)
**or an itx expression that PRODUCES them**, which runs inside Cloudflare's `LOADER.get(id, getCode)`
— on a cold isolate only — and is refused without a `cacheKey` (`worker-loader.ts:166–169`). That
producer path is v3's answer to building, and it is already exercised with the literal spelling
`source: "itx.build('todo')"` in `worker-loader.test.ts:76`.

The design is on the record twice. `docs/itx-surface-as-built.md:580`: the KV-artifact tier "belongs
to a build capability, not to the loader door." `docs/reviews/2026-09-02-futures.md:399–410`
prescribes the whole shape: *"Nothing new at the loader door"* — `itx.build` as a hosted facet with a
single-flight coordinator and a KV artifact; **the bundler is a second deployed worker (a sidecar),
not a loaded isolate — "the 13 MiB wasm and the 128 MiB isolate ceiling make that a topology fact,
not a preference"**; `source: "itx.build.artifact('<buildKey>')"` with `cacheKey: '<buildKey>'`; one
new spec field `budgetMs?` and one code `BUILD_IN_PROGRESS`.
`docs/assessment-userspace-apps-on-the-clean-room.md:352` writes activation the same way:
`itx.apps.docs ⇒ itx.workers.get({ source: <the TanStack build>, cacheKey: <build id> })`.

**Where v4 conflicts with v3:**
1. **Two doors for one host, with different rules.** `workers.load` is not "another input shape for
   the existing execution host" (`docs/structural-simplicity-research.md:171`). `loadConfinedWorker`
   forces `compatibilityFlags: ["no_nodejs_compat","no_nodejs_compat_v2",
   "allow_irrevocable_stub_storage"]`, `mainModule: "cap.js"`, `env: { ITX }` only, and injects the
   processor SDK on demand (`worker-loader.ts:202–228`). `loadNativeWorker` forces **none** of it: it
   spreads the caller's `code` through. So a `workers.load` worker gets nodejs_compat on by default
   (v4's bundler emits only `["no_nodejs_compat"]`, `bundler.ts:89`), cannot persist its ITX stub
   (`e2e/facets-persistent-stub.e2e.test.ts`'s trick), and never gets `processor.js`.
2. **`workers.load` has no facet twin.** v4's `facets.get` still takes `FacetSpec { source:
   WorkerSource, … }` (the `built-ins.ts` diff touches only `workers`). So a built bundle can be a
   stateless worker but **cannot be hosted as a processor or a durable facet** — build-then-host is
   unreachable, which is most of what an app wants.
3. **The bundle is inlined into a durable rewrite target** rather than named by a producer
   expression. v4's own `docs/structural-simplicity-research.md:173–178` concedes this: "that target
   remains in core state and its checkpoint and is printed when listing rules… a real cost." It
   collides with d3's memory arc — the 8 MiB read ceiling, `EVENT_TOO_LARGE`, and the refusal of a
   4.5 MiB literal processor target.
4. **No single-flight, no budget, no `BUILD_IN_PROGRESS`.** A build blocks its caller for 456–774 ms
   (v4's own measurements) and two identical concurrent builds do the work twice.
5. **Merge friction:** v4 forked before `src/principal.ts`, so its `built-ins.ts` `append` is
   `ownContext().append(...e)` where v3 now has `stampPrincipal(event, deps.principal())`.

**Where v4 is right and v3 is wrong — two real loader bugs, take both:**
- **djb2 collides.** v3's 32-bit content hash (`worker-loader.ts:91–101`) is a rolling `h*33 + c`, so
  the single-character substitution `"Aa" → "B@"` at the same offset is a *whole-string* collision. I
  computed both module maps from `e2e/workers-native-input.e2e.test.ts:9`: **both hash to
  `1967169959`**. Two different sources share one isolate — silently the wrong code. v4 uses SHA-256
  over name-sorted modules.
- **The loaderId delimiter is ambiguous.** v3 composes `${kind}:${deployId}:${owner}:${sourceVersion}`
  (`worker-loader.ts:180`). `facetLoaderOwner` length-prefixes the *facet* owner, but a **caller's
  `cacheKey` may contain `:`**: context `/x` + cacheKey `y:z` and context `/x:y` + cacheKey `z` both
  compose `worker:d:prj_u.iterate/x:y:z` — a cross-context authority transfer, the exact bug
  `facetLoaderOwner` exists to prevent. v4's `JSON.stringify([...])` fixes it.
- v4 also **drops the WeakMap memo** (a caller may mutate a modules record after its first load) —
  fair, but v3's memo is a measured hot-path claim. Keep the fix; memoize on the serialized string.

## 3. Proposed layering on v3

**Answers to the three questions, sharply.** *What can the sidecar do that a loaded worker cannot?* Not "esbuild can't run in an isolate" — it
can; v4 proves it. **Delivery and residency.** The compiler is 13 MB of wasm + 4.4 MB of TypeScript
+ 2.7 MB of generated `.d.ts`. A loaded worker's modules travel through the DO on every cold load and
are part of its cacheKey digest; v3 refuses a 4.5 MiB literal source and caps a read page at 8 MiB,
and the DO isolate ceiling is 128 MiB. And **not npm resolution**: v4 explicitly *refuses*
dependencies (`bundler.ts:47–53`, "registry installation is not enabled") even though
`@cloudflare/worker-bundler` ships `installDependencies`. Also: a cross-project artifact cache needs
a KV outside any one project — `itx.kv` is project-prefixed.

*Separate worker, or a library member behind `itx.fetch`?* **Separate deployed worker.** Not the
library: `src/library/` members take only `itx` and run *inside the DO isolate*
(`library/boundary.test.ts`) — esbuild there would be in every DO and every `/api` isolate. v3 has
the precedent already (`FALLBACK` → the separately deployed `iterate-control-plane`). But it is
**not** a new concept: classify `build`/`check` as a **binding root**, the same tier as `itx.ai`
("Cloudflare's Workers AI binding, VERBATIM"). It fails the userspace litmus test only on size, and
`check` is genuinely platform-coupled — its type graph is emitted from `src/iterate-context.ts` and
`src/session.ts`, so it must be regenerated with the platform.

*Replace or sit beside `workers.get`?* **Neither — do not land `workers.load` at all.** Once
activation names a producer expression, native input has no consumer. What remains of it
(caller-chosen compat flags, `limits`, `env` bindings, `tails`) is precisely what v3's confinement
contract refuses on purpose (`worker-loader.ts:210–223`: "trusted clients", no `limits`; the whole
world of a loaded isolate *is* its owning context). `bundle: true` is `createWorker`'s default, so a
build is one JS module — rename its entry to `"cap.js"` and v3's existing `WorkerModules` carries it.

**The spelling:**
- `itx.builtins.build(input)` → `{ status, key, code, diagnostics, cache }` — root, over a `BUNDLER`
  service binding. `input` is v4's `BundleInput | RepositoryBuildInput`, verbatim: it is good.
- `itx.builtins.check(input)` → `{ status, diagnostics }` — root, same binding.
- `itx.builtins.workers.get({ source, cacheKey?, className?, props? })` — **unchanged**. Activation is
  `itx.workers.get({ source: "itx.build({ source: { repo: '/apps/docs', revision: '<sha>' }, options:
  { entryPoint: 'src/main.ts' } }).code", cacheKey: "<buildKey>" })`. The producer names the *pinned
  input*, not the artifact key, so a KV eviction rebuilds instead of stranding a durable activation —
  v4's own compatibility law (`structural-simplicity-research.md:187`), satisfied more cheaply than
  v4's futures note (`itx.build.artifact('<key>')`) would.
- `itx.builtins.facets.get(name, { source: "<the same producer>", cacheKey, className })` — a built
  processor gets hosted for free. This is the capability v4 does not have.
- **Deliberately left out:** `workers.load`, `NativeWorkerCode`, the cache-value digest and its
  live-binding refusal (~130 lines — unreachable once `source` stays a data-only module map),
  caller-chosen compat flags / `limits` / `env` / `tails`, npm resolution, and (for a first cut) the
  single-flight coordinator and `budgetMs` / `BUILD_IN_PROGRESS` — the producer already runs inside
  `getCode` on a cold isolate only, which is most of what single-flight buys.
- **Events:** none new. Activation stays `events.iterate.com/itx/rewrite-rule-configured` with a
  producer target — a few hundred bytes in core state instead of a whole bundle.

## 4. Implementation sketch

1. **Fix the two loader bugs first** (independent, lands tonight). `src/context/worker-loader.ts`:
   SHA-256 (name-sorted) for `contentHashOfWorkerModules`, memoized on the serialized string;
   `JSON.stringify([kind, deployId, owner, sourceVersion])` for `loaderIdBase`. Extend
   `src/context/worker-loader.test.ts` with the `"Aa"`/`"B@"` collision row and a
   context-`/x`+key-`y:z` vs context-`/x:y`+key-`z` row. Proof: `e2e/workers-and-facets-sources.e2e.test.ts`
   gains a two-source-no-share case, run deployed with `WORKER_BASE_URL`.
2. **The sidecar.** New `packages/v3/project-worker/src/bundler.ts` — port v4's `build()` and
   `check()` (drop `storeModules`/`restoreCode`'s ArrayBuffer arm; a `Record<string,string>` module
   map needs no base64 codec), plus `build-types.mjs` and `wrangler.bundler.jsonc`. Emit the entry as
   `"cap.js"`. Proof: unit tests on the sidecar's cache key.
3. **The root.** New `src/build.ts` (the zod shapes, minus `NativeWorkerCode`); `BUNDLER:
   Service<Bundler>` in `iterate-context-durable-object.ts`; `build`/`check` in
   `src/context/built-ins.ts` + `built-in-roots.ts` + `src/iterate-context.ts`; the `#resolveSource`
   repo hop. Infra alongside: `envs.ts` gains `bundlerWorkerName` + `buildCacheKvId`,
   `wrangler.jsonc` the `BUNDLER` binding, the deploy script the ordering. Proof: a port of
   `e2e/build.e2e.test.ts` (miss/hit, minify changes the key, diagnostics are data), deployed.
4. **The producer round-trip — the proof that matters.** New
   `e2e/build-producer-activation.e2e.test.ts`: build a pinned revision, append **one**
   `rewrite-rule-configured` whose target is the producer expression, close the session, then reach
   `itx.docs` from a fresh client and from the project host. Assert the stored target is under ~500
   bytes and that `itx.builtins.rewriteRules.list()` does not print a bundle. Deployed.
5. **The facet twin.** Host a built processor via `facets.get(name, { source: <producer>, cacheKey,
   className })`; proof: a port of `e2e/processor-facet-same-name-source.e2e.test.ts` over a build.

Step 3 needs a repo capability for the `RepositoryBuildInput` arm. Ship 1–3 with `BundleInput` only
(files in, code out) and add the repo arm when repos land (§6).

## 5. Effort

v4's upper bound, measured: 51 + 224 + 13 + 190 (`build-types.mjs`) + ~65 (built-ins + DO + deploy
wiring) + 130 (the native block) = **~673 implementation lines**, plus ~360 test lines.

The proposal drops the 130-line native block, ~30 lines of `workers.load` in `built-ins.ts`, and
~25 lines of base64/ArrayBuffer codec in `bundler.ts` — and adds ~15 lines of loader-bug fix.
**~500 implementation lines + ~300 test lines.** At v3's density (~300 code lines with tests, docs
and a deployed proof in ~3 hours), that is **~6–8 working hours**, assuming the sidecar port is
mechanical. Step 1 alone is ~15 lines and ~45 minutes; it should land tonight regardless.

## 6. Dependencies and sequencing

- **Independent, land first:** step 1 (the two loader bugs) — it touches only `worker-loader.ts` and
  is a correctness fix to shipped behaviour.
- **Must land first for the full feature:** *nothing in the platform* for `BundleInput`. The
  `RepositoryBuildInput` arm needs a **repo capability** — v3's Gap 3
  (`docs/assessment-userspace-apps-on-the-clean-room.md:195`), ranked third, whose recommended shape
  is a git-wire client in a loaded worker, not a platform repo DO. v4 instead ships `src/repos.ts`
  (275 lines) as a platform root; that is a separate review's call.
- **Infra:** a new Worker name and a new KV namespace per environment, plus an ordered two-worker
  deploy. No DNS, no new secrets.
- **Unblocks:** the Docs publish flow; a userspace app served on a project host (Gap 1's point —
  `assessment:352`); any "config worker from a repo" tier.
- **Interacts with** ingress/identity only at the merge (`append` + `principal`), and with d3's
  memory work in that the producer-expression activation is what keeps bundles out of core state.

## 7. Risks and questions for Jonas

1. **Is `build` a root, or a userspace remote app?** I recommend a root beside `itx.ai` (a binding
   exposed verbatim). The purist litmus reading says mount it behind `itx.fetch` as a remote app and
   ship zero build code in the platform. `check` argues against that: its type graph is emitted from
   the platform's own `.d.ts` and must be regenerated with it.
2. **npm.** v4 refuses dependencies outright. That is the *right* first cut and it dodges the
   hermeticity bug the record flags twice ("npm ranges re-resolve at build time, so the 'immutable'
   build key isn't"). But pinning a resolved lockfile into the key is "a one-field decision now and
   an un-fixable one later" (`futures.md:420`). Decide now even if deps ship later.
3. **Producer expression vs inlined bundle.** I recommend against v4's shipped choice; v4's own
   research doc agrees it is a cost but calls the fix "not implemented or measured here". If you want
   the inlined form for auditability (the bundle is *in* the log), say so — a storage decision.
4. **Single-flight and budgets.** Deferred in my sketch; v3's futures review wanted `budgetMs?` +
   `BUILD_IN_PROGRESS` from day one. At 456–774 ms with the producer running only on a cold isolate,
   I would wait for a measurement — your call.
5. **Unverified v4 claims.** I read but did not run: that the build/native tests pass against the
   deployed preview (`README.md`, `docs/preview-proof.md`); that the sidecar's compiled script fits
   under the Workers script-size limit (13 MB wasm + 4.4 MB TS + 2.7 MB `.d.ts` compresses, but I did
   not measure the uploaded artifact); and that `check`'s `skipLibCheck: true` hides nothing real.
6. **Who owns the runtime contract?** My proposal routes built modules through
   `loadConfinedWorker`, so the *platform* fixes compat flags and a built worker can persist its ITX
   stub — but the app then never chooses its own compat date, flags or `limits`. Confirm.
