# Ingress and hostnames — v4 vs v3

All line counts are measured (non-blank, non-comment) unless marked raw.

## 1. What v4 has

**Files.**

| File                                                               | Code lines | What                                                                          |

≈ **130 code lines** of implementation attributable to ingress, plus the 9-line example.

**The public API as spelled.** There is none on `itx`. Ingress is entirely edge + config:

```ts
export type ProjectHostDirectory = {
  projectHostnameBase: string;
  projects: Readonly<Record<string, string>>; // slug  -> projectId
  customHostnames: Readonly<Record<string, string>>; // host  -> projectId
};
export type ProjectHostResolution =
  | { kind: "project"; projectId: string; app: string | null }
  | { kind: "unknown" }
  | null;
export function resolveProjectHost(
  url: URL,
  directory: ProjectHostDirectory,
): ProjectHostResolution;
```

Resolution order (`src/ingress.ts:24-59`): normalize (lowercase, strip a leading `*.` and a trailing
`.`) → exact `customHostnames` hit → longest registered custom domain with **one** label below it →
under `.<base>`, exact `projects` slug → longest registered slug with a `--` **or** `-` prefix →
otherwise `{ kind: "unknown" }` under the base, `null` off it.

The user-space contract is the README's: "Project and custom hostnames enter the root context's
ordinary `itx.fetch` policy. A user-space router can send a host to `itx.docs.fetch(request)` and
must delegate ordinary external requests to `itx.builtins.fetch(request)`." The router is installed
as a durable `events.iterate.com/itx/rewrite-rule-configured` fact with
`match: "itx.fetch"` (`e2e/project-ingress-deployed.e2e.test.ts:31-46`).

**Events it appends.** None. Ingress appends nothing; the log never names a hostname (same as v3).
The router's _installation_ is an ordinary rewrite-rule event.

**Config/bindings/infra.** `APP_CONFIG_PROJECT_HOSTNAME_BASE` (default `localhost`),
`APP_CONFIG_PROJECTS_JSON`, `APP_CONFIG_CUSTOM_HOSTNAMES_JSON`, `PUBLIC_ORIGIN`; three worker
routes in `envs.ts` (`v4.iterate2.app/*`, `*v4-demo.iterate2.app/*`, `v4-custom.iterate2.app/*`) in
zone `iterate2.app`. The checked-in `wrangler.jsonc` has **no routes** — deploy configs are
generated. **There is no Cloudflare-for-SaaS / SSL-for-SaaS anywhere**: `v4-custom.iterate2.app` is
a second name in v4's own zone, so "custom hostname" is proved only as a second map entry, not as a
third-party domain.

**Tests.** `src/ingress.test.ts` (47 lines, 3 cases: slug/app precedence, custom-name precedence,
unknown + prototype-pollution). `e2e/ingress.e2e.test.ts` (103) — local, drives raw `node:http`
with a forged `Host`; proves a header cannot choose the project, `/api` on a project host is the
app's, and an unknown host is 421. `e2e/project-ingress-deployed.e2e.test.ts` (95) — one local row;
two rows **deployed-only and opt-in behind `PROJECT_INGRESS_PROOF=1`** plus four env vars, so they
do not run in the default lane. `docs/preview-proof.md:960-987` records both hostnames serving 200
after the installer session closed.

**What inside v4 it depends on.** `app-config.ts` (the directory vars), `DurableObjectNameCodec`,
the DO fetch door's default expression `"itx"` (`iterate-context-durable-object.ts:951-954`), the
rewrite-rule table (the router row), `workers.get`/`load` (the router is a loaded worker),
`#egress` + `FetchPolicy` (the terminal), and `auth.ts`'s `PUBLIC_ORIGIN` reservation.

## 2. What v3 has today for the same need

`src/project-host.ts` (29 code lines; 18 of them the resolver, 11 the session-cookie helpers that
belong to identity) + the `worker.ts:66-114` branch (42 code lines, of which **16 are ingress** and
26 the `/.itx/session` identity door) + `src/project-host.test.ts` (47, a 15-row table) +
`e2e/ingress-project-host.e2e.test.ts` (116) + `e2e/support/project-host.ts` (55). Deployed under
route `*.project-worker.iterate.com/*` with a proxied wildcard AAAA `100::`.

v3: `projectHostOf(hostname, base)` → `{ projectId, itxExpression: "itx.apps.<label>" }`, apex ⇒
`itx.apps.default`. The edge strips `x-itx-*`, sets `x-itx-expression` to that spelling and
`x-itx-expression-hops: 1`, stamps `x-itx-principal` from the host cookie, and rides the Request
**verbatim** into the fetch lane the DO already had. No directory, no redeploy, no new DO code.

**Where v4 conflicts with v3's doctrines / tonight's work.**

1. **Ingress is spelled as egress.** v4's edge sets no expression, so the DO defaults to `"itx"` →
   `itxExpressionEndingInFetch` → `itx.fetch(request)` → with no rule, `itx.builtins.fetch` =
   `#egress`. An _inbound browser request_ is therefore run through
   `substituteHeaderSecrets(request, "project", …)` (`iterate-context-durable-object.ts:998-1002`)
   before the loop guard fires. A visitor who sends a header containing
   `{{secret:project:NAME}}` gets a 502 that **names the token** when no such secret exists and a
   different status when it does — an unauthenticated existence oracle on secret names. v3's
   ingress never touches the egress door.
2. **The default answer for an unconfigured host is self-recursion.** `docs/preview-proof.md:981`
   records it happening live: disposing the `provide()`d rule "caused the self-loop", and the
   `PROJECT_FETCH_NOT_CONFIGURED` terminal guard exists to "turn that missing-route state into a
   bounded 404 instead of self-recursion". v3's equivalent failure is `NO_ITX_EXPRESSION_MATCH` →
   404 — structurally incapable of looping.
3. **An ingress route can no longer be a live capability.** `examples/docs/router.ts:1-6` warns the
   router "must not be lent with `itx.provide()`: that deliberately recalls its rule when the
   provider session ends." That kills the D1 headline use — `iterate tunnel site 3000` ==
   `itx.provide("itx.apps.site", new Tunnel(3000))`, one call, one event, dying with the laptop.
   In v3 that is the _correct_ semantics; in v4 it is a footgun to be avoided.
4. **`itx.apps` does not exist in v4** (grep: zero hits in `src/`, `examples/`, `e2e/`, `docs/`).
   The label is parsed and then **discarded**: `ProjectHostResolution.app` has no consumer anywhere
   in production code (only `worker.ts:180` reading `.projectId` and `:1022` in the guard). It is
   asserted only in `src/ingress.test.ts`. So v4 pays for label parsing and gets nothing; the
   router re-derives the host itself from `request.url`.
5. **The directory is a deployment variable.** Adding a project slug or a hostname means editing
   `envs.ts` and **redeploying the worker** (and adding a route). That is not a control plane; it
   is a constant pretending to be one — against "configuration is what differs between deployments"
   (as-built §10) and against D6, which puts `routes(host, project_id, app)` in the control plane.
6. **No identity on a project host.** v4's `BrowserPrincipal` exists only on `PUBLIC_ORIGIN`
   (`worker.ts:169-171` → `dashboard`); the ingress branch stamps nothing. Tonight's v3 ingress
   carries `x-itx-principal` from the host-scoped `itx-project-session` cookie
   (`e2e/ingress-project-host.e2e.test.ts:87-127`). v4 has no `/.itx/session` equivalent.
7. **The single-hyphen spelling needs the directory to disambiguate.** `editor-blue-team` is only
   resolvable because `blue-team` is a registered slug. v3's `--` is unambiguous with zero lookup.

## 3. Proposed layering on v3

**Verdict: v3's primitive is the right one — a hostname names a capability
(`itx.apps.<label>`), and the Request enters the fetch lane it already had.** v4's
router-through-`itx.fetch` is a **second mechanism, not a safety mechanism**. The safety property
its README claims ("cannot bypass secret substitution or approval policy") comes entirely from the
_terminal_ being `itx.builtins.fetch`, which is equally true in v3, where inbound traffic never
enters that verb at all. Note also that v3 already permits `itx.provide("itx.fetch", <gate>)` —
`fetch` is a shadowable platform row (`src/context/built-in-roots.ts:18`, rewrite rule 5) — so v4
invented no new middleware power. And v4's own router is expressible in v3 today, unchanged, as
**one row**: `itx.provide("itx.apps.default", "itx.workers.get({ source })")`. Routing ingress
through `itx.fetch` buys nothing and costs items 1–3 above.

**But v4 found one real hole in v3, and it is serious.** v3's convention makes every DNS label
under the wildcard a valid address, and the v3 DO constructor appends `stream/created` +
`stream/woken` synchronously (`iterate-context-durable-object.ts` constructor;
`stream/stream.ts:24-26`: "a probe on a never-seen context materializes it — deliberately"). So
`curl https://x--anything.project-worker.iterate.com/` mints a durable, storage-backed DO, from the
public internet, unauthenticated, unboundedly. v4's `{ kind: "unknown" }` → 421 closes this before
any DO is dialled. **This is the thing to take.**

The smallest v3 design that keeps the doctrines:

- **Keep** `projectHostOf(hostname, base)` and `itx.apps.<label>` verbatim. Keep `--` only.
- **Add an admission step at the edge, before the DO is dialled.** One directory lookup, in the
  edge worker, cached per isolate: `env.FALLBACK` — the control-plane shell — answers
  `resolveProjectHostname(hostname) → { projectId, label } | null`. This is exactly D2's own
  prescription ("ONE directory read through FALLBACK, cached for the incarnation") and D6's row
  ("host → projectId: control plane"). A decline is **421**, before any DO exists.
- **The directory subsumes pretty slugs and custom domains for free** — `notes.acme.com →
{ projectId, label: "default" }` is one row; the convention `<label>--<projectId>.<base>` is a row
  the control plane synthesizes for ids it owns. One code path, not two.
- **Take v4's config map as the _test seam_ only**: `APP_CONFIG_PROJECT_HOSTNAMES_JSON`
  (host → `projectId`) for the solo/workers lanes where there is no control plane, consulted before
  FALLBACK. Deployed, FALLBACK is the authority. Be honest in the header that the map is the local
  stand-in, never the production directory.
- **Take v4's `normalizeHostname`** (2 lines): strip a trailing `.` and a leading `*.`. Today a
  Host of `site--p.base.` (legal, fully-qualified) misses v3's `endsWith` and falls through to the
  platform doors instead of the app.
- **Take v4's reserved-origin guard** as a config row (`APP_CONFIG_RESERVED_HOSTNAMES_JSON`),
  needed the moment the platform's own dashboard shares the base zone. v3's base is a dedicated
  subdomain today, so this is one row and a comment, not a mechanism.
- **Deliberately left out**: `itx.fetch` as the ingress verb; the `-` (single-hyphen) spelling;
  `customHostnames` as a deployment var; the `PROJECT_FETCH_NOT_CONFIGURED` guard (unneeded once
  ingress never enters egress); a router example (an app is a row, not a program).
- **Events**: still none. The log never names a hostname; the directory row is control-plane state
  with its own lifetime. **Doors**: `/.itx/session` unchanged.

## 4. Implementation sketch

1. **`src/project-host.ts`** — add `normalizeHostname` to `projectHostOf` and two rows to the
   15-row table (`FQDN.` and `*.`). Change the return to include `label`. _Proof_:
   `src/project-host.test.ts` rows (unit).
2. **`src/app-config.ts`** — one row `APP_CONFIG_PROJECT_HOSTNAMES_JSON` with a `stringRecord`
   parser lifted from v4 (`src/app-config.ts:54-64`), default `{}`; one row
   `APP_CONFIG_RESERVED_HOSTNAMES_JSON`, default `{}`. _Proof_: `app-config.test.ts`.
3. **`packages/v3/control-plane-shell`** — add `ControlPlaneShell.resolveProjectHostname(hostname)`
   returning `{ projectId, label } | null` over its existing service binding, backed by whatever
   table it keeps; synthesize the convention row for ids it owns. _Proof_: a shell unit test.
4. **`src/worker.ts`** — the branch becomes: normalize → reserved-hostname check → config map →
   `env.FALLBACK.resolveProjectHostname(...)` with an isolate-level `Map` cache (short TTL) →
   decline ⇒ **421** → else the existing strip/stamp/dial, unchanged. _Proof (deployed)_: extend
   `e2e/ingress-project-host.e2e.test.ts` with (a) an unregistered host under the base answering 421
   and creating no context — assert `itx.readEvents()` on that id is empty afterwards; (b) a
   directory-only host (a pretty slug with no `--`) serving the same app.
5. **Infra** — the wildcard route stays; add the pretty-slug host as a route only if it is outside
   the wildcard. Real third-party domains need Cloudflare for SaaS (see §7).

## 5. Effort

v4's implementation is the upper bound at **≈130 code lines** (§1) and it does less (no identity,
no label, an unusable-for-tunnels route). The v3 delta above: `project-host.ts` +4,
`app-config.ts` +18, `worker.ts` +~14, control-plane shell +~15 ⇒ **≈50 code lines**, plus ~20 unit
rows and ~35 e2e lines. At tonight's density (v3 shipped project-host ingress at 34 lines + a
15-row table + a deployed proof, and identity beside it, in ~3 hours) this is **3-4 hours**
including the deployed proof; add ~1 hour if the control-plane shell has no table to read yet.

## 6. Dependencies and sequencing

- **Must land first**: nothing in the platform. The directory verb needs
  `packages/v3/control-plane-shell` to exist as a deployable (it does — `FALLBACK` binds
  `iterate-control-plane` / `ControlPlaneShell`, `wrangler.jsonc:72-78`). Steps 1, 2 and the 421
  behaviour can land _before_ step 3 using only the config map, which already closes the
  DO-minting hole for the poc.
- **Independent of**: identity (landed tonight; ingress just keeps stamping the cookie's
  principal), the memory-budget arc, repos/build, provenance, the fetch policy.
- **Unblocks**: pretty slugs and custom domains (assessment Gap 1's remainder), `itx.appUrl(label)`,
  the Docs app's real URL, member-gated ingress (Gap 3), and any Slack-shareable project link.
- **Conflicts with** any plan that also wants to own `itx.fetch` for outbound middleware — which is
  precisely why ingress should not be spelled there.

## 7. Risks and questions for Jonas

1. **The open wildcard is live today.** `*.project-worker.iterate.com` lets anyone mint DOs by
   varying the hostname, and the DO writes `stream/created` on construction. Acceptable for the
   poc, or fix before anything else? (I would fix it; it is the one thing v4 gets right here.)
2. **Where does the host directory live** — a control-plane RPC through `FALLBACK` (D2/D6's
   answer), or a KV the project worker reads directly (what `apps/os` does today with
   `PROJECT_DIRECTORY`)? The RPC is one hop per cold isolate; the KV is a second writer.
3. **Custom domains are not proved by v4.** `v4-custom.iterate2.app` is a name in v4's own zone.
   A real `notes.acme.com` needs Cloudflare for SaaS custom hostnames + SSL-for-SaaS + a fallback
   origin — none of which exists in either tree. Who provisions it, and is it in scope now?
4. **Should `itx.fetch` stay user-shadowable at all?** It is today in v3 (`built-in-roots.ts:18`).
   v4 leans on that for ingress; I propose not to. But a project rewriting its own _outbound_
   fetch is a legitimate D2 use — confirm it stays, and stays outbound-only.
5. **Separator**: keep `--` only, or also accept `-` (v4 does, at the cost of needing the directory
   to disambiguate)? I recommend `--` only.
6. **Unverified v4 claims.** I did not run v4's tests (per the brief). Its two deployed ingress
   rows are opt-in behind `PROJECT_INGRESS_PROOF=1` + four env vars and are skipped by default, so
   "85 deployed tests" does not by itself include them; the evidence I can point at is
   `docs/preview-proof.md:960-987`, which is prose, not a re-runnable lane.
