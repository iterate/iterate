# Layering: v4's model, v3's model, the blessed skeleton — and the order the tech tree should take

Read-only; nothing under `packages/v4` or the tutorial repo was edited, built, tested or checked out. Counts are mine, measured today: non-blank, non-comment `.ts`, tests and `src/generated/` excluded.

## 1. v4's layering model

**Source:** `docs/reading-guide.md` (307) · `docs/structural-simplicity-research.md` (204) · `README.md` (247), all under `packages/v4/project-worker/`.

**The budget, as the guide words it** (`reading-guide.md:4-8`): "The current landing budget is 15k
total implementation lines. A teaching path below 5k lines is a separate, **not yet measured or
demonstrated** goal. It is not permission to exclude difficult production code from the
implementation count." The closing section adds the gate: before claiming a sub-5k teaching
implementation, produce "a checked manifest of the actual executable source it includes", count it,
pair every omission with its production module and preserved invariant, and have any independent
Part 0 "run a named subset of the production public tests verbatim". Until then "the honest claim is a
small conceptual vocabulary and a production-backed reading path — not a sub-5k implementation."

**The nine chapters** (each = one idea, a public e2e proof, a named "next problem", and a second pass
called "Expansion" that is explicitly "**not** code that can safely be deleted"): 1 a live capability
crossing sessions · 2 dots and strings are one expression, one `invoke` door · 3 names are data, the
stream is the commit point · 4 a subscription names a delivery · 5 a processor is a subscription to a
facet · 6 fetch in both directions under one policy · 7 domain decisions that must share the
transaction (`repos.ts`, `provenance.ts`, `fetch/policy.ts`) · 8 "a public root is not automatically a
primitive" (`build`, `check`, `repos`, `secrets.list`, `approvals.pending`, `workers.load`, OAuth, MCP,
hostname maps) · 9 an application with no new kernel mechanism (Docs).

**"How this differs from a strict dependency onion"** (the section by that name): the teaching order is
not the import order; the core fold itself understands rewrite/subscription configuration, and "that
is a real dependency, not something a folder rename removes"; type-only imports must be distinguished
from runtime ones. It replaces the onion with **four categories, not four nested rings**: physical
primitives · synchronous transaction decisions · post-commit compositions · native transport/edge
adapters. The governing sentence: "A module's place is determined by the guarantee it owns, not
whether its public name is flat on `itx`." Plus an anti-refactor clause: a structural refactor earns
its place only if it removes knowledge from callers, preserves the public contracts, and passes their
existing tests unchanged.

**The research note.** Decision: land additive v4 inside 15,000 lines, keep the original session /
expression / processor / event contracts, use the production-backed reading guide, "do not create a
second toy runtime or claim an unmeasured sub-5k core." Its provenance: five read-only CLI
consultations reporting `claude-fable-5-1` at `xhigh` on 5 Sep 2026, resumed in one session so
objections were challenged against source; a sixth reported `claude-opus-5` and is not counted.

Seven challenged proposals, as recorded: (1) public roots are not automatically primitives;
(2) keep repository and trust decisions synchronous — an expected stream offset is not "this head is
unchanged"; (3) no preparation framework — the DO is the composition root and legitimately knows its
domain modules, and deleting the pager's guard against unprepared provenance would permit forged
receipts; (4) measured constraints (the JSON5 heap crash, native RPC result ownership, checkpoint
admission) are not speculative defensive code; (5) keep the native fetch-upgrade transport — workerd
cannot serialize `Response.webSocket` through an ordinary native RPC result; (6) a type reference is
not a runtime dependency — the alleged `events → provenance → checkpoint` cycle was type-only;
(7) verify storage semantics at the source that owns them — workerd's depth-named savepoints, pinned
at commit `c4e03fa1`.

Concrete findings, each with a named public regression: terminal delivery halts and last-pager cleanup
used the _external_ append door, where a configured trust policy could reject those unsigned mechanical
facts — moved to a private system append (`e2e/trusted-mechanical-facts.e2e.test.ts`); the resume sweep
could delete a raw durable rule naming a provider that had never connected ("absence at resume is not
evidence of a disconnect"); the processor SDK acquired an `ITX.get()` capability per fixed-point
read/append without releasing it; same-name processor source replacement keeps the old source (a
limitation, not hot reload); a cold-alarm idle loop grew one wake into seven in 125 s, fixed by
persisting the last activated durable head. The next bounded experiment is **additive source-reference
ergonomics**, fenced by five observable laws — no silent literal→reference rewrite; `readEvents`
preserves the appended body; a reference must resolve from durable pinned inputs or immutable content
(a bundler cache key is not enough); the synchronous reduce does no network dereference; isolation and
disposal stay covered by unchanged tests.

**Measured size.** v4 `src/` = **9,660 code lines in 55 files** (v3: 6,415 in 45); `examples/` adds 66.
v4-only modules: `fetch/policy.ts` 535 · `client/docs.ts` 495 · `provenance.ts` 310 · `repos.ts` 275 ·
`auth.ts` 236 · `bundler.ts` 224 · `stream/resource-budget.ts` 188 · `context/rpc-admission.ts` 184 ·
`mcp-server.ts` 71 · `build.ts` 51 · `ingress.ts` 47 · `fetch/secret-substitution.ts` 34. The README's
`pnpm size` (14,814) counts a wider scope — scripts, config, `envs.ts`, dependency patches.

## 2. v3's layering model

**As-built §5, "Two groups of built-ins, one record."** `itx.builtins` IS the record and the reserved
root; a `itx.builtins.<root>` call never reads the rule table; every short `itx.<root>` reaches it
through the _implicit platform row_ `itx.<root> ⇒ itx.builtins.<root>`. Above the axioms sit exactly
**two** groups: **ROOTS**, implemented against `ctx` or `env` (log, stub registry, rule table, the two
hosts, bindings, addressing), and **THE LIBRARY** (`src/library/`), first-party code "whose ONLY
dependency is `itx`, the same dotted handle a loaded worker holds after `env.ITX.get()`". The litmus
test, in the owner's words (`docs/brief-for-misha-2026-09-06.md:48`, `src/library/index.ts:5`):
**"could this be written in a userspace worker?"** — and the answer is a _signature_, pinned executably
by `src/library/boundary.test.ts` (no runtime import from the stream, the DO, the fetch module, or
`context/` except `invoke-handle.ts`). "The surface shows no level." Companion doctrine: **the
platform never spells a short name**.

**As-built §12** records the arcs: the builtins arc (rules resolve FIRST to one fixed point; `null` is a
mask under a platform root and a delete elsewhere; the removal spelling is the platform-equivalent
target; hosting decided on the **resolved** target; core contract 6.0.0); memory hygiene; review round
two; arc two (`@`, `itx.ai` = `env.AI` verbatim, `read`→`readEvents`); arc three (the library tier);
arc four (one typed app config). Then tonight's two — **project-host ingress**: "a label is the
address", `<label>--<projectId>.<base>` ⇒ `itx.apps.<label>`, `src/project-host.ts` (29 code lines) +
one edge branch, DO untouched, slug directory and custom domains _deliberately deferred to the control
plane_; and **identity**: `src/principal.ts` (86), a signed project token,
`authenticate({ projectToken })`, `session.whoami()`, `source.principal` stamped by the DO, the
`/.itx/session` cookie door — "identity is ATTRIBUTION, not authority".

**`docs/design-onion-subscriptions-processors.md`** holds the layer numbers: L0 axioms · L1 rewrite
rules · L2 subscriptions · L3 processors, "each layer only uses what is below it", sugar kept visibly
apart from axioms. §0 states the rule flatly: **"Anything expressible in userspace is not a
built-in."** §5.2, "There are no built-in processors": the one built-in `StreamProcessor` is the core
reduce, inline at the commit point because every reader is synchronous; anything not needed
synchronously before an append is not built in at all (the breaker left core and became an ordinary
userspace facet processor). §6 gives the edge surface with axioms apart from sugar, and the rule that
every handle-returning verb is session-scoped — **the durable spelling of any verb is its raw event**.
(`LAYERS.md` numbers the same nouns differently; the reading guide is right that some of its wording
predates the fixed `itx.builtins` root.)

**BUILD-LOG 2026-09-04, "the builtins root"** is the mechanism entry: the fixed point, rules-first
resolution, `resolve(call)` pure and returning the chain, the law
`invoke(call) ≡ invoke(resolve(call).at(-1))`, the two door guards (a match may not be rooted at
`itx.builtins`, nor start with a proxy verb), the removal spelling, and the measured hot path (0.13 µs
per short-name resolve at 0 rows, 2.36 µs at 300, 0.01–0.04 µs at the fixed point).

## 3. The human-blessed skeleton

`/Users/jonastemplestein/src/github.com/iterate/iterate-context-tutorial`, branch `main`, one commit
(`a32f58f`, "Skeleton: the blessed implementation — humans hold the pen here"), last touched 2 Sep.
`worker.ts` = **265 raw / 193 code lines**; `worker.test.ts` = 66; `prove.sh` = types, tsc, vitest.

**README (the repo's own framing).** "The API-design LAB for the iterate context system. The tutorial
is the instrument: **if the system's abstractions don't decompose into a sequence of small,
each-one-motivated steps, that is a design finding about the system — not a writing problem.**"
`main` is "the SKELETON. Humans hold the pen here" — "a complete, runnable, tested implementation of
the whole system in miniature (target: 1–2k LOC mirroring every type, API, and module of the
10×-larger production implementation)". Nothing lands there without the owner's blessing.

**NARRATION.md (Jonas's intent, verbatim).** "There are exactly **THREE primitives** — the context
(capabilities called in both directions), fetch (in both directions), and the stream — and everything
else is **composition on top**. The tutorial exists to make that layering undeniable." Part 0 is ONE
`worker.ts` grown brick by brick, "each brick's DEMONSTRATED flaw forces the next brick"; "show the
naive thing first and let it fail for real"; "tests are tutorial content… always the external-client
perspective — a client is JUST a capnweb peer over a plain WebSocket; never in-workerd test magic."
Taste: "radical simplicity; no invented nouns; verbose, intuitive, fully-qualified identifiers."

**What the code says is CORE.** Seven top-level declarations, which the tutorial's map calls "not
_like_ the architecture — it IS the architecture, in miniature, with the production names":
`startRpcStubRelay` (park a live stub) · `IterateContext extends RpcTarget` (the surface) ·
`ItxEntrypoint extends WorkerEntrypoint` (`env.ITX`) · `RpcStubDirectory` (held stubs → hibernatable
pager sockets) · `Stream` (the log + one commit point) · `IterateContextDurableObject` (composes both,
walks the doors) · `export default { fetch }` (`/api` + `/cap`). Brick 8's reveal: **"provide IS an
append"**, `#mounts` is a fold of the log — with the honest bridge that the real platform inverts the
composition, running the fold inside the commit transaction.

**What Jonas's own words say is COMPOSITION.** The `tutorial` branch's 13 commits run intro, bricks
1–8, "The map", Chapters 1–3 (the context · fetch · streams and stream processors) — and **Chapter 4,
titled "everything else is on top"**: "Three primitives; the rest is composition, policy, and road
ahead — the one home for every FUTURE item." Its _Shipped_ list: **LiveState**, **projects & routing**
("a project is just the prefix of every context DO name"), **secrets** (the sentinel substitution),
**MCP for agents** ("each mounted capability is a tool"). Its _Ahead_ list: **real auth**
("`authenticate()` in the shipped tree is today a no-op… the HMAC-signed session machinery exists in
the control plane and drops into that one method without changing a single caller"), **trust** ("the
current model is _trusted clients_: intra-project coordination, no malicious-client defense, no signed
events"), **git-backed config repos**, a **device client**.

So, in Jonas's own words: repos, secrets, auth, trust, MCP, routing and live state are all **Chapter 4
— composition**. Not one of them is a primitive. Closing line of the tutorial: "Everything a client
can do is a capability; everything durable is a reduced event."

## 5. The ordering principle for the tech tree

**The principle, in one sentence:** a v4 feature layers onto v3 in the position where its proof can be
written as an ordinary call through the _unchanged_ public door (`/api` → `invoke` / `append`) against
the **deployed** worker — and adding it must not require re-spelling anything beneath it.

That is the intersection of the three sources' own tests: v4's compatibility gate ("Additional tests
must prove added behavior through the same public APIs"); the onion-as-structure test its guide keeps
("removing an outer composition should not require rewriting the primitives beneath it"); v3's rule
that the durable spelling of every verb is its raw event, so every step must be expressible as
`itx.append({ type: … })` with no verb at all, proved against the DEPLOYED worker; and the skeleton's
rule that each step's _demonstrated flaw_ motivates the next.

**Two ordering constraints fall out of that**, and they fix the sequence: (1) **transaction-sharing
first** — anything deciding inside `Stream.append`'s transaction changes the contract every layer
above re-proves against, so it lands before anything that merely reacts (v4's disagreement 2 is right
on the facts: an expected offset is not "this head is unchanged", and a post-commit processor cannot
recover that guarantee); (2) **litmus-passing things last, and outside the kernel** — anything whose
only dependency is `itx` costs the kernel nothing, never blocks, and never earns a root before
someone has failed to write it in userspace.

**The resulting order** (each step = one root or one event family, one deployed e2e, no change beneath):

| #   | Step                                                                                         | Layer                                           | Deployed proof shape                                                                            |
| --- | -------------------------------------------------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | `workers.load(code, { cacheKey })` — a second input shape on the existing host               | root (additive)                                 | native loader input, one call, no new event                                                     |
| 2   | The secrets **write door** + `itx.secrets.list()` safe receipts (Gap 7)                      | root + admin door                               | write a secret out of band, prove `{{secret:…}}` still substitutes and ITX shows only a receipt |
| 3   | The **synchronous commit seam** for domain decisions (repository CAS + rollback)             | axiom (touches `Stream.append`)                 | parent/head CAS refusal and atomic batch rollback, both through `itx.append`                    |
| 4   | `itx.repos` over that seam — immutable revisions, `head()`/`read()`/`list()`                 | root _or_ library (decide with the litmus test) | commit → head → read, one durable receipt                                                       |
| 5   | `check` / `build` against a **pinned** `{ repo, revision }`, result inert loader input       | library tier                                    | build a pinned revision, load it with step 1, `fetch` it                                        |
| 6   | The **fetch policy** — origin binding, one-shot approval receipts, `itx.approvals.pending()` | root over the existing egress terminal          | approval replay refusal; a user-space router that must delegate to `itx.builtins.fetch`         |
| 7   | Custom hostnames on top of `itx.apps.<label>` (needs the control plane's directory)          | edge                                            | a custom host serving the same row                                                              |
| 8   | Provenance / trust levels — **only if Jonas lifts the trusted-client doctrine**              | axiom (append admission)                        | signed append admitted, unsigned refused at `minimumLevel: 2`                                   |
| 9   | Served MCP + OAuth as the token minter for step 0's identity                                 | composition (edge / control plane)              | an MCP `tools/call` that is an ordinary `itx.…` invocation                                      |
| 10  | A Docs-class application, entirely in userspace                                              | userspace                                       | two browsers converge; the app survives the installer session                                   |

Step 8 is deliberately last and conditional: it is the only step that changes what the log will
_accept_, and v4's own finding — two internal mechanical call sites had to move to a private system
append before a locked policy tolerated them — shows admission rules ripple _down_ into the kernel
rather than layering on top of it.

## 6. Risks and questions for Jonas

1. **Three kernels — which line is developed?** v3: committed, deployed, 6,415 code lines. v4:
   untracked, 9,660 code lines, another session's live work. The skeleton: 193 code lines, separate
   repo, human-blessed, last touched 2 Sep. The tech tree needs exactly one trunk. My reading of the
   three documents says **v3 is the trunk, v4 is a features quarry, the skeleton is the acceptance
   test for the layering claim** — but that is your call, not a finding.
2. **"A teaching path below 5k lines" — which meaning?** The skeleton already _is_ a sub-5k teaching
   implementation (193 lines), and its whole premise is a second, human-blessed runtime whose
   decomposition is the design finding. v4's guide forbids a second runtime and redefines the goal as
   a manifest-checked _subset_ of production source running production tests verbatim. Not the same
   project: if the skeleton is the answer, v4's 15k budget is the wrong instrument; if v4's subset is
   the answer, the skeleton repo's `main` is dead.
3. **Does the litmus test still bind?** v4 adds five roots (`repos`, `secrets`, `approvals`, `build`,
   `check`) and replaces "could this be written in a userspace worker?" with "a public root is not
   automatically a primitive". One verifiable side effect: v4's `src/context/built-ins.ts:1-10` still
   says the record has "Three kinds of key" (axioms, bindings, library) while its `built-in-roots.ts`
   lists five keys that are none of the three and arrive as injected `deps` (`built-ins.ts:334-338`).
   The classification in the code no longer matches the code. One rule has to win.
4. **Trusted clients, or signed events?** `provenance.ts` (310 lines) plus trust-level admission
   reverses the doctrine you set, and the skeleton's Chapter 4 lists trust as _Ahead_. v4's README is
   candid that at `minimumLevel: 0` "an unsigned holder may change [policy and rewrite facts],
   including removing an approval gate" — so it only means anything once a project locks itself down.
5. **Two ingress spellings and two principal shapes are already in the tree.** Ingress: v3's
   `projectHostOf` (deployed tonight) makes the label the address and keeps hostnames out of the log;
   v4's `resolveProjectHost` needs deployment-owned `projects` and `customHostnames` maps in app config
   and leaves app selection to a user-space router — custom domains are the one thing it has that v3
   deferred. Identity: `Principal { actor, email? }` (verified token, DO-stamped) vs `BrowserPrincipal
{ kind: "unverified-email", email }` (OAuth props). Each pair needs one winner before more lands.
6. **What I could not verify.** I ran no v4 test and did not touch the deployed worker, so v4's "85
   deployed tests in 19 files", the 14,814 `pnpm size` figure, the 4/5 and 1/1 resource verdicts and
   everything in `docs/preview-proof.md` are v4's assertions, not confirmed facts.
