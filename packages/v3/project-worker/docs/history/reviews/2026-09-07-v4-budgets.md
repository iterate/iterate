## 2. What v3 has today for the same need

v3's memory arc is **closed and deployed** (BUILD-LOG 2026-09-04 "memory hygiene", the evening ledger
entry, 2026-09-06 read-admission, 2026-09-07 fan-out + "remainder: CLOSED"; live-49 and live-53):

- `EVENT_BODY_MAX_CHARS = 8 MiB` append ceiling → `EVENT_TOO_LARGE` (`src/stream/stream.ts:59`, door at 326).
- `READ_PAGE_BUDGET_BYTES = 8 MiB` / `READ_PAGE_MAX_EVENTS = 1000` byte-budgeted pages (`stream.ts:63,66`).
- `READ_OUTSTANDING_BUDGET_BYTES = 16 MiB` **plus the async read-admission door** — `async read()`
  awaits room, reserves a worst-case page, retires on the continuation read or a 5 s TTL sweep
  (`stream.ts:79,482`); `readInternal()` (499) is the sync exempt path for the stream's own scans.
- Delivery ledger: `DELIVERY_IN_FLIGHT_BUDGET_CHARS = 8 MiB`, `PENDING_PUSHES_TOTAL_BUDGET_CHARS = 8 MiB`
  (`subscription-delivery.ts:61,65`), oldest-first drops, `CURSOR_PASS_CONCURRENCY = 4`,
  `LIVE_STATE_PATCH_MAX_CHARS = 1 MiB`, `REDUCE_CHECKPOINT_TOO_LARGE`, `EVENT_UNREADABLE` skip in the
  constructor re-reduce.
- Deployed pins v4 does **not** have: `CONCURRENT READERS` (24 sessions × 144 MiB), `SLOW LIVE CLIENT`,
  `POISON FACET`, `LOADED-ISOLATE OOM`, `CONCURRENT BIG APPENDS`, the documented fan-out limit
  (`e2e/stream-uncontrolled-degradation.e2e.test.ts:128,149,191,243,283,311`).

**The three v3 red pins in this feature's territory** (`src/stream/memory-budget.test.ts`):
`test.fails:188` a legal 32 MiB batch commits then its **echo** overflows the 32 MiB RPC result cap —
a committed-but-errored append; `test.fails:394` two 4 MiB object-dense events share one 8 MiB page
that parses to ~150 MiB; `test.fails:410` one legal 8 MiB object-dense event needs ~150 MiB to
deserialize — "the size door never runs".

**Measured here, not taken from v4:** a 4 MiB `[[]],…` body (838,820 items) is 4,194,101 chars and
parses to **77 MiB**; v3's append door measures `JSON.stringify(event).length` = 4,194,138 chars,
comfortably under 8 MiB, so v3 **admits it**. Two of them in one page is ~154 MiB — a reset.

**The 4.5 MiB literal, today, measured.** v3's `parse()` slices the call args and hands them to
`JSON5.parse` (`src/context/expression.ts:96,129`); the core reduce parses `payload.target` on every
`subscription-configured` event (`core-processor.ts:367`) and the M1 memo recovery re-parses it from
the log on every post-eviction materialization (`iterate-context-durable-object.ts:598`). Running v3's
exact seam in a 128 MiB child:

```
PATCHED  (what v3 resolves today) → sourceChars 4718592, 233 ms, heap 45 MB, RSS 113 MB
STOCK json5@2.2.3                 → FATAL ERROR: Reached heap limit — OOM
```

So v3 is only safe because the **uncommitted** v4 patch is already installed in this worktree
(`packages/v3/project-worker/node_modules/json5 → …patch_hash=6c95362…`). v3 has **no** facet startup
memo ceiling: `ctx.storage.kv.put('facet:<name>', spec)` (`iterate-context-durable-object.ts:580,603`)
is unguarded, so a 4.5 MiB source fails late, at materialization, against the ~2 MB cell.

**Conflicts with v3 doctrine / tonight's work**

1. **`rpc-admission.ts` contradicts a decision v3 made deliberately.** BUILD-LOG 2026-09-07
   ("remainder arc: CLOSED"): an edge in-flight budget "is DELIBERATELY NOT DONE and should NOT be
   reopened… we don't care about the edge worker dying as clients can just reconnect; it's just the DO."
   `CONCURRENT BIG APPENDS` is already the boundary control asserting exactly that. v4 puts 184 lines
   of hand-rolled lexer on the shared `/api` hot path to protect the edge.
2. **v4's `APPEND_REPLY_BUDGET_BYTES = 30 MiB` over an ×2 UTF-16 estimate refuses legal traffic.**
   v4 had to rewrite v3's green control ("control: a 4 × 8 MiB idempotent retry … fits both RPC caps",
   `memory-budget.test.ts` diff) into `expect(refusedCode).toBe("APPEND_REPLY_TOO_LARGE")`. The same
   rule refuses v3's deployed `CONCURRENT BIG APPENDS` row (8 sessions × 4 × 7 MiB → 56 MiB estimated).
3. **v4 has no read-admission door.** v4's `read()` is sync with a 32 MiB level; v3 proved on live-49
   that a level which only _shrinks_ cannot bound N readers below N × one row. Taking v4's stream.ts
   wholesale would re-open v3's concurrent-reader reset.
4. **`stream_resource_halts` is back-compat machinery.** Its own comment says it exists because
   "stores already existed". v3 is resettable by doctrine (`no backcompat cruft`), and once the append
   side refuses dense shapes, no such row can be created.
5. Style: v4 replaced v3's teaching comments with one-line docstrings throughout these files.

## 3. Proposed layering on v3

Nothing here is spelled on the itx surface — these are isolate axioms, invisible at the doors, exactly
as `EVENT_BODY_MAX_CHARS` already is. Litmus test: a userspace worker cannot write them.
No new events; refusals are coded errors on the existing `lib/errors.ts` channel.

**Take (four pieces, ~130 code lines).**

1. **A structural estimate beside the char count at the append door.** One small function in
   `src/stream/stream.ts` next to the existing ceiling — charge containers and members, cap at
   `EVENT_SHAPE_MAX_BYTES = 64 MiB`, code `EVENT_TOO_COMPLEX`. Take v4's `estimateNativeValue` shape
   (Maps/Sets/typed arrays/Errors, `WeakSet` cycle guard, the array-index caution at
   `resource-budget.ts:106–118`, which is a genuinely good catch) but **add a depth cap** — v4's
   `visit` recurses unbounded once past the edge scanner. Closes `test.fails:410` for every caller
   that reaches the DO through JS, and `test.fails:394`'s producer.
2. **A reply-shape budget before commit**, code `APPEND_REPLY_TOO_LARGE`, closing `test.fails:188`.
   **Set it against measured serialized bytes, not v4's ×2 estimate**: keep v3's 4 × 8 MiB control and
   `CONCURRENT BIG APPENDS` green. Charge strings at 1 byte/char for the ASCII common case with the
   remaining headroom against 32 MiB — measure once, pin the constant, exactly as `EVENT_BODY_MAX_CHARS`
   was tuned.
3. **A parsed-bytes budget on the read page** in `src/stream/stream-storage.ts` `readPage` — take v4's
   `#estimateParsedBytes` (96 B per container, quote-aware) and its extra `parsedBudgetBytes` cut. Set
   the parsed budget to ~48 MiB (v3's isolate already spends 16 MiB on outstanding pages + core state +
   the DB working set; v4's 80 MiB leaves no room). A single row still over it is coded
   `EVENT_UNREADABLE` and reported — reusing the skip the constructor re-reduce already has
   (`stream.ts:222`) rather than inventing a halt. Closes `test.fails:394`.
4. **A facet startup memo ceiling**, `FACET_STARTUP_MEMO_TOO_LARGE`, checked in the
   `subscription-configured` reduce (`core-processor.ts:367`) — the exact rhyme of the existing
   `REDUCE_CHECKPOINT_TOO_LARGE`, and grounded in v3's own recorded fact that a SQLite TEXT cell caps
   near 2 MB (`stream-storage.ts` `EVENT_CHUNK_SIZE` comment). **Additionally, and this is the point:
   refuse the oversize source in `expression.ts` `parse()` BEFORE `JSON5.parse` runs** — an O(1) length
   check on the args span, `ITX_EXPRESSION_ARGS_MAX_CHARS = 2 MiB`.

**On the json5 patch: do not take it.** v4 needs it because its refusal is _downstream_ of the parse —
`core-processor.ts:452` checks the memo size only after `parse(payload.target)` has already lexed the
4.5 MiB literal. Refuse _upstream_ and the parse never happens, so 299 patched lines of a shared
workspace dependency (which currently changes json5 for `apps/os` and every other consumer, and must
be re-applied on every bump) buy nothing v3 needs. Keep `docs/json5-memory.md`'s measurements as a
citation in the BUILD-LOG entry. Two caveats for Jonas in §7.

**Deliberately left out:** `rpc-admission.ts` in full (doctrine — §2.1); the `stream_resource_halts`
table and `STREAM_RESOURCE_HALTED` (back-compat machinery — §2.4); v4's `appendSystem`/`participant`
split and its sync `read()` (they belong to other v4 arcs and would regress live-49).

## 4. Implementation sketch

1. **Refuse the oversize expression before JSON5 sees it.** `src/context/expression.ts` — length check
   on `inner` before line 129. Unit: `expression.test.ts` row; heap-capped child pinning that a 4.5 MiB
   literal is _refused in milliseconds_, and — with the patch reverted — that stock json5 is never
   reached. Deployed: extend `e2e/processor-lifecycle*` with the append refusal + "no facet installed,
   neither row landed".
2. **Facet startup memo ceiling.** `src/stream/core-processor.ts` (+ `lib/errors.ts` code, + a bump of
   `CoreContract.version`). Unit: `core-processor.test.ts`. Deployed: same e2e row as step 1 — a
   `configureProcessor` with a >2 MiB source is refused atomically.
3. **Append input shape + reply shape.** New `src/stream/event-shape.ts` (one pure module, table tests,
   per `feedback_rule_modules_one_file_table_tests`), called from `Stream.append` step 1 and after
   enrichment. Flip `memory-budget.test.ts:188` and `:410` from `test.fails`. Deployed: two rows in
   `e2e/stream-memory-budget.e2e.test.ts` — the receipt refusal and the object-dense refusal — plus
   re-run `CONCURRENT BIG APPENDS` to prove the reply budget did not tighten legal traffic.
4. **Parsed-bytes page budget.** `src/stream/stream-storage.ts` `readPage` + `stream.ts` `#readPage`
   threading. Flip `memory-budget.test.ts:394`. Deployed: the 144 MiB read row must stay byte-identical
   and the facet catch-up row green (the parsed budget must never shrink a normal page).
5. **Edge preflight (optional, 3 lines).** `IterateContext.invoke` (`iterate-context.ts:213`) runs the
   same input-shape assert before the Workers-RPC hop, so a dense append dies at the edge and never
   materializes in the DO isolate. Proof: the deployed object-dense row asserts the DO's
   `highestDurableOffset` did not move and no wake fact was burned.
6. BUILD-LOG entry; run the full deployed lane `--no-file-parallelism` against a fresh deploy.

## 5. Effort

Upper bound (v4's own implementation of the same ground): **493 code lines** + 299 patch lines.
Proposal: **≈ 130 code lines** of product (expression cap ~8, memo ceiling ~20, `event-shape.ts` ~70,
storage parsed budget ~25, edge preflight ~3) + **≈ 120 lines** of tests (4 flipped `test.fails` rows,
2 table-test files, 3 deployed rows) + BUILD-LOG. **6–8 working hours**, of which ~3 is the deployed
loop (a full `--no-file-parallelism` deployed lane is ~13 min per round, and the 144 MiB seed rows are
slow). Steps 1+2 alone are ~30 code lines and ~1.5 h, and they are what removes the json5 patch.

## 6. Dependencies and sequencing

- **Independent of everything else in this review.** No bindings, DNS, secrets or control-plane work.
  It touches `stream.ts`/`stream-storage.ts`/`core-processor.ts`/`expression.ts`, so it should not run
  concurrently with another reviewer's edit to the same files.
- **Step 2 bumps `CoreContract.version`** (currently `6.0.0`, `core-processor.ts:273`), which triggers a
  full core re-reduce on every existing context's next wake. Land it with, or after, any other core
  version bump in this batch — not as a second one.
- **Must land before** the json5 patch and `pnpm-workspace.yaml:136` are reverted; today v3 is only
  green on the 4.5 MiB literal because that patch is installed.
- **Unblocks** the userspace-apps assessment's processor-install path: a real bundle can be sized
  against a stated ceiling instead of failing late at `kv.put`.

## 7. Risks and questions for Jonas

1. **The edge.** v4 spends 184 lines guarding `/api` against a structural bomb; your standing doctrine
   (BUILD-LOG 2026-09-07, `feedback_clients_always_connected`) says the edge may die. My proposal
   honours the doctrine and leaves the edge unguarded. If you now want the edge guarded, that is a
   doctrine change, not an implementation detail — say so and I'll take v4's transport wrappers. Cost,
   measured: v4's scanner runs at ~400–500 MiB/s on this laptop, so ~40 ms of edge CPU on an 8 MiB
   message at edge-core speed, on every `/api` call.
2. **What is the real maximum facet source?** I propose 2 MiB (v4's number, grounded in the storage
   cell). If a legitimate userspace processor bundle can exceed that, the memo needs chunking and the
   ceiling must move — that changes step 2 and re-opens the case for keeping the json5 patch.
3. **The json5 patch is a monorepo-wide change** currently sitting uncommitted in `pnpm-workspace.yaml`
   and `patches/`. Who owns the decision to keep or drop it? Dropping it after my steps 1–2 is safe for
   v3; I have **not** audited whether any other workspace consumer (`apps/os`, `codemirror-json5`)
   parses adversarially large JSON5.
4. **Unverified v4 claims.** I did not run v4's tests. The deployed evidence in `docs/preview-proof.md`
   (seventh deployment, `FACET_STARTUP_MEMO_TOO_LARGE`, `retryable: false`, no row landed) is v4's own
   record. v4's README also states the 8 MiB object-dense _native append decode_ remains an expected
   failure in v4 — so v4's structural admission closes the public capnweb path but **not** an in-worker
   caller (a facet loopback, a sibling context), because the native V8 decoder runs before any JS.
   My step 5 has the same limit, honestly.
5. **`retryable: true` / `durableObjectReset: true`.** v4's README classifies that exact flag triple as
   a "platform interruption" and permits one caller retry in its recovery proof. v3 already honours
   workerd's stamped flags (`lib/errors.ts` header) and has no retry policy by doctrine. I have not
   proposed one. If you want v4's bounded-recovery behaviour, that is a separate decision.
