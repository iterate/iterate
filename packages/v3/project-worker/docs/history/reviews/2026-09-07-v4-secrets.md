**Public API as spelled.** On ITX, read-only receipts only:
`itx.secrets.list() → { name, origin, revision }[]` and
`itx.approvals.pending() → { requestId, expiresAt, origin, method, policyRevision, decidedAtOffset, allow, used }[]`
(`src/context/built-ins.ts:98,100`). Writing bytes is off ITX entirely:
`POST /secrets?context=<doName>` with `authorization: Bearer $EXPERIMENT_ADMIN_TOKEN`, body
`{ name: /^[A-Z][A-Z0-9_]{0,63}$/, value: string(1..65536), origin: bare https origin }` →
`{ name, origin, revision }`; it hops to the DO's `putSecret` (`worker.ts:73–88`). New egress syntax:
an **unscoped** `{{secret:NAME}}` that must be the **entire** header value — anywhere else (including
the URL) is `SECRET_REFERENCE` 400 (`policy.ts:404–427`). The secret only substitutes when the
request's `url.origin` equals the stored origin, else `SECRET_ORIGIN` 403. Held request →
HTTP **202** `{ code: "APPROVAL_REQUIRED", requestId, fingerprint, expiresAt }`; the caller retries the
byte-identical request with `x-iterate-approval: <requestId>`.

**Events it appends.** Two userspace-writable facts: `events.iterate.com/egress/policy-configured`
with `{approval:"none"} | {approval:"required", expiresInMs}` and
`events.iterate.com/approval/decided` with `{requestId, fingerprint(43 b64url), allow}`. Three
platform facts through the new `Stream.appendSystem` door: `itx.system.secret.put`,
`itx.system.egress.requested`, `itx.system.egress.released` — payloads are
`{policyRevision, fingerprint, method, origin, bodyHash, secrets:[{header,name,revision}]}`, never
plaintext. Three SQL tables inside the context DO, outside the core reduce: `egress_secrets`,
`egress_policy`, `egress_pending` (`policy.ts:83–92`).

**Config / bindings / infra.** `EGRESS_KEY` — one deployment-wide 32-byte base64url AES-GCM key
(AAD binds `{domain,context,name,origin,revision}`); `EXPERIMENT_ADMIN_TOKEN`. Both are required
secrets in `scripts/deploy.ts:20,56–78`; the e2e lane fakes them in `e2e/support/solo-config.ts:41–42`.
No new binding, DNS or KV namespace. It reuses v3's `SECRETS_KV` unchanged for the legacy scope.

**Tests.** `e2e/fetch-policy.e2e.test.ts` (97 code lines, 3 tests: 401 without the admin bearer, receipts
carry no plaintext, gate → 202, a stale retry after `approval:"none"` is `APPROVAL_MISMATCH` 409;
plus URL-embedded reference 400 and wrong-origin 403). `e2e/approval.e2e.test.ts` (212, 4 tests:
untouched context untouched, release-exactly-once + `APPROVAL_USED` replay, signer rotation across a
failed atomic batch, expiry). `e2e/fetch-policy-authority.e2e.test.ts` (94, 2 tests: at
`minimumLevel: 0` an **unsigned** append removes the gate; at `minimumLevel: 2` it is refused).
`e2e/fetch-door-egress-missing-secret-502.e2e.test.ts` (32) and `src/fetch/egress.test.ts` (66) are
v3's, unchanged. **Deployed-only:** `e2e/egress-deployed.e2e.test.ts` (117) — skipped unless
`WORKER_BASE_URL` + `WORKER_DEMO_LOGIN` + `EXPERIMENT_ADMIN_TOKEN` are set; it is the only proof the
released request actually reaches a real upstream.

**What inside v4 it depends on.** `src/provenance.ts` (310 code lines): `isTrustedApproval` is
`event.verification?.level === 2` (DO:354), so the approval gate is inert without the Ed25519 trust
stack. `Stream.appendSystem` + `StreamCommitParticipant`. `resolveProjectHost` (its ingress work).

## 2. What v3 has today for the same need

`#egress` (`packages/v3/project-worker/src/iterate-context-durable-object.ts:824–845`) is the whole
mechanism: `substituteHeaderSecrets(request, "project", …SECRETS_KV.get("secret:<projectId>:<name>"))`,
a loud 502 naming any surviving project token, then `env.FALLBACK.fetch(...)` — the control-plane
shell (`packages/v3/control-plane-shell/src/index.ts:26–31`) which substitutes the `platform` scope and
hits terminal. The as-built §5 row is one line: "`fetch(request)` — egress: `{{secret:project:NAME}}`
substituted → `FALLBACK`"; §10 "Fetch" describes only the three lanes, no policy. There is **no
write door**: nothing in `src/` writes `SECRETS_KV` (the e2e seeds through wrangler) — assessment
Gap 7, which asks for exactly `itx.secrets.set(name, value)` "~50 lines".

**Where v4 conflicts with v3's doctrines:**

- **A second commit reducer.** `core-processor.ts`'s header is explicit: "ONE reduce, no effects, no
  verbs… its readers are the append door, the dispatcher and the delivery loop". v4 adds
  `StreamCommitParticipant` and three tables of synchronous state the core fold does not own.
- **A second control protocol.** `POST /secrets` + a deployment-wide bearer is precisely the
  "second control protocol" the stream is supposed to replace; and the 202/`x-iterate-approval`
  retry is a third, on the fetch door.
- **Event naming.** `stream/events.ts:15` fixes the convention `events.iterate.com/<domain>/<fact>`.
  `itx.system.secret.put` / `.egress.requested` / `.egress.released` invent a new namespace.
- **Authority, not attribution.** v3 shipped identity tonight with the opposite law
  (`src/principal.ts:9`: "Identity is ATTRIBUTION, not authority… the trusted-client doctrine").
  v4's gate makes an Ed25519 signer level 2 the authority for a decision.
- **v4 forked before tonight's identity.** v4 has no `src/principal.ts`, and its `lib/errors.ts`
  lacks v3's `INVALID_CREDENTIALS` / `FORBIDDEN`. Its admin door authenticates with a deployment-wide
  bearer where v3 now has a per-project signed token and `session.whoami()`.
- **Two grammars for one idea.** `{{secret:project:NAME}}` (anywhere, incl. the URL — v3 has a test
  for exactly that, `egress.test.ts:57`) now coexists with `{{secret:NAME}}` (whole header only, URL
  refused). Same concept, two spellings, opposite placement rules.
- **The gate self-refutes at the default.** `fetch-policy-authority.e2e.test.ts:44–71` proves an
  ordinary unsigned `itx.append` removes the gate at `minimumLevel: 0`. So 300+ lines of one-shot
  machinery buy nothing unless the whole provenance stack is also configured — v4's README says so
  itself.

**Where v4 is better:** the **origin binding**. v3 will substitute any project secret into a request
to any host, so a typo'd URL in a loaded worker mails every credential to a stranger. That is a
mis-addressing bug, not a malicious client, and the terminal is the only place that can catch it.

## 3. Proposed layering on v3

**AXIOM — the physical terminal.** `itx.builtins.fetch` stays the one egress door, and remains the
only place plaintext exists (between the KV read and `FALLBACK.fetch`; one service-binding hop to the
control-plane shell, as today). Two changes there, both tiny:

1. read the secret with `SECRETS_KV.getWithMetadata(...)` and refuse when
   `metadata.origin` is set and `!== new URL(request.url).origin` — a 502 naming the secret and the
   host, same loud shape as the existing missing-secret refusal;
2. (independent, free) refuse a request whose host `projectHostOf(...)` resolves to **this** project —
   v4's `PROJECT_FETCH_NOT_CONFIGURED`, which is a real loop v3 currently sends out to the internet.

**ROOT — `itx.builtins.secrets`.** The Gap 7 verb, spelled as the physical built-in it is:

- `itx.builtins.secrets.set(name, value, { origin? }) → { name, origin? }` — write-only; the value is
  never readable back through any door.
- `itx.builtins.secrets.list() → { name, origin? }[]` — names and origins, never values.

This is not a new concept: `itx.builtins.kv.put(k, v)` is already a project-prefixed physical write
with no event (the "events are the interface, **except built-ins**" carve-out). Same store
(`SECRETS_KV`, `secret:<projectId>:<name>` — BUILD-LOG records that prefix as a constant), same
project scoping, one added leaf in `built-in-roots.ts`. **No `get`.**

**EVENT — one fact, no value.** `set` appends `events.iterate.com/secrets/changed { name, origin? }`
through the ordinary `append` door, so a rotation is orderable, subscribable and attributed by
tonight's `source.principal`. Nothing else is an event: a policy is not an event, an approval is not
an event, an egress is not an event.

**USERSPACE — the gate, if a project wants one.** A router facet in front of the door:
`itx.provide("itx.fetch", "itx.facets.get('egress-guard').fetch")`, which decides and then calls
`itx.builtins.fetch(request)` — v4's own docs router already demonstrates exactly this delegation
(`examples/docs/router.ts:12–16`). It holds the Request object, so it needs no request id, no
fingerprint, no 202, no retry header, no `egress_pending` table: it simply does not call the terminal
until it decides to. Rewrite rule 5 makes `itx.builtins.fetch` unshadowable, so the router cannot be
bypassed _and_ cannot bypass secret substitution. A breaker that wants to stop the whole stream
already has the v3 spelling: append `events.iterate.com/stream/paused`.

**LIBRARY — nothing.**

**Deliberately left out** (and why): `EGRESS_KEY`/AES-GCM at rest (KV is already encrypted at rest and
the binding is only in this worker; a deployment-wide key with no key id has no rotation story);
`POST /secrets` + `EXPERIMENT_ADMIN_TOKEN` (a second control plane for something `itx` can spell);
`x-iterate-approval`, the 202 protocol, the fingerprint, `egress_pending`, `APPROVAL_*` codes
(**speculative machinery** — see §7); `Stream.appendSystem` and the second commit participant; the
`itx.system.*` namespace; the unscoped `{{secret:NAME}}` grammar and its whole-header-only rule
(v3's `{{secret:project:NAME}}` substitutes in the URL too, which real APIs need).

**Verdict on approval receipts: yes, speculative.** The gate defends the project's operator against
the project's own code — the malicious-insider model the trusted-client doctrine deletes. It is
~300 of the 535 lines, drags in 310 lines of provenance to mean anything, and is removable by an
unsigned append at the default trust level. The 5% of it that is real (a human wants to see and hold
outbound traffic) is a userspace router, and it is strictly easier to write there.

## 4. Implementation sketch

1. **The origin binding at the terminal.** `src/iterate-context-durable-object.ts` `#egress`: swap
   `SECRETS_KV.get` for `getWithMetadata<{origin?: string}>`; refuse on mismatch with a 502 naming the
   secret and the destination host. `src/fetch/egress.test.ts`: one unit row (the resolver returning
   null for a wrong origin already round-trips through the existing "unresolved ⇒ 502" path).
   _Proof:_ extend `e2e/fetch-door-egress-missing-secret-502.e2e.test.ts` — a secret bound to
   `https://a.invalid` sent to `https://b.invalid` is a 502 naming both.
2. **The write verb.** Add `secrets` to `src/context/built-in-roots.ts` and `BuiltInScope`
   (`src/context/built-ins.ts`), implemented over `env.SECRETS_KV` with the `secret:<projectId>:` prefix
   (mirror the `kv` root's five lines) and the `{ metadata: { origin } }` put; declare it on the edge
   type in `src/iterate-context.ts`. Append `events.iterate.com/secrets/changed` from `set`.
   _Proof (deployed):_ new `e2e/secrets-write-and-origin.e2e.test.ts` — `set` then `list` shows
   `{name, origin}` and no value; `JSON.stringify(await readEvents())` does not contain the value;
   `itx.fetch` to the bound origin with `{{secret:project:NAME}}` reaches upstream once; to another
   origin it is a 502. Run it with `WORKER_BASE_URL` against the deployed worker.
3. **The self-host loop refusal** (optional, independent): in `#egress`, `projectHostOf(url, appConfig)`
   matching this `projectId` → a 404 naming the missing `itx.fetch` rewrite rule.
   _Proof:_ one case appended to the ingress e2e.
4. **The userspace guard, as an example not a kernel feature.** A ~40-line `egress-guard` processor
   source in `e2e/support/sources.ts` plus one e2e that provides it at `itx.fetch`, watches it hold a
   request, appends a userspace `approved` fact, and sees it delegate to `itx.builtins.fetch`. This is
   what closes the "can a project gate its own egress?" question **without** kernel code.
5. **Docs.** as-built §5 `fetch` row (+ origin) and a new `secrets` row; §10 "Fetch" gains three
   sentences (the write verb, the origin binding, "the gate is a userspace router"); assessment Gap 7
   marked closed except the born credential, which belongs to the control plane.

## 5. Effort

Upper bound (v4's implementation of the same ground): 535 + 17 + ~40 + ~55 error/stream seams ≈ **650
code lines**, plus 520 test lines and a 310-line provenance dependency.

Proposal: step 1 ~12, step 2 ~45, step 3 ~8, step 5 (docs) ~25 → **~65–70 code lines**, ~90 test lines,
plus step 4's ~70 example/test lines if the guard demo is wanted. About **11% of v4's**.

At tonight's density (~300 code lines with tests, docs and a deployed proof in ~3 hours):
**1.5–2 hours** for steps 1–3 + 5; **+1 hour** for step 4.

## 6. Dependencies and sequencing

**Must land first:** nothing. `SECRETS_KV` is already bound (`wrangler.jsonc:83`) and the
`secret:<projectId>:<name>` convention already exists; the change is read → read+write. No DNS, no new
Doppler secret, no control-plane change. Step 3 only needs tonight's ingress (`773978230`), already in.

**Independent of:** v4's provenance/repos work, its build/check service, its OAuth/MCP doors. Nothing
in this proposal needs Ed25519, `EGRESS_KEY`, or a trust policy.

**Sequencing with identity:** if the answer to Q1 below is "not every holder of `itx` may write a
secret", then the gate rides tonight's `source.principal` (`src/principal.ts`) and identity must land
first — it has. It must _not_ ride a second bearer token.

**It unblocks:** the machine lane in assessment Gap 7 (§6 item 6) and any library connector that
needs a real credential — `connectToMcp` / `connectToOpenApi` / `connectToCapnweb` all take `headers`
and go through `itx.fetch`, so a project can finally install its own upstream token without a
wrangler seed. The born project credential half of Gap 7 stays with the control plane.

## 7. Risks and questions for Jonas

1. **The write door's shape — only he can call this.** Is `itx.builtins.secrets.set` (write-only,
   any holder of the project's `itx`, exactly like `itx.builtins.kv.put`) the right answer, or does he
   agree with v4 that plaintext must only ever enter through a control-plane door outside `itx`? I
   recommend the verb: v4's admin door is a second control protocol and a deployment-wide bearer.
2. **Origin binding: keep or drop?** It is the one genuinely new invariant v4 found, it costs ~12
   lines, and only the terminal can enforce it — but it does constrain a trusted client, so it needs
   his ruling. I recommend keeping it, optional per secret (no origin ⇒ v3's behaviour today).
3. **Encryption at rest inside the DO** (v4: AES-GCM + `EGRESS_KEY`) versus KV as today. ~60 lines
   plus a rotation story v4 does not have (no key id in the row, no re-encrypt path). I recommend not
   now.
4. **Any synchronous egress hold in the kernel at all?** My recommendation is no — a userspace router
   in front of `itx.fetch` is strictly simpler and v4's own docs router proves the shape. If he wants
   one in the kernel, that is a decision against the trusted-client doctrine and should be recorded
   as one.

**Things v4 asserts that I could not verify** (I read the code; I did not run v4's tests, per the
brief):

- The deployed proof `e2e/egress-deployed.e2e.test.ts` is opt-in on three env vars and I have no
  evidence of a green run; every other proof of this feature is local-lane only.
- **WebSockets and streaming bodies under a configured gate are untested.** `policy.ts:183` preserves
  them only on the fast path (`approval:"none"` and no direct secret). Once `approval:"required"`,
  every request is buffered (1 MiB cap, `EGRESS_BODY` 413) and rebuilt as
  `new Request(url, {method, headers, body})` — no test covers a 101 or a large upload through that
  path, and v3's `secret-substitution.ts:3` names "must not break a WebSocket upgrade" as the file's
  one hard rule. `connectToCapnweb`'s WebSocket transport rides `itx.fetch`.
- The audit facts are appended **inside** `storage.transactionSync` during a fetch
  (`policy.ts:331–334, 382`), i.e. a durable commit and a delivery fan-out per outbound request once a
  policy exists. v4 does not measure that cost.
- `#directReferences` reports an unknown secret and a wrong-origin secret with the same
  `SECRET_ORIGIN` code (`policy.ts:422–424`) — deliberate non-disclosure, but under trusted-client it
  just makes a typo hard to debug.
