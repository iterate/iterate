transaction refuses an unproved payload (`REPO_UNVERIFIED`, :127-129) and re-checks parent vs. head
(`REPO_HEAD_CONFLICT`, :134). The synchronous append door (pager attach) refuses repo events outright (DO:433-441).

**Tests that prove it.** `e2e/repos.e2e.test.ts` — six: CAS + head rollback on a stale parent; idempotent retry

for `repos`/`Repositories` in `v4/src/*.test.ts` and `v4/__workers-tests__/` returns nothing.

**What inside v4 it depends on.** `context/invoke-handle.ts` (byte-identical to v3), `stream/events.ts`,

## 2. What v3 has today for the same need

**No repo.** The three stores are: the log (8 MiB per event, `EVENT_BODY_MAX_CHARS`, `stream.ts:59`; bodies over
512 KiB auto-chunk), `itx.builtins.kv` — string-only, `${projectId}:` prefixed, `get/put/delete/list` over
`ITX_KV` (`built-ins.ts:94-100`, impl :293-317), and a facet's own DO SQLite (`iterate-context-durable-object.ts:649`,
`sdk/stream-processor-durable-object.ts:90`). No R2, no `crypto.subtle.digest` anywhere in `src/` except
`principal.ts`'s HMAC, no runtime bundler (`esbuild` is a devDependency used only by `build-sdk.mjs`).

v3 **had** `itx.repo.{get,put,list}` (Increment 13, `BUILD-LOG.md:201`) and **deleted it on purpose**:
`PLAN.md:90-92` — "repo/files roots and hello-files DIE — source is plain kv; proofs seed their own sources; a
future real repo mounts at **itx.files** as an ordinary capability." `docs/itx-surface-as-built.md` §12 F parks the
other half: apps/os "derives its key from a repo content hash and caches the BUILD artifact in KV under it; that
tier belongs to a build capability, not to the loader door."

`docs/assessment-userspace-apps-on-the-clean-room.md` Gap 3 (:195-231) is the standing decision, and it splits the
same way v4 does not: **Files** are "buildable in userspace TODAY as a facet with a `files(path, content, base)`
SQLite table"; the only platform addition contemplated is "an `itx.blobs` root over R2, ~80 lines, which Docs
itself does not need"; **Git** is "a fetch to a git remote … running in a loaded worker"; and "Platform-hosted
repos would be the full 3,840-line port and **should not be the first cut**." The ordering at :378 puts
git-as-a-fetch fifth, after the userspace workspace facet.

**Where v4 conflicts, specifically:**

1. **The litmus test.** `repos` fails "could this be written in a userspace worker?" only because v4 added the
   seam that makes it fail. v3's roots are physical primitives (the log, the two hosts, the bindings, addressing);
   a repo is a domain module. v4's counter-argument is its own reading-guide chapter title, "8. A public root is not
   automatically a primitive" (`docs/reading-guide.md:235`) — a case for an exception, not a v3 doctrine.
2. **A new kernel mechanism in the most protected file.** v3's `Stream` has exactly one in-transaction reduce slot,
   hard-wired to `CoreStreamProcessor` (`v3 stream.ts:465`, called :435). v4 generalises it and immediately runs
   three participants through it (`#trust`, `#repos`, `#fetchPolicy` — DO:375-378). This directly contradicts v4's
   own chapter 9, "Build an application without adding a kernel mechanism".
3. **Trusted client.** The WeakMap proof, `REPO_UNVERIFIED`, and the sync-door guard exist to stop a _client_
   claiming a revision it did not hash — the sixth e2e is exactly that. Under `feedback_trusted_clients_radical_simplicity`
   that defence is speculative machinery. The real driver is mechanical (async SHA-256 vs. `transactionSync`), and
   the design would collapse if the hash were not required.
4. **Tonight's identity work.** v4 forked before `v3/src/principal.ts`. The v3→v4 diff of `stream/events.ts`
   **deletes** `source.principal` and replaces it with `provenance`/`verification`, so a v4 repo commit records no
   author. On v3, `itx.builtins.append` stamps it (`built-ins.ts:322-324`, `stampPrincipal`) — attribution comes free
   _if_ the commit goes through the ordinary append door.
5. **"Content-addressed" is half true.** The revision is `sha256(JSON.stringify({files,parent,message}))`
   (`repos.ts:110`, :304). The blobs are not: `const digest = \`${commit.revision}:${path}\`` (`repos.ts:139`).
`repository_blobs`+`repository_files`therefore never dedupe across revisions — every commit re-stores every
file, and the join buys nothing a`(revision, path, content)` table would not. Files are stored twice: once in the
   durable event body, once in the blob table.
6. **The declared caps are internally inconsistent.** `files()` admits 1–256 files at up to 65,536 bytes each
   (`repos.ts:246-252`) = 16 MiB, over the 8 MiB `EVENT_TOO_LARGE` append ceiling that d3's memory arc set. And the
   64 KiB per-file cap already defeats the app: v4's own `examples/docs/README.md:100-103` says minified Yjs does not
   fit, so "publishing the processor's dependency requires a package/chunk layer".
7. **v4's app does not use the atomicity v4 paid for.** `src/client/docs.ts:477-520` commits (one call), checks,
   builds, then appends activation + rewrite-rule in a _separate_ batch. Cross-fact batch rollback is proved only by
   a synthetic e2e (`repos.e2e.test.ts:73`).

## 3. Proposed layering on v3

**Verdict: a repo is not an AXIOM.** It is USERSPACE, with a small LIBRARY helper — which is also what v3's own
Gap 3 already decided. Nothing about parent→head compare-and-swap requires the log's transaction; it requires _a_
single-writer transaction, and v3 already has a second one: **a facet is a real Cloudflare DO facet with its own
SQLite and single-threaded turns**.

- **USERSPACE (the store and the CAS).** `itx.builtins.facets.get("repos", { source, className, cacheKey })
.commit({ files, parent, message })`. The facet's turn _is_ the transaction, so the swap is atomic by
  construction — no participant seam, no WeakMap, no async/sync split (a facet turn is async, so `crypto.subtle.digest`
  is legal there). After the swap it appends `events.iterate.com/repo/committed` through
  `env.ITX.get().builtins.append`, so the log stays the interface and a fresh context can rebuild the projection.
- **LIBRARY (`src/library/repos.ts`).** The pure half only: canonical bytes, `sha256`, path/file validation.
  Honest cost: the tier's declared dependency is `LibraryItx = Pick<BuiltInScope, "fetch">`
  (`v3/src/library/index.ts:40`); a repos member needs `facets` + `append`, so `LibraryItx` widens there — which
  that file already names as the one place widening happens. `src/library/boundary.test.ts` keeps it honest.
- **Deliberately left out:** no `itx.repos` root; no `StreamCommitParticipant`; no `repository_blobs` table (one
  `revisions(revision, parent, message, offset)` + one `files(revision, path, content)`); no cross-fact atomic batch
  (the door is the facet method, not raw append); and **no `itx.build` / `itx.check`** — that is the separate build
  capability §12 F parks, and it is the only part that actually needs a new binding.

**If Jonas wants a root anyway,** the smallest root-shaped design that keeps v3's doctrines:

- Spell it **`itx.builtins.files`**, not `itx.builtins.repos` — `PLAN.md:92` already reserved that name, so it coins
  no new concept noun.
- **Drop content-addressing: the revision IS the committing event's offset.** Server-assigned, monotonic, already
  unique, already in `RepositoryHead`. `commit({ files, parent: number | null, message })` and the CAS becomes
  `parent === currentHeadOffset` — a pure integer compare, legal inside `transactionSync`. That deletes `prepare()`,
  the WeakMap, `REPO_UNVERIFIED`, `REPO_REVISION`, the sync-door guard and the async/sync split: roughly 90 of v4's
  275 code lines. Build caching does not lose anything — `built.key` already hashes the resolved files.
- The head map (`repoPath → offset`) is then small enough for the **existing** core reduce (`v3 stream.ts:465`),
  which is already transactional and already checkpointed under `REDUCE_CHECKPOINT_STATE_MAX_CHARS` (2 MB − 4 KiB).
  File bytes stay in the event bodies; the side table is a cache.

**Where v4 is better than v3, and should be kept whichever tier wins:**

1. `{ source: { repo, revision }, options }` — a **pinned** build input as _data_ — is the right answer to as-built
   §12 F, and better than a producer expression with a hand-managed `cacheKey`, because nothing has to be trusted to
   produce the same bytes twice.
2. Compiling in a stateless `BUNDLER` service with its own `BUILD_CACHE` keeps `nodejs_compat`, `typescript` and a
   `.d.ts` corpus out of the project worker. That is the right shape for the parked build capability.
3. `RepositoryHandle extends InvokeHandle` — the same brand as `FacetHandle`/`RpcStubHandle`, so a dotted call
   pipelines in one round trip.

## 4. Implementation sketch

1. **The store, entirely in userspace.** Add `v3/e2e/support/fixtures/repos-facet.ts` — a `DurableObject` subclass
   (~90 code lines: two SQL tables, `commit/head/read/list`, one `env.ITX.get().builtins.append`). Prove with a new
   `v3/e2e/repos-facet.e2e.test.ts` re-running v4's six assertions minus the raw-batch one, **against the deployed
   worker** (`WORKER_BASE_URL=https://… pnpm e2e`).
2. **The pinned source, with zero new code.** v3's `workers.get({ source, cacheKey })` already accepts an itx
   expression that produces modules under a required key. Extend `v3/e2e/workers-and-facets-sources.e2e.test.ts` to
   prove `itx.builtins.workers.get({ source: "itx.builtins.facets.get('repos', …).read('<rev>')", cacheKey: '<rev>' })`
   runs the committed source. This closes the "config worker from a repo" tier without any build capability.
3. **Only if a root is wanted:** `v3/src/files.ts` (~110 code lines, offset-as-revision), plus
   `src/context/built-in-roots.ts` +1, `src/context/built-ins.ts` +8 (type + wiring),
   `src/stream/core-processor.ts` +25 (one reduce case for the head map),
   `src/iterate-context-durable-object.ts` +6, `src/lib/errors.ts` +4 codes, and the §5 row in
   `docs/itx-surface-as-built.md`. Prove: `v3/e2e/files.e2e.test.ts` (CAS, race, isolation, idempotent retry), deployed.
4. **Build/check is a separate feature, sequenced after** — a `BUNDLER` service worker + binding, the generated
   type corpus, `itx.builtins.build`/`check`, `e2e/build.e2e.test.ts`. Do not land it inside this one.

## 5. Effort

**Upper bound, v4 measured:** repos alone = 275 (`repos.ts`) + ~37 attributable elsewhere + 172 (`repos.e2e.test.ts`)
= **~484 lines**, excluding build/check (`build.ts` 51 + `bundler.ts` 224 + `build.e2e.test.ts` 119 + a new deployed
worker + a generated `.d.ts` corpus ≈ another 400 code lines and a binding).

At this codebase's density (~300 code lines with tests, docs and a deployed proof in ~3 h):

- Step 1 (userspace facet): ~90 fixture + ~130 e2e = **~220 lines, 2–3 hours**. No platform change.
- Step 2 (pinned-source proof): ~40 e2e lines, **0.5–1 hour**.
- Step 3 (the `itx.builtins.files` root, offset-as-revision): ~155 code + ~140 e2e + docs = **~300 lines, 3–4 hours**.
- Step 4 (build/check): **a day**, not an evening — a second deployed worker and a generated corpus dominate.

Steps 1+2 together are under half of v4's repos-only line count and add nothing to the kernel.

## 6. Dependencies and sequencing

- **Nothing must land first for steps 1–2.** The facet host, `env.ITX`, `builtins.append`, `workers.get` with
  `cacheKey`, and the e2e harness all exist in v3 today. Step 3 needs no binding either (the DO's own SQL).
- **Identity should land first if commits are to be attributed.** `itx.builtins.append` stamps `source.principal`
  (`built-ins.ts:322-324`); what a _facet's_ engine append stamps is unverified (see §7).
- **Independent of** ingress/project-host, subscriptions, the rewrite table, and d3's memory arc — except the
  8 MiB event ceiling, which caps a commit's total file bytes and must be reflected in the declared caps.
- **It unblocks** the "Files" half of Gap 3, hence the Docs workspace facet (assessment step 3), and it is the
  precondition for the "config worker from a repo" tier and for build/check's pinned input. It does **not** unblock
  git — that stays "a fetch from a loaded worker" (assessment:224-231).

## 7. Risks and questions for Jonas

1. **Does the platform host source at all?** Gap 3's standing answer is no ("files buildable in userspace as a facet";
   "platform-hosted repos … should not be the first cut"). v4 reverses that decision without arguing against it.
   Everything else here follows from your answer.
2. **Is a cross-context-stable sha256 revision name worth its cost?** It buys the `prepare()`/WeakMap/async-sync
   split and ~90 lines; `built.key` already content-keys the build, and v4's blob table does not dedupe by content
   anyway. Offset-as-revision is strictly cheaper and loses only "the same tree has the same name in two contexts".
3. **Is `StreamCommitParticipant` acceptable in v3's `stream.ts` at all?** v4 opens it and immediately runs three
   modules through it. Opening it invites a fourth.
4. **If a root lands, `itx.builtins.repos` or the already-reserved `itx.builtins.files` (`PLAN.md:92`)?**
5. **Handle lifetime.** `repos.get()` mints an `InvokeHandle` stub per call and `client/docs.ts` never disposes one —
   same class as `reference_rpc_result_objects_pin_callee_until_disposed`. Acceptable for a per-path handle, or should
   the path be an argument (`itx.builtins.files.commit('/site', …)`)?
6. **Unverified — I read the code but did not run v4's tests or its deployment.** (a) the README's "85 deployed
   public API/application tests in 19 files"; (b) whether `repos.e2e.test.ts` has ever run against a deployed v4
   worker — the file is not `.deployed.` and the lane defaults to a local `wrangler` harness; (c) the cap arithmetic
   in §2.6 (256 × 64 KiB = 16 MiB vs. an 8 MiB append ceiling) — both limits are in the source, I observed no refusal;
   (d) whether a facet's engine append stamps `source.principal` on v3.
