One assistant, two halves — the voice colleague overhaul

What PR #2536 changes and why, told through the real conversations that broke it and then proved it. Click any timeline row for the event underneath. All times are from live production runs on 2026-08-26.

caller / client voice agent (the "fast half") colleague (the "backend")

Takeaway: a voice assistant has ~200ms of judgement, so hard questions go to a "colleague" — a full agent with tools and time. Before this PR the colleague was reborn with amnesia on every reconnect, its replies raced a 3-minute deadline down a lane that lost them three different ways, and nobody could see what it was doing. Now: one colleague per stream (memory survives), every reply is a durable event (nothing lost), progress statuses flow to the caller, and each conversation leaves a readable transcript. Merging is low-risk: the diff touches a per-project template, lab tooling, evals and one C fix — zero platform (apps/os/src) changes; nothing deployed changes until a project installs the template.
Vocabulary — enough to read the timelines
stream An append-only event log with an address like /agents/voice/2608261249. Everything below — audio, presses, transcripts, statuses — is an event on one.
voice agent / fast half A processor living on the call's stream. It holds the realtime provider socket (OpenAI voice), pumps audio both ways, and runs the tools. It is a mouth, ears, and quick judgement — nothing more, by design.
colleague / backend A full text agent on its own stream (/agents/voice-notes/…) that the voice consults via a note_to_self tool for anything needing tools, files, or time. The person hears one assistant; these are its two halves.
durable vs ephemeral Durable events are stored forever and replayable; ephemeral ones (audio frames) reach live connections and vanish. What should survive a crash must be durable.
fold The processor's state, recomputed from the stream's durable events. Anything in the fold survives the process being killed; anything in memory does not.
idle deadline A call with no caller input for 60s is hung up server-side. This makes reconnects a routine event, which is the pressure the whole overhaul answers.
contract version The voice agent's schema version. Bumps are clean breaks: an old persisted fold is recomputed from events rather than migrated. This PR walks it 11.0.0 → 17.0.0.

Scenario 1 — the morning it all went wrong (before)

Real session, prd, 2026-08-26 ~12:50. The ask: “prime factorize the first 23 digits of pi.” Under the old design the colleague was minted per conversation and replies came back through ask() — append a question, wait up to 180s for the next chat reply, matched by order.

12:50 caller asks for the factorization note_to_self call 1
The voice says “let me look into that” and mints colleague #1 at /agents/voice-notes/conv_7bb6298f… — a path named for the conversation, not the stream. Remember that.
12:51 colleague #1 starts working web search + bigint factorization
It does the job properly — verifies the digits against NIST, computes 2³ × 233 × 138337 × 200023 × 274521601. Correctly. Nobody will ever hear it.
12:51–12:56 a platform stall freezes colleague #1 separate incident
A processor-host staleness window (investigated separately that day) froze the colleague for 4½ minutes — which pushed its reply past the 180-second ask() deadline. The deadline design turned a slow answer into a lost one.
12:53 idle deadline hangs up call 1 no input for 60s
The caller was waiting quietly for the answer. Waiting quietly is indistinguishable from being gone, so the server hung up. This is routine, and the design has to survive it.
12:56 caller calls back: “what’s going on?” call 2
New conversation → new colleague (#2), born with no memory of the question. Asked “what’s going on”, it went spelunking through the platform to find out — and, finding colleague #1 frozen, committed an “ops: redeploy” to the project’s config repo. Helpful. Terrifying.
12:58 colleague #1’s correct answer arrives — and is dropped ask() deadline passed 
# the reply lane, before:
ask():
  matched: by order, not correlation   # two pending asks? first reply feeds both
  deadline: 180s                        # a slow answer resolves nothing
  unsolicited replies: lost             # no ask waiting = message vanishes
Three loss modes, all observed live that day. The answer was computed twice (calls 1 and 4, two amnesiac colleagues, two interpretations) and spoken zero times.

after scenario 1 — what the system knew

4 conversations, 4 colleagues, 0 answers delivered.
No transcript existed: audio is ephemeral, so the calls left no readable record at all.
The caller’s question: still unanswered.

the three design faults

1. colleague per conversation → reconnect = amnesia
2. replies ride ask() → three loss modes
3. no durable record → no memory, no debugging, no evals

Scenario 2 — the same ask, after the overhaul

From the passing evals/voicelab-first-cause run and the evening sessions. Same shape of question; every fault above has a specific counterpart fix.

+0s caller asks something hard note_to_self
The note goes to the stream’s one colleague at /agents/voice-notes/voice/<stream> — same desk for every call, ever (contract 12.0.0). The facet also appends an instant “picking up a note” status, so the next question has an answer even before the colleague’s first turn.
+4s… statuses stream back as the colleague works copy-to-stream 
# forwarded from the colleague's own stream, transformed en route (15.0.0):
colleague-status: { phase: writing code }
colleague-status: { phase: running code }
colleague-status: { activity: "Reading the requested codeword file" }
colleague-status: { phase: a script failed, failure: "TypeError: …" }  # failures included
The same lifecycle the web UI shows (“writing code”, “running code”), pushed — never polled — onto the call stream. The voice whispers each change into the model’s context without speaking it, so “what’s it doing?” gets “it’s running the code now” instead of vamping, and a failure gets said instead of invented around.
+15s the answer arrives as a durable event colleague-note · 16.0.0 
# the reply lane, after: every chat message the colleague sends is copied
# to the call stream as a durable colleague-note. No deadline. No order
# matching. Solicited or not. Survives eviction. A note landing between
# calls is folded and briefed into the next session.
+15.5s the voice speaks it answer-transcript
And — new in 13.0.0 — both sides of every finished turn land as durable utterance-transcript / answer-transcript events. pnpm cli voicelab transcript prints any conversation after the fact; the evals assert against it; the recap below is folded from it.

Scenario 3 — hang up, call back, it remembers

+60s idle deadline hangs up — mid-task routine
The colleague keeps working; its stream, memory, and pending statuses are unaffected.
+90s caller calls back 
# the fresh provider session is briefed from the fold:
- transcript recap        # "Said so far, oldest first: …" (13.0.0)
- mid-task line           # "Your backend is mid-task — do not re-send the note" (14.0.0)

The reconnect is invisible: no fresh greeting, no repeated question, no duplicate note (the observed reconnect bug where the model re-asked and the duplicate answer became undeliverable). With greeting on the certificate (17.0.0) the model even speaks first — “hi again” falls out of the recap for free.
+2m a late reply lands in whichever call is live
Or, if no call is live, in the next session’s briefing. “Silence is always an option” remains true — but losing an answer no longer is.

Why it’s built this way

Why a subscription instead of fixing ask()’s deadline?

Any request/response lane needs correlation, a timeout, and a story for unsolicited messages — three things to get wrong, and all three were observed wrong in one evening. A durable event lane needs none of them: the platform already guarantees ordered, at-least-once, replayable delivery, and “a reply that outlives its call” stops being an edge case because the fold keeps it for the next briefing. The same copy-to-stream subscription that forwards statuses forwards replies — one mechanism, not two.

Why whisper statuses instead of speaking them?

Statuses are injected as quiet context items, never spoken unprompted. The model knows; the person asks if they care. The earlier “never mention your other half” secrecy rule was dropped the same day — a model forbidden to mention its backend rounded every status down to “I’m working on it”, and one that couldn’t admit a delay invented an explanation for it. The briefing now says: statuses are ground truth, failures are to be said plainly.

The filter-vs-transform postmortem (why the eval exists)

The reply lane shipped with the transform handling web-message-sent but the subscription filter not delivering it — dead code that looked alive, found only because the end-to-end eval insisted on hearing the answer. The unit test had been written from the same wrong list. Lesson encoded in the eval: assert on what the caller hears, not on what the plumbing intends.

buildCacheKey — the diagnostic this PR leaves behind

Mid-overhaul, prod served a three-commit-old facet build beside a fresh entrypoint for ~2 hours (self-healed by isolate eviction before it could be pinned). The one missing instrument was “which build is this live facet actually running?” — so health() and the facet runtime bag now report the content-addressed build key, turning the next such window into a two-second check.

What else rides along

The host CLI writes its report in attended mode too (it used to error on every quit); talk --auto skips both prompts; two self-contained evals (voicelab-roundtrip, voicelab-first-cause) drive the real prd pipeline with say-synthesized speech and assert against durable transcripts.

Is it safe to merge?

The diff is 10 files: the voice-agent template (configs/voice-agent/), voicelab tooling and tests (apps/os/scripts/voicelab/), two evals, task files, and one attended-mode fix in the C host CLI. There are no changes under apps/os/src — merging deploys nothing and changes no running system. The template reaches a project only when something installs it (voicelab talk, or the mobile app’s setup), and the 17.0.0 contract is already live on the iterate, misha, and voicelab-eval prd projects plus the PR‑2537 preview, where it has been exercised all day. The boards’ event surface (presses, audio frames, speaker policy) is untouched. Riskiest line: the colleague-mint block’s revision-keyed subscription install — covered by unit tests and both evals.
