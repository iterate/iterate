PR #2532: the attempt-progress watchdog

Read the story top to bottom — it assumes nothing. Then the timelines: click any card and the right pane shows the log entry plus who-holds-what at that moment.

1. What this system is, in five sentences

A user sends a chat message to an agent. The platform must call an LLM and stream the answer back. The machine doing this work is a Cloudflare Durable Object, and Cloudflare is allowed to kill it at any moment — memory pressure, deploys, whim. So the rule of the whole codebase is: nothing that matters lives only in memory. Every fact gets appended to a per-agent log (the codebase calls it a stream, and its entries events), and the current state of the world is always recomputed by replaying that log — a killed machine loses nothing, because its replacement reads the same log.

2. So what does "call an LLM" look like here?

Three steps, two durable and one fragile:

1. append to the log:  "llm-request-requested"      durable — "someone owes an answer for message X"
2. actually call the LLM, in memory                  fragile — this is the "attempt"
3. append to the log:  "llm-request-settled"         durable — the ending: succeeded / failed / cancelled

Step 1's log entry is called the request; its position in the log (its offset, e.g. @44) is its name forever. Step 2 is an attempt — one in-memory try at answering it. The distinction matters because a request can take several attempts: retries are new attempts (in fact new requests — more later), but the user-visible question "did message X get answered?" is about the request.

Recovery is free by design: if the machine dies between 1 and 3, the replacement replays the log, sees "requested, never settled", and just runs another attempt. This is called adopting the open request.

3. One more rule, and then the bug is obvious

When does the code check "do I owe anything?" — replaying the log is not free, so it happens when a new entry lands in the log (a "delivery"). Every append wakes the machinery, which catches up and, at the head of the log, runs its obligations check (#atHead): expire overdue things, adopt open requests, open new ones. No new entry → no check. The codebase calls this being delivery-driven.

The bug (what #2530 diagnosed): suppose the in-memory attempt hangs — the network path to the LLM is severed mid-call, the promise never resolves, and (worst case) it even ignores cancellation. Then: no success entry, no failure entry, no log entry at all. And because checks are delivery-driven, nothing ever asks "is that attempt okay?". The log says "request open" forever; the user watches a spinner. On busy systems some unrelated entry eventually lands and wakes things (30–40s later); on a quiet one the only guaranteed wake is a crash-detector ~15 minutes out. Measured on preview: first replies taking 150–183 seconds. A hung attempt never fails — and only a written failure triggers a retry.

4. The fix: a watchdog per attempt

When an attempt starts, start a second in-memory task next to it whose only job is to watch the first. Both share one little record (#inFlightLlmCall) holding the request's name, a cancel button (AbortController), and a timestamp lastProgressAtMs. Every streamed chunk from the LLM refreshes the timestamp. The watchdog loops: "any progress in the last 45 seconds? sleep until the deadline. None? write the failure entry to the log myself, then cancel the attempt." That one log write is the whole cure — it is a delivery, so it wakes the machinery, and it is a failure, so the retry logic engages.

That's the whole job of #appendAttemptFailure: "write the failed ending to the log, properly". It writes two entries in one atomic append — the ending itself, plus a human-readable error line ("attempt 1 of 3 … Retrying.") that ends up visible in the agent's context. It's a shared helper because exactly two callers need to write a failed ending: the attempt's own catch (the LLM call threw) and the watchdog (the LLM call hung). Note what it does not do: it never schedules the retry. Retrying works like everything else here — by log replay: 

#appendAttemptFailure writes:  llm-request-settled { status: failed }   + the visible error line
        ↓ that entry replays through the state recompute (the "fold")
fold:   open request → closed;  failure count += 1;  count < 3? → note "we owe another try"
        ↓ next obligations check (woken by this very entry!)
after a pause (10s, then 20s, then 40s — the "retry ladder"):
        append a NEW llm-request-requested → new attempt + new watchdog

5. The two dangers, and the two tricks that handle them

Danger A — duplicate endings. Five different pieces of code can try to end the same request: the attempt succeeding, the attempt erroring, the watchdog giving up, a user interrupt, and a 10-minute-overdue backstop. Two of them can fire in the same instant (attempt finishes at 44.9s of silence; watchdog wakes at 45.0s). The trick: every ending is appended with the same dedupe key, settle/<request-offset>. The log accepts the first write with a given key and silently ignores the rest (appendUnlessLostIdempotencyRace — the name says it: append, unless you lost the race). So the journal always holds exactly one ending, no matter who raced.

Danger B — the watchdog killing a healthy attempt. Ordering, inside the watchdog: append first, cancel second. If it cancelled first and then lost the dedupe race to a just-completed success — fine, cancelling a finished thing is a no-op. But the reverse order could cancel an attempt that was about to succeed while the watchdog's own write then failed → nothing ends the request at all. Append-first means an ending is durably decided before anything gets cancelled. (And the cancelled attempt can't make a mess afterwards: every one of its writes checks the cancel signal first.)

What if the machine dies with both tasks in it? That's the beauty of keeping the watchdog in memory: it can only be lost together with the very attempt it watches. A heartbeat mechanism (the keepalive) notices the dead machine, boots a replacement, and appends a "processor revived" entry to the log — a delivery! — which triggers the obligations check → adopt the open request → new attempt, new watchdog. There is no reachable state where an attempt runs unwatched.

6. The full call graph of agent-llm-request.ts

a new log entry lands (any entry at all)
└─ AgentTurnLoop.#atHead                       "do I owe anything?" — only runs on deliveries
   ├─ open request 10min overdue → cancel + write settled{cancelled/expired}   the backstop
   ├─ open request, no attempt running here → run(args, open)            first dial, adopt after a death, ladder retry
   └─ owed a new request & pause elapsed → append llm-request-requested        which opens one

run(args, open)
├─ inFlight = { requestOffset, controller, partialText, lastProgressAtMs: now }
├─ start watchdog (task ①):
│    loop while (record still mine AND not cancelled):
│      quiet < 45s → sleep the remainder            each chunk pushes the deadline back
│      quiet ≥ 45s → #appendAttemptFailure     write the ending FIRST…
│                    abandonExpired(offset)          …then cancel + free the record
└─ start attempt (task ②):
     ├─ rebuild the prompt from the log's committed history
     ├─ call the LLM;  each chunk → refresh lastProgressAtMs + append llm-response-chunk
     ├─ success → append [assistant message, settled{succeeded}, token usage]   one atomic write, key settle/<offset>
     ├─ error   → cancelled? do nothing (someone else ended it)
     │           else #appendAttemptFailure
     └─ finally → free the record (if still mine)

#appendAttemptFailure   the shared "write a failed ending" — used by attempt-error and watchdog
├─ attempt number = failures-so-far + 1              read from replayed state, not a counter in memory
└─ atomic append, dedupe key settle/<offset>:
     llm-request-settled { failed, errorMessage }
     stream/error-occurred { "…failed (attempt N of 3): … Retrying." }

Appendix: why this shape and not the obvious alternatives
  • Why not just give the LLM call a timeout? Because the failure case that hurt was a severed network path whose promise never resolves and which ignores cancellation. Any fix that waits on that promise inherits its hang. The watchdog ends the request from the outside, without ever awaiting the attempt.
  • Why 45 seconds? A slow model legitimately pauses between chunks; killing it too eagerly costs a retry (10–60s wasted). Too lazily, and users stare at a spinner. 45s clears every observed healthy pause, and a false trip is cheap because retries are safe by construction.
  • Why is an in-memory watchdog acceptable in a nothing-lives-in-memory codebase? Because it protects something equally in-memory. Both die together; the keepalive + log replay resurrect both together. Durability is only required for facts, and the watchdog's one fact — "this attempt failed" — is written to the log at the moment it matters.
  • Why are retries new requests instead of re-running the old one? Same reason as everything: the log is the truth. A new request entry gives the retry its own name, its own visible history, and its own ending — replay tells the whole story without hidden state.
