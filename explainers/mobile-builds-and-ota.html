Mobile builds & OTA — how the phone decides what to run

Click any event to see the state of the whole system (phone + update server) right after it, as YAML on the right. Times are made up but realistic. Scenarios 1–2 are the happy paths, 3 is a real trap caught by field-testing on Misha's phone (red events), 4 is the same taps after the fix.

The whole system is three pointers, and every bug here is one of them lying. The binary decides what CAN run (its runtime fingerprint must match the JS). The channel decides what SHOULD run (which branch's JS to follow). The override is a user-held pointer at a different channel — and it persists across restarts and reinstalls, which is more than anyone expects. Rules that fall out: a PR's binary is built FOR the PR's channel, so installing it is enough; the app learns its binary's own channel rather than trusting Updates.channel (which reports the override, not the baked value); and an explicit switch to a channel with nothing runnable is undone instead of left dangling.
Reference — the six words you need
word meaning
binary / build The installed app itself, compiled by EAS in the cloud. Installing one replaces the previous (keychain survives). Contains an embedded copy of the JS from the moment the build was triggered.
update A JS bundle published to the update server. The app can swap to a newer one without reinstalling — that's OTA (over the air).
channel A named stream of updates, like a git branch. preview follows main; each PR gets a channel named after its branch. Every binary has one channel baked in at build time — its default.
runtime fingerprint A hash of everything native (modules, config). A binary only accepts updates with the SAME fingerprint. The update server filters by it before answering — so "no update" and "your binary is too old" are indistinguishable from the phone.
override "Fetch updates from THIS channel instead of the baked one." Set by scanning a PR's OTA QR. Persists in native storage across restarts and reinstalls; a fresh install force-clears it on first boot.
embedded fallback On launch, if nothing downloaded is runnable for the current channel, the app runs the JS baked into the binary — which can be older than what you were just running.

Appendix — why Updates.channel lies (the scenario-3 root cause)

In expo-updates, the JS-visible constant is built from the request headers as merged at launch — and a persisted override wins that merge: 

// AppController.swift
"channel": requestHeaders["expo-channel-name"] ?? ""
// UpdatesConfigOverride.swift — loaded from UserDefaults and merged into config at launch

The plist's original (baked) headers never cross the bridge. So after a restart with an override set, Updates.channel IS the override. The fix: on a boot that launched override-free, Updates.channel is trustworthy — cache it per binary; on polluted boots it's honestly "unknown", which counts as watched.
