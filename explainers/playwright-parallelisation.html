How many Playwright workers?

One runner can start many tests while they wait on the network. But every Playwright worker is a separate Node process, normally with its own browser. How much concurrency helps before CPU, memory or the backend starts slowing things down?

32 workers shortened Playwright from 148s to 114s; Vitest now finishes last at 125s. Full preview: 10m05s → 8m53s, including a 39s faster install. The 32-worker run needed one dashboard retry; both runs had the same quarantined photo failure. Next: 64 workers. Repeats will check whether these gains and failures recur.

What this experiment holds fixed

Same application revision and 92 named root browser cases; 16, 32, 64 or 92 workers; one unsharded runner; the same Playwright retry, timeout, trace and video settings; the same readiness, lease and cleanup policy. Every run gets a fresh runner. The image uses the same mutable tag, so an identical resolved image is not proven. Preview slot, test retries, deploy reuse, remote-service latency and cold filesystem reads can still vary.

The older 16-worker reference is from another PR/slot. The two sharded runs split the same catalogue across six browser jobs, alongside an app-test job, plus Prepare and Finish. They explain the motivation; the new same-branch runs are the worker-count comparison.

How to interpret a “retry”, a quarantine result and a queue

A test retry is a second attempt of one test, not a rerun of the whole CI job. Retries are shown separately in the trace. The existing flake wrapper marks some tests as expected failures; when their bodies pass it deliberately throws “Flaky test passed this run”. Those are body passes, not regressions. A quarantined body failure is called out separately. Skipped cases never occupy an active worker slot.

Playwright runs one test at a time in each worker process. More workers let waiting tests overlap, but process/browser startup and page work still use CPU and RAM. Worker count is a maximum, not proof that that many tests are simultaneously active. The trace records actual test start/end times and worker IDs.

Earlier pnpm / Depot / Nub investigation

Why does an “up to date” install take a minute?

A fresh-runner install is doing expensive work even when it adds no packages. On an isolated 16-core Depot runner using the same baked image and commit, the first install took 72.4s. Repeating it in the same checkout took 7.2s.

Isolated probe, in order Elapsed CPU: user + system What it tells us
First pnpm install on fresh runner 72.4s 9.7s No packages added or removed; most elapsed time is outside CPU execution.
Identical command, same runner 7.2s 8.4s The first invocation warmed or changed local state that a new job does not reliably inherit.
Third invocation, ignoring scripts 6.7s 7.7s Hooks are small. The root prepare hook itself took 22–31ms.

The detailed pnpm log puts most of the first-run delay between package import completion and manifest updates, around dependency and executable linking. The pinned pnpm source still hoists and links executables on this path. Fresh filesystem access is the leading explanation; we have not identified which Depot storage/cache layer accounts for it.

Probe method and limits

Probe workflow 6x072ksg55, run ndjqbsdmlq, commit ec079ad, Node 24.21.0, pnpm 10.24.0, 16x64 runner. Same named custom image as preview CI; checkout uses clean: false. Commands: pnpm install --frozen-lockfile --prefer-offline --reporter=ndjson, repeated twice, then once with --ignore-scripts. The pnpm store and checkout are on the same ext4 filesystem. CPU totals include child processes and may overlap across cores.

First-run gaps: import work ~6.4s; the next ~58s includes hoisting, bin linking and direct dependency linking; project linking and state writes add ~6s. These are intervals between pnpm events, not separately instrumented function durations. Bin-conflict messages mark progress; they do not prove the conflicts themselves cause the delay. All three installs succeeded. Raw evidence is retained as pnpm-install-probe.

This separates first-use state from warm state, not OS page cache from image lazy reads or pnpm metadata writes. No new package-import/download events appeared. A fresh PR run gets new machines; it does not reuse the last run’s in-memory filesystem cache. Some fresh machines can nevertheless be fast, as the repeat preview trace shows.

Depot / pnpm changes worth doing first

Order Change Why / what to validate
1 Start shard setup during Prepare. Checkout, pnpm and Chromium can run before the backend is ready. Moves setup off the path after readiness. Today needs: prepare prevents the entire job from starting. Gate the test command on the prepared deployment identity instead.
2 Stop doing a fresh full-workspace install before cleanup. Reuse the prepared runner for finalization, or prepare the finalizer while tests run. The old run spent 74s installing in Finish. Account for idle runner cost if keeping a runner alive. A small standalone collector/cleaner is another option, but needs its runtime dependencies packaged correctly.
3 Give the baked install an exact input fingerprint. Skip reconciliation only when the checkout matches the image’s recorded dependency inputs. Hash lockfile, workspace config, all package manifests, patches, pnpm hooks/config, toolchain/platform and any install-hook inputs. On mismatch, run the normal frozen install. Measure total job time: some cold reads may move into test startup.
4 Record image identity and setup timings. Log the resolved image digest/bake identity, input fingerprint, install phase and Chromium start/end. Distinguishes an old dependency image from a slow filesystem with the right dependencies. The current mutable tag alone cannot prove which snapshot was used.

Depot also recommends questioning the final merge job. Our report merge itself takes under a second; the expensive part is getting another machine ready and doing cleanup. We still need reliable cleanup and complete results, but they need not require another full install.

The repo already follows Depot’s main custom-image advice: bake the installed workspace, pnpm store and Chromium, and preserve them with checkout clean:false. Another ordinary cache action would not remove the work observed here.

How to overlap setup safely

Start the test machines alongside Prepare. After local setup, wait for a ready record scoped to the current run/attempt, commit and preview lease. The record names the actual deployed versions. Preparation failure or cancellation ends that wait; it must not fall through to an old preview. Prepare’s own install still precedes its deployment scripts; it is the other machines’ setup that can overlap. Keep the existing lifecycle lock through tests and cleanup.

Depot’s parallel steps can overlap independent work on one runner, with a join before dependent work. They do not bypass a cross-job needs edge. For separate shard machines, readiness must be a step-level barrier, or the workflow must be split into smaller jobs. Test the cancellation and missing-plan paths as well as success.

Cache disks and image refresh: useful, but not the first fix

Depot cache disks could retain fetched packages between runs when dependencies change. Our slow no-op probe fetched none, so that is not yet evidence they will speed this case. Benchmark a pnpm-store mount separately; do not share one mutable node_modules tree among concurrent checkouts.

The image rebuilds on main dependency-file changes and weekly. Empty commits do not refresh it. The rebuild path list names manifests and lock/workspace files, but omits direct patch and pnpm-hook/config paths; include those inputs explicitly when introducing the fingerprint. A matching lockfile often already triggers a rebuild, so this omission does not explain today’s measured delay by itself.

Relevant repo files: .depot/workflows/build-preview-ci-image.yml, scripts/depot-ci/bake-preview-ci-image.sh, .depot/workflows/cloudflare-preview-sharded.yml.

Why not just enable optimisticRepeatInstall?

It is tempting, but the 10.24.0 implementation can return “up to date” when no package manifests have newer timestamps, before examining lockfile and patch changes. That is the wrong assumption for a checkout restored from an image. Prove invalidation for lockfile-only changes, overrides, catalogs, patches and hooks before adopting a fast path. An explicit content fingerprint avoids depending on those timestamps.

Nub: promising idea, fails this repo’s first compatibility check

I tried Nub v0.9.2 in a disposable clean source tree on Depot. nub install --frozen-lockfile rejected the existing lockfile immediately. The same commit’s frozen install succeeds with pnpm 10.24.0. 

ERR_NUB_OUTDATED_LOCKFILE
apps/dummy-petshop / capnweb:
  manifest: npm:@iterate-com/capnweb@^0.12.2
  lockfile: npm:@iterate-com/capnweb@0.12.2

Our workspace has a parent-scoped override pinning Dummy Petshop’s capnweb to 0.12.2. Nub’s freshness check appears not to apply that override as pnpm does. The lockfile remained unchanged. This is a compatibility failure, not a fast-install result.

Recommendation: keep Nub as a separate experiment. Resolve that blocker first, then verify patches, package extensions, workspace aliases, native builds and the actual Expo/Vite/Playwright tools before timing a replacement.

What Nub offers, and what was actually checked

Nub’s pnpm compatibility docs claim pnpm v9 lockfiles, catalogs, workspace links, overrides and patches. nub install uses its own installation engine; nub pm instead provisions the real pinned package manager, so it is not the same optimization.

The global virtual-store design aims to replace large numbers of per-file links with package-level links. In our actual probe Nub printed “global virtual store auto-disabled in CI” and chose an isolated layout. Its published warm global-store benchmarks therefore do not predict this CI setup.
