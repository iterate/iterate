Mobile install-state matrix

What happens when your phone meets a mobile PR — for every combination of what's on the phone and what the PR changes. Find your row (phone), find the PR's column, read the cell. "pr-1234" is the PR whose QR codes you're looking at; "pr-5678" is any other PR.

Takeaway: the worst any cell gets is Download → Install → Open in app → Switch, and the app tells you when you're in that cell. Native builds happen only when native code actually changed — one build per fingerprint, shared by the PR, its siblings, and main after merge. Only two facts about your phone matter — the binary's fingerprint and the channel it points at; where any of it came from never does. Nothing is silently stale anymore.
Glossary — the six words the table uses
binary (native build)
The installed app itself, compiled by EAS. Carries a runtime fingerprint — a hash of everything native (dependencies, config, native modules). "main binary" and "pr-1234 binary" mean binaries with main's / the PR's fingerprint.
JS bundle / OTA update
The JavaScript, published separately on every push. A binary only ever runs bundles published with its exact fingerprint — anything else is invisible to it (the update server filters before answering).
channel
Which stream of JS the binary pulls from. Every CI binary is built pointing at preview (= main). Each mobile PR publishes to its own channel (pr-1234 ≈ its branch name).
override / Switch
Scanning a PR's OTA QR opens a confirm screen; Switch points the binary at that channel. The first boot of any newly installed binary clears the override — which is why installs come before channel switches, never after.
snapshot
On every publish, CI records each channel's latest runtime + expected build on prd (/m/channel-status/<channel>). It's how the app can say "this channel's latest JS expects a different native build" — the one thing the update check can't see.
install page
os.iterate.com/m/install/<channel> — what install QRs encode. Resolves the channel's expected build at scan time (never stale), and keeps an Open in app link for the post-install switch.

The three rules that generate every cell

1 · The runtime gate A binary runs only JS published with its exact fingerprint. Mismatched JS isn't "rejected" — it's invisible.
2 · One build per fingerprint A JS-only PR has no binary of its own — "its" binary is main's. A native-change PR gets the one build its fingerprint will ever need; main reuses it after merge.
3 · Mismatches announce themselves When your channel's latest JS needs a different fingerprint than your binary, the app (via the snapshot) shows a banner + Download button. Download opens the install page, which orders the steps: Install, then Open in app.

Distinctions that sound meaningful but aren't

The phone's entire behavior-relevant state is two facts: its binary's fingerprint and the channel it points at. Everything else about where things came from is provenance the system neither stores nor consults — it only affects what Build info displays and which backend the bundle recommends. So several states you can describe don't exist as far as the machinery cares:

"Whose build is my binary?" Not a thing. "pr-1234's binary" means "a binary with pr-1234's fingerprint" — when fingerprints match, the PR, its siblings and main share one literal build. The rows below are named by provenance only as a courtesy.
Intra-PR pushes (old JS + old native of the same PR) Not a new column — re-read the matrix with "what the PR changes" measured against what you hold. Staying on the channel: a follow-up push that keeps the fingerprint is the ALREADY-THERE cell (banner / rescan pulls it); one that moves the fingerprint is the DOWNLOAD cell — your binary just became "old main" relative to its own PR. A push changing native and JS is still one fingerprint move: install once, the JS comes with it.
JS from old PR A on a binary from old PR B Legal, and unremarkable: scanning any QR compares B's fingerprint (the binary's) to the target channel's latest — match → one scan, mismatch → Download. Which PR the running JS came from never enters; it only contributes its stamped backend recommendation. There is no "wrong pairing" state the phone can be trapped in.

ONE SCAN

Running pr-5678's JS on this binary means the two PRs share a fingerprint (rule 1) — sibling PRs sharing one build is by design. So pr-1234's OTA QR is one scan: Switch → instant. (A binary whose fingerprint doesn't match this PR's latest is just the DOWNLOAD cell above, whoever built it.)

if 5678 later diverges
If pr-5678 moves its fingerprint past your binary, its channel goes quiet for you and the Download banner fires for its expected build — each channel's snapshot speaks for itself.

…and when the PR merges

JS-only changes Native changes No app changes
Main's publish OTAs every main phone on next launch. The merged PR's channel, snapshot and QR assets are deleted, and the PR body's section is swapped for main's QRs — the merged PR is the on-ramp back onto main. Same swap — and main reuses the PR's already-finished build (same fingerprint), so the merged body's install link is usually live immediately instead of waiting out a fresh ~20-minute build. Phones on old binaries see the Download banner until they install. Nothing mobile happens.
