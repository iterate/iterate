A phone call to your project

How the Iterate iOS app's voice button works, from first principles. Read top to bottom; click any timeline row to see the real event underneath. Times are from live runs against production on 2026-08-28.

The gist: the phone is deliberately dumb. It records tiny slices of microphone audio and posts them to the server; the server holds the connection to the speech model, decides everything, and sends slices of answer audio back. The phone's entire playback policy is three rules: if told to clear, throw away queued audio; play what arrives; nothing else. All of the intelligence — turn-taking, interruption, the "thinking backend" that can browse and run code, memory across calls — lives server-side, which is why the same server works identically for a terminal, an ESP32 dev board with a microphone, and now a phone.
Words you need (skip if you know the platform)
stream An append-only log of events living in one Cloudflare Durable Object. Everything on Iterate — chats, repos, this voice call — is a stream. This phone's calls all live on ONE stream named for the device, e.g. /agents/voice/mobile-<device-uuid>.
durable event Appended to the log forever; anyone can read it later. Call lifecycle, transcripts, and backend statuses are durable.
ephemeral event Delivered only to connections that are live at that moment, never stored. Audio frames are ephemeral — nobody wants last Tuesday's microphone replayed.
voice-agent facet The server-side program hosted inside the stream's own Durable Object. It holds the WebSocket to the speech provider (OpenAI Realtime), paces answer audio out, and runs the call's rules. The phone never talks to the provider.
frontend / backend Two halves of one assistant. The frontend is the realtime voice model — fast, no tools. The backend ("colleague") is a full agent on a sibling stream with tools, files, and time; the frontend sends it notes and relays its replies. Both are server-side; the phone just hears the result.
server VAD Voice Activity Detection, done by the provider: it decides when you started and stopped talking. The phone's mic just streams continuously ("open mic") — same posture as the boards.
AEC Echo cancellation. With mic and speaker open together on one handset, the phone would hear the assistant and interrupt it with its own voice. iOS's voiceChat audio mode subtracts what the speaker is playing from what the mic hears.

Scenario 1 — tap the button, have a conversation

phone did thisserver did this

@1 tap phone mic permission 0ms
The mic button lives on the floating note pill. First ever tap asks for microphone permission (denied → the caption says so and tapping opens Settings). The pulse you see later is computed on the phone from raw mic loudness — pure visual feedback, zero network involved.
@2 setup (first call on this device only) phone setupVoiceAgent 0–2s once, then 0ms
The app asserts the stream's "birth certificate": open mic, backend enabled, a hang_up tool for the model. A local hash marker means this round trip happens once per device, not per call — later taps skip straight to connecting. 
setupVoiceAgent:
  streamPath: /agents/voice/mobile-<device-uuid>
  clientTakesTurns: false        # open mic: server VAD owns the turns
  colleague: true                # the thinking backend
  tools: [hang_up]
  instructions: "You are Iterate, a voice assistant on a phone…"
@3 open live connection from the head phone replayAfterOffset=head ~150ms
One WebSocket connection to the stream, subscribed to answer audio, call lifecycle, and backend status/note events. It starts at the CURRENT end of the log on purpose: this stream holds every previous call, and replaying last week's "call ended" would kill this call before it starts.
@4 the one durable press phone ptt-start ~300ms
A single durable event mints the call. Durable because losing the opening press strands a human; everything that follows rides ephemeral lanes. 
type: voice-agent/ptt-start
payload: { t: 1787873080238 }
@5 call minted, provider dialled server call-started → conversation-accepted 0.7–1.8s
The facet mints a conversation id, dials OpenAI Realtime, and configures the session (voice, VAD, the assistant's instructions, the recap of previous calls — see scenario 4). Mic frames that arrived during the handshake were held, then released in order: nothing you said is lost to connection setup. 
type: voice-agent/conversation-accepted
payload: { conversationId: conv_44c5…, handshakeTookMs: 1807, heldMicFrames: 27 }
@6 microphone streams phone ~16 frames/s, ephemeral continuous
iOS hands the app ~64ms buffers (1024 samples at 16kHz). Each becomes one ephemeral event — base64 PCM16, a device sequence number — and one pulse update. If the network stalls, frames are DROPPED rather than queued: a moment of lost audio beats the model answering the past. The same buffer feeds the button's pulse before any network is involved. 
type: voice-agent/mic-frame   (ephemeral)
payload: { pcm: "base64…", deviceMicFrameSeq: 141, capturedAtDeviceMs: 9024 }
@7 the provider hears you stop server server VAD ~0.5s after you stop
You never press anything to end a turn. The provider's VAD hears the trailing silence (the phone keeps streaming silent frames — that IS the signal) and starts answering. Your words also land as a durable transcript event, so the conversation leaves a readable record. 
type: voice-agent/utterance-transcript
payload: { conversationId: conv_44c5…, text: "Hello, please say the words purple lantern back to me…" }
@8 answer audio flows back server spk-frame, paced ~1–3s later
The provider generates a 90-second answer in seconds; the SERVER buffers it and releases it at playback rate, never running more than ~3s ahead of your ears. The phone appends each frame to a playback queue and does nothing else — measured live from Node: first answer audio ~13s after call start including setup, ~3s turn-to-answer once warm. 
type: voice-agent/spk-frame   (ephemeral)
payload: { conversationId: conv_44c5…, deviceSpeakerFrameSeq: 12, pcm: "base64…" }
@9 the answer's words, durably server answer-transcript as each answer finishes
Every finished answer lands as text on the stream. Three things read it: the reconnect memory (scenario 4), the `voicelab transcript` CLI, and any test that wants to assert what was actually said without ears.

Scenario 2 — you ask for something hard

“Find me recent YouTube debates about that” is not something a 200ms voice model can do. It sends a note to its backend — a full agent on a sibling stream (/agents/voice-notes/…) with web search, code execution, and no clock on it — says “I've sent that to my backend”, and keeps talking. Everything the backend does comes back to the call stream as durable events:

@10 note dispatched server colleague-status +0s 
payload: { activity: "picking up a note from the frontend", waitingFor: null }
@11 the backend narrates itself server writing code → running code +5–20s
The same status feed the web dashboard shows ("writing code", "running code", failed scripts WITH their error) is forwarded onto the call stream. The voice model receives each change as a quiet context note — so "what's it doing?" gets "it's running the code now" instead of a guess — and the phone shows the latest one as the caption under the pulse. 
payload: { phase: "running code" }
@12 the backend replies server colleague-note +20–120s
Every chat message the backend sends becomes a durable note on the call stream — no deadline, no request/response matching, nothing lost if it arrives between calls. The voice reads it out; the phone also shows it briefly in the caption. 
payload: { text: "Here's the short list. First, 'A philosopher and a child debate god…'" }

Scenario 3 — you interrupt mid-answer

@13 you talk over it phone just… talk 0ms
Open mic + echo cancellation means the provider hears you even while the phone's speaker is playing (iOS's voiceChat mode subtracts the speaker signal from the mic). No button.
@14 the barge server clearSpeakerBufferBeforeFrame ~0.5s
The provider cancels its answer server-side; the facet sends one frame flagged "clear your buffer first". The phone throws away its queued audio — one native call — and the assistant is also TOLD how much you actually heard, so "how far did you get?" gets an honest answer rather than the model's memory of what it generated. 
type: voice-agent/spk-frame   (ephemeral)
payload: { deviceSpeakerFrameSeq: 40, pcm: "", clearSpeakerBufferBeforeFrame: true }

Scenario 4 — hang up, call back, it remembers

@15 tap hang up phone conversation-ended 0ms
The phone appends the call's obituary (same as a board's hang-up button). The model saying goodbye (its hang_up tool) and 60 seconds of mutual silence are the other two ways a call ends. 
type: voice-agent/conversation-ended
payload: { conversationId: conv_44c5…, reason: "hang-up button" }
@16 the next call resumes the thread server transcript recap next tap
Because the device always calls on the same stream, the server briefs each fresh provider session with a bounded recap of recent turns, any note still being worked, and recent backend notes. Hanging up mid-task and calling back later, the assistant picks up mid-thread — including relaying an answer that arrived while no call was live.

State on the phone (all of it)

audio session (mic + queue-player, AEC on)
playback queue of received frames
≤8 in-flight frame uploads (drop past that)
a pulse value, a caption string, a call handle

State on the server (the interesting half)

provider WebSocket + pacing schedule
call fold: conversation id, idle deadline, recap
transcript + backend status/note history (durable)
the backend agent, with its own memory

Why it's built this way

The dumb-client doctrine, and the WebRTC road not taken

An earlier prototype (PR #1605) had the phone speak WebRTC directly to OpenAI, holding an ephemeral API secret. That makes every client — phone, board, terminal — reimplement turn-taking, interruption, memory, and multiplexing, and gives the server no record of the conversation. The current design inverts it: the server holds the provider socket and every rule; a client is "microphone in, speaker out, three-line buffer policy". The proof of the doctrine is this PR's test story: the exact TypeScript that ships in the app was driven from a laptop Node process against production — synthesized speech in, real answer audio and durable transcripts out, in 15 seconds — before any phone build existed, because nothing about a phone is load-bearing.

Why frames, not a WebRTC audio track?

Events on a stream compose with everything else on the platform: the same connection that carries audio carries the backend's statuses; transcripts land beside the audio they transcribe; any tool (or test) can read the whole conversation later. The cost is doing our own pacing and buffering — which the server does once, for every client, instead of each client doing it badly.

What the phone deliberately does not do

No transcript UI (glance at the caption, or open the dashboard), no background/lock-screen audio yet, no Android yet, no local VAD or wake word. Each is possible later; none is needed to prove the lane.
