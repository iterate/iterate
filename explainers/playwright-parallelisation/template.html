How many Playwright workers?

One runner can start many tests while they wait on the network. But every Playwright worker is a separate Node process, normally with its own browser. How much concurrency helps before CPU, memory or the backend starts slowing things down?

A worker is a test process, not a CPU core. It keeps its test slot while awaiting I/O. Chromium itself uses multiple processes. Raising workers increases both remote requests and local browser work; CPU, memory, Expo and the deployed services can all become limits.

How to interpret a “retry”, a quarantine result and a queue

A test retry is a second attempt of one test, not a rerun of the whole CI job. Retries are shown separately in the trace. The existing flake wrapper marks some tests as expected failures; when their bodies pass it deliberately throws “Flaky test passed this run”. Those are body passes, not regressions. A quarantined body failure is called out separately. The monthly flake sentinel deliberately throws at random to test failure reporting; its expected outcome is labeled separately from real body failures. Skipped cases never occupy an active worker slot.

Playwright runs one test at a time in each worker process. More workers let waiting tests overlap, but process/browser startup and page work still use CPU and RAM. Worker count is a maximum, not proof that that many tests are simultaneously active. The trace records actual test start/end times and worker IDs.
